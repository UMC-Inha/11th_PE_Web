# chapter03

- 3계층 아키텍처 이외에 어떤 아키텍처들이 있을까?
    
    #### 1. MVC 아키텍처
    
    애플리케이션을 **Model, View, Controller**로 나누는 구조이다.
    
    - **Model**: 데이터와 비즈니스 로직을 담당한다.
    - **View**: 사용자에게 보여지는 화면을 담당한다.
    - **Controller**: 사용자의 요청을 받아 Model과 View를 연결한다.
    
    **장점**
    
    - 각 영역의 역할이 구분되어 유지보수가 편리하다.
    - 화면과 비즈니스 로직을 분리할 수 있다.
    
    **단점**
    
    - 프로젝트가 커지면 Controller에 코드가 집중되어 복잡해질 수 있다.
    
    ---
    
    #### 2. 헥사고날 아키텍처 (Hexagonal Architecture)
    
    애플리케이션의 **핵심 비즈니스 로직을 DB, 웹, 외부 API와 같은 외부 요소로부터 분리**하는 아키텍처이다.
    
    외부 요소와 핵심 비즈니스 로직을 직접 연결하지 않고 **Port와 Adapter**를 통해 연결한다.
    
    ```
    외부(DB, API 등)
          ↕
       Adapter
          ↕
        Port
          ↕
    비즈니스 로직
    ```
    
    **장점**
    
    - DB나 외부 API가 변경되어도 핵심 비즈니스 로직에 미치는 영향이 적다.
    - 외부 요소와 핵심 로직이 분리되어 테스트하기 쉽다.
    
    **단점**
    
    - Port와 Adapter 등을 추가해야 하므로 구조가 복잡해질 수 있다.
    - 작은 프로젝트에서는 불필요하게 복잡한 구조가 될 수 있다.
    
    ---
    
    #### 3. 클린 아키텍처 (Clean Architecture)
    
    **비즈니스 로직을 중심에 두고 외부 기술에 대한 의존성을 최소화**하는 아키텍처이다.
    
    의존성이 바깥쪽에서 안쪽으로 향하도록 구성하여 핵심 비즈니스 로직이 DB, 프레임워크 등의 외부 요소에 의존하지 않도록 한다.
    
    **장점**
    
    - DB나 프레임워크가 변경되어도 핵심 비즈니스 로직을 유지하기 쉽다.
    - 각 영역이 분리되어 테스트와 유지보수에 유리하다.
    
    **단점**
    
    - 계층과 인터페이스가 많아져 구조가 복잡해질 수 있다.
    - 작은 프로젝트에서는 구현해야 할 코드가 많아질 수 있다.
    
    ---
    
    #### 4. 마이크로서비스 아키텍처 (MSA)
    
    하나의 큰 애플리케이션을 **여러 개의 독립적인 서비스로 분리**하는 아키텍처이다.
    
    예를 들어 쇼핑몰 서비스를 회원, 주문, 결제, 배송 등의 서비스로 나누어 구성할 수 있다.
    
    ```
    회원 서비스
    주문 서비스
    결제 서비스
    배송 서비스
    ```
    
    각 서비스는 독립적으로 개발하고 배포할 수 있으며 필요한 경우 특정 서비스만 확장할 수도 있다.
    
    **장점**
    
    - 서비스별로 독립적인 개발과 배포가 가능하다.
    - 필요한 서비스만 개별적으로 확장하기 쉽다.
    - 하나의 서비스 변경이 다른 서비스에 미치는 영향을 줄일 수 있다.
    
    **단점**
    
    - 서비스 간 통신을 별도로 처리해야 한다.
    - 여러 서비스를 운영하기 때문에 배포와 관리가 복잡해질 수 있다.
    - 분산된 데이터의 일관성을 관리하기 어려울 수 있다.
    
    ---
    
    ### 정리
    
    3계층 아키텍처는 역할에 따라 계층을 나누어 비교적 이해하고 적용하기 쉬운 구조이다.
    
    헥사고날 아키텍처와 클린 아키텍처는 **핵심 비즈니스 로직과 외부 요소의 분리**에 중점을 두며, 마이크로서비스 아키텍처는 하나의 애플리케이션을 **여러 독립적인 서비스로 분리**하는 데 중점을 둔다.
    
    따라서 하나의 아키텍처가 항상 좋은 것이 아니라 **프로젝트의 규모, 복잡도, 유지보수 및 확장 요구사항에 따라 적절한 아키텍처를 선택하는 것이 중요하다.**
    
- SQL Injection을 포함한 대표적인 웹 보안 공격 기법
    
    #### 1. SQL Injection
    
    사용자가 입력한 값을 이용하여 **의도하지 않은 SQL 쿼리가 실행되도록 만드는 공격**이다.
    
    사용자 입력값을 SQL문에 문자열로 직접 연결할 경우 발생할 수 있다.
    
    ```java
    String sql = "SELECT * FROM users WHERE name = '" + name + "'";
    ```
    
    공격자가 SQL 문법이 포함된 값을 입력하면 원래 의도와 다른 쿼리가 실행될 수 있다.
    
    **방어 방법**
    
    - Prepared Statement와 **파라미터 바인딩**을 사용한다.
    - 사용자 입력값을 SQL문에 직접 연결하지 않는다.
    - DB 계정에 필요한 최소한의 권한만 부여한다.
    
    이번 실습에서 사용한 다음 방식도 SQL Injection을 방지하기 위한 파라미터 바인딩이다.
    
    ```java
    String sql = "SELECT * FROM book WHERE category_id = ?";
    jdbcTemplate.queryForList(sql, categoryId);
    ```
    
    ---
    
    #### 2. XSS (Cross-Site Scripting)
    
    웹 페이지에 **악성 스크립트를 삽입하여 다른 사용자의 브라우저에서 실행되도록 하는 공격**이다.
    
    예를 들어 게시글이나 댓글에 악성 JavaScript를 삽입하고, 다른 사용자가 해당 페이지를 조회할 때 스크립트가 실행되도록 할 수 있다.
    
    **방어 방법**
    
    - 사용자 입력값을 화면에 출력할 때 적절하게 이스케이프한다.
    - 입력값을 검증한다.
    - CSP(Content Security Policy)를 적용한다.
    
    ---
    
    #### 3. CSRF (Cross-Site Request Forgery)
    
    로그인된 사용자의 인증 정보를 이용하여 **사용자가 의도하지 않은 요청을 서버에 보내도록 유도하는 공격**이다.
    
    예를 들어 사용자가 로그인한 상태에서 공격자가 만든 페이지에 접근했을 때, 사용자 모르게 정보 변경 등의 요청이 전송될 수 있다.
    
    **방어 방법**
    
    - CSRF Token을 사용하여 정상적인 요청인지 검증한다.
    - 쿠키의 `SameSite` 속성을 적절하게 설정한다.
    - 중요한 작업은 추가 인증 등을 통해 검증할 수 있다.
    
    ---
    
    #### 4. 인증 및 접근 제어 취약점
    
    인증이나 권한 검사가 제대로 이루어지지 않아 **허가되지 않은 사용자가 다른 사용자의 정보나 기능에 접근하는 문제**이다.
    
    예를 들어 일반 사용자가 URL의 사용자 ID만 변경하여 다른 사용자의 개인정보를 조회하거나 관리자 기능을 실행할 수 있는 경우가 있다.
    
    **방어 방법**
    
    - 서버에서 사용자의 인증 여부를 확인한다.
    - 요청마다 해당 기능이나 데이터에 접근할 권한이 있는지 검사한다.
    - 사용자에게 필요한 최소한의 권한만 부여한다.
    
    ---
    
    #### 5. 파일 업로드 공격
    
    파일 업로드 기능을 이용하여 **서버가 허용하지 않아야 할 파일이나 악성 파일을 업로드하는 공격**이다.
    
    파일의 이름이나 확장자만 검사하면 이를 우회하여 위험한 파일이 업로드될 수 있다.
    
    **방어 방법**
    
    - 허용할 파일 형식과 크기를 제한한다.
    - 파일의 실제 형식을 검증한다.
    - 업로드한 파일을 서버에서 임의의 이름으로 저장한다.
    - 업로드 파일이 실행되지 않도록 저장 위치와 권한을 제한한다.
    
    ---
    
    ### 정리
    
    웹 애플리케이션은 사용자로부터 다양한 입력을 받기 때문에 이를 그대로 신뢰해서는 안 된다.
    
    특히 **SQL Injection은 파라미터 바인딩**, **XSS는 출력값 처리**, **CSRF는 요청 검증**, **접근 제어 취약점은 서버 측 권한 검사**와 같이 공격 방식에 맞는 방어 방법을 적용하는 것이 중요하다.
    
- 커넥션 풀(Connection Pool)이란?
    
    #### 커넥션 풀 (Connection Pool)
    
    커넥션 풀은 애플리케이션이 데이터베이스와 통신할 때 사용하는 **DB Connection을 미리 여러 개 만들어 두고 재사용하는 방식**이다.
    
    DB에 SQL을 실행하려면 먼저 애플리케이션과 DB 사이에 Connection을 생성해야 한다. 요청이 들어올 때마다 새로운 Connection을 생성하고 종료하면 반복적인 연결 과정 때문에 시간과 자원이 많이 소모될 수 있다.
    
    커넥션 풀을 사용하면 일정 개수의 Connection을 미리 생성해두고 필요한 순간에 빌려서 사용한 뒤 다시 풀에 반환한다.
    
    ```
    애플리케이션
         ↓ Connection 요청
    ┌─────────────────────┐
    │   Connection Pool   │
    │                     │
    │ Connection 1        │
    │ Connection 2        │
    │ Connection 3        │
    └─────────────────────┘
         ↓
      Database
    ```
    
    예를 들어 여러 사용자가 동시에 API를 호출하면 각 요청은 커넥션 풀에서 사용 가능한 Connection을 빌려 SQL을 실행하고, 작업이 끝나면 Connection을 종료하는 대신 **커넥션 풀에 반환하여 다른 요청이 다시 사용할 수 있도록 한다.**
    
    **장점**
    
    - DB Connection을 매번 새로 생성하는 비용을 줄일 수 있다.
    - Connection을 재사용하여 DB 접근 성능을 향상시킬 수 있다.
    - 동시에 생성할 수 있는 Connection의 수를 제한하여 DB 자원을 효율적으로 관리할 수 있다.
    
    **단점**
    
    - 커넥션 풀의 크기를 너무 작게 설정하면 요청이 Connection을 얻기 위해 오래 기다릴 수 있다.
    - 반대로 너무 크게 설정하면 DB에 과도한 Connection이 생성되어 DB에 부담을 줄 수 있다.
    
    ### Spring Boot에서의 Connection Pool
    
    Spring Boot에서는 JDBC를 사용할 때 기본적으로 **HikariCP**라는 커넥션 풀을 사용할 수 있다.
    
    이번 실습에서도 `JdbcTemplate`이 SQL을 실행할 때 필요한 DB Connection을 `DataSource`를 통해 얻어 사용한다.
    
    ```
    Controller
        ↓
    Service
        ↓
    Repository
        ↓
    JdbcTemplate
        ↓
    DataSource (Connection Pool)
        ↓
    MySQL
    ```
    
    따라서 개발자가 SQL을 실행할 때마다 직접 DB Connection을 생성하고 종료하지 않아도 커넥션 풀을 통해 Connection을 효율적으로 사용할 수 있다.
    
- Raw SQL vs ORM
    
    #### Raw SQL
    
    Raw SQL은 개발자가 **SQL문을 직접 작성하여 데이터베이스에 접근하는 방식**이다.
    
    이번 실습에서 `JdbcTemplate`을 사용해 작성한 코드가 Raw SQL에 해당한다.
    
    ```java
    String sql = "SELECT * FROM book WHERE category_id = ?";
    return jdbcTemplate.queryForList(sql, categoryId);
    ```
    
    개발자가 `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `JOIN` 등의 SQL을 직접 작성한다.
    
    **장점**
    
    - 실행되는 SQL을 직접 확인하고 제어할 수 있다.
    - 복잡한 쿼리를 원하는 형태로 작성하기 쉽다.
    - SQL을 직접 작성하기 때문에 데이터베이스의 기능을 세밀하게 활용할 수 있다.
    
    **단점**
    
    - SQL을 직접 작성해야 하므로 코드 작성량이 많아질 수 있다.
    - 조회 결과를 객체로 변환하는 작업을 직접 처리해야 할 수 있다.
    - DB 종류가 변경되면 SQL 문법 차이로 인해 코드를 수정해야 할 수 있다.
    
    ---
    
    #### ORM (Object Relational Mapping)
    
    ORM은 **객체와 관계형 데이터베이스의 테이블을 연결하여 객체를 통해 DB를 다룰 수 있도록 하는 기술**이다.
    
    Java에서는 대표적으로 **JPA**가 ORM을 위한 표준 기술이며, **Hibernate**가 JPA의 대표적인 구현체이다.
    
    예를 들어 `Book` 객체와 `book` 테이블을 연결하면 다음과 같이 생각할 수 있다.
    
    ```
    Book 객체                 book 테이블
    
    id        ←────────→      book_id
    title     ←────────→      title
    description ←──────→      description
    ```
    
    Raw SQL에서는 직접 SQL을 작성하지만 ORM을 사용하면 객체를 중심으로 데이터를 다룰 수 있다.
    
    예를 들어 Spring Data JPA를 사용하면 단순 조회의 경우 다음처럼 Repository 메서드로 표현할 수 있다.
    
    ```java
    List<Book> findByCategoryId(Long categoryId);
    ```
    
    ORM이 이러한 정보를 바탕으로 필요한 SQL을 생성하여 DB와 통신한다.
    
    **장점**
    
    - 반복적인 SQL 작성량을 줄일 수 있다.
    - DB 데이터를 Java 객체 중심으로 다룰 수 있다.
    - 객체지향적인 방식으로 애플리케이션을 설계하기 좋다.
    - 단순한 CRUD를 비교적 간단하게 구현할 수 있다.
    
    **단점**
    
    - ORM의 동작 원리를 이해하지 못하면 예상하지 못한 SQL이 실행될 수 있다.
    - 복잡한 조회에서는 ORM만으로 표현하기 어렵거나 코드가 복잡해질 수 있다.
    - 생성되는 SQL과 성능을 확인하고 최적화해야 하는 경우가 있다.
    
    ---
    
    ### Raw SQL과 ORM 비교
    
    | 구분 | Raw SQL | ORM |
    | --- | --- | --- |
    | DB 접근 | SQL 직접 작성 | 객체를 통해 접근 |
    | SQL 제어 | 직접 제어하기 쉬움 | ORM이 SQL 생성 |
    | 코드 작성량 | 상대적으로 많음 | 반복적인 CRUD 코드 감소 |
    | 객체 매핑 | 직접 처리할 수 있음 | ORM이 객체와 테이블을 매핑 |
    | 복잡한 SQL | 직접 작성하기 편리함 | 경우에 따라 별도 쿼리가 필요 |
    | 학습 | SQL 이해가 중요 | SQL + ORM 동작 원리 이해가 중요 |
    
    ### 정리
    
    Raw SQL은 **개발자가 SQL을 직접 작성하고 제어하는 방식**이고, ORM은 **객체와 DB 테이블을 매핑하여 객체 중심으로 DB를 다루는 방식**이다.
    
    둘 중 하나가 항상 더 좋은 것은 아니며, 단순한 CRUD에서는 ORM을 활용하고 복잡하거나 세밀한 SQL 제어가 필요한 경우 직접 SQL을 사용하는 등 프로젝트 상황에 따라 적절한 방식을 선택할 수 있다.
    
- INSERT 외에 데이터를 다루는 핵심 SQL 문법
    
    #### SELECT
    
    `SELECT`는 데이터베이스에서 **데이터를 조회할 때 사용하는 SQL문**이다.
    
    ```sql
    SELECT * FROM book;
    ```
    
    `book` 테이블의 모든 데이터를 조회한다.
    
    특정 조건의 데이터만 조회하려면 `WHERE`를 사용할 수 있다.
    
    ```sql
    SELECT * FROM book
    WHERE category_id = 1;
    ```
    
    ---
    
    #### UPDATE
    
    `UPDATE`는 이미 저장되어 있는 **데이터를 수정할 때 사용하는 SQL문**이다.
    
    ```sql
    UPDATE book
    SET title = '클린 코드 개정판'
    WHERE book_id = 4;
    ```
    
    `book_id`가 4인 도서의 제목을 변경한다.
    
    `WHERE` 조건을 작성하지 않으면 여러 데이터가 한꺼번에 수정될 수 있으므로 주의해야 한다.
    
    ---
    
    #### DELETE
    
    `DELETE`는 테이블에 저장된 **데이터를 삭제할 때 사용하는 SQL문**이다.
    
    ```sql
    DELETE FROM book
    WHERE book_id = 4;
    ```
    
    `book_id`가 4인 데이터를 삭제한다.
    
    `UPDATE`와 마찬가지로 `WHERE`를 생략하면 테이블의 모든 행이 대상이 될 수 있으므로 주의해야 한다.
    
    ---
    
    #### WHERE
    
    `WHERE`는 `SELECT`, `UPDATE`, `DELETE` 등에서 **특정 조건을 만족하는 데이터만 선택하기 위해 사용**한다.
    
    ```sql
    SELECT * FROM book
    WHERE is_available = true;
    ```
    
    대여 가능한 도서만 조회한다.
    
    여러 조건을 사용할 때는 `AND`, `OR` 등을 함께 사용할 수 있다.
    
    ```sql
    SELECT * FROM book
    WHERE category_id = 1
      AND is_available = true;
    ```
    
    ---
    
    #### ORDER BY
    
    `ORDER BY`는 조회한 데이터를 **특정 컬럼을 기준으로 정렬**할 때 사용한다.
    
    ```sql
    SELECT * FROM book
    ORDER BY book_id DESC;
    ```
    
    - `ASC`: 오름차순
    - `DESC`: 내림차순
    
    ---
    
    #### JOIN
    
    `JOIN`은 **서로 연관된 여러 테이블의 데이터를 함께 조회**할 때 사용한다.
    
    예를 들어 `rental`의 `book_id`와 `book`의 `book_id`를 연결할 수 있다.
    
    ```sql
    SELECT r.rental_id, b.title, r.rented_at
    FROM rental r
    JOIN book b
        ON r.book_id = b.book_id;
    ```
    
    이를 통해 대여 기록과 해당 도서의 제목을 한 번에 조회할 수 있다.
    
    ---
    
    ### 정리
    
    데이터를 다루는 기본적인 SQL 작업을 흔히 **CRUD**로 구분한다.
    
    | CRUD | SQL | 역할 |
    | --- | --- | --- |
    | Create | `INSERT` | 데이터 생성 |
    | Read | `SELECT` | 데이터 조회 |
    | Update | `UPDATE` | 데이터 수정 |
    | Delete | `DELETE` | 데이터 삭제 |
    
    `WHERE`, `ORDER BY`, `JOIN` 등은 이러한 SQL문과 함께 사용하여 **조건을 지정하거나 데이터를 정렬하고 여러 테이블을 연결하는 데 사용**한다.
