# chapter07

- 인증(Authentication)과 인가(Authorization)
    
    ### 인증과 인가란?
    
    인증(Authentication)과 인가(Authorization)는 사용자의 신원과 접근 권한을 확인하는 보안 과정이다.
    
    | 구분 | 인증(Authentication) | 인가(Authorization) |
    | --- | --- | --- |
    | 핵심 질문 | 누구인가? | 무엇을 할 수 있는가? |
    | 목적 | 사용자의 신원 확인 | 리소스 접근 권한 확인 |
    | 판단 기준 | 비밀번호, 토큰 등 | 사용자 권한, 리소스 소유 여부 등 |
    | 실패 시 | 일반적으로 401 Unauthorized | 일반적으로 403 Forbidden |
    | 예시 | 이메일과 비밀번호로 로그인 | 자신의 영화 평점만 수정 |
    
    쉽게 말하면 다음과 같다.
    
    - 인증: "너 누구야?"
    - 인가: "네가 이 작업을 해도 돼?"
    
    ### 인증(Authentication)
    
    인증은 사용자가 주장하는 신원이 실제로 맞는지 확인하는 과정이다.
    
    대표적인 인증 방법
    
    | 인증 방법 | 설명 |
    | --- | --- |
    | 비밀번호 | 아이디와 비밀번호를 확인 |
    | OTP | 일회용 인증번호를 확인 |
    | 생체 인증 | 지문, 얼굴 등으로 신원 확인 |
    | 토큰 기반 인증 | 서버가 발급한 토큰을 검증 |
    
    JWT를 이용한 인증 과정
    
    1. 사용자가 이메일과 비밀번호로 로그인한다.
    2. 서버가 로그인 정보를 검증한다.
    3. 검증에 성공하면 JWT를 발급한다.
    4. 사용자는 이후 요청에 JWT를 포함한다.
    5. 서버는 JWT의 서명, 만료 여부 등을 검증하여 요청을 인증한다.
    
    JWT는 사용자의 신원과 관련된 정보를 담을 수 있는 토큰 형식이다. 단, JWT 자체가 로그인 방식은 아니며 서버가 토큰을 올바르게 검증해야 안전하게 사용할 수 있다.
    
    ### 인가(Authorization)
    
    인가는 인증된 사용자가 특정 기능이나 데이터에 접근할 권한이 있는지 확인하는 과정이다.
    
    대표적인 인가 기준
    
    - 역할 기반: 관리자만 회원 관리 기능 사용
    - 소유자 기반: 자신이 작성한 평점만 수정·삭제
    - 권한 기반: 특정 권한을 가진 사용자만 기능 실행
    
    영화 평점 서비스 예시
    
    | 상황 | 결과 | 이유 |
    | --- | --- | --- |
    | A가 자신의 평점 수정 | 200 OK | 인증 및 권한 확인 성공 |
    | B가 A의 평점 수정 | 403 Forbidden | 인증은 성공했지만 수정 권한 없음 |
    | 토큰 없이 평점 수정 | 401 Unauthorized | 유효한 인증 정보 없음 |
    
    로그인에 성공했다고 해서 모든 기능을 사용할 수 있는 것은 아니다. 서버는 요청한 작업에 대한 권한도 별도로 확인해야 한다.
    
    ### 인증과 인가의 차이
    
    인증 → 인가 → 요청 처리
    
    예를 들어 영화 평점 수정 API를 호출하면 다음과 같이 동작한다.
    
    1. 인증: JWT를 검증하여 요청한 회원이 누구인지 확인한다.
    2. 인가: 수정하려는 평점의 작성자가 해당 회원인지 확인한다.
    3. 처리: 두 검증을 모두 통과하면 평점을 수정한다.
    
    401과 403의 차이
    
    - `401 Unauthorized`: 인증 정보가 없거나 유효하지 않아 인증에 실패한 경우
    - `403 Forbidden`: 요청을 이해했지만 해당 작업을 수행할 권한이 없는 경우
    
    HTTP 상태 코드 이름만 보면 401과 403이 헷갈릴 수 있지만, 핵심은 인증 실패와 권한 부족의 차이이다.
    
    ### 정리
    
    - 인증은 사용자의 신원을 확인하는 과정이다.
    - 인가는 사용자가 특정 작업을 수행할 권한이 있는지 확인하는 과정이다.
    - JWT는 인증에 활용할 수 있지만, 토큰이 유효하다고 모든 작업이 허용되는 것은 아니다.
    - 따라서 안전한 서비스를 구현하려면 인증과 인가를 모두 검증해야 한다.
- 해시와 salt, bcrypt
    
    ### 해시(Hash)란?
    
    해시는 임의의 길이를 가진 데이터를 해시 함수를 통해 일정한 길이의 값으로 변환하는 기술이다.
    
    비밀번호를 데이터베이스에 평문으로 저장하면 정보가 유출되었을 때 비밀번호가 그대로 노출될 수 있다. 따라서 비밀번호는 해시 처리하여 저장하는 것이 안전하다.
    
    | 특징 | 설명 |
    | --- | --- |
    | 단방향성 | 해시값으로 원래 데이터를 복원하기 매우 어려움 |
    | 결정성 | 같은 입력값은 항상 같은 해시값을 생성 |
    | 고정 길이 | 입력 데이터의 길이와 관계없이 일정한 길이의 결과 생성 |
    | 눈사태 효과 | 입력값이 조금만 달라져도 해시값이 크게 달라짐 |
    
    예를 들어 SHA-256을 사용하면 다음과 같다.
    
    ```
    비밀번호: password123
           ↓ SHA-256
    64자리의 16진수 해시값
    ```
    
    다만 SHA-256처럼 계산 속도가 빠른 일반 해시 함수만으로 비밀번호를 저장하면 무차별 대입 공격에 취약할 수 있다. 따라서 비밀번호 저장에는 bcrypt와 같은 전용 알고리즘을 사용하는 것이 권장된다.
    
    ### Salt란?
    
    Salt는 비밀번호를 해시 처리할 때 추가하는 무작위 데이터이다.
    
    같은 비밀번호를 사용하는 사람이라도 서로 다른 Salt를 적용하면 서로 다른 해시값이 생성된다.
    
    Salt를 사용하는 이유
    
    - 동일한 비밀번호라도 서로 다른 해시값 생성
    - 미리 계산된 해시값을 이용하는 레인보우 테이블 공격 방어
    - 비밀번호 해시값의 동일 여부로 사용자들의 비밀번호가 같다는 사실을 쉽게 알아내지 못하도록 방지
    
    Salt 적용 예시
    
    ```
    사용자 A
    비밀번호: password123
    Salt: abc123
            ↓
    서로 다른 해시값 A
    
    사용자 B
    비밀번호: password123
    Salt: xyz789
            ↓
    서로 다른 해시값 B
    ```
    
    Salt는 비밀번호처럼 비밀로 유지해야 하는 값은 아니며, 일반적으로 해시값과 함께 저장한다. 중요한 것은 사용자마다 충분히 무작위적인 Salt를 사용하는 것이다.
    
    ### bcrypt란?
    
    bcrypt는 비밀번호를 안전하게 저장하기 위해 설계된 단방향 비밀번호 해싱 알고리즘이다.
    
    일반적인 해시 함수와 달리 계산 비용을 의도적으로 높여 공격자가 수많은 비밀번호를 빠르게 추측하기 어렵도록 만든다.
    
    | 특징 | 설명 |
    | --- | --- |
    | 단방향 해싱 | 해시값에서 원래 비밀번호를 직접 복원할 수 없음 |
    | Salt 자동 생성 | 비밀번호 해싱 시 무작위 Salt 사용 |
    | Cost 설정 | 해싱에 필요한 계산 비용 조절 가능 |
    | 느린 연산 | 무차별 대입 공격의 비용 증가 |
    
    bcrypt의 동작 과정
    
    ```
    [회원가입]
    
    사용자 비밀번호 입력
            ↓
    무작위 Salt 생성
            ↓
    bcrypt 해싱
            ↓
    Salt와 Cost 정보가 포함된 해시값 저장
    
    [로그인]
    
    사용자 비밀번호 입력
            ↓
    DB에 저장된 bcrypt 해시값 조회
            ↓
    저장된 Salt와 Cost를 이용해 검증
            ↓
    일치 → 로그인 성공
    불일치 → 로그인 실패
    ```
    
    bcrypt는 비밀번호를 복호화해서 비교하는 것이 아니라, 입력된 비밀번호가 저장된 해시값과 일치하는지 검증한다.
    
    ### bcrypt의 Cost Factor
    
    Cost Factor는 bcrypt의 계산 비용을 결정하는 설정값이다.
    
    Cost가 1 증가하면 필요한 계산량이 대략 2배 증가한다.
    
    | Cost | 상대적인 계산 비용 |
    | --- | --- |
    | 10 | 2¹⁰ = 1,024 |
    | 11 | 2¹¹ = 2,048 |
    | 12 | 2¹² = 4,096 |
    | 13 | 2¹³ = 8,192 |
    - Cost가 높을수록 비밀번호 추측 공격에 필요한 시간이 증가한다.
    - 반면 정상적인 회원가입과 로그인 처리 시간도 증가한다.
    - 따라서 서버 성능과 보안 요구사항을 고려하여 적절한 값을 설정해야 한다.
    
    ### 해시, Salt, bcrypt의 차이
    
    | 구분 | 해시(Hash) | Salt | bcrypt |
    | --- | --- | --- | --- |
    | 개념 | 데이터를 해시값으로 변환하는 기술 | 해싱에 추가하는 무작위 데이터 | 비밀번호 전용 해싱 알고리즘 |
    | 주요 목적 | 데이터의 단방향 변환 | 동일 비밀번호의 해시값 구별 | 안전한 비밀번호 저장 |
    | 특징 | 원본 복원이 어려움 | 사용자마다 다른 값 사용 | Salt와 Cost를 함께 사용 |
    | 관계 | 기본 개념 | 해싱의 보안 강화 요소 | 해시와 Salt를 활용하는 알고리즘 |
    
    ### 정리
    
    - 해시는 데이터를 일정한 길이의 해시값으로 변환하는 기술이다.
    - Salt는 동일한 비밀번호라도 서로 다른 해시값을 생성하도록 돕는다.
    - bcrypt는 Salt와 Cost Factor를 활용하여 비밀번호 추측 공격을 어렵게 만드는 알고리즘이다.
    - 비밀번호는 암호화 후 복호화하는 방식보다 bcrypt와 같은 전용 해싱 알고리즘으로 저장하는 것이 적절하다.
- JWT (Header / Payload / Signature, Claim)
    
    ### JWT(JSON Web Token)란?
    
    JWT는 사용자에 대한 정보를 JSON 형태로 표현하고, 이를 안전하게 전달하기 위한 토큰 형식이다.
    
    주로 로그인 이후 사용자의 인증 정보를 전달하는 데 사용하며, 서버는 JWT를 검증하여 요청한 사용자가 누구인지 확인할 수 있다.
    
    JWT의 특징
    
    | 특징 | 설명 |
    | --- | --- |
    | 토큰 기반 인증 | 로그인 후 발급받은 토큰으로 사용자 인증 |
    | 자체 정보 포함 | 사용자 ID, 발급 시간, 만료 시간 등의 정보 포함 가능 |
    | 서명 검증 | 토큰의 위조 및 변조 여부 확인 |
    | 만료 시간 | 토큰의 유효 기간 설정 가능 |
    | Stateless 활용 | 서버에 별도의 세션을 저장하지 않고 인증 가능 |
    
    단, JWT는 기본적으로 암호화된 데이터가 아니므로 토큰에 비밀번호 같은 민감한 정보를 저장해서는 안 된다.
    
    ### JWT의 구조
    
    JWT는 Header, Payload, Signature 세 부분으로 구성되며, 각 부분은 점(`.`)으로 구분된다.
    
    ```
    Header.Payload.Signature
    ```
    
    각 부분은 다음과 같은 역할을 한다.
    
    | 구성 요소 | 역할 | 포함되는 정보 |
    | --- | --- | --- |
    | Header | 토큰의 유형과 서명 알고리즘 명시 | `typ`, `alg` |
    | Payload | 사용자 정보와 토큰 관련 데이터 저장 | `sub`, `email`, `iat`, `exp` |
    | Signature | 토큰의 무결성과 서명 유효성 검증 | 서명값 |
    
    ### Header
    
    Header는 JWT의 유형과 서명에 사용한 알고리즘 정보를 담는다.
    
    ```
    {
      "alg": "HS256",
      "typ": "JWT"
    }
    ```
    
    - `alg`: 서명에 사용하는 알고리즘 (HS256 등)
    - `typ`: 토큰의 유형 (JWT)
    
    Header는 Base64URL 방식으로 인코딩되어 JWT의 첫 번째 부분에 저장된다.
    
    ### Payload
    
    Payload는 사용자 정보와 토큰의 유효 기간 등 실제 데이터를 담는 부분이다.
    
    ```
    {
      "sub": "1",
      "email": "user@example.com",
      "iat": 1762900000,
      "exp": 1762903600
    }
    ```
    
    | Claim | 의미 | 설명 |
    | --- | --- | --- |
    | `sub` | Subject | 토큰의 주체 (회원 ID 등) |
    | `email` | Email | 사용자 이메일 |
    | `iat` | Issued At | 토큰 발급 시간 |
    | `exp` | Expiration Time | 토큰 만료 시간 |
    | `iss` | Issuer | 토큰 발급자 |
    | `aud` | Audience | 토큰의 대상 |
    
    Payload도 Base64URL로 인코딩되므로 누구나 디코딩하여 내용을 확인할 수 있다.
    
    따라서 비밀번호나 주민등록번호처럼 민감한 정보는 포함하지 않아야 한다.
    
    ### Claim이란?
    
    Claim은 JWT의 Payload에 저장되는 개별 정보 항목이다.
    
    예를 들어 `"sub": "1"`은 토큰의 주체가 회원 ID 1이라는 정보를 나타내는 Claim이다.
    
    Claim의 종류
    
    | 종류 | 설명 | 예시 |
    | --- | --- | --- |
    | Registered Claim | JWT 표준에 정의된 Claim | `sub`, `iss`, `exp`, `iat` |
    | Public Claim | 공개적으로 정의하거나 충돌을 방지하도록 사용하는 Claim | 공개적으로 정의된 사용자 정보 항목 |
    | Private Claim | 서비스 내부에서 약속하여 사용하는 Claim | `role`, `memberId` |
    
    등록된 Claim은 모두 필수인 것은 아니며, 서비스의 요구사항에 따라 필요한 항목을 사용한다.
    
    ### Signature
    
    Signature는 JWT가 발급된 이후 내용이 변경되지 않았는지 확인하기 위한 서명값이다.
    
    HS256을 사용하는 경우 다음 정보를 바탕으로 서명을 생성한다.
    
    ```
    Base64URL(Header)
            +
            "."
            +
    Base64URL(Payload)
            +
    서버의 Secret Key
            ↓
    HMAC-SHA256
            ↓
    Signature
    ```
    
    서버는 JWT를 전달받으면 설정된 비밀키로 서명을 검증한다.
    
    - 서명이 유효하면 토큰의 무결성을 확인할 수 있다.
    - Header나 Payload가 변조되면 서명 검증에 실패한다.
    - Signature가 있다고 해서 Payload 내용이 암호화되는 것은 아니다.
    
    HS256에서는 토큰을 발급하고 검증하는 서버가 동일한 비밀키를 사용한다.
    
    ### JWT를 이용한 인증 과정
    
    1. 사용자가 이메일과 비밀번호로 로그인을 요청한다.
    2. 서버가 로그인 정보를 검증한 뒤 JWT를 발급한다.
    3. 클라이언트는 이후 API 요청의 Authorization 헤더에 JWT를 포함한다.
    4. 서버는 JWT의 서명과 만료 시간 등을 검증한 후 요청을 처리한다.
    
    요청 헤더 예시
    
    ```
    Authorization: Bearer <accessToken>
    ```
    
    ### JWT의 장단점
    
    | 장점 | 단점 |
    | --- | --- |
    | 서버에 세션을 저장하지 않는 방식으로 인증 가능 | 발급된 토큰을 즉시 무효화하기 어려울 수 있음 |
    | 서버 간 인증 정보 전달에 활용 가능 | 토큰 탈취 시 유효 기간 동안 악용될 위험 |
    | 서명으로 데이터 변조 여부 검증 가능 | Payload가 암호화되지 않아 정보 노출 주의 |
    | 필요한 Claim을 포함할 수 있음 | 토큰 크기가 커지면 요청 데이터 증가 |
    
    ### 정리
    
    - JWT는 Header, Payload, Signature로 구성된 토큰 형식이다.
    - Header는 토큰 유형과 서명 알고리즘을 나타낸다.
    - Payload는 사용자 정보와 토큰 관련 Claim을 저장한다.
    - Signature는 토큰의 위조 및 변조 여부를 검증하는 데 사용된다.
    - Claim은 Payload에 포함된 개별 정보 항목이다.
    - JWT는 기본적으로 암호화되지 않으므로 민감한 정보를 담지 않아야 한다.
    - 서버는 JWT의 서명뿐 아니라 만료 시간 등도 검증해야 한다.
- Bearer 인증과 Authorization 헤더
    
    ### Bearer 인증이란?
    
    Bearer 인증은 클라이언트가 서버에 API 요청을 보낼 때 액세스 토큰(Access Token)을 함께 전달하여 인증하는 방식이다.
    
    Bearer는 '소지자'라는 의미로, 서버는 유효한 토큰을 제시한 요청을 해당 토큰의 권한에 따라 처리한다.
    
    | 특징 | 설명 |
    | --- | --- |
    | 토큰 기반 인증 | 발급받은 액세스 토큰을 이용하여 인증 |
    | 인증 정보 전달 | HTTP Authorization 헤더에 토큰 포함 |
    | 비밀번호 재전송 불필요 | 로그인 이후 매번 비밀번호를 보낼 필요 없음 |
    | 토큰 검증 | 서버가 토큰의 유효성을 확인 |
    | 보안 주의 | 토큰을 탈취당하면 다른 사람이 사용할 수 있음 |
    
    Bearer 인증 과정
    
    1. 사용자가 이메일과 비밀번호로 로그인한다.
    2. 서버가 로그인 정보를 검증하고 액세스 토큰을 발급한다.
    3. 클라이언트는 발급받은 토큰을 저장한다.
    4. 이후 API 요청 시 Authorization 헤더에 토큰을 포함한다.
    5. 서버는 토큰을 검증하고 요청을 처리한다.
    
    Bearer 인증은 JWT와 함께 자주 사용되지만, Bearer 토큰이 반드시 JWT 형식이어야 하는 것은 아니다.
    
    ### Authorization 헤더란?
    
    Authorization 헤더는 클라이언트가 서버에 인증 정보를 전달하기 위해 사용하는 HTTP 요청 헤더이다.
    
    Bearer 인증에서는 다음과 같은 형식으로 사용한다.
    
    ```
    Authorization: Bearer <accessToken>
    ```
    
    | 구성 요소 | 의미 |
    | --- | --- |
    | `Authorization` | 인증 정보를 전달하는 HTTP 헤더 |
    | `Bearer` | Bearer 인증 방식을 사용한다는 표시 |
    | `<accessToken>` | 서버에서 발급받은 액세스 토큰 |
    
    예를 들어 평점 등록 API를 호출할 때 다음과 같이 사용할 수 있다.
    
    ```
    POST /ratings HTTP/1.1
    Host: localhost:8080
    Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
    Content-Type: application/json
    
    {
      "movieId": 10,
      "score": 5,
      "comment": "재미있는 영화"
    }
    ```
    
    이때 `Authorization` 헤더에는 인증 정보가 들어가고, 요청 본문에는 평점 등록에 필요한 데이터가 들어간다.
    
    따라서 기존처럼 요청 본문에 `memberId`를 직접 전달하지 않고, 서버가 검증된 JWT에서 회원 ID를 추출하여 사용할 수 있다.
    
    ### Bearer 인증과 JWT의 차이
    
    Bearer와 JWT는 같은 개념이 아니다.
    
    | 구분 | Bearer 인증 | JWT |
    | --- | --- | --- |
    | 개념 | 토큰을 제시하는 인증 방식 | 토큰의 형식 |
    | 역할 | 인증 정보를 서버에 전달 | 사용자 정보와 Claim 등을 표현 |
    | 주요 특징 | 토큰 소지자가 토큰을 제시 | Header, Payload, Signature로 구성 |
    | 관계 | JWT를 Bearer 토큰으로 사용할 수 있음 | Bearer 방식으로 전달할 수 있음 |
    
    즉, JWT는 토큰의 형식이고 Bearer는 해당 토큰을 서버에 전달하는 인증 방식이다.
    
    ### Bearer 인증의 장단점
    
    | 장점 | 단점 |
    | --- | --- |
    | 로그인 이후 비밀번호를 반복해서 전송하지 않아도 됨 | 토큰 탈취 시 악용될 수 있음 |
    | HTTP 헤더를 통해 간편하게 인증 정보 전달 | 토큰 만료 및 갱신 관리 필요 |
    | 웹과 모바일 등 다양한 환경에서 사용 가능 | 토큰을 안전하게 저장하고 전송해야 함 |
    | JWT 등 여러 토큰 형식과 함께 사용 가능 | 토큰 자체만으로 소지자의 신원을 추가 확인하지 않음 |
    
    Bearer 토큰은 소지한 사람이 사용할 수 있으므로 HTTPS를 통해 전송하고, 토큰이 외부에 노출되지 않도록 관리해야 한다.
    
    ### 401 Unauthorized와 403 Forbidden
    
    Bearer 인증을 사용하는 API에서는 인증 실패와 권한 부족을 구분해야 한다.
    
    | 상태 코드 | 의미 | 예시 |
    | --- | --- | --- |
    | `401 Unauthorized` | 유효한 인증 정보가 없음 | 토큰 누락, 만료, 잘못된 토큰 |
    | `403 Forbidden` | 요청을 수행할 권한이 없음 | 다른 회원의 평점 수정 시도 |
    
    예를 들어 회원 A가 발급받은 JWT로 자신의 평점을 수정하면 요청이 정상적으로 처리된다.
    
    반면 회원 B가 유효한 JWT를 가지고 있더라도 회원 A의 평점을 수정할 권한이 없다면 `403 Forbidden`이 반환된다.
    
    ### 정리
    
    - Bearer 인증은 액세스 토큰을 제시하여 인증하는 방식이다.
    - Authorization 헤더는 HTTP 요청에 인증 정보를 담아 전달하는 역할을 한다.
    - `Authorization: Bearer <accessToken>` 형식으로 토큰을 전달한다.
    - JWT는 토큰의 형식이고 Bearer는 토큰을 전달하는 인증 방식이다.
    - 서버는 전달받은 토큰을 검증한 뒤 사용자 정보를 확인한다.
    - Bearer 토큰은 소지자가 사용할 수 있으므로 안전한 저장과 전송이 중요하다.
- HandlerInterceptor / Guard
    
    ### HandlerInterceptor란?
    
    `HandlerInterceptor`는 Spring MVC에서 HTTP 요청이 컨트롤러에 전달되기 전과 후에 공통 작업을 수행할 수 있도록 제공하는 인터페이스이다.
    
    주로 인증 검사, 요청 로깅, 권한 확인 등에 사용한다.
    
    | 특징 | 설명 |
    | --- | --- |
    | 요청 가로채기 | 컨트롤러 실행 전후에 공통 로직 수행 |
    | 인증 처리 | JWT 등 인증 정보의 유효성 검사 |
    | 인가 처리 | 요청에 대한 접근 권한 확인 가능 |
    | 코드 중복 감소 | 여러 컨트롤러에 공통 로직 적용 |
    | 요청 차단 | 조건에 따라 컨트롤러 실행을 막을 수 있음 |
    
    ### HandlerInterceptor의 주요 메서드
    
    | 메서드 | 실행 시점 | 역할 |
    | --- | --- | --- |
    | `preHandle()` | 컨트롤러 실행 전 | 인증·인가 검사, 요청 차단 |
    | `postHandle()` | 컨트롤러 실행 후 | 모델 및 뷰 관련 후처리 |
    | `afterCompletion()` | 요청 처리 완료 후 | 로깅, 리소스 정리 등 |
    
    가장 중요한 메서드는 `preHandle()`이다.
    
    - `true` 반환: 다음 처리 단계로 진행
    - `false` 반환: 이후 핸들러 실행 중단
    - 예외 발생: 설정된 예외 처리 흐름에 따라 오류 처리
    
    JWT 인증에서는 주로 `preHandle()`에서 토큰을 검사한다.
    
    ### HandlerInterceptor를 이용한 JWT 인증 과정
    
    ```
    클라이언트
        ↓
    HTTP 요청
    Authorization: Bearer <accessToken>
        ↓
    HandlerInterceptor
        ↓
    JWT 존재 여부 확인
        ↓
    JWT 서명 및 만료 시간 검증
        ↓
    회원 ID 추출
        ↓
    Controller
        ↓
    Service
        ↓
    응답 반환
    ```
    
    JWT가 없거나 유효하지 않다면 컨트롤러에 요청이 전달되기 전에 인증 실패로 처리할 수 있다.
    
    Spring MVC에서 인터셉터는 `HandlerMapping`이 선택한 핸들러를 실행하기 전후에 동작한다.
    
    ### Guard란?
    
    Guard는 특정 요청이나 기능을 실행하기 전에 접근 가능 여부를 검사하는 보호 장치를 의미한다.
    
    주로 인증 여부나 사용자 권한을 검사하여 허용되지 않은 접근을 차단하는 역할을 한다.
    
    Guard는 여러 프레임워크에서 사용되는 개념으로, Spring MVC의 `HandlerInterceptor`처럼 모든 환경에서 동일한 인터페이스를 의미하는 것은 아니다.
    
    | 종류 | 역할 | 예시 |
    | --- | --- | --- |
    | Authentication Guard | 사용자 인증 여부 확인 | 로그인한 사용자만 접근 허용 |
    | Authorization Guard | 사용자 권한 확인 | 관리자만 특정 API 접근 허용 |
    | Role Guard | 사용자 역할 확인 | ADMIN 역할인지 검사 |
    
    예를 들어 회원 정보 조회 API는 로그인한 사용자만 접근할 수 있도록 Guard를 적용할 수 있다.
    
    ```
    GET /members/me
           ↓
    인증 검사
           ↓
    토큰이 유효한가?
           ↓
      YES       NO
       ↓         ↓
    조회 허용   401 반환
    ```
    
    ### HandlerInterceptor와 Guard의 차이
    
    | 구분 | HandlerInterceptor | Guard |
    | --- | --- | --- |
    | 개념 | Spring MVC에서 제공하는 인터페이스 | 접근 제어를 위한 개념 또는 프레임워크 기능 |
    | 주요 목적 | 요청 전후의 공통 처리 | 인증 및 인가를 통한 접근 제한 |
    | 사용 범위 | 인증, 로깅, 공통 처리 등 | 인증 및 권한 검사 중심 |
    | 적용 예시 | Spring Boot의 JWT 인증 | NestJS의 AuthGuard, RoleGuard |
    
    핵심은 `HandlerInterceptor`가 Spring MVC에서 제공하는 구체적인 기술인 반면, Guard는 접근을 보호하는 역할을 나타내는 개념이라는 점이다.
    
    Spring Boot에서는 HandlerInterceptor를 이용하여 Guard와 유사한 인증 및 인가 기능을 구현할 수 있다.
    
    ### HandlerInterceptor와 Filter의 차이
    
    Spring에서는 인터셉터와 비슷한 역할을 하는 Filter도 제공한다.
    
    | 구분 | Filter | HandlerInterceptor |
    | --- | --- | --- |
    | 소속 | Servlet API | Spring MVC |
    | 실행 위치 | DispatcherServlet 전후 | 컨트롤러 실행 전후 |
    | 주요 용도 | 인코딩, CORS, 보안 처리 등 | 인증 검사, 로깅, 컨트롤러 공통 처리 |
    | 특징 | Spring MVC 외부 요청 처리에도 적용 가능 | Spring MVC의 핸들러 정보 활용 가능 |
    
    Filter는 서블릿 처리 단계에서 동작하고, HandlerInterceptor는 Spring MVC의 핸들러 실행 단계에서 동작한다.
    
    실제 Spring Security는 주로 Filter 기반으로 인증과 인가를 처리하므로, 보안 기능을 구현할 때는 Spring Security 사용도 고려해야 한다.
    
    ### 장단점
    
    | 장점 | 단점 |
    | --- | --- |
    | 인증 로직을 여러 컨트롤러에서 재사용 가능 | 적용 경로를 잘못 설정하면 인증이 누락될 수 있음 |
    | 컨트롤러의 중복 코드 감소 | 복잡한 권한 검사를 모두 처리하기에는 구조가 복잡해질 수 있음 |
    | 요청을 컨트롤러 실행 전에 차단 가능 | Spring MVC의 요청 처리 흐름을 이해해야 함 |
    | 공통 로직을 한곳에서 관리 가능 | Spring Security와 역할이 중복될 수 있음 |
    
    ### 정리
    
    - `HandlerInterceptor`는 Spring MVC에서 컨트롤러 실행 전후에 공통 작업을 수행하는 인터페이스이다.
    - `preHandle()`을 사용하면 컨트롤러 실행 전에 JWT 인증을 검사할 수 있다.
    - Guard는 인증 및 인가를 통해 허용되지 않은 접근을 차단하는 보호 장치이다.
    - Spring Boot에서는 HandlerInterceptor를 이용하여 Guard와 유사한 기능을 구현할 수 있다.
    - Filter는 서블릿 단계에서, HandlerInterceptor는 Spring MVC의 핸들러 실행 단계에서 동작한다.
    - 인증과 인가가 복잡해지는 서비스에서는 Spring Security와 같은 보안 프레임워크를 활용하는 것이 일반적이다.
- 401 Unauthorized와 403 Forbidden의 차이
    
    ### 401 Unauthorized와 403 Forbidden이란?
    
    `401 Unauthorized`와 `403 Forbidden`은 HTTP 요청이 거부되었을 때 반환되는 상태 코드이다.
    
    두 상태 코드의 가장 큰 차이는 인증(Authentication)과 인가(Authorization)의 실패 여부이다.
    
    - `401 Unauthorized`: 인증 실패 → "누구인지 확인할 수 없음"
    - `403 Forbidden`: 접근 권한 부족 → "누구인지는 알지만 이 작업을 허용할 수 없음"
    
    ### 401 Unauthorized
    
    401은 요청에 유효한 인증 정보가 없을 때 반환하는 HTTP 상태 코드이다.
    
    주요 발생 상황
    
    - Authorization 헤더가 없는 경우
    - JWT가 만료된 경우
    - JWT의 서명이 올바르지 않은 경우
    - 잘못된 형식의 토큰을 전달한 경우
    
    예를 들어 로그인하지 않은 사용자가 자신의 회원 정보를 조회하려고 하면 인증에 실패한다.
    
    ```
    GET /members/me
    ```
    
    응답 예시
    
    ```
    HTTP/1.1 401 Unauthorized
    ```
    
    UMC 실습에서는 인증 토큰 없이 보호된 API를 호출하면 `401 / AUTH401_2`가 반환되도록 구현하였다.
    
    참고로 HTTP 표준에서 401 응답은 일반적으로 `WWW-Authenticate` 헤더를 통해 필요한 인증 방식을 안내한다.
    
    ### 403 Forbidden
    
    403은 서버가 요청을 이해했지만 해당 작업을 수행하도록 허용하지 않을 때 반환하는 HTTP 상태 코드이다.
    
    주요 발생 상황
    
    - 일반 사용자가 관리자 전용 기능에 접근한 경우
    - 다른 회원이 작성한 데이터를 수정하려는 경우
    - 특정 리소스에 대한 접근 권한이 없는 경우
    
    예를 들어 회원 A가 작성한 평점을 회원 B가 수정하려고 하면 접근 권한이 없어 요청이 거부된다.
    
    ```
    PATCH /ratings/5
    Authorization: Bearer <회원 B의 JWT>
    ```
    
    응답 예시
    
    ```
    HTTP/1.1 403 Forbidden
    ```
    
    UMC 실습에서는 로그인한 회원과 평점 작성자가 일치하지 않으면 `403 / RATING403_1`이 반환되도록 구현하였다.
    
    403은 인증된 사용자에게만 발생하는 것은 아니지만, 인증에는 성공했으나 권한이 부족한 상황을 설명할 때 자주 사용된다.
    
    ### 401과 403의 차이
    
    | 구분 | 401 Unauthorized | 403 Forbidden |
    | --- | --- | --- |
    | 핵심 의미 | 유효한 인증 정보 없음 | 요청 수행이 허용되지 않음 |
    | 관련 개념 | 인증(Authentication) | 인가(Authorization) |
    | 대표 원인 | 토큰 누락, 만료, 위조 | 접근 권한 부족 |
    | 해결 방법 | 로그인 또는 유효한 토큰 전달 | 필요한 권한 확보 |
    | UMC 오류 코드 | `AUTH401_2` | `RATING403_1` |
    
    ### 실제 API 요청 비교
    
    | 요청 상황 | 결과 | 이유 |
    | --- | --- | --- |
    | 토큰 없이 평점 수정 | 401 | 인증 정보 없음 |
    | 만료된 JWT로 평점 수정 | 401 | 유효하지 않은 인증 정보 |
    | 회원 A가 자신의 평점 수정 | 200 | 인증 및 인가 성공 |
    | 회원 B가 A의 평점 수정 | 403 | 수정 권한 없음 |
    | 존재하지 않는 평점 수정 | 404 | 요청한 리소스가 존재하지 않음 |
    
    여기서 `404 Not Found`는 인증이나 권한 문제가 아니라 요청한 리소스를 찾을 수 없다는 의미이다. 다만 실제 API에서는 보안 정책과 검사 순서에 따라 반환되는 상태 코드가 달라질 수 있다.
    
    ### 정리
    
    - `401 Unauthorized`는 유효한 인증 정보가 없어 인증이 필요한 요청을 처리할 수 없다는 의미이다.
    - `403 Forbidden`은 서버가 요청을 이해했지만 해당 작업을 허용하지 않는다는 의미이다.
    - JWT가 없거나 유효하지 않으면 일반적으로 401을 반환한다.
    - 유효한 JWT가 있어도 다른 회원의 평점을 수정할 권한이 없다면 403을 반환한다.
    - 인증과 인가를 구분하여 적절한 상태 코드를 반환하면 클라이언트가 오류 원인을 파악하고 대응하기 쉬워진다.
