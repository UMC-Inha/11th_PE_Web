# chapter08

- 트랜잭션(Transaction)
    
    ### **트랜잭션이란?**
    
    트랜잭션(Transaction)은 데이터베이스에서 여러 작업을 하나의 논리적인 작업 단위로 묶어 처리하는 것이다.
    
    여러 데이터가 함께 변경되어야 하는 상황에서 일부 작업만 성공하면 데이터의 일관성이 깨질 수 있다. 트랜잭션은 이러한 문제를 방지하기 위해 사용한다.
    
    ### **트랜잭션의 핵심 특징**
    
    - 작업 단위: 여러 데이터베이스 작업을 하나로 묶는다.
    - 성공 시 확정: 모든 작업이 정상적으로 완료되면 변경사항을 확정한다.
    - 실패 시 취소: 오류가 발생하면 변경사항을 되돌릴 수 있다.
    - 데이터 보호: 일부 작업만 반영되는 상황을 방지한다.
    
    ### **트랜잭션이 필요한 이유**
    
    영화 서비스에서 사용자가 평점과 즐겨찾기를 함께 등록한다고 가정한다.
    
    | 작업 | 트랜잭션이 없는 경우 | 트랜잭션이 있는 경우 |
    | --- | --- | --- |
    | 평점 저장 | 성공 | 성공 |
    | 즐겨찾기 저장 | 실패 | 실패 |
    | 최종 결과 | 평점만 저장될 수 있음 | 두 작업 모두 취소 |
    
    트랜잭션을 사용하면 서로 관련된 작업을 하나의 단위로 처리하여 데이터가 불완전하게 저장되는 문제를 방지할 수 있다.
    
    ### **트랜잭션의 처리 과정**
    
    1. 트랜잭션을 시작한다.
    2. 필요한 데이터베이스 작업을 수행한다.
    3. 모든 작업이 성공하면 Commit한다.
    4. 작업 중 오류가 발생하면 Rollback한다.
    
    Spring에서는 `@Transactional`을 사용하여 트랜잭션을 관리할 수 있다. 일반적인 설정에서는 런타임 예외가 발생하면 자동으로 롤백된다.
    
    ### **정리**
    
    - 트랜잭션은 여러 작업을 하나의 단위로 묶는 것이다.
    - 관련된 데이터가 함께 저장되거나 취소되도록 관리한다.
    - 데이터의 일관성과 무결성을 유지하는 데 중요한 역할을 한다.
- commit / rollback
    
    ### **Commit과 Rollback이란?**
    
    Commit과 Rollback은 트랜잭션의 실행 결과를 확정하거나 취소하는 작업이다.
    
    | 구분 | Commit | Rollback |
    | --- | --- | --- |
    | 의미 | 변경사항 확정 | 변경사항 취소 |
    | 목적 | 정상 처리 결과 반영 | 실패한 작업 복구 |
    | 결과 | 데이터 변경 유지 | 트랜잭션 이전 상태로 복구 |
    | 사용 시점 | 작업이 정상 완료된 경우 | 오류 발생 등으로 취소가 필요한 경우 |
    
    ### **Commit**
    
    Commit은 트랜잭션에서 수행한 변경사항을 최종적으로 확정하는 작업이다.
    
    예를 들어 사용자가 영화 평점과 즐겨찾기를 모두 성공적으로 등록했다면 Commit을 통해 두 작업의 결과가 확정된다.
    
    - 트랜잭션의 변경사항을 확정한다.
    - Commit이 완료되면 해당 트랜잭션은 종료된다.
    - 확정된 변경사항은 일반적인 Rollback으로 되돌릴 수 없다.
    
    ### **Rollback**
    
    Rollback은 트랜잭션에서 수행한 변경사항을 취소하고 트랜잭션 시작 전 상태로 되돌리는 작업이다.
    
    예를 들어 평점 저장에는 성공했지만 즐겨찾기 저장에 실패했다면 Rollback을 통해 평점 저장도 취소할 수 있다.
    
    - 트랜잭션에서 수행한 변경사항을 취소한다.
    - 일부 작업만 반영되는 상황을 방지한다.
    - 오류 발생 시 데이터의 일관성을 유지하는 데 사용한다.
    
    ### **정리**
    
    - Commit: 작업 결과를 확정한다.
    - Rollback: 작업 결과를 취소한다.
    - 두 기능은 트랜잭션을 안전하게 관리하기 위한 핵심 동작이다.
- 원자성(Atomicity)
    
    ### **원자성이란?**
    
    원자성(Atomicity)은 트랜잭션에 포함된 모든 작업이 전부 성공하거나 전부 실패해야 한다는 성질이다.
    
    이를 All or Nothing(전부 또는 전무)이라고 한다.
    
    ### **원자성의 핵심 특징**
    
    - 트랜잭션을 나눌 수 없는 하나의 작업 단위로 취급한다.
    - 모든 작업이 성공해야 결과가 확정된다.
    - 작업 중 실패하면 전체 변경사항을 취소한다.
    - 데이터가 일부만 반영되는 문제를 방지한다.
    
    ### **원자성의 예시**
    
    은행 계좌 A에서 B로 10만 원을 이체하는 상황을 생각해 보자.
    
    1. A 계좌에서 10만 원을 차감한다.
    2. B 계좌에 10만 원을 추가한다.
    
    | A 계좌 차감 | B 계좌 입금 | 최종 결과 |
    | --- | --- | --- |
    | 성공 | 성공 | 이체 완료 |
    | 성공 | 실패 | 전체 취소 |
    | 실패 | 실행되지 않음 | 전체 취소 |
    
    만약 A 계좌에서 돈만 빠져나가고 B 계좌에는 입금되지 않는다면 심각한 문제가 발생한다.
    
    원자성은 이러한 상황을 방지하기 위해 두 작업을 하나의 단위로 처리하도록 보장한다.
    
    ### **트랜잭션과 원자성의 관계**
    
    - 트랜잭션: 여러 작업을 하나로 묶는 단위
    - 원자성: 묶인 작업이 전부 성공하거나 실패해야 한다는 성질
    - Rollback: 실패한 트랜잭션의 변경사항을 취소하는 동작
    
    ### **정리**
    
    원자성의 핵심은 All or Nothing이다. 트랜잭션의 일부 작업만 반영되지 않도록 보장하여 데이터의 일관성을 유지한다.
    
- ACID
    
    ### **ACID란?**
    
    ACID는 데이터베이스 트랜잭션이 안전하고 신뢰성 있게 동작하기 위해 갖추어야 하는 네 가지 핵심 성질이다.
    
    | 속성 | 의미 | 핵심 키워드 |
    | --- | --- | --- |
    | Atomicity (원자성) | 모든 작업이 전부 성공하거나 실패 | All or Nothing |
    | Consistency (일관성) | 데이터가 정해진 규칙을 유지 | 무결성 |
    | Isolation (격리성) | 동시 실행되는 트랜잭션 간 간섭 제어 | 동시성 |
    | Durability (지속성) | 확정된 결과가 장애 이후에도 유지 | 영구 저장 |
    
    ### **Atomicity - 원자성**
    
    트랜잭션에 포함된 작업은 전부 성공하거나 전부 실패해야 한다.
    
    예시: 평점 저장에 성공했더라도 즐겨찾기 저장이 실패하면 두 작업 모두 취소한다.
    
    ### **Consistency - 일관성**
    
    트랜잭션이 완료된 후에도 데이터베이스의 무결성 규칙이 유지되어야 한다.
    
    예시: 영화 평점이 1~5점만 허용된다는 규칙이 있다면, 트랜잭션 이후에도 해당 규칙을 만족해야 한다.
    
    일관성은 데이터베이스의 제약 조건과 애플리케이션의 검증 규칙 등을 통해 유지된다.
    
    ### **Isolation - 격리성**
    
    여러 트랜잭션이 동시에 실행될 때 서로의 작업이 부적절하게 간섭하지 않도록 제어하는 성질이다.
    
    예를 들어 두 사용자가 동시에 같은 데이터를 수정할 경우, 격리 수준에 따라 서로의 변경사항을 확인하거나 영향을 받는 방식이 달라진다.
    
    대표적인 격리 수준은 다음과 같다.
    
    | 격리 수준 | 특징 |
    | --- | --- |
    | READ UNCOMMITTED | 커밋되지 않은 변경사항도 읽을 수 있음 |
    | READ COMMITTED | 커밋된 데이터만 읽음 |
    | REPEATABLE READ | 같은 트랜잭션에서 반복 조회한 행의 값이 유지되도록 보장 |
    | SERIALIZABLE | 트랜잭션이 순차 실행된 것과 같은 결과를 보장하는 가장 엄격한 수준 |
    
    일반적으로 격리 수준이 높아질수록 동시성 문제를 더 강하게 방지하지만, 성능과 동시 처리량에 영향을 줄 수 있다.
    
    ### **Durability - 지속성**
    
    트랜잭션이 성공적으로 Commit되면 그 결과는 시스템 장애가 발생하더라도 유지되어야 한다.
    
    예시: 영화 평점 저장이 완료된 이후 서버가 재시작되더라도 저장된 평점은 남아 있어야 한다.
    
    ### **정리**
    
    - 원자성: 일부만 저장되지 않도록 한다.
    - 일관성: 데이터의 규칙을 유지한다.
    - 격리성: 동시에 실행되는 작업의 간섭을 제어한다.
    - 지속성: 확정된 데이터를 보존한다.
- UNIQUE 제약 조건
    
    ### **UNIQUE 제약 조건이란?**
    
    UNIQUE는 데이터베이스에서 특정 컬럼 또는 여러 컬럼의 조합에 중복된 값이 저장되지 않도록 제한하는 제약 조건이다.
    
    데이터의 중복을 방지하고 무결성을 유지하기 위해 사용한다.
    
    ### **UNIQUE의 핵심 특징**
    
    - 특정 컬럼에 중복된 값이 저장되는 것을 방지한다.
    - 여러 컬럼을 조합하여 중복 여부를 판단할 수 있다.
    - 중복 값 삽입 시 제약 조건 위반 오류가 발생한다.
    - 애플리케이션의 중복 검사와 별개로 데이터베이스에서 중복을 방지한다.
    
    단, `NULL` 값의 중복 허용 여부는 DBMS에 따라 차이가 있을 수 있다.
    
    ### **UNIQUE 제약 조건의 예시**
    
    영화 서비스에서 한 회원이 같은 영화를 중복 즐겨찾기하지 못하도록 설정한다고 가정한다.
    
    이때 `member_id`와 `movie_id`를 하나의 UNIQUE 제약 조건으로 묶을 수 있다.
    
    | member_id | movie_id | 저장 가능 여부 |
    | --- | --- | --- |
    | 1 | 100 | 가능 |
    | 1 | 200 | 가능 |
    | 2 | 100 | 가능 |
    | 1 | 100 | 불가능 (중복) |
    
    서로 다른 회원이 같은 영화를 즐겨찾기하는 것은 가능하지만, 동일한 회원이 같은 영화를 중복 등록하는 것은 불가능하다.
    
    ### **애플리케이션 중복 검사와의 차이**
    
    | 구분 | 애플리케이션 중복 검사 | UNIQUE 제약 조건 |
    | --- | --- | --- |
    | 검사 위치 | Service 등 애플리케이션 계층 | 데이터베이스 |
    | 처리 방식 | 저장 전 중복 여부 조회 | 저장 시 중복 값 제한 |
    | 장점 | 사용자에게 명확한 오류 안내 가능 | 동시 요청에서도 중복 저장 방지 |
    | 한계 | 검사 이후 다른 요청이 먼저 저장할 수 있음 | 오류를 적절히 처리해야 함 |
    
    두 방식을 함께 사용하면 사용자에게 명확한 오류를 제공하면서 데이터베이스의 무결성도 보호할 수 있다.
    
    ### **정리**
    
    - UNIQUE는 중복 데이터 저장을 방지하는 제약 조건이다.
    - 여러 컬럼을 조합하여 중복 여부를 판단할 수 있다.
    - 동시 요청이 발생하더라도 데이터베이스 차원에서 중복 저장을 방지할 수 있다.
- 낙관적 잠금(Optimistic Locking)
    
    ### **낙관적 잠금이란?**
    
    낙관적 잠금(Optimistic Locking)은 여러 사용자가 같은 데이터를 동시에 수정할 때 버전 정보를 비교하여 충돌 여부를 확인하는 동시성 제어 방식이다.
    
    데이터 충돌이 자주 발생하지 않는다고 가정하며, 조회 시점부터 데이터를 배타적으로 잠그지 않는 것이 특징이다.
    
    ### **낙관적 잠금의 핵심 특징**
    
    - 데이터 수정 충돌이 드물다고 가정한다.
    - 주로 버전 번호를 사용하여 변경 여부를 확인한다.
    - 수정 시 버전이 일치하지 않으면 충돌로 판단한다.
    - 충돌 발생 시 수정 실패 처리나 재시도 등의 대응이 필요하다.
    
    ### **낙관적 잠금의 동작 과정**
    
    영화 정보를 두 사용자가 동시에 수정하는 상황을 가정한다.
    
    초기 데이터의 버전은 1이다.
    
    1. 사용자 A가 버전 1의 데이터를 조회한다.
    2. 사용자 B도 버전 1의 데이터를 조회한다.
    3. 사용자 A가 수정을 완료하여 버전이 2로 변경된다.
    4. 사용자 B가 버전 1을 기준으로 수정을 시도한다.
    5. 현재 버전이 2이므로 충돌이 발생한다.
    
    이처럼 버전을 비교하면 다른 사용자가 먼저 수정한 데이터를 덮어쓰는 문제를 방지할 수 있다.
    
    ### **낙관적 잠금과 비관적 잠금**
    
    | 구분 | 낙관적 잠금 | 비관적 잠금 |
    | --- | --- | --- |
    | 기본 가정 | 충돌이 드물다 | 충돌 가능성이 높다 |
    | 처리 방식 | 버전 비교로 충돌 감지 | 데이터베이스 잠금 사용 |
    | 장점 | 충돌이 적을 때 효율적 | 충돌이 많은 상황에서 유용 |
    | 단점 | 충돌 시 재시도 등이 필요 | 잠금 대기 및 교착 상태 가능 |
    | 적합한 상황 | 읽기가 많고 수정 충돌이 적은 경우 | 동일 데이터에 대한 수정 경쟁이 많은 경우 |
    
    ### **UNIQUE 제약 조건과의 차이**
    
    낙관적 잠금과 UNIQUE 제약 조건은 모두 데이터의 무결성을 보호하지만 목적이 다르다.
    
    - 낙관적 잠금: 여러 사용자가 동일한 데이터를 수정할 때 충돌을 감지한다.
    - UNIQUE 제약 조건: 동일한 값이나 컬럼 조합이 중복 저장되는 것을 방지한다.
    
    ### **정리**
    
    - 낙관적 잠금은 버전 비교를 통해 동시 수정 충돌을 감지한다.
