# chapter07

- 인증과 인가
    - 인증과 인가는 무엇을 확인하는 과정인가요?
        
        ### 인증과 인가
        
        인증(Authentication)은 사용자가 누구인지 확인하는 과정이고, 인가(Authorization)는 해당 사용자가 특정 기능을 이용할 권한이 있는지 확인하는 과정이다.
        
        예를 들어 영화 서비스에서 이메일과 비밀번호를 입력해 로그인하는 것은 인증에 해당한다. 서버는 입력한 정보가 등록된 계정과 일치하는지 확인하여 사용자의 신원을 확인한다.
        
        반면 인가는 로그인한 사용자가 어떤 기능을 사용할 수 있는지 판단하는 과정이다. 예를 들어 로그인한 사용자는 자신의 프로필을 수정할 수 있지만, 다른 사용자의 프로필을 마음대로 수정할 수는 없다.
        
        즉, 인증은 '누구인가?'를 확인하고, 인가는 '무엇을 할 수 있는가?'를 확인하는 과정이라고 이해하면 된다.
        
    - 로그인한 사용자도 특정 기능을 이용하지 못할 수 있는 이유는 무엇인가요?
        
        ### 인가를 통한 접근 권한 제어
        
        로그인에 성공했다고 해서 모든 기능을 사용할 수 있는 것은 아니기 때문이다. 로그인은 사용자가 누구인지 확인하는 인증 과정일 뿐이며, 실제로 특정 기능을 사용할 수 있는지는 인가 과정을 통해 별도로 판단한다.
        
        예를 들어 영화 서비스에서 로그인한 사용자는 자신의 프로필을 수정할 수 있지만, 다른 사용자의 프로필을 마음대로 수정할 수는 없다. 또한 일반 사용자는 관리자만 사용할 수 있는 회원 관리 기능에 접근할 수 없다.
        
        즉, 로그인한 사용자라도 해당 기능을 사용할 권한이 없다면 접근이 제한될 수 있다. 이를 통해 다른 사용자의 정보를 보호하고 서비스의 보안을 유지할 수 있다.
        
- JWT
    - header, payload, signature는 각각 어떤 역할을 하나요?
        
        ### JWT의 구조와 각 구성 요소의 역할
        
        JWT(JSON Web Token)는 사용자와 관련된 정보 등을 JSON 형태로 표현하고, 이를 토큰으로 전달하기 위한 표준 형식이다. 주로 로그인에 성공한 사용자에게 토큰을 발급하고, 이후 API 요청에서 사용자를 확인하는 데 활용한다. 
        
        JWT는 Header, Payload, Signature의 세 부분으로 구성되며, 각 부분은 점(.)으로 구분된다.
        
        JWT의 기본 구조: `Header.Payload.Signature`
        
        #### Header (헤더)
        
        Header는 JWT의 기본 정보를 담는 부분이다. 토큰의 종류와 서명에 사용한 알고리즘 등의 정보가 포함된다.
        
        예를 들어 토큰의 종류가 JWT이고 서명 알고리즘이 HS256이라는 정보를 담을 수 있다.
        
        #### Payload (페이로드)
        
        Payload는 사용자와 관련된 정보나 토큰의 유효기간 등을 담는 부분이다.
        
        예를 들어 사용자 ID, 토큰 발급 시간, 만료 시간 등의 정보가 포함될 수 있다. 다만 Payload는 암호화된 것이 아니라 인코딩된 것이므로 누구나 내용을 확인할 수 있다. 따라서 비밀번호와 같은 민감한 정보는 저장하면 안 된다.
        
        #### Signature (서명)
        
        Signature는 JWT가 신뢰할 수 있는 발급자에 의해 서명되었는지, 서명된 내용이 이후 변경되지 않았는지 검증하는 데 사용된다.
        
        서버는 Header와 Payload를 바탕으로 생성된 서명을 검증하여 토큰의 내용이 변경되지 않았는지 확인한다. 서명 검증에 실패하면 해당 토큰을 신뢰할 수 없다.
        
        ### 실제 사용 예시
        
        영화 서비스에서 사용자가 로그인에 성공하면 서버는 JWT를 발급할 수 있다. 이후 사용자가 자신의 프로필 정보를 요청할 때 JWT를 함께 전달하면, 서버는 토큰의 서명과 만료 시간 등을 검증하고 사용자 정보를 확인할 수 있다.
        
        즉, Header는 토큰의 기본 정보, Payload는 사용자 및 토큰 관련 정보, Signature는 토큰의 무결성을 검증하는 역할을 한다.
        
    - JWT를 디코딩하는 것과 서명을 검증하는 것은 어떻게 다른가요?
        
        ### JWT 디코딩과 서명 검증의 차이
        
        JWT를 디코딩하는 것은 토큰에 담긴 정보를 읽을 수 있는 형태로 변환하는 과정이고, 서명을 검증하는 것은 토큰이 위조되거나 변조되지 않았는지 확인하는 과정이다.
        
        #### JWT 디코딩(Decoding)
        
        JWT의 Header와 Payload는 Base64URL 방식으로 인코딩되어 있다. 디코딩은 인코딩된 데이터를 원래의 형태로 변환하여 내용을 확인하는 과정이다.
        
        예를 들어 JWT를 디코딩하면 사용자 ID나 토큰 만료 시간 등의 정보를 확인할 수 있다. 이 과정에는 별도의 비밀키가 필요하지 않으므로 누구나 내용을 확인할 수 있다.
        
        하지만 디코딩만으로는 토큰의 내용이 실제로 신뢰할 수 있는 정보인지 판단할 수 없다.
        
        #### JWT 서명 검증(Signature Verification)
        
        서명 검증은 JWT의 Header와 Payload가 발급 이후 변경되지 않았는지 확인하는 과정이다.
        
        서버는 허용된 서명 알고리즘과 적절한 검증 키를 사용하여 Signature가 올바른지 확인한다. 검증에 성공하면 토큰이 신뢰할 수 있는 발급자에 의해 서명되었고, 서명된 내용이 변경되지 않았음을 확인할 수 있다.
        
        반대로 서명 검증에 실패하면 토큰이 위조되거나 변조되었을 가능성이 있으므로 해당 토큰을 신뢰해서는 안 된다.
        
        ### 실제 사용 예시
        
        영화 서비스에서 사용자가 JWT를 이용해 자신의 프로필 정보를 요청한다고 가정해 보자.
        
        JWT를 디코딩하면 토큰에 담긴 사용자 ID를 확인할 수 있다. 하지만 누군가 토큰의 Payload를 임의로 변경했을 가능성이 있으므로 디코딩한 정보만으로 사용자를 신뢰해서는 안 된다.
        
        따라서 서버는 서명을 검증하여 토큰이 변조되지 않았는지 확인해야 한다. 이후 만료 시간과 발급자 등의 조건도 확인하여 토큰을 사용할 수 있는지 판단한다.
        
        즉, 디코딩은 '토큰에 어떤 정보가 들어 있는가?'를 확인하는 과정이고, 서명 검증은 '토큰의 내용을 신뢰할 수 있는가?'를 확인하는 과정이다.
        
    - payload에 비밀번호를 담으면 안 되는 이유는 무엇인가요?
        
        ### JWT Payload에 비밀번호를 담으면 안 되는 이유
        
        JWT의 Payload는 암호화된 것이 아니라 Base64URL 방식으로 인코딩된 데이터이기 때문이다. 인코딩은 데이터를 다른 형태로 표현하는 것일 뿐, 내용을 숨기는 기술이 아니므로 누구나 JWT를 디코딩하여 Payload에 담긴 정보를 확인할 수 있다.
        
        예를 들어 영화 서비스에서 로그인한 사용자에게 발급한 JWT의 Payload에 비밀번호를 포함했다고 가정해 보자. 이 경우 토큰을 획득한 사람이 JWT를 디코딩하면 비밀번호를 확인할 수 있어 계정 정보가 유출될 위험이 있다.
        
        또한 JWT의 Signature는 토큰의 위조나 변조 여부를 검증하는 역할을 할 뿐, Payload의 내용을 숨겨주지는 않는다.
        
        따라서 JWT의 Payload에는 비밀번호와 같은 민감한 정보를 담지 않아야 하며, 사용자 ID나 토큰 만료 시간 등 인증에 필요한 최소한의 정보만 포함하는 것이 좋다.
        
        즉, JWT는 서명을 통해 데이터의 무결성을 검증할 수 있지만, Payload의 기밀성까지 보장하지는 않기 때문에 비밀번호를 저장해서는 안 된다.
