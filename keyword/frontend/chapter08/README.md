# chapter08

- 클라이언트 상태와 서버 상태
    - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.
        
        #### **입력값**
        
        입력값은 사용자가 로그인이나 회원가입 화면에서 직접 입력하는 이메일, 비밀번호 등의 데이터이다.
        
        입력값은 브라우저에서 생성되고 변경되며, 일반적으로 특정 컴포넌트에서만 사용하므로 `useState`로 관리하는 것이 적절하다.
        
        ```tsx
        const [email, setEmail] = useState("");
        const [password, setPassword] = useState("");
        ```
        
        입력값의 원본은 사용자가 브라우저에서 입력한 값이며, 서버에 전송하기 전까지 클라이언트에서 관리된다.
        
        #### **로그인 토큰**
        
        로그인 토큰은 사용자가 로그인에 성공했을 때 서버에서 발급하는 인증 정보이다.
        
        발급받은 토큰은 여러 페이지에서 인증이 필요한 API를 요청할 때 사용하므로 Zustand와 같은 전역 Store에서 관리할 수 있다.
        
        ```tsx
        const accessToken = useAuthStore((state) => state.accessToken);
        ```
        
        토큰은 서버에서 발급하지만, 클라이언트는 발급받은 토큰을 저장하고 API 요청에 사용한다.
        
        따라서 클라이언트에서 사용하는 토큰 상태는 전역 Store로 관리할 수 있으며, 토큰의 유효성은 서버가 최종적으로 판단한다.
        
        다만 토큰을 어디에 저장할지는 보안 요구사항과 인증 방식에 따라 달라질 수 있다.
        
        #### **회원 정보**
        
        회원 정보는 닉네임, 이메일처럼 서버의 데이터베이스에 저장되는 데이터이다.
        
        클라이언트는 API 요청을 통해 회원 정보를 가져오므로 TanStack Query의 `useQuery`로 관리하는 것이 적절하다.
        
        ```tsx
        const { data } = useQuery({
          queryKey: ["members", "me"],
          queryFn: getMe,
        });
        ```
        
        회원 정보의 원본은 서버에 있으며, TanStack Query는 서버에서 가져온 데이터를 캐시에 저장하여 관리한다.
        
        회원 정보가 수정되면 `invalidateQueries`로 서버 데이터를 다시 조회하거나 `setQueryData`로 캐시를 갱신하여 변경 결과를 화면에 반영할 수 있다.
        
        #### **정리**
        
        각 상태는 데이터의 원본과 사용 목적이 다르므로 적절한 관리 방법을 선택해야 한다.
        
        | 상태 | 관리 방법 | 데이터의 원본 |
        | --- | --- | --- |
        | 입력값 | `useState` | 클라이언트 |
        | 로그인 토큰 | Zustand 등 전역 Store | 서버에서 발급 |
        | 회원 정보 | TanStack Query | 서버의 데이터베이스 |
        
        입력값은 클라이언트에서 생성되는 상태이므로 `useState`로 관리하고, 로그인 토큰은 여러 컴포넌트에서 공유할 수 있도록 Zustand와 같은 전역 Store에서 관리할 수 있다.
        
        반면 회원 정보는 서버에 원본이 존재하는 데이터이므로 TanStack Query를 사용하여 조회하고 캐싱하는 것이 적절하다.
        
        이처럼 상태의 원본이 어디에 있는지와 어떤 목적으로 사용되는지를 기준으로 관리 방법을 구분하는 것이 중요하다.
        
    - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?
        
        #### **데이터 불일치 문제**
        
        같은 회원 정보를 Zustand와 같은 전역 Store와 TanStack Query 캐시에 각각 저장하면 데이터 불일치 문제가 발생할 수 있다.
        
        예를 들어 회원의 닉네임이 `user1`이라고 가정한다.
        
        처음에는 Zustand와 Query 캐시에 모두 `user1`이 저장되어 있지만, 사용자가 닉네임을 `user2`로 변경한 후 Query 캐시만 갱신하면 다음과 같은 상황이 발생한다.
        
        | 저장 위치 | 닉네임 | 상태 |
        | --- | --- | --- |
        | Zustand Store | user1 | 이전 데이터 |
        | TanStack Query 캐시 | user2 | 최신 데이터 |
        
        이 경우 헤더에서는 이전 닉네임인 `user1`이 표시되고, 마이페이지에서는 변경된 닉네임인 `user2`가 표시될 수 있다.
        
        즉, 같은 회원 정보를 사용하더라도 어느 저장소의 데이터를 참조하는지에 따라 화면에 서로 다른 값이 나타날 수 있다.
        
        #### **상태 동기화 문제**
        
        동일한 데이터를 여러 저장소에 저장하면 데이터가 변경될 때마다 모든 저장소를 함께 갱신해야 한다.
        
        예를 들어 회원 정보를 수정한 후 Query 캐시를 갱신하는 것뿐만 아니라 Zustand Store에 저장된 회원 정보도 별도로 수정해야 한다.
        
        이 과정에서 하나라도 갱신하지 않으면 데이터가 서로 달라지는 문제가 발생할 수 있다.
        
        또한 데이터를 동기화하기 위한 코드가 추가되므로 상태 관리 로직이 복잡해지고 유지보수가 어려워진다.
        
        #### **해결 방법**
        
        이러한 문제를 방지하려면 상태의 성격에 따라 관리 역할을 구분하는 것이 적절하다.
        
        - `useState`: 입력값이나 모달 상태처럼 특정 컴포넌트에서 사용하는 클라이언트 상태를 관리한다.
        - `Zustand`: 로그인 토큰처럼 여러 컴포넌트에서 공유해야 하는 클라이언트 상태를 관리한다.
        - `TanStack Query`: 회원 정보처럼 서버에 원본이 존재하는 데이터를 조회하고 캐싱한다.
        
        예를 들어 회원 정보는 Zustand에 중복 저장하지 않고 TanStack Query를 통해 관리할 수 있다.
        
        ```tsx
        const { data } = useQuery({
          queryKey: ["members", "me"],
          queryFn: getMe,
        });
        ```
        
        회원 정보가 수정되면 `invalidateQueries`를 통해 서버에서 최신 데이터를 다시 가져오거나 `setQueryData`를 사용하여 캐시를 갱신할 수 있다.
        
        이렇게 하면 여러 컴포넌트가 동일한 Query 캐시를 참조하므로 회원 정보의 일관성을 유지하기 쉬워진다.
        
        #### **정리**
        
        같은 회원 정보를 전역 Store와 Query 캐시에 중복 저장하면 데이터 불일치, 동기화 문제, 유지보수의 어려움이 발생할 수 있다.
        
        따라서 서버에서 관리하는 회원 정보는 TanStack Query를 중심으로 관리하고, 전역 Store는 로그인 토큰과 같은 클라이언트 상태를 관리하도록 역할을 분리하는 것이 적절하다.
        
- 캐시 일관성
    - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?
        
        #### **Query 캐시에 이전 데이터가 남아 있기 때문**
        
        서버에서 데이터를 수정했는데 다른 화면에 이전 값이 표시되는 이유는 클라이언트에 저장된 캐시 데이터가 최신 상태로 갱신되지 않았기 때문이다.
        
        TanStack Query는 서버에서 가져온 데이터를 Query 캐시에 저장하고, 여러 컴포넌트에서 재사용할 수 있도록 한다.
        
        하지만 서버의 데이터가 변경되었다고 해서 클라이언트의 Query 캐시가 자동으로 변경되는 것은 아니다.
        
        예를 들어 사용자가 마이페이지에서 닉네임을 `user1`에서 `user2`로 변경했다고 가정한다.
        
        | 구분 | 닉네임 | 상태 |
        | --- | --- | --- |
        | 서버 데이터베이스 | user2 | 최신 데이터 |
        | Query 캐시 | user1 | 이전 데이터 |
        | 화면에 표시되는 값 | user1 | 이전 데이터 표시 |
        
        서버에서는 닉네임 수정이 정상적으로 완료되었지만, Query 캐시에는 이전 값인 `user1`이 남아 있으므로 다른 화면에서도 이전 닉네임이 표시될 수 있다.
        
        #### **invalidateQueries를 이용한 해결 방법**
        
        `invalidateQueries`는 특정 Query 캐시를 오래된 데이터로 표시하고, 활성화된 Query에 대해 기본적으로 재조회를 수행하도록 하는 기능이다.
        
        ```tsx
        queryClient.invalidateQueries({
          queryKey: ["members", "me"],
        });
        ```
        
        회원 정보 수정이 성공한 후 해당 코드를 실행하면 `["members", "me"]`에 해당하는 Query가 무효화된다.
        
        해당 Query를 사용하는 컴포넌트가 활성화되어 있다면 서버에 다시 요청하여 최신 회원 정보를 가져올 수 있다.
        
        따라서 서버에서 변경된 닉네임인 `user2`가 화면에도 반영된다.
        
        #### **setQueryData를 이용한 해결 방법**
        
        `setQueryData`는 서버에 다시 요청하지 않고 Query 캐시에 저장된 데이터를 직접 변경하는 기능이다.
        
        예를 들어 회원 정보 수정 API가 변경된 회원 정보를 반환한다면 해당 응답을 사용하여 캐시를 갱신할 수 있다.
        
        ```tsx
        queryClient.setQueryData(
          ["members", "me"],
          updatedMember,
        );
        ```
        
        이렇게 하면 Query 캐시에 저장된 회원 정보가 즉시 변경되고, 해당 캐시를 사용하는 컴포넌트에도 변경 결과가 반영된다.
        
        단, `updatedMember`는 해당 Query 캐시가 사용하는 데이터 구조와 일치해야 한다.
        
        #### **invalidateQueries와 setQueryData의 차이**
        
        | 구분 | invalidateQueries | setQueryData |
        | --- | --- | --- |
        | 동작 방식 | 캐시를 무효화하고 재조회 유도 | 캐시 데이터를 직접 변경 |
        | 서버 재요청 | 활성 Query는 기본적으로 재요청 | 재요청하지 않음 |
        | 장점 | 서버의 최신 데이터 확인 가능 | 변경 결과를 빠르게 반영 가능 |
        | 주의점 | 네트워크 요청이 추가될 수 있음 | 정확한 데이터로 갱신해야 함 |
        
        #### **정리**
        
        서버에서 데이터를 수정하더라도 클라이언트의 Query 캐시가 자동으로 변경되는 것은 아니므로 다른 화면에 이전 값이 표시될 수 있다.
        
        이를 해결하려면 데이터 수정에 성공한 후 `invalidateQueries`로 서버 데이터를 다시 조회하거나, `setQueryData`로 Query 캐시를 직접 갱신해야 한다.
        
        즉, 서버 데이터가 변경되었을 때 **클라이언트의 캐시도 최신 상태로 유지하는 것이 중요하다.**
        
    - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?
        
        #### **invalidateQueries를 이용한 재조회 방식**
        
        `invalidateQueries`는 기존 Query 캐시를 무효화하고, 활성화된 Query에 대해 기본적으로 서버에 데이터를 다시 요청하도록 하는 기능이다.
        
        서버에서 데이터가 변경되었을 때 클라이언트가 변경된 결과를 정확히 알 수 없다면 재조회 방식을 사용하는 것이 적절하다.
        
        예를 들어 사용자가 영화에 평점을 등록했다고 가정한다.
        
        평점 등록 후 서버에서 평균 평점이나 평점 개수까지 변경되었다면, 클라이언트는 이러한 변경 결과를 모두 알기 어려울 수 있다.
        
        이때 `invalidateQueries`를 사용하면 서버에서 최신 데이터를 다시 가져올 수 있다.
        
        ```tsx
        queryClient.invalidateQueries({
          queryKey: ["ratings", movieId],
        });
        ```
        
        이 코드는 `["ratings", movieId]`에 해당하는 Query를 무효화한다. 해당 Query가 활성화되어 있다면 기본적으로 서버에 다시 요청하여 최신 평점 데이터를 가져온다.
        
        재조회 방식은 다음과 같은 상황에 적절하다.
        
        - 서버에서 변경된 데이터의 최종 결과를 정확히 알 수 없는 경우
        - 하나의 수정 작업으로 여러 데이터가 함께 변경되는 경우
        - 서버에서 계산하거나 가공한 최신 데이터가 필요한 경우
        - 추가 API 요청이 발생하더라도 데이터의 정확성이 중요한 경우
        
        #### **setQueryData를 이용한 캐시 직접 수정 방식**
        
        `setQueryData`는 서버에 다시 요청하지 않고 Query 캐시에 저장된 데이터를 직접 변경하는 기능이다.
        
        서버에서 변경된 결과를 이미 알고 있거나, 수정 API가 최신 데이터를 응답으로 반환하는 경우에 적절하다.
        
        예를 들어 사용자가 닉네임을 `user1`에서 `user2`로 변경했고, 서버가 수정된 회원 정보를 반환했다고 가정한다.
        
        이때 서버에 회원 정보를 다시 요청하지 않고 수정 API의 응답을 이용하여 Query 캐시를 갱신할 수 있다.
        
        ```tsx
        queryClient.setQueryData(
          ["members", "me"],
          updatedMember,
        );
        ```
        
        이 코드는 `["members", "me"]`에 저장된 데이터를 `updatedMember`로 변경한다.
        
        따라서 해당 Query 캐시를 사용하는 컴포넌트는 서버에 다시 요청하지 않고도 변경된 회원 정보를 표시할 수 있다.
        
        단, `updatedMember`는 해당 Query 캐시에 저장되는 데이터와 동일한 구조여야 한다.
        
        캐시 직접 수정 방식은 다음과 같은 상황에 적절하다.
        
        - 수정 API가 변경된 최신 데이터를 응답으로 반환하는 경우
        - 변경된 결과를 클라이언트에서 정확히 알고 있는 경우
        - 불필요한 API 요청을 줄이고 싶은 경우
        - 변경 결과를 화면에 빠르게 반영하고 싶은 경우
        
        #### **invalidateQueries와 setQueryData 비교**
        
        | 구분 | invalidateQueries | setQueryData |
        | --- | --- | --- |
        | 동작 방식 | 캐시 무효화 후 재조회 유도 | 캐시 데이터를 직접 변경 |
        | 서버 재요청 | 활성 Query는 기본적으로 재요청 | 재요청하지 않음 |
        | 데이터 정확성 | 서버의 최신 데이터를 다시 확인 | 직접 설정한 데이터에 의존 |
        | 화면 반영 속도 | 서버 응답을 기다려야 함 | 즉시 반영 가능 |
        | 적절한 상황 | 변경 결과를 정확히 알 수 없는 경우 | 변경 결과를 이미 알고 있는 경우 |
        
        #### **정리**
        
        서버에서 데이터가 수정되었지만 변경된 결과를 정확히 알 수 없다면 `invalidateQueries`를 사용하여 최신 데이터를 다시 조회하는 것이 적절하다.
        
        반면 수정 API가 최신 데이터를 반환하거나 변경 결과를 정확히 알고 있다면 `setQueryData`로 캐시를 직접 수정하는 것이 효율적이다.
        
        즉, **데이터의 정확한 최신 상태를 다시 확인해야 한다면** `invalidateQueries`**, 변경 결과를 이미 알고 있어 불필요한 재요청을 줄이고 싶다면** `setQueryData`**를 사용하는 것이 적절하다.**
