- 인증(Authentication)과 인가(Authorization)
    
    **인증은 요청자의 신원을 확인하는 과정이고, 인가는 그 요청자가 특정 데이터에 특정 작업을 수행할 수 있는지 판단하는 과정이다.** 백엔드에서는 두 검사를 통과한 요청만 실제 데이터 변경으로 이어지도록 처리해야 한다.
    
    워크북의 평점 수정 기능에서는 다음과 같이 구분된다.
    
    | 단계 | 서버가 확인하는 내용 |
    | --- | --- |
    | 인증 | 전달받은 토큰을 검증하고 요청자의 회원 번호를 확인한다. |
    | 인가 | 해당 회원이 수정하려는 평점의 작성자인지 확인한다. |
    | 데이터 변경 | 두 검사를 통과한 경우에만 평점과 내용을 변경한다. |
    
    여기서 중요한 것은 **회원 번호의 값보다 그 값을 어디에서 가져왔는지이다.** URL이나 요청 바디에 들어 있는 회원 번호는 사용자가 바꿀 수 있으므로 신원을 증명하지 못한다. 반면 서버가 검증한 토큰에서 추출한 회원 번호는 요청자를 식별하는 데 사용할 수 있다.
    
    예를 들어 평점을 등록할 때 클라이언트는 영화 번호와 평점 내용을 전달하고, **작성자는 서버가 인증 정보로 결정해야 한다.** 요청 바디에 작성자 번호까지 포함하도록 만들면 다른 회원의 이름으로 평점을 등록할 위험이 생긴다.
    
    또한 **인증은 로그인할 때 한 번 수행하고 끝나는 작업이 아니다.** 로그인에서는 이메일과 비밀번호를 확인하고, 이후 보호된 API 요청에서는 토큰을 검증해 요청자를 다시 확인한다.
    
    인가에서는 사용자의 등급뿐 아니라 **데이터의 소유권과 수행하려는 작업**도 함께 고려해야 한다. 다른 사람의 평점을 조회할 수 있다고 해서 수정하거나 삭제할 권한까지 생기는 것은 아니다.
    
    실제 구현에서는 다음 사항도 중요하다.
    
    - **데이터 번호를 UUID처럼 추측하기 어렵게 만들어도 권한 검사는 필요하다.** 주소를 알아내기 어렵게 만드는 것과 접근 권한을 확인하는 것은 별개이다.
    - **새 API뿐 아니라 기존 API의 접근 경로도 점검해야 한다.** 새 수정 API에 인증을 추가했더라도 기존 수정 API가 그대로 열려 있다면 우회 경로가 남는다.
    - **인가 검사는 데이터 변경 전에 수행해야 한다.** 실패 응답을 반환하더라도 이미 DB가 변경되었다면 올바른 접근 제한이 아니다.
- 해시와 salt, bcrypt
    
    비밀번호는 원문을 저장하지 않고, **비밀번호 검증을 위해 설계된 해시 알고리즘으로 처리한 결과를 저장해야 한다.** 로그인에서는 저장된 값을 복호화하는 것이 아니라, 입력한 비밀번호가 저장된 해시에 대응하는지 확인한다.
    
    | 개념 | 역할 | 주의할 점 |
    | --- | --- | --- |
    | 해시 | 입력값을 일정한 방식으로 변환한 결과이다. | 역으로 복원하는 기능은 없지만, 후보 비밀번호를 대입하는 공격은 가능하다. |
    | Salt | 비밀번호마다 섞는 무작위 값이다. | 비밀키가 아니며, 해시와 함께 저장해도 된다. |
    | bcrypt | Salt와 계산 비용을 적용하는 비밀번호 해시 알고리즘이다. | 검증 비용이 높으므로 보안성과 서버 처리 성능을 함께 고려해야 한다. |
    
    **일반적인 해시 함수가 모두 비밀번호 저장에 적합한 것은 아니다.** SHA-256처럼 빠른 해시 함수는 파일 검증 등에 유용하지만, 공격자도 비밀번호 후보를 빠르게 대입할 수 있다. bcrypt는 계산 비용을 높여 대량의 비밀번호 추측을 어렵게 만든다.
    
    Salt는 같은 비밀번호를 사용하더라도 저장되는 결과를 다르게 만든다. bcrypt의 저장 문자열에는 알고리즘 정보, 계산 비용, salt, 해시 결과가 포함되므로 검증할 때 이 정보를 다시 사용할 수 있다.
    
    Spring에서는 다음처럼 저장과 검증을 구분한다.
    
    ```java
    String storedHash = passwordEncoder.encode("Umc1234!");
    
    boolean matches = passwordEncoder.matches(
            "Umc1234!",
            storedHash
    );
    ```
    
    **로그인할 때 비밀번호를 새로 encode한 뒤 저장된 문자열과 비교하면 안 된다.** 새 salt가 적용되므로 같은 비밀번호라도 결과가 달라질 수 있기 때문이다. 반드시 입력한 원문과 저장된 해시를 matches에 전달해야 한다.
    
    추가로 알아둘 부분은 다음과 같다.
    
    - **계산 비용을 무조건 높이는 것이 정답은 아니다.** bcrypt는 정상적인 로그인 검증에도 계산 시간이 필요하다. 실제 서버에서 처리 시간을 측정하고 동시 요청량을 고려해야 한다.
    - **bcrypt만으로 로그인 공격을 모두 막을 수는 없다.** 반복 로그인 시도에 대한 요청 제한도 함께 필요하다.
    - **bcrypt에는 일반적으로 72바이트의 입력 제한이 있다.** 이는 72글자가 아니며, 한글처럼 UTF-8에서 여러 바이트를 사용하는 문자는 더 빨리 제한에 도달한다. 사용하는 구현의 처리 방식을 확인하고 서버에서 일관되게 검증해야 한다.
    - **비밀번호에 임의로 trim이나 소문자 변환을 적용하면 안 된다.** 사용자가 입력한 비밀번호 자체가 달라지기 때문이다. 공백 등을 허용하지 않는 정책이라면 조용히 바꾸기보다 검증 단계에서 거절해야 한다.
    
    해시는 노출되어도 괜찮은 정보가 아니다. DB가 유출되면 공격자가 해시를 대상으로 비밀번호 후보를 계속 대입할 수 있으므로, **비밀번호 해시도 응답이나 로그에 포함하지 않아야 한다.**
    
- JWT (Header / Payload / Signature, Claim)
    
    일반적인 서명된 JWT는 사용자 식별 정보 등을 전달하면서 **내용의 변조 여부를 검증할 수 있도록 만든 토큰 형식이다.**
    
    | 구성 요소 | 역할 |
    | --- | --- |
    | Header | 서명 알고리즘과 토큰 유형 등의 정보를 담는다. |
    | Payload | 회원 식별자, 발급 시각, 만료 시각 등의 정보를 담는다. |
    | Signature | Header와 Payload가 변경되지 않았는지 검증하는 데 사용한다. |
    | Claim | Payload 등에 담기는 개별 정보 항목이다. |
    
    백엔드에서는 토큰을 읽는 것보다 **어떤 검증을 통과한 정보를 사용하는지**가 중요하다. 디코딩으로 회원 번호를 읽을 수 있더라도, 서명과 만료 여부 등을 검증하기 전에는 신뢰해서는 안 된다.
    
    대표적인 claim은 다음과 같다.
    
    | Claim | 의미 | 서버에서 고려할 점 |
    | --- | --- | --- |
    | sub | 토큰의 주체이다. | 변경 가능한 닉네임보다 회원 번호처럼 안정적인 식별자가 적합하다. |
    | iat | 발급 시각이다. | 발급 시각이 있다는 것만으로 토큰이 만료되는 것은 아니다. |
    | exp | 만료 시각이다. | 서버가 현재 시각과 비교해 사용 가능 여부를 판단한다. |
    | iss | 발급자이다. | 기대한 발급자의 토큰인지 확인하는 데 사용한다. |
    | aud | 토큰의 사용 대상이다. | 다른 서비스용 토큰이 잘못 사용되는 것을 제한하는 데 사용한다. |
    
    **토큰의 정보와 DB의 최신 정보는 다를 수 있다.** 예를 들어 토큰 발급 후 닉네임이나 권한이 변경되어도 기존 토큰의 내용은 자동으로 갱신되지 않는다. 따라서 내 정보 조회에서는 토큰으로 회원 번호를 확인하고, 실제 표시할 정보는 DB에서 조회하는 방식이 적절하다.
    
    또한 **JWT를 사용한다고 서버가 DB를 전혀 조회하지 않는 것은 아니다.** 별도의 세션 저장소를 조회하지 않고 토큰 자체를 검증할 수 있다는 뜻에 가깝다. 회원의 현재 상태나 데이터 소유권을 확인하려면 여전히 DB 조회가 필요할 수 있다.
    
    서명키 관리도 중요하다. 워크북에서 사용하는 HMAC 방식은 같은 비밀키로 서명과 검증을 수행하므로, **비밀키를 아는 사람은 토큰을 검증할 뿐 아니라 새로 만들어낼 수도 있다.**
    
    - 비밀키는 충분히 무작위적인 값으로 생성해야 한다. 길기만 한 예측 가능한 문장이 좋은 키인 것은 아니다.
    - 비밀키는 백엔드에서 관리해야 하며, 프론트엔드에 전달하면 안 된다.
    - 특히 Vite의 VITE_ 환경변수는 클라이언트 코드에서 사용되므로 JWT 서명키를 넣는 위치가 아니다.
    - 키가 유출되면 환경변수로 옮기는 것만으로 해결되지 않는다. 키를 교체하고 기존 토큰의 처리도 결정해야 한다.
    
    만료 시간을 시험할 때는 **허용 시계 오차도 확인해야 한다.** 워크북의 Spring 예제는 60초의 시계 오차를 허용하므로, 설정한 만료 시각을 조금 지났어도 토큰이 잠시 허용될 수 있다. 이는 주로 발급 서버와 검증 서버 사이의 시각 차이를 고려한 설정이다.
    
- Bearer 인증과 Authorization 헤더
    
    **Bearer 인증은 토큰을 소지한 요청자를 그 토큰에 해당하는 사용자로 취급하는 방식이다.** 요청마다 비밀번호를 다시 보내는 대신 다음처럼 Authorization 헤더에 토큰을 전달한다.
    
    ```
    GET /members/me HTTP/1.1
    Host: localhost:8080
    Authorization: Bearer eyJhbGciOi...
    ```
    
    Bearer와 JWT는 같은 개념이 아니다.
    
    | 구분 | 의미 |
    | --- | --- |
    | Bearer | 토큰을 소지한 사람이 사용할 수 있다는 인증 방식이다. |
    | JWT | 토큰에 정보를 담고 표현하는 형식이다. |
    | Authorization | 인증 정보를 전달하는 HTTP 요청 헤더이다. |
    
    따라서 Bearer 방식에서 사용하는 토큰이 반드시 JWT일 필요는 없다. 서버가 별도로 조회해야 의미를 알 수 있는 임의의 문자열도 Bearer 토큰으로 사용할 수 있다.
    
    서버는 Authorization 헤더에서 토큰을 추출한 뒤 검증해야 한다. **Bearer라는 문자열이 붙어 있거나 토큰이 존재한다는 사실만으로 인증이 완료되는 것은 아니다.**
    
    Bearer 토큰은 탈취한 사람도 사용할 수 있으므로 전달 과정과 기록 방식이 중요하다.
    
    - **HTTPS를 사용해야 한다.** JWT 서명은 토큰의 내용을 숨기거나 전송 중 탈취를 방지하는 기능이 아니다.
    - **토큰을 URL의 쿼리 파라미터에 넣는 방식은 피해야 한다.** URL은 브라우저 기록이나 서버 로그 등에 남기 쉽다.
    - **요청 헤더를 기록할 때도 Authorization 값을 가려야 한다.** 헤더에 넣었다고 로그 노출까지 자동으로 방지되는 것은 아니다.
    
    브라우저에서는 CORS 설정도 함께 고려해야 한다. 다른 출처의 서버에 Authorization 헤더를 포함해 요청하면 사전 요청인 OPTIONS가 먼저 전송될 수 있다.
    
    **이 사전 요청에는 실제 Bearer 토큰이 없으므로, 이를 일반적인 인증 실패로 막으면 실제 API 요청까지 도달하지 못한다.** 서버는 허용할 출처·메서드·헤더를 설정하고 사전 요청을 적절히 처리해야 한다.
    
    다만 **CORS는 인증이나 인가를 대신하지 않는다.** Postman이나 다른 서버 프로그램은 브라우저와 같은 CORS 제한을 받지 않으므로, 실제 API의 토큰 검증과 권한 검사는 별도로 필요하다.
    
- HandlerInterceptor / Guard
    
    **HandlerInterceptor와 Guard는 컨트롤러가 실행되기 전에 공통 조건을 확인하는 데 사용할 수 있는 구성 요소이다.** 워크북에서는 토큰 검사 코드를 여러 컨트롤러에 반복하지 않도록 공통 인증 처리를 담당한다.
    
    Spring의 HandlerInterceptor는 preHandle에서 요청을 검사하고, 통과한 요청을 컨트롤러로 전달한다. NestJS의 Guard도 요청을 계속 처리해도 되는지 판단하는 역할을 한다.
    
    이번 구현의 책임은 다음처럼 나눌 수 있다.
    
    | 위치 | 담당하는 역할 |
    | --- | --- |
    | 인터셉터 또는 Guard | 토큰을 검증하고 요청자의 회원 번호를 확인한다. |
    | 컨트롤러 | 인증된 회원 번호와 요청 데이터를 받아 서비스에 전달한다. |
    | 서비스 | 데이터 소유권과 업무 규칙을 확인하고 실제 작업을 수행한다. |
    
    **토큰 검증과 평점 소유권 검사를 한곳에 전부 넣을 필요는 없다.** 토큰 검증은 여러 API에서 공통으로 수행하지만, 평점의 작성자 확인은 해당 데이터를 조회해야 판단할 수 있는 업무 규칙이기 때문이다.
    
    Spring 예제에서는 검증한 회원 번호를 요청 객체의 속성에 저장한다.
    
    ```
    request.setAttribute("memberId", memberId);
    ```
    
    이 값은 해당 요청을 처리하는 동안 서버 내부에서 전달하는 값이다. **클라이언트가 보낸 쿼리 파라미터나 JSON의 memberId와는 별개이다.** 컨트롤러에서는 서버가 검증해 넣은 값을 받아야 한다.
    
    특히 **현재 로그인한 회원 번호를 인터셉터의 인스턴스 필드에 저장하면 안 된다.** 일반적인 Spring 싱글턴 빈은 여러 요청에서 공유되므로, 동시에 들어온 다른 사용자의 값이 섞일 수 있다.
    
    예를 들어 A의 요청 처리 중 인스턴스 필드에 A의 번호를 저장했는데, B의 요청이 같은 필드를 덮어쓰면 A의 작업이 B의 번호로 처리될 위험이 있다. 인증 결과는 요청 단위로 관리해야 한다.
    
    적용 범위도 점검해야 한다.
    
    - 클래스만 작성하는 것으로 끝나지 않고 실제 요청 처리 과정에 등록되어 있어야 한다.
    - 로그인과 회원가입처럼 인증 없이 사용할 API는 공개 범위로 구분해야 한다.
    - 경로를 제외하면 같은 경로의 다른 HTTP 메서드까지 함께 제외되는지 확인해야 한다.
    - 예외를 잡고 무조건 요청을 통과시키면 안 된다. **검증에 실패한 요청은 데이터 처리 단계에 도달하지 않아야 한다.**
    
    예를 들어 회원가입 때문에 POST /members를 공개하더라도, 나중에 추가한 GET /members까지 공개해도 되는지는 별도로 판단해야 한다. **접근 정책은 경로뿐 아니라 HTTP 메서드까지 함께 고려해야 한다.**
    
- 401 Unauthorized와 403 Forbidden의 차이
    
    워크북의 인증 API에서는 **401은 유효한 인증 정보를 제시하지 못한 상황이고, 403은 인증된 사용자가 해당 작업을 수행할 권한이 없는 상황이다.**
    
    | 상황 | 상태 코드 | 의미 |
    | --- | --- | --- |
    | 이메일 또는 비밀번호가 틀린 경우 | 401 | 로그인에 필요한 신원 확인에 실패한 것이다. |
    | 토큰이 없는 경우 | 401 | 보호된 요청의 사용자를 확인할 수 없는 것이다. |
    | 토큰이 변조되었거나 만료된 경우 | 401 | 전달받은 인증 정보를 사용할 수 없는 것이다. |
    | 다른 회원의 평점을 수정하는 경우 | 403 | 요청자는 확인했지만 해당 평점을 수정할 권한이 없는 것이다. |
    | 수정하려는 평점 자체가 없는 경우 | 404 | 작업 대상이 존재하지 않는 것이다. |
    
    401과 403은 해결 방법도 다르다. 만료된 토큰으로 발생한 401은 새 인증 정보를 얻으면 해결될 수 있지만, 다른 회원의 평점을 수정하려다 발생한 403은 **같은 계정으로 다시 로그인해도 해결되지 않는다.**
    
    백엔드에서는 **HTTP 상태 코드와 응답 바디의 오류 코드를 함께 설계하는 것**이 중요하다. 같은 401이라도 토큰 누락과 만료는 클라이언트가 취해야 할 동작이 다를 수 있기 때문이다.
    
    예를 들어 다음처럼 구분할 수 있다.
    
    | HTTP 상태 코드 | 서비스 오류 코드 | 구체적인 원인 |
    | --- | --- | --- |
    | 401 | AUTH401_2 | 인증 토큰이 없다. |
    | 401 | AUTH401_3 | 토큰 형식이나 서명이 유효하지 않다. |
    | 401 | AUTH401_4 | 토큰이 만료되었다. |
    | 403 | RATING403_1 | 평점의 작성자가 아니다. |
    
    **응답 바디에 실패라고 적는 것만으로 충분하지 않다.** HTTP 상태를 200으로 보내면서 바디에만 오류를 표시하면 클라이언트나 모니터링 도구가 정상 응답으로 처리할 수 있다. 실제 HTTP 상태와 응답 내용이 일치해야 한다.
    
    또한 토큰 오류를 처리한다는 이유로 모든 예외를 401로 바꾸면 안 된다. DB 연결 실패나 서버 코드의 결함까지 인증 실패로 처리하면 원인을 숨기게 된다. **예상한 인증 예외와 서버 내부 오류를 구분해야 한다.**
    
    권한 검사는 실패 응답뿐 아니라 실제 데이터 상태까지 확인해야 한다. 다른 회원의 토큰으로 평점 수정을 요청했을 때 다음 두 조건이 모두 충족되어야 한다.
    
    - 403 응답이 반환되어야 한다.
    - DB의 평점과 내용이 변경되지 않아야 한다.
    
    따라서 인증·인가 테스트에서는 정상 요청의 성공 여부뿐 아니라, **허용되지 않은 요청이 차단되고 데이터도 그대로 유지되는지** 확인하는 것이 중요하다.
