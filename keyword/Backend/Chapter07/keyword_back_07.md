- 인증(Authentication)과 인가(Authorization)
    
    #### 인증 (Authentication, AuthN)
    
    - 요청을 보낸 사용자가 누구인지 확인하는 과정
    - 사용자가 주장하는 신원이 맞는지 증거(비밀번호, 토큰, 세션 등)로 확인
    - 예: 로그인 시 이메일·비밀번호 확인, 요청에 담긴 토큰이 유효한지 확인
    
    #### 인가 (Authorization, AuthZ)
    
    - 인증된 사용자가 요청한 리소스·동작에 대한 권한이 있는지 확인하는 과정
    - 예: 관리자 API 호출 가능 여부, 게시글 수정·삭제 가능 여부
    
    #### 세션 기반 인증 (Session-based Authentication)
    
    - 로그인 성공 시 서버가 세션(로그인 상태 정보)을 서버 메모리·DB·Redis 등에 저장하고, 클라이언트에는 세션 ID만 쿠키로 전달
    - 이후 요청에서 세션 ID로 서버 저장소를 조회해 사용자를 확인 → 서버가 상태를 가짐 (Stateful)
    
    #### 토큰 기반 인증 (Token-based Authentication)
    
    - 로그인 성공 시 서버가 사용자 정보가 담긴 서명된 토큰(JWT 등) 을 발급
    - 이후 요청에서 서버는 저장소 조회 없이 토큰의 서명만 검증해서 사용자를 확인 → 서버가 상태를 갖지 않음 (Stateless)
    
    ### 인증과 인가의 차이
    
    | 구분 | 인증 (Authentication) | 인가 (Authorization) |
    | --- | --- | --- |
    | 확인하는 것 | **신원** (누구인가) | **권한** (무엇을 할 수 있는가) |
    | 순서 | 먼저 | 인증 이후 |
    | 서버에서 하는 일 | 비밀번호 비교, 토큰 서명 검증, 세션 조회 | 역할 확인, 리소스 소유자 확인 |
    | 실패 시 응답 | **401 Unauthorized** | **403 Forbidden** |
    | NestJS에서 주로 처리하는 곳 | 인증 Guard (`JwtAuthGuard`) | 인가 Guard (`RolesGuard`), 서비스 로직 |
    
    ### 세션 방식과 토큰 방식 비교
    
    | 구분 | 세션 기반 | 토큰 기반 (JWT) |
    | --- | --- | --- |
    | 상태 저장 위치 | 서버 (세션 저장소) | 토큰 자체 |
    | 클라이언트가 보내는 것 | 세션 ID (쿠키) | 토큰 (`Authorization` 헤더 또는 쿠키) |
    | 서버 확장 | 서버가 여러 대면 세션 저장소 공유 필요 (Redis 등) | 서버끼리 비밀 키만 공유하면 됨 |
    | 강제 로그아웃 | 세션을 삭제하면 즉시 무효화 | 토큰이 만료될 때까지 유효 → 짧은 만료 시간 + Refresh Token 사용 |
    | 요청마다 저장소 조회 | 필요 | 불필요 (서명 검증만) |
    
    ### 서버의 인증·인가 흐름
    
    ```
    요청 + 토큰
       │
       ▼  ① 인증 (JwtAuthGuard)
       │     - 토큰이 있는가? 서명이 맞는가? 만료되지 않았는가?
       │     - 실패 → 401 Unauthorized
       │     - 성공 → request.user에 사용자 정보 저장
       │
       ▼  ② 인가 (RolesGuard)
       │     - 이 API에 필요한 역할을 가지고 있는가?
       │     - 실패 → 403 Forbidden
       │
       ▼  ③ 인가 (서비스 로직)
       │     - 이 리소스의 소유자인가? 같은 팀 멤버인가?
       │     - 실패 → 403 Forbidden
       │
       ▼  ④ 비즈니스 로직 실행
    ```
    
    ### 인가의 종류
    
    | 방식 | 의미 | 처리 위치 (NestJS) |
    | --- | --- | --- |
    | **역할 기반 (RBAC)** | 사용자의 역할(`USER`, `ADMIN`)로 판단 | Guard + 커스텀 데코레이터 (`@Roles`) |
    | **소유자 기반** | 리소스의 작성자·소유자인지 판단 | 서비스 로직 (DB에서 리소스 조회 후 비교) |
    | **속성 기반 (ABAC)** | 사용자·리소스·상황의 여러 속성을 조합해 판단 | 서비스 로직 또는 정책(Policy) 클래스 |
    - 역할 검사는 요청 정보만으로 판단할 수 있어서 **Guard**에서 처리하기 좋음
    - 소유자 검사는 **리소스를 DB에서 조회해야** 알 수 있어서 보통 **서비스 로직**에서 처리
- 해시와 salt, bcrypt
    
    ### 용어 정의
    
    #### 해시 함수 (Hash Function)
    
    - 임의 길이의 입력을 받아 고정된 길이의 값(해시 값, 다이제스트) 으로 변환하는 함수
    
    | 성질 | 의미 |
    | --- | --- |
    | 결정성 | 같은 입력이면 **항상 같은 결과** |
    | 단방향성 | 해시 값으로 **원래 입력을 되돌릴 수 없음** |
    | 고정 길이 | 입력 길이와 상관없이 결과 길이가 같음 |
    | 눈사태 효과 | 입력이 조금만 바뀌어도 **결과가 완전히 달라짐** |
    | 충돌 저항성 | 서로 다른 입력이 같은 결과를 내는 경우를 찾기 매우 어려움 |
    
    #### 해시와 암호화의 차이
    
    | 구분 | 해시 | 암호화 |
    | --- | --- | --- |
    | 방향 | **단방향** (복원 불가) | **양방향** (키로 복호화 가능) |
    | 키 | 필요 없음 | 필요 |
    | 용도 | 비밀번호 저장, 데이터 무결성 확인 | 나중에 원문이 필요한 데이터 보호 |
    - 비밀번호는 서버도 원문을 알 필요가 없으므로 해시로 저장하고, 로그인 시 입력값을 해시해서 저장된 값과 비교
    
    #### 솔트 (Salt)
    
    - 해시하기 전에 비밀번호에 덧붙이는 사용자마다 다른 무작위 값
    - 같은 비밀번호라도 해시 결과가 사용자마다 달라짐
    
    #### 레인보우 테이블 (Rainbow Table)
    
    - 자주 쓰이는 비밀번호와 그 해시 값을 미리 계산해 둔 표
    - 솔트가 없으면 DB의 해시 값을 표에서 찾아 원래 비밀번호를 바로 알아낼 수 있음
    
    #### 페퍼 (Pepper)
    
    - 모든 비밀번호에 공통으로 붙이는 비밀 값으로, DB가 아닌 서버 환경 변수 등 별도 위치에 보관
    - DB만 유출된 경우 공격을 더 어렵게 만드는 추가 방어 (선택 사항)
    
    #### bcrypt
    
    - 비밀번호 저장용으로 설계된 느린 해시 함수
    - 솔트를 자동 생성해 결과 문자열 안에 함께 저장하고, cost(salt round) 로 계산 강도를 조절
    
    #### salt round (cost factor)
    
    - bcrypt 내부 연산의 반복 강도. 반복 횟수는 2^cost
    - cost가 1 오르면 계산 시간이 약 2배
    
    ### 솔트가 필요한 이유
    
    ```
    [솔트 없음]
    userA: password123 → ef92b778...
    userB: password123 → ef92b778...   ← 같은 해시 → 같은 비밀번호인 것이 드러남, 레인보우 테이블로 역추적 가능
    
    [솔트 있음]
    userA: password123 + a8Fk... → 3c1d9e...
    userB: password123 + Qz2p... → 9b7f02...   ← 같은 비밀번호여도 해시가 다름
    ```
    
    - 솔트는 비밀일 필요는 없음 → 사용자마다 **달라서 미리 계산한 표를 쓸 수 없게 만드는 것**이 목적
    
    ### 일반 해시 대신 bcrypt를 쓰는 이유
    
    | 구분 | SHA-256 등 일반 해시 | bcrypt |
    | --- | --- | --- |
    | 설계 목적 | 빠른 계산 (파일 무결성 확인 등) | **느린 계산** (비밀번호 저장) |
    | 공격자 입장 | GPU로 초당 수십억 번 대입 가능 | 한 번에 수십~수백 ms → 대입 공격 비용이 매우 큼 |
    | 솔트 | 직접 생성·저장해야 함 | **자동 생성, 결과에 포함** |
    | 강도 조절 | 불가 | cost 값으로 조절 |
    
    ### bcrypt 해시 구조
    
    ```
    $2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
     │   │  └───────────┬──────────┘└──────────────┬──────────────┘
     │   │       솔트 (22자)                  해시 값 (31자)
     │   └ cost = 10
     └ 알고리즘 버전
    ```
    
    - 총 **60자** → DB 컬럼은 `VARCHAR(60)` 이상
    - 비교할 때 이 문자열에서 **버전·cost·솔트를 꺼내 같은 조건으로 다시 계산**하므로, 솔트 컬럼을 따로 둘 필요 없음
    
    ### cost 값 정하기
    
    | cost | 반복 횟수 | 계산 시간 (대략) |
    | --- | --- | --- |
    | 10 | 1,024 | 수십 ms ~ 100ms 내외 |
    | 12 | 4,096 | 수백 ms |
    | 14 | 16,384 | 1초 이상 |
    - 보통 **10~12** 사용 (OWASP 권장 최솟값 10)
    - 너무 높으면 로그인·회원가입 요청마다 CPU 사용량이 커져 서버가 느려짐
- JWT (Header / Payload / Signature, Claim)
    
    ### 용어 정의
    
    #### JWT (JSON Web Token)
    
    - 사용자 식별 정보와 권한 같은 데이터를 JSON으로 담고 서명한 토큰
    - 서버는 세션 저장소 없이 토큰의 서명만 검증해서 사용자를 확인할 수 있음 (Stateless)
    - 구조: `Header.Payload.Signature` (각 부분은 Base64URL 인코딩)
    
    ```
    eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjQyLCJyb2xlIjoiVVNFUiJ9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
    └────────────── Header ─────────────┘└────────────── Payload ──────────┘└────────────── Signature ─────────────┘
    ```
    
    #### Base64URL 인코딩
    
    - 데이터를 URL·헤더에 안전한 문자로 바꾸는 인코딩 (암호화 아님)
    - Header와 Payload는 누구나 디코딩해서 읽을 수 있음
    
    #### 클레임 (Claim)
    
    - Payload에 담긴 정보 하나하나(키-값 쌍)
    - 예: `"sub": 42`, `"role": "USER"`, `"exp": 1794000000`
    
    #### Access Token과 Refresh Token
    
    - Access Token: API 요청 시 사용하는 토큰. 유출 피해를 줄이기 위해 만료 시간을 짧게 (예: 15분~1시간)
    - Refresh Token: Access Token이 만료됐을 때 새 Access Token을 발급받는 용도의 토큰. 만료 시간이 길고 (예: 2주), 서버 DB 등에 저장해 무효화·관리함
    
    ### Header
    
    - 토큰의 타입과 서명 알고리즘 정보
    
    json
    
    ```json
    { "alg": "HS256", "typ": "JWT" }
    ```
    
    | 필드 | 의미 |
    | --- | --- |
    | `alg` | 서명 알고리즘 |
    | `typ` | 토큰 타입 |
    | `kid` | (선택) 서명에 사용한 키 ID → 키를 여러 개 쓰거나 교체할 때 |
    
    | 알고리즘 | 방식 | 특징 |
    | --- | --- | --- |
    | `HS256` | HMAC-SHA256, **비밀 키 하나**로 서명·검증 | 간단함. 검증하는 서버도 같은 비밀 키 필요 |
    | `RS256` | RSA, **개인 키로 서명, 공개 키로 검증** | 여러 서비스가 검증할 때 공개 키만 배포하면 됨 |
    
    ### Payload
    
    - 전달할 데이터(클레임) 를 담는 부분
    
    json
    
    ```json
    { "sub": 42, "role": "USER", "iat": 1793990000, "exp": 1794000000 }
    ```
    
    #### 클레임 종류
    
    | 종류 | 의미 | 예시 |
    | --- | --- | --- |
    | **등록된 클레임 (Registered)** | 표준으로 이름·의미가 정해진 클레임 | `iss`, `sub`, `exp` |
    | **공개 클레임 (Public)** | 충돌하지 않도록 공개적으로 정의해 쓰는 클레임 | `email`, `name` |
    | **비공개 클레임 (Private)** | 발급자와 사용자끼리 약속한 커스텀 클레임 | `role`, `teamId` |
    
    #### 주요 등록된 클레임
    
    | 클레임 | 의미 |
    | --- | --- |
    | `iss` (Issuer) | 토큰 발급자 |
    | `sub` (Subject) | 토큰의 주체 (보통 **사용자 id**) |
    | `aud` (Audience) | 토큰을 사용할 대상 서비스 |
    | `exp` (Expiration Time) | **만료 시각** (초 단위 Unix 시간) |
    | `nbf` (Not Before) | 이 시각 이전에는 사용 불가 |
    | `iat` (Issued At) | 발급 시각 |
    | `jti` (JWT ID) | 토큰 고유 id (재사용 방지·블랙리스트 관리) |
    - Payload는 누구나 읽을 수 있으므로 비밀번호·개인정보 같은 민감 정보는 넣지 않음
    
    ### Signature
    
    - Header와 Payload가 변조되지 않았고(무결성), 비밀 키를 가진 서버가 발급했음(발급자 확인) 을 증명
    
    ```
    signature = HMACSHA256(
      base64UrlEncode(header) + "." + base64UrlEncode(payload),
      JWT_SECRET
    )
    ```
    
    - Payload를 바꾸면 서명이 맞지 않게 되고, 비밀 키 없이는 올바른 서명을 만들 수 없음
    - 서명은 내용을 숨기지 않음 (기밀성 X, 무결성 O)
    
    ### 디코딩과 검증
    
    | 구분 | 디코딩 (`decode`) | 검증 (`verify`) |
    | --- | --- | --- |
    | 하는 일 | Header·Payload 읽기 | 서명 + `exp` 등 클레임 확인 |
    | 키 필요 | ❌ | ⭕ |
    | 위조된 토큰 | 그대로 읽힘 | **실패** |
    | 서버 인증에 사용 | ❌ | ⭕ |
    
    ### 토큰 검증 흐름
    
    ```
    토큰 수신
       ├─ ① 형식 확인 (세 부분인가)
       ├─ ② 서명 검증 (비밀 키로 다시 계산한 서명과 일치하는가)     → 실패 시 401
       ├─ ③ 클레임 검증 (exp 만료, iss·aud 일치)                   → 실패 시 401
       └─ ④ payload의 sub, role로 사용자 식별 → 인가 진행
    ```
    
    ### JWT의 장단점
    
    | 장점 | 단점 |
    | --- | --- |
    | 서버에 세션 저장소가 필요 없음 (Stateless) | 발급 후 만료 전까지 강제로 무효화하기 어려움 |
    | 서버를 여러 대로 늘리기 쉬움 | Payload가 공개되어 민감 정보를 담을 수 없음 |
    | 다른 서비스와 인증 정보 공유가 쉬움 | 토큰이 세션 ID보다 커서 요청마다 전송량 증가 |
    - 무효화 문제는 짧은 Access Token 만료 시간 + Refresh Token(DB 저장·폐기 가능) 조합으로 보완
    - 로그아웃·비밀번호 변경 시 Refresh Token을 DB에서 삭제해 재발급을 막음
- Bearer 인증과 Authorization 헤더
    
    ### 용어 정의
    
    #### Authorization 헤더
    
    - 클라이언트가 서버에 자신을 인증하기 위한 정보(자격 증명, credentials) 를 담아 보내는 HTTP 요청 헤더
    - 형식: **`Authorization: <인증 방식(scheme)> <자격 증명>`**
    
    ```
    Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
                   └ scheme ┘└──────────── credentials ─────────────┘
    ```
    
    - 이름은 Authorization(인가)이지만 실제로는 **인증 정보**를 담는 헤더
    
    #### 인증 스킴 (Authentication Scheme)
    
    - 자격 증명을 어떤 방식으로 표현했는지 알려주는 이름
    
    | 스킴 | 자격 증명 | 특징 |
    | --- | --- | --- |
    | `Basic` | `아이디:비밀번호`를 Base64 인코딩 | 매 요청마다 비밀번호 전송, 인코딩일 뿐이라 HTTPS 필수. 내부 도구 등에 제한적으로 사용 |
    | `Bearer` | 토큰 (JWT, OAuth Access Token 등) | 현재 API 인증에서 가장 많이 사용 |
    | `Digest` | 비밀번호의 해시 값 | 최근에는 거의 사용하지 않음 |
    
    #### Bearer 토큰
    
    - Bearer는 "소지자, 지닌 사람" 이라는 뜻
    - 토큰을 가지고 있는 사람에게 권한을 주는 방식 → 토큰만 있으면 누구든 해당 사용자로 인정됨
    - OAuth 2.0의 Bearer 토큰 사용 방법은 RFC 6750에 정의되어 있음
    
    #### WWW-Authenticate 헤더
    
    - 서버가 401 응답을 보낼 때, 어떤 인증 방식이 필요한지 알려주는 응답 헤더
    
    ```
    HTTP/1.1 401 Unauthorized
    WWW-Authenticate: Bearer error="invalid_token", error_description="The access token expired"
    ```
    
    ### Bearer 인증 흐름
    
    ```
    ① 로그인
       POST /auth/login  { email, password }
       ← 200 OK  { "accessToken": "eyJ..." }
    
    ② 인증이 필요한 API 요청
       GET /users/me
       Authorization: Bearer eyJ...
    
    ③ 서버
       - Authorization 헤더 읽기
       - "Bearer " 스킴 확인 후 토큰 추출
       - 토큰 서명·만료 검증
         ├ 성공 → 요청 처리 (200)
         └ 실패 → 401 Unauthorized
    ```
    
    ### Bearer 토큰을 다룰 때 지켜야 할 점
    
    | 항목 | 이유 |
    | --- | --- |
    | **HTTPS 필수** | 토큰만 있으면 사용자로 인정되므로, 평문 HTTP에서 가로채이면 그대로 악용됨 |
    | **URL 쿼리 스트링에 넣지 않기** | `?token=...`은 서버 로그, 브라우저 기록, Referer 헤더에 남음 |
    | **로그에 남기지 않기** | 요청 헤더를 그대로 로깅하면 토큰이 유출될 수 있음 → `Authorization` 헤더는 마스킹 |
    | **짧은 만료 시간** | 유출되어도 피해 기간을 줄임 |
    | **CORS 설정** | 다른 Origin에서 `Authorization` 헤더를 보내면 Preflight 요청이 발생 → `allowedHeaders`에 `Authorization` 포함 |
    
    ### Authorization 헤더 방식과 쿠키 방식
    
    | 구분 | Authorization 헤더 (Bearer) | 쿠키 |
    | --- | --- | --- |
    | 전송 | 클라이언트가 **직접 헤더에 추가** | 브라우저가 **자동으로 전송** |
    | CSRF | 자동 전송이 아니라서 **CSRF에 비교적 안전** | 자동 전송되므로 **SameSite, CSRF 토큰** 등 방어 필요 |
    | 서버 처리 | 헤더에서 토큰 추출 | 쿠키 파싱 (`cookie-parser`) 후 추출 |
    | 모바일 앱·다른 서버 | 사용하기 쉬움 | 쿠키 관리가 번거로움 |
- HandlerInterceptor / Guard
    
    ### 용어 정의
    
    #### 횡단 관심사 (Cross-Cutting Concern)
    
    - 인증, 인가, 로깅, 실행 시간 측정처럼 여러 API에 공통으로 필요한 기능
    - 각 컨트롤러마다 반복해서 작성하지 않고, 요청이 컨트롤러에 도착하기 전후의 공통 단계에서 한 번에 처리
    
    #### Guard (NestJS)
    
    - 요청을 라우트 핸들러(컨트롤러 메서드)에 보낼지 말지 결정하는 클래스
    - `CanActivate` 인터페이스의 `canActivate()`를 구현하고, `true`면 통과, `false`면 차단
    - 인증·인가처럼 "이 요청을 처리해도 되는가" 를 판단하는 역할에 특화됨
    
    #### ExecutionContext (NestJS)
    
    - Guard 등에서 **현재 실행 중인 요청의 정보**에 접근할 수 있게 해주는 객체
    - 요청 객체(`switchToHttp().getRequest()`), 실행될 핸들러(`getHandler()`), 컨트롤러 클래스(`getClass()`)를 꺼낼 수 있음
    
    #### Reflector와 메타데이터 (NestJS)
    
    - **메타데이터**: 데코레이터로 핸들러·클래스에 붙여두는 추가 정보 (예: 이 API는 `ADMIN`만 가능)
    - **Reflector**: Guard 안에서 그 메타데이터를 **읽어오는 도구**
    
    ### 요청 처리 순서
    
    #### NestJS
    
    ```
    요청 → Middleware → Guard → Interceptor (전) → Pipe → Controller
         → Interceptor (후) → 응답
                             (중간에 예외 발생 시 → Exception Filter)
    ```
    
    - NestJS에서 Guard는 Pipe(ValidationPipe)보다 먼저 실행됨 → 인증되지 않은 요청은 body 검증 전에 차단
    
    #### Guard 적용 범위
    
    | 범위 | 방법 |
    | --- | --- |
    | 메서드 | `@UseGuards(RolesGuard)` |
    | 컨트롤러 | 클래스에 `@UseGuards(JwtAuthGuard)` |
    | 전역 | 모듈 providers에 `{ provide: APP_GUARD, useClass: JwtAuthGuard }` |
- 401 Unauthorized와 403 Forbidden의 차이
    
    ### 용어 정의
    
    #### 401 Unauthorized
    
    - 요청에 **유효한 인증 정보가 없어서** 처리할 수 없음
    - 의미상 **"인증되지 않음(Unauthenticated)"** → 이름은 Unauthorized지만 실제로는 **인증 실패**
    - 클라이언트는 **로그인하거나 유효한 토큰을 다시 보내면** 성공할 수 있음
    - 서버는 401 응답에 어떤 인증 방식이 필요한지 **`WWW-Authenticate` 헤더**로 알려줘야 함
    
    ```
    HTTP/1.1 401 Unauthorized
    WWW-Authenticate: Bearer error="invalid_token"
    ```
    
    #### 403 Forbidden
    
    - 서버가 요청한 사용자를 **알고 있지만(또는 인증과 무관하게)**, 그 요청을 **수행할 권한이 없어서 거부**함
    - 의미상 **"인가 실패"**
    - **같은 사용자로 다시 로그인해도 결과가 바뀌지 않음** → 권한이 바뀌어야 성공 가능
    
    ### 차이 비교
    
    | 구분 | 401 Unauthorized | 403 Forbidden |
    | --- | --- | --- |
    | 실패한 단계 | **인증** | **인가** |
    | 서버의 판단 | "너가 누군지 모르겠다" | "누군지는 알지만, 이건 안 된다" |
    | 해결 방법 | 로그인, 토큰 재발급 후 재요청 | 권한 부여 (역할 변경, 초대 등) |
    | 재시도 의미 | 인증 정보를 바꾸면 성공 가능 | 같은 사용자로 재시도해도 실패 |
    | 관련 헤더 | `WWW-Authenticate` | 없음 |
    | NestJS 예외 | `UnauthorizedException` | `ForbiddenException` |
    
    ### 상황별 상태 코드
    
    | 상황 | 상태 코드 |
    | --- | --- |
    | `Authorization` 헤더 없이 보호된 API 요청 | **401** |
    | 토큰 서명이 맞지 않음 (위조·변조) | **401** |
    | 토큰이 만료됨 | **401** |
    | 로그인 시 이메일·비밀번호 불일치 | **401** |
    | 일반 사용자가 관리자 API 요청 | **403** |
    | 다른 사람의 게시글 수정·삭제 시도 | **403** |
    | 초대받지 않은 프로젝트에 접근 | **403** |
    | 이용 정지된 계정으로 쓰기 기능 요청 | **403** |
    
    ### 403 대신 404를 사용하는 경우
    
    - 403은 **"그 리소스가 존재한다"** 는 사실을 알려줌
    - 비공개 리소스의 존재 자체를 숨기고 싶을 때는 **404 Not Found**로 응답하기도 함
        - 예: 다른 사람의 비공개 저장소, 다른 회사의 내부 문서 URL로 접근한 경우
