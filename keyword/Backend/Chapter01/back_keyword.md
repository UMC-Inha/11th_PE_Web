- PK, FK란?
    
    ### 1. PK(Primary Key, 기본키)
    
    - 역할: 테이블 안에서 특정 행을 고유하게 식별하는 값
    - 특징:
        - NULL 허용 X
        - 중복된 값을 가질 수 없음
    
    ### 2. FK(Foreign Key, 외래키)
    
    - 역할: 다른 테이블의 PK를 연결고리로 삼아 두 테이블의 관계를 정의하는 값
    - 특징:
        - 테이블 사이를 연결하고 데이터 무결성을 지킴
        - 참조하는 쪽이 자식, 참조되는 쪽이 부모 테이블
        - 설정에 따라 중복 값이나 NULL 허용 가능
    
    #### + key의 핵심 속성
    
    - 유일성(Uniqueness): 하나의 테이블 내에서 서로 다른 두 행을 반드시 구별할 수 있는 특성
    - 최소성(Minimality): 꼭 필요한 최소한의 칼럼들로만 키를 구성하는 특성
    - 슈퍼키(Super Key): 유일성 ⭕ / 최소성 ❌ (행을 구별할 수만 있으면 속성이 아무리 많아도 괜찮음)
    - 후보키(Candidate Key): 유일성 ⭕/ 최소성 ⭕(PK가 될 자격이 있는 후보들)
    - 기본키(Primary Key): 유일성 ⭕/ 최소성 ⭕
- ERD란?
    
    ### 1. ERD(Entity-Relationship Diagram)
    
    DB 구조를 시각적으로 그려낸 데이터 베이스 설계도
    
    ### 2. ERD의 3대 핵심 구성 요소
    
    - 개체 (Entity): 데이터로 관리해야 하는 실제 세상의 객체 (ex. 회원, 상품, …)
        - 다이어그램에서는 보통 네모 상자로 표현함
    - 속성 (Attribute): 개체가 가지고 있는 고유한 정보나 항목 (ex. 회원의 ‘이름’, ‘아이디’,…)
        - 다이어그램에서는 상자 안의 텍스트나 원형으로 표현하며, PK와 FK가 여기에 표시
    - 관계 (Relationship): 개체와 개체가 서로 어떤 연관성을 가지고 있는지 나타냄 (ex. 회원이 주문을 ‘한다’)
        - 다이어그램에서는 선이나 마름모로 표현
    
    ### 3. ERD에서 관계를 표현하는 방법
    
    - 1:1 관계: 선 끝이 직선으로 끝나며, 양쪽 데이터가 딱 하나씩만 매칭 (ex. 회원 - 회원상세정보)
    - 1:N 관계: 한쪽 선 끝이 까마귀 발 모양으로 갈라짐 (ex. 부서 - 사원 여러명)
    - N:M 관계: 양쪽 선 끝이 모두 갈라짐. 실제 데이터베이스를 만들 때는 중간 테이블을 두어 1:N 관계로 풀어내야함 (ex. 학생 여러 명 - 과목 여러 개)
- 연관관계란? 그리고 연관관계를 설정하는 방법은?
    
    ### 1. 연관 관계의 정의(Relationship)
    
    DB에서 연관 관계란 한 테이블의 데이터가 다른 테이블의 데이터와 연결되는 구조를 의미한다. 서로 관련된 데이터를 여러 테이블로 분리해 저장한 뒤, 기본 키(PK)와 외래 키(FK)를 통해 테이블 간 관계를 표현한다.
    
    ### 2. 연관 관계의 종류
    
    - **일대일(1:1)**: 한 테이블의 행 하나가 다른 테이블의 행 하나와 연결되는 관계
        
        예: 회원과 회원 상세 정보
        
    - **일대다(1:N)**: 한 테이블의 행 하나가 다른 테이블의 여러 행과 연결되는 관계
        
        예: 회원 한 명과 여러 주문
        
    - **다대다(N:M)**: 양쪽 테이블의 여러 행이 서로 연결되는 관계
        
        예: 여러 학생과 여러 과목
        
    
    ### 3. 연관 관계 설정 방법
    
    연관 관계는 일반적으로 외래 키를 사용하여 설정한다. 외래 키는 다른 테이블의 기본 키 또는 고유 키를 참조하는 열이다.
    
    #### 1:1 관계
    
    한쪽 테이블에 외래 키를 두고 `UNIQUE` 제약 조건을 설정한다.
    
    ```sql
    CREATE TABLE member_detail (
        detail_id BIGINT PRIMARY KEY,
        member_id BIGINT UNIQUE NOT NULL,
        FOREIGN KEY (member_id) REFERENCES member(member_id)
    );
    ```
    
    #### 1:N 관계
    
    여러 데이터를 가지는 N쪽 테이블에 1쪽 테이블의 기본 키를 외래 키로 저장한다.
    
    ```sql
    CREATE TABLE orders (
        order_id BIGINT PRIMARY KEY,
        member_id BIGINT NOT NULL,
        FOREIGN KEY (member_id) REFERENCES member(member_id)
    );
    ```
    
    #### N:M 관계
    
    두 테이블의 기본 키를 외래 키로 가지는 중간 테이블을 생성한다. 이를 통해 N:M 관계를 두 개의 1:N 관계로 변환한다.
    
    ```sql
    CREATE TABLE enrollment (
        student_id BIGINT,
        course_id BIGINT,
        PRIMARY KEY (student_id, course_id),
        FOREIGN KEY (student_id) REFERENCES student(student_id),
        FOREIGN KEY (course_id) REFERENCES course(course_id)
    );
    ```
    
    ### 4. 연관 관계 설정의 목적
    
    - 데이터 간 연결 구조 표현
    - 잘못된 참조 데이터 저장 방지
    - 참조 무결성 유지
    - 데이터 중복 감소
    - 관련 데이터의 효율적인 조회 및 관리
- 정규화란?
    
    ### 1. 정규화(Normalization)
    
    정규화란 데이터의 중복을 최소화하고 데이터의 일관성과 무결성을 유지하기 위해 테이블을 구조적으로 분리하는 과정이다. 하나의 테이블에 여러 종류의 정보를 함께 저장할 때 발생할 수 있는 삽입·수정·삭제 이상을 방지하는 것이 목적이다.
    
    ### 2. 이상 현상의 종류
    
    - **삽입 이상**: 불필요한 데이터가 없으면 필요한 데이터를 추가할 수 없는 현상
    - **수정 이상**: 중복된 데이터 일부만 수정되어 데이터가 서로 달라지는 현상
    - **삭제 이상**: 특정 데이터를 삭제할 때 필요한 다른 정보까지 함께 삭제되는 현상
    
    ### 3. 주요 정규형
    
    #### 제1정규형(1NF)
    
    테이블의 모든 속성이 하나의 값만 가지도록 구성한다. 즉, 한 칸에 여러 값을 저장하지 않는다.
    
    ```
    정규화 전: 회원 | 전화번호
              지은 | 010-1111, 010-2222
    
    정규화 후: 회원 | 전화번호
              지은 | 010-1111
              지은 | 010-2222
    ```
    
    #### 제2정규형(2NF)
    
    제1정규형을 만족하고, 기본 키의 일부에만 종속되는 속성을 제거한다. (부분함수 종속 제거)
    
    주로 기본 키가 두 개 이상의 컬럼으로 구성된 복합 키일 때 적용된다.
    
    ```
    수강(학생ID, 과목ID, 학생이름, 성적)
    ```
    
    - `성적`은 학생ID와 과목ID 모두에 종속
    - `학생이름`은 학생ID에만 종속
    
    따라서 다음과 같이 분리한다.
    
    ```
    학생(학생ID, 학생이름)
    수강(학생ID, 과목ID, 성적)
    ```
    
    #### 제3정규형(3NF)
    
    제2정규형을 만족하고, 기본 키가 아닌 속성 간의 종속 관계를 제거한다. (이행함수 종속 제거)
    
    ```
    학생(학생ID, 학과ID, 학과명)
    ```
    
    - 학생ID → 학과ID
    - 학과ID → 학과명
    
    `학과명`이 학생ID가 아닌 학과ID에 종속되므로 다음과 같이 분리한다.
    
    ```
    학생(학생ID, 학과ID)
    학과(학과ID, 학과명)
    ```
    
    ### 4. 정규화의 장단점
    
    **장점**
    
    - 데이터 중복 감소
    - 데이터 일관성 및 무결성 향상
    - 삽입·수정·삭제 이상 방지
    - 데이터 구조 변경과 관리가 용이함
    
    **단점**
    
    - 테이블 수가 증가함
    - 데이터 조회 시 JOIN이 많아질 수 있음
    - 복잡한 조회의 성능이 저하될 수 있음
    
    조회 성능을 높이기 위해 의도적으로 테이블을 합치거나 중복 데이터를 허용하는 과정을 **반정규화(Denormalization)**라고 한다.
    
- 반 정규화란?
    
    ### 1. 반정규화(Denormalization)
    
    반정규화란 정규화된 데이터베이스의 조회 성능을 향상하기 위해 테이블을 합치거나 중복 데이터를 의도적으로 허용하는 과정이다. 조회 시 발생하는 JOIN과 복잡한 연산을 줄이는 것이 주요 목적이다.
    
    ### 2. 반정규화 방법
    
    - **테이블 병합**: 자주 JOIN되는 테이블을 하나로 합치는 방법
    - **테이블 분할**: 하나의 큰 테이블을 사용 목적에 따라 수평 또는 수직으로 분리하는 방법
    - **중복 컬럼 추가**: 자주 조회되는 다른 테이블의 값을 컬럼으로 중복 저장하는 방법
    - **파생 컬럼 추가**: 합계, 평균, 개수 등 계산 결과를 미리 저장하는 방법
    - **중복 테이블 생성**: 특정 조회에 필요한 데이터를 별도의 테이블로 구성하는 방법
    
    ### 3. 반정규화 예시
    
    주문을 조회할 때마다 상품 테이블과 JOIN하여 상품명을 가져오는 구조는 다음과 같다.
    
    ```
    주문(주문ID, 상품ID, 수량)
    상품(상품ID, 상품명, 가격)
    ```
    
    상품명을 주문 테이블에 중복 저장하면 JOIN 없이 주문 정보를 조회할 수 있다.
    
    ```
    주문(주문ID, 상품ID, 상품명, 수량)
    상품(상품ID, 상품명, 가격)
    ```
    
    ### 4. 반정규화의 장단점
    
    **장점**
    
    - JOIN 횟수 감소
    - 복잡한 조회 단순화
    - 읽기 및 통계 조회 성능 향상
    
    **단점**
    
    - 데이터 중복과 저장 공간 증가
    - 삽입·수정·삭제 작업이 복잡해짐
    - 중복된 값을 함께 수정하지 않으면 데이터 불일치 발생
    - 데이터 무결성 관리가 어려워짐
    
    ### 5. 적용 시 고려사항
    
    반정규화는 정규화를 하지 않는 것이 아니라, 정규화된 구조에서 실제 성능 문제가 확인됐을 때 제한적으로 적용하는 최적화 방법이다. 따라서 조회 빈도, JOIN 비용, 데이터 변경 빈도와 일관성 유지 방법을 함께 고려해야 한다.
    
- DB에서의 상속 관계 표현은 어떻게 하는가?
    
    ### 1. 상속 관계
    
    객체지향에서 상속 관계는 상위 타입의 공통 속성을 하위 타입이 물려받는 구조이다. 관계형 데이터베이스는 상속을 직접 지원하지 않으므로 테이블 구조와 외래 키를 사용하여 표현한다.
    
    예를 들어 `회원`을 상위 타입으로 두고 `일반 회원`과 `관리자`가 이를 상속한다고 가정한다.
    
    ### 2. 주요 표현 방법
    
    #### 단일 테이블 전략(Single Table)
    
    상위 타입과 모든 하위 타입의 속성을 하나의 테이블에 저장하고, 구분 컬럼으로 타입을 식별한다.
    
    ```
    회원(
        회원ID,
        이름,
        회원유형,
        배송주소,
        관리자등급
    )
    ```
    
    ```sql
    CREATE TABLE member (
        member_id BIGINT PRIMARY KEY,
        name VARCHAR(50) NOT NULL,
        member_type VARCHAR(20) NOT NULL,
        delivery_address VARCHAR(200),
        admin_level INT
    );
    ```
    
    - 장점: JOIN이 필요 없어 조회가 단순하고 빠름
    - 단점: 특정 타입에서 사용하지 않는 컬럼에 `NULL`이 많이 발생하며, 테이블이 커질 수 있음
    
    #### 조인 전략(Joined Table)
    
    상위 타입의 공통 속성은 상위 테이블에 저장하고, 하위 타입의 고유 속성은 별도의 하위 테이블에 저장한다. 하위 테이블의 기본 키는 상위 테이블을 참조하는 외래 키로도 사용한다.
    
    ```
    회원(회원ID, 이름)
    일반회원(회원ID, 배송주소)
    관리자(회원ID, 관리자등급)
    ```
    
    ```sql
    CREATE TABLE member (
        member_id BIGINT PRIMARY KEY,
        name VARCHAR(50) NOT NULL
    );
    
    CREATE TABLE normal_member (
        member_id BIGINT PRIMARY KEY,
        delivery_address VARCHAR(200),
        FOREIGN KEY (member_id) REFERENCES member(member_id)
    );
    
    CREATE TABLE administrator (
        member_id BIGINT PRIMARY KEY,
        admin_level INT,
        FOREIGN KEY (member_id) REFERENCES member(member_id)
    );
    ```
    
    - 장점: 데이터 중복과 `NULL`이 적고 정규화된 구조를 유지함
    - 단점: 전체 정보를 조회할 때 JOIN이 필요함
    
    #### 구현 클래스별 테이블 전략(Table per Concrete Class)
    
    상위 테이블을 만들지 않고 각 하위 테이블에 공통 속성과 고유 속성을 모두 저장한다.
    
    ```
    일반회원(회원ID, 이름, 배송주소)
    관리자(회원ID, 이름, 관리자등급)
    ```
    
    ```sql
    CREATE TABLE normal_member (
        member_id BIGINT PRIMARY KEY,
        name VARCHAR(50) NOT NULL,
        delivery_address VARCHAR(200)
    );
    
    CREATE TABLE administrator (
        member_id BIGINT PRIMARY KEY,
        name VARCHAR(50) NOT NULL,
        admin_level INT
    );
    ```
    
    - 장점: 특정 하위 타입을 조회할 때 JOIN이 필요 없음
    - 단점: 공통 속성이 중복되며 전체 타입 조회 시 `UNION`이 필요함
    
    ### 3. 전략 비교
    
    | 전략 | 테이블 구조 | 장점 | 단점 |
    | --- | --- | --- | --- |
    | 단일 테이블 | 하나의 통합 테이블 | 조회가 단순하고 빠름 | `NULL` 컬럼 증가 |
    | 조인 | 상위 테이블 + 하위 테이블 | 정규화 및 무결성 유지 | JOIN 증가 |
    | 구현 클래스별 테이블 | 하위 타입별 독립 테이블 | 하위 타입 조회가 단순함 | 공통 속성 중복 |
    
    관계형 데이터베이스에서 상속 관계는 일반적으로 위 세 가지 전략으로 표현하며, 데이터 중복과 조회 성능, 타입 확장 가능성을 고려하여 적절한 방법을 선택한다.
    
- 인덱스란?
    
    ### 1. 인덱스(Index)
    
    인덱스란 테이블의 데이터를 빠르게 조회하기 위해 특정 컬럼의 값과 해당 데이터의 위치를 별도로 저장하는 자료구조이다. 책의 목차나 색인처럼 전체 데이터를 처음부터 확인하지 않고 원하는 데이터의 위치를 빠르게 찾도록 돕는다.
    
    ### 2. 인덱스의 동작 방식
    
    인덱스가 없는 경우 DB는 조건에 맞는 데이터를 찾기 위해 테이블 전체를 확인하는 **Full Table Scan**을 수행할 수 있다.
    
    인덱스가 있는 경우에는 인덱스에서 조건에 맞는 값의 위치를 찾은 후 실제 테이블 데이터에 접근한다. 대부분의 관계형 DB에서는 인덱스 자료구조로 **B-Tree 계열**을 사용한다.
    
    ```sql
    CREATE INDEX idx_member_email
    ON member(email);
    ```
    
    위 인덱스는 다음 조회의 성능을 높일 수 있다.
    
    ```sql
    SELECT *
    FROM member
    WHERE email = 'user@example.com';
    ```
    
    ### 3. 인덱스의 종류
    
    - **기본 키 인덱스**: `PRIMARY KEY` 설정 시 일반적으로 자동 생성되는 인덱스
    - **고유 인덱스**: 중복 값을 허용하지 않는 인덱스
    - **단일 컬럼 인덱스**: 하나의 컬럼으로 구성된 인덱스
    - **복합 인덱스**: 두 개 이상의 컬럼으로 구성된 인덱스
    - **클러스터형 인덱스**: 인덱스 순서에 따라 실제 데이터가 저장되는 구조
    - **비클러스터형 인덱스**: 인덱스와 실제 데이터가 별도로 저장되는 구조
    
    ### 4. 복합 인덱스
    
    복합 인덱스에서는 컬럼의 순서가 중요하다.
    
    ```sql
    CREATE INDEX idx_orders_member_status
    ON orders(member_id, status);
    ```
    
    일반적으로 다음 조건에는 인덱스를 활용할 수 있다.
    
    ```sql
    WHERE member_id = 1
    WHERE member_id = 1 AND status = 'PAID'
    ```
    
    그러나 선두 컬럼인 `member_id` 없이 다음 조건만 사용하는 경우에는 인덱스를 효율적으로 활용하기 어렵다.
    
    ```sql
    WHERE status = 'PAID'
    ```
    
    이를 **복합 인덱스의 최좌측 접두사 원칙**이라고 한다.
    
    ### 5. 인덱스의 장단점
    
    **장점**
    
    - `SELECT` 조회 속도 향상
    - 정렬 및 그룹화 연산 성능 향상 가능
    - 검색 범위를 줄여 디스크 접근 감소
    - `JOIN` 조건이나 외래 키 조회 성능 향상 가능
    
    **단점**
    
    - 별도의 저장 공간 필요
    - 데이터 추가·수정·삭제 시 인덱스도 변경해야 하므로 쓰기 성능 저하
    - 인덱스가 많으면 관리 비용과 옵티마이저의 선택 부담 증가
    
    ### 6. 인덱스 설정 시 고려사항
    
    인덱스는 다음과 같은 컬럼에 설정하는 것이 효과적이다.
    
    - `WHERE` 조건에 자주 사용되는 컬럼
    - `JOIN` 조건으로 자주 사용되는 컬럼
    - `ORDER BY`, `GROUP BY`에 자주 사용되는 컬럼
    - 중복 값이 적어 데이터 구분도가 높은 컬럼
    
    데이터가 적은 테이블이나 값의 종류가 매우 적은 컬럼에는 인덱스의 효과가 작을 수 있다. 또한 인덱스를 생성해도 항상 사용되는 것은 아니며, DB 옵티마이저가 실행 비용을 비교해 사용 여부를 결정한다.
