- Swagger / OpenAPI
    
    OpenAPI는 API의 경로, 요청 형식, 응답 구조, 인증 방식 등을 표현하는 표준 명세다. Swagger는 이 명세를 작성하거나 활용하는 도구 모음이며, Swagger UI는 명세를 읽어 문서 화면과 API 호출 기능을 제공하는 도구다.
    
    **자동으로 생성되는 API 문서도 실제 동작과 일치하는지 확인해야 한다.** 컨트롤러의 경로나 DTO의 자료형처럼 코드에서 읽을 수 있는 정보는 자동으로 반영되지만, 개발자가 직접 작성한 설명과 응답 예시는 구현이 바뀌어도 그대로 남을 수 있기 때문이다. 예를 들어 중복 등록 시 반환하는 오류 코드를 변경했다면 문서에 적어둔 오류 예시도 함께 수정해야 한다.
    
    문서용 애너테이션과 실제 서버 동작을 만드는 설정은 다음과 같이 구분할 수 있다.
    
    | 구분 | 문서에 표현하는 설정 | 실제 동작을 담당하는 부분 |
    | --- | --- | --- |
    | 입력값 설명 | `@Schema`의 설명, 예시, 범위 | DTO와 서비스의 입력 검증 |
    | 필수 입력과 값의 제한 | 문서에 표시되는 필수 여부와 제약 조건 | `@NotNull`, `@Positive` 등의 제약과 검증 실행 |
    | 인증 필요 여부 | `@SecurityRequirement` | 인증 인터셉터나 보안 설정 |
    | 성공·실패 응답 | Swagger의 `@ApiResponse` | 컨트롤러의 응답과 예외 처리 로직 |
    
    따라서 문서에 필수 입력이라고 표시하거나 자물쇠 아이콘이 나타난다는 것만으로 입력 검증과 인증 처리가 구현되었다고 판단할 수는 없다. DTO의 제약 조건은 요청 처리 과정에서 `@Valid` 등으로 검증해야 하며, 토큰의 유효성은 별도의 인증 코드가 검사해야 한다.
    
    또한 `@Schema(example = "550")`의 예시 값은 요청에서 값을 생략했을 때 자동으로 채워지는 기본값이 아니다. 문서를 읽는 사람이 어떤 값을 넣어야 하는지 이해하도록 보여주는 값이다. 기본값이 필요한 경우에는 실제 요청 처리 코드에서도 해당 동작을 구현해야 한다.
    
    API 문서를 작성할 때는 예시 JSON뿐 아니라 각 필드의 의미와 구조도 분명해야 한다. 예를 들어 조회 결과가 없을 때 빈 배열을 반환하는지, null을 반환하는지, 오류를 반환하는지에 따라 프론트엔드의 처리 방식이 달라진다. 이런 규칙까지 명확하게 적어두면 연동 과정에서 서로 다르게 이해하는 상황을 줄일 수 있다.
    
- 단위 테스트
    
    단위 테스트는 특정 기능의 동작을 작은 범위에서 검증하는 테스트다. 테스트 대상이 판단을 올바르게 내리는지 확인할 수 있도록 DB나 외부 API처럼 실행에 영향을 주는 의존성을 통제하는 것이 중요하다.
    
    서비스를 테스트한다면 서비스 자체는 실제 객체로 사용하고, 필요한 Repository 등을 대체할 수 있다. 서비스까지 Mock으로 만들고 미리 지정한 반환값을 확인하면 실제 서비스 로직은 실행되지 않으므로 해당 로직을 검증했다고 볼 수 없다.
    
    `@InjectMocks`는 Mockito가 테스트 대상에 Mock 객체를 주입하도록 하는 기능이다. 이 애너테이션 자체가 Spring 컨테이너를 실행하는 것은 아니다. 따라서 이 구성의 단위 테스트는 서비스의 자바 로직을 확인하는 데 적합하며, Spring의 트랜잭션 처리나 HTTP 요청 검증까지 확인했다고 해석해서는 안 된다.
    
    **테스트의 검증 범위는 실행한 코드보다 실제로 확인한 조건에 의해 결정된다.** 예를 들어 다음 코드는 저장 메서드가 호출되었는지만 확인한다.
    
    ```java
    verify(favoriteRepository).save(any(Favorite.class));
    ```
    
    이 검증만으로는 올바른 영화 ID를 전달했는지 알 수 없다. 서비스가 잘못된 영화 ID로 객체를 만들었더라도 저장 메서드를 호출했다면 통과할 수 있다.
    
    저장하려던 객체의 내용까지 확인하려면 ArgumentCaptor를 사용할 수 있다. 다음 코드는 기존 정상 등록 테스트에서 서비스 호출이 끝난 뒤 추가할 수 있는 검증이다.
    
    ```java
    ArgumentCaptor<Favorite> captor =
            ArgumentCaptor.forClass(Favorite.class);
    
    verify(favoriteRepository).save(captor.capture());
    
    assertThat(captor.getValue().getMovieId()).isEqualTo(550L);
    ```
    
    ArgumentCaptor는 Mock 객체의 메서드에 전달된 인자를 가져와 추가로 검증하는 도구다. 이 예시에서는 저장 호출 여부와 함께 저장하려던 영화 ID까지 확인한다. 다만 실제 DB 저장 성공 여부는 별도의 통합 테스트에서 확인해야 한다.
    
    테스트할 입력을 고를 때는 정상적인 값뿐 아니라 경계값과 실패 조건도 고려해야 한다. 예를 들어 닉네임이 2~12자라는 규칙을 검증한다면 1자, 2자, 12자, 13자를 확인하면 최소·최대 길이의 경계를 모두 살펴볼 수 있다.
    
    또한 테스트는 다른 테스트의 실행 순서나 공유 상태에 의존하지 않도록 작성하는 것이 좋다. 필요한 데이터를 각 테스트가 준비하고, 같은 조건에서는 같은 결과가 나오도록 해야 실패 원인을 쉽게 찾을 수 있다.
    
- 통합 테스트
    
    통합 테스트는 여러 구성 요소를 연결했을 때 함께 올바르게 동작하는지 검증하는 테스트다. 서비스 내부의 판단이 정확하더라도 컨트롤러 매핑, 인증, DTO 검증, 예외 처리, DB 연결 과정에서 문제가 생길 수 있으므로 구성 요소 사이의 연결을 확인해야 한다.
    
    통합 테스트를 작성할 때는 **어디까지 실제 구성 요소를 사용하는지**를 먼저 확인해야 한다. 컨트롤러 테스트에서 서비스를 Mock으로 대체했다면 실제 서비스와 DB 저장까지 검증한 것은 아니다. 반대로 실제 서비스와 Repository를 연결하면 요청 처리부터 데이터 접근까지 더 넓은 범위를 확인할 수 있다.
    
    `@SpringBootTest`와 `@AutoConfigureMockMvc` 조합은 애플리케이션의 설정을 불러와 Spring MVC의 요청 처리 과정을 실행한다. 다만 기본 구성의 MockMvc는 실제 서버 포트를 열어 네트워크 통신을 하는 방식은 아니다. 요청·응답 객체를 이용해 처리 흐름을 실행하며, 이때 서비스와 Repository는 실제 객체를 사용할 수 있다.
    
    검증할 때는 상태 코드와 응답 내용에 더해 필요한 DB 상태도 확인하는 것이 좋다. 예를 들어 잘못된 영화 ID로 등록을 요청했다면 400 응답을 반환하는지와 함께 즐겨찾기 개수가 늘어나지 않았는지도 확인할 수 있다.
    
    다음 코드는 정상 회원과 유효한 인증 헤더가 준비된 기존 API 테스트에 추가할 수 있는 예시다.
    
    ```java
    @ParameterizedTest
    @ValueSource(longs = {0L, -1L})
    void rejectInvalidMovieId(Long movieId) throws Exception {
        long countBefore = favoriteRepository.count();
    
        mockMvc.perform(post("/favorites")
                        .header(HttpHeaders.AUTHORIZATION, authorizationHeader)
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(objectMapper.writeValueAsString(
                                new CreateFavoriteRequest(movieId))))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.isSuccess").value(false));
    
        assertThat(favoriteRepository.count()).isEqualTo(countBefore);
    }
    ```
    
    `@ParameterizedTest`와 `@ValueSource`를 사용하면 같은 검증을 입력값만 바꾸어 반복할 수 있다. 위 테스트는 영화 ID가 0인 경우와 음수인 경우를 각각 실행한다. 입력값마다 별도의 테스트 메서드를 작성하지 않아도 되므로 중복 코드를 줄일 수 있다.
    
    통합 테스트에서는 데이터 격리도 중요하다. 앞선 테스트가 저장한 데이터 때문에 다음 테스트가 중복 등록으로 실패한다면, 기능 오류와 테스트 환경 문제를 구분하기 어렵다. 테스트에 `@Transactional`을 적용하면 기본적으로 테스트 메서드가 끝날 때 해당 테스트 트랜잭션을 롤백한다. 다만 실제 HTTP 서버에 요청하는 방식에서는 서버가 별도의 스레드와 트랜잭션으로 처리하므로 같은 정리 방식이 그대로 적용된다고 가정하면 안 된다.
    
    `ddl-auto: create-drop`도 테스트 메서드마다 데이터를 초기화한다는 의미는 아니다. Hibernate의 SessionFactory가 시작될 때 스키마를 다시 만들고 종료될 때 삭제하는 설정이므로, 테스트 사이의 데이터 정리는 롤백이나 별도의 정리 방식으로 관리해야 한다.
    
    H2의 MySQL 모드는 일부 문법과 동작을 MySQL에 맞추는 호환 설정이다. 실제 MySQL과 완전히 같은 환경은 아니므로, MySQL 전용 SQL이나 DB별 동작에 의존하는 기능은 MySQL을 사용하는 테스트 환경에서도 확인하는 것이 좋다.
    
- Mock, Stub
    
    Mock과 Stub은 테스트에서 실제 의존 객체를 대신하는 테스트 대역(Test Double)이다. 둘을 구분할 때는 객체를 어떤 도구로 만들었는지보다 **테스트에서 어떤 역할로 사용하는지**를 기준으로 생각하면 이해하기 쉽다.
    
    | 구분 | 주요 역할 | 확인하려는 내용 |
    | --- | --- | --- |
    | Stub | 미리 정한 결과를 반환해 테스트 조건을 만든다. | 특정 상황에서 테스트 대상이 어떻게 동작하는지 확인한다. |
    | Mock | 메서드 호출을 기록하고 기대한 상호작용과 비교한다. | 어떤 메서드를 어떤 인자로 몇 번 호출했는지 확인한다. |
    
    예를 들어 회원이 존재하는 상황에서 서비스를 테스트하고 싶다면 Repository가 특정 회원을 반환하도록 설정할 수 있다.
    
    ```java
    given(memberRepository.findById(1L))
            .willReturn(Optional.of(member));
    ```
    
    이 코드는 테스트에 필요한 상황을 제공하는 스텁 설정이다. 실제 DB에 회원이 있는지 조회하는 대신, 서비스가 회원을 조회했을 때 준비한 객체를 받도록 한다.
    
    반면 중복 등록을 처리한 뒤 저장을 시도하지 않았는지 확인하려면 다음과 같이 호출 기록을 검증할 수 있다.
    
    ```java
    verify(favoriteRepository, never())
            .save(any(Favorite.class));
    ```
    
    이 검증은 중복 상황을 준비하고 실제 서비스 동작을 실행한 뒤에 수행해야 의미가 있다. 서비스를 호출하기도 전에 확인하면 저장이 호출되지 않은 것이 당연하기 때문이다.
    
    Mockito에서는 `@Mock`으로 만든 객체에 반환값을 설정해 Stub 역할을 수행하게 할 수 있고, 같은 객체의 호출 기록을 검증할 수도 있다. 따라서 `@Mock`으로 생성했다는 이유만으로 반환값 설정과 호출 검증을 같은 개념으로 이해해서는 안 된다.
    
    Mock 객체는 실제 Repository의 저장 동작을 수행하지 않는다. `save()`를 호출했다고 해서 데이터가 저장되거나 ID가 자동으로 생성되는 것은 아니다. 서비스에서 저장 결과를 사용한다면 테스트에 필요한 반환값을 직접 설정해야 한다.
    
    또한 Mockito의 기본 Mock은 별도로 설정하지 않은 호출에 자료형에 따른 기본값을 반환한다. 예를 들어 boolean에는 false, 숫자에는 0, 일부 참조형에는 null이나 빈 값이 반환될 수 있다. 필요한 설정을 빠뜨리면 의도한 상황과 다른 경로로 테스트가 실행될 수 있으므로, 해당 시나리오의 판단에 중요한 반환값은 명확하게 설정하는 것이 좋다.
    
    검증할 필요가 없는 내부 호출까지 모두 고정하면 기능이 동일한 리팩토링에도 테스트가 쉽게 깨질 수 있다. 중복 등록 시 저장을 호출하지 않아야 한다는 규칙처럼, 요구사항과 직접 연결된 상호작용을 중심으로 검증하는 것이 좋다.
    
- given-when-then
    
    given-when-then은 테스트를 준비 조건, 실행할 행동, 기대 결과로 나누어 표현하는 방식이다. 테스트를 읽는 사람이 어떤 상황을 검증하는지 쉽게 파악할 수 있도록 돕는다.
    
    각 단계는 다음 질문에 답하도록 작성하면 된다.
    
    | 단계 | 작성 기준 |
    | --- | --- |
    | given | 이 상황을 만들기 위해 어떤 데이터와 상태가 필요한가를 정한다. |
    | when | 검증하려는 핵심 행동을 실행한다. |
    | then | 그 행동의 결과로 무엇이 반환되거나 변경되어야 하는지 확인한다. |
    
    예를 들어 즐겨찾기 해제 기능은 다음과 같은 시나리오로 정리할 수 있다.
    
    - given: 회원이 특정 영화를 즐겨찾기에 등록한 상태를 준비한다.
    - when: 해당 회원이 그 영화의 즐겨찾기를 해제한다.
    - then: 해제한 즐겨찾기가 목록에서 제외되고, 즐겨찾기 여부 조회 결과가 false인지 확인한다.
    
    **하나의 테스트에서는 하나의 시나리오를 분명하게 설명하는 것이 중요하다.** 정상 등록, 중복 등록, 권한 없는 삭제를 한 테스트에 모두 넣으면 중간에 실패했을 때 어느 규칙에 문제가 생겼는지 파악하기 어렵다.
    
    다만 한 테스트에 검증문이 반드시 하나만 있어야 하는 것은 아니다. 하나의 등록 시나리오에서 응답 상태 코드, 반환된 영화 ID, DB에 저장된 값을 함께 확인할 수 있다. 여러 검증문이 같은 행동의 결과를 설명한다면 자연스러운 구성이다.
    
    given에는 현재 시나리오에 필요한 조건만 준비하는 것이 좋다. 모든 테스트에 필요한 객체 생성은 `@BeforeEach`로 묶을 수 있지만, 중복 여부나 특정 조회 결과처럼 테스트마다 달라지는 조건은 해당 테스트 안에 두는 편이 이해하기 쉽다.
    
    예외를 검증할 때는 when과 then이 코드상 하나의 표현 안에 들어갈 수 있다.
    
    ```java
    assertThatThrownBy(() ->
            favoriteService.create(1L, new CreateFavoriteRequest(550L)))
            .isInstanceOf(ApiException.class);
    ```
    
    이 코드에서는 람다 안의 서비스 호출이 when이고, 발생한 예외의 종류를 확인하는 부분이 then이다. 서비스 호출을 람다 밖에서 먼저 실행하면 예외가 검증문에 도달하기 전에 발생하므로, 예외를 발생시킬 동작을 검증 함수 안에 전달해야 한다.
    
    테스트 이름도 조건과 기대 결과를 함께 드러내는 것이 좋다. `createTest`처럼 기능명만 적는 것보다 `@DisplayName`을 활용해 구체적으로 작성할 수 있다.
    
    ```java
    @DisplayName("이미 등록한 영화를 다시 즐겨찾기하면 중복 오류를 반환한다")
    ```
    
    이렇게 작성하면 실패한 테스트 이름만으로도 어떤 규칙이 깨졌는지 이해할 수 있다. 테스트 코드가 단순히 기능을 확인하는 역할을 넘어 해당 기능의 요구사항을 설명하는 문서 역할도 수행할 수 있게 된다.
    
- 회귀 테스트
    
    회귀 테스트는 코드 변경 이후에도 기존에 정상적으로 동작하던 기능이 유지되는지 확인하는 테스트다.
    
    단위 테스트와 통합 테스트가 주로 검증 범위에 따른 구분이라면, 회귀 테스트는 테스트를 수행하는 목적에 따른 구분이다. 기존 단위 테스트와 통합 테스트를 코드 변경 후 다시 실행하면 둘 다 회귀 테스트 역할을 할 수 있다.
    
    회귀 테스트를 보강할 때는 이미 발견한 버그뿐 아니라 그 버그와 가까운 정상 상황도 함께 살펴보는 것이 좋다. 특정 오류만 막도록 코드를 수정하다가 정상적인 요청까지 차단할 수 있기 때문이다.
    
    예를 들어 회원 A가 영화 550을 즐겨찾기에 등록한 상태라면 다음 상황을 구분해야 한다.
    
    | 추가 등록 요청 | 기대 결과 |
    | --- | --- |
    | 회원 A가 영화 550을 다시 등록한다. | 같은 회원의 중복 등록이므로 거절한다. |
    | 회원 A가 다른 영화 551을 등록한다. | 다른 영화이므로 등록을 허용한다. |
    | 회원 B가 영화 550을 등록한다. | 다른 회원의 즐겨찾기이므로 등록을 허용한다. |
    
    같은 회원의 중복 등록만 테스트하면, 중복 검사에서 회원 ID를 빠뜨리고 영화 ID만 확인하는 오류를 놓칠 수 있다. 다른 회원이 같은 영화를 등록하는 경우까지 확인하면 중복 판단의 기준이 올바른지도 검증할 수 있다.
    
    버그를 수정할 때는 다음 흐름으로 테스트를 남기는 것이 좋다.
    
    1. 문제가 발생한 입력과 상태를 테스트로 만든다.
    2. 수정 전 코드에서 해당 테스트가 실패하는지 확인한다.
    3. 코드를 수정한 뒤 해당 테스트가 통과하는지 확인한다.
    4. 기존 테스트도 함께 실행해 다른 기능에 영향을 주지 않았는지 확인한다.
    5. 재현 테스트를 유지해 같은 문제가 다시 발생했을 때 발견할 수 있도록 한다.
    
    수정 전 코드에서도 새 테스트가 통과한다면 실제 버그를 재현하지 못했거나 검증 조건이 부족할 수 있다. 따라서 수정 후의 통과 여부와 함께, 잘못된 동작을 제대로 잡아내는지도 확인해야 한다.
    
    테스트가 실패했을 때는 기대값을 현재 결과에 맞춰 바로 바꾸지 않아야 한다. 먼저 요구사항이 변경된 것인지, 구현이 기존 규칙을 어긴 것인지 확인해야 한다. 요구사항이 그대로인데 테스트 기대값만 바꾸면 기존 동작을 보호하던 검증이 사라질 수 있다.
    
    코드 커버리지가 높다는 사실만으로 회귀 오류를 충분히 막는다고 볼 수도 없다. 코드를 실행했더라도 중요한 결과를 검증하지 않으면 잘못된 동작을 놓칠 수 있다. 정상적인 요청이 유지되는지와 잘못된 요청이 올바르게 거절되는지를 함께 확인해야 한다.
    
    회귀 테스트는 GitHub Actions와 같은 CI 환경에서도 활용할 수 있다. 코드를 Push하거나 Pull Request를 생성할 때마다 전체 테스트를 자동으로 실행하도록 설정하면, 문제가 있는 코드가 main 브랜치에 병합되기 전에 발견할 수 있다.
    
    결국 회귀 테스트의 목적은 단순히 테스트 통과 개수를 늘리는 것이 아니라, 기존 기능의 안정성을 유지하면서 새로운 기능 개발과 리팩토링을 지속할 수 있도록 하는 데 있다.
