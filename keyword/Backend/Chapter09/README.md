# Backend Chapter09

## 키워드 정리

### Swagger / OpenAPI

#### OpenAPI Specification(OAS)

- 정의: HTTP API의 구조와 사용 방법을 사람과 기계가 모두 읽을 수 있도록 정의한 공개 표준 명세
- 표현 형식: OpenAPI 명세를 따르는 문서를 JSON 또는 YAML로 작성
- 주요 내용: API 경로, HTTP 메서드, 요청 파라미터와 본문, 응답 상태 코드와 스키마, 인증 방식
- 특징: 특정 프로그래밍 언어나 프레임워크에 독립적. 같은 명세를 API 문서화, 클라이언트 코드 생성, 요청·응답 검증 등에 활용 가능

#### Swagger

- 이름의 유래: 현재 OpenAPI Specification의 전신은 Swagger Specification. Swagger Specification 2.0이 OpenAPI Initiative에 기증된 뒤, 표준 명세의 이름은 OpenAPI Specification으로 변경
- 현재 의미: Swagger는 OpenAPI 명세를 작성하고 활용하는 도구 모음의 이름
    - Swagger Editor: OpenAPI 문서 작성 및 검증
    - Swagger UI: OpenAPI 문서를 브라우저에서 보여 주고 API 요청도 보낼 수 있도록 지원

#### Code First / Spec First

OpenAPI 자체는 코드와 명세 중 무엇을 먼저 작성할지 정하지 않음. 프로젝트의 협업 방식에 따라 선택 가능.

| 방식 | 작업 순서 | 장점 | 주의점 |
| --- | --- | --- | --- |
| Code First | API 구현 → 코드에서 OpenAPI 문서 생성 | 기존 코드에 문서화를 적용하기 쉽고, 경로나 DTO 등 구현 정보를 문서에 반영하기 편리 | 업무상 발생할 수 있는 오류 응답이나 필드의 의미까지 자동 추론되지는 않으므로 보완 필요 |
| Spec First | OpenAPI 문서 작성·합의 → 명세를 기준으로 API 구현 | 구현 전에 요청·응답 형식을 합의할 수 있어 프런트엔드와 백엔드의 병렬 작업에 유리 | 명세를 먼저 작성·검토해야 하며, 이후에도 구현이 명세와 일치하는지 검증 필요 |

- Spring Boot의 Code First: `springdoc-openapi`는 컨트롤러의 요청 매핑과 DTO 구조 등을 바탕으로 OpenAPI 문서를 생성하는 연동 라이브러리. 자동으로 드러나지 않는 응답이나 설명은 `@Operation`, `@ApiResponse` 등의 어노테이션으로 보완 가능.

### 단위 테스트

#### 정의 및 목적

- 정의: 함수, 메서드, 클래스 등 애플리케이션의 가장 작은 동작 단위가 의도한 대로 동작하는지 독립적으로 검증하는 테스트.
- 검증 대상: 입력값에 따른 반환값, 객체 내부의 상태 변화, 예외 발생 여부 등 테스트 대상 자체의 순수 비즈니스 로직.
- 격리(Isolation) 원칙: 외부 의존성(DB, 외부 API, 파일 시스템, 다른 레이어)이 테스트 결과나 속도에 영향을 줄 경우 테스트 대역(Test Double)으로 대체하여 대상을 고립시킴. (단, 순수 도메인 로직 등 외부 의존성이 없다면 대역 없이도 단위 테스트 작성 가능)

#### 프레임워크 적용 (Spring Boot 관점)

- JUnit 5 + Mockito: 스프링 컨테이너(`@SpringBootTest`)를 띄우지 않고 순수 자바 객체 수준에서 빠르게 실행.
- 핵심 구분: 스프링 빈(Bean)과 DB 연결 없이 실행되므로 밀리초(ms) 단위로 종료되며, 실패 시 어느 메서드의 로직이 틀렸는지 즉시 특정 가능.

#### 장점과 한계

- 장점: 실행 속도가 매우 빨라 개발 중 수시로 피드백을 받을 수 있고, 실패 범위가 좁아 디버깅 비용이 낮음.
- 한계: 개별 메서드의 로직이 완벽하더라도 실제 데이터베이스 쿼리 문법 오류, 트랜잭션 전파, 네트워크 직렬화/역직렬화 등 모듈 간 연결 과정에서 발생하는 결함은 잡아내지 못함.

### 통합 테스트

#### 정의 및 범위

- **정의:** 둘 이상의 구성 요소(Controller-Service-Repository, 애플리케이션-DB 등)를 실제로 연결했을 때 데이터 전달과 상호작용이 올바르게 이루어지는지 검증하는 테스트.
- **검증 범위의 유연성:** 반드시 애플리케이션 전체를 실행해야만 통합 테스트인 것은 아니며, 검증 목적에 따라 필요한 계층만 선택적으로 연결 가능.

#### 계층별 테스트 범위 비교

| 구분 | 어노테이션 예시 | 연결 범위 | 특징 및 검증 목적 |
| --- | --- | --- | --- |
| 웹 계층 슬라이스 | `@WebMvcTest` | HTTP 요청 → Controller → JSON 응답 | 요청 파라미터 바인딩, `@Valid` 검증, HTTP 상태 코드 및 응답 포맷 확인 |
| 데이터 계층 슬라이스 | `@DataJpaTest` | Repository → 실제 DB(또는 인메모리 DB) | JPA 쿼리 메서드, JPQL, 매핑 설정, 제약 조건 동작 확인 |
| 전체 통합 테스트 | `@SpringBootTest` | 전체 애플리케이션 빈 + 실제 DB 및 인프라 | 실제 운영 환경과 가장 유사한 조건에서 End-to-End 흐름 검증 |

- **장점:** 단위 테스트에서 놓치기 쉬운 설정 누락, JSON 직렬화 오류, 트랜잭션 롤백 문제, 실제 SQL 문법 및 DB 제약 조건 위반 등을 발견하기에 유리.
- **한계:** 스프링 컨텍스트 로딩 및 DB 초기화로 인해 실행 비용과 시간이 크며, 테스트 실패 시 어느 계층에서 원인이 발생했는지 추적하는 데 시간이 더 걸림. (일부를 Mock으로 대체하면 속도는 빨라지지만 해당 연결부는 검증에서 제외됨)

### Mock, Stub

#### 개념 및 역할 구분

실제 객체 대신 테스트에 투입하는 가짜 객체(Test Double)의 대표적인 유형. 차이는 객체의 생성 방식이 아니라 테스트에서 검증하려는 목적(역할)에 있음.

| 구분 | 핵심 역할 | 검증 방식 | 테스트가 묻는 질문 |
| --- | --- | --- | --- |
| Stub | 미리 정해진 반환값이나 예외를 제공하여 테스트 환경(상태)을 조성 | 상태 검증 (State Verification) | "의존성이 A라는 값을 줄 때, 내 로직이 B라는 결과를 내는가?" |
| Mock | 메서드의 호출 여부, 호출 횟수, 전달된 인자 등 행위 자체를 검증 | 행위 검증 (Behavior Verification) | "내 로직이 의존성에게 기대한 파라미터로 요청을 보냈는가?" |

#### 라이브러리 활용과 주의점

- Mockito 관점: 하나의 Mock 객체(`@Mock`)가 두 역할을 모두 수행할 수 있음. `given(...).willReturn(...)`을 쓰면 Stub으로 동작하고, `verify(...).times(1)`을 쓰면 Mock으로 동작.
- 과도한 행위 검증의 위험: 내부 구현(특정 private/내부 메서드를 몇 번 호출하는지 등)을 지나치게 세세하게 `verify`하면, 외부 비즈니스 결과는 동일한데 내부 코드를 리팩터링할 때마다 테스트가 깨지는 취약한 테스트(Fragile Test)가 됨. 이메일 발송, 외부 결제 API 호출처럼 '호출 행위 자체가 요구사항'일 때 Mock 검증이 가장 유용.

### given-when-then

#### 구조 및 작성 원칙

BDD(Behavior-Driven Development)에서 유래한 테스트 코드 작성 패턴으로, 테스트의 의도를 사전 조건 → 실행 동작 → 기대 결과의 흐름으로 명확히 구조화.

| 단계 | 작성할 내용 | 코드 작성 팁 |
| --- | --- | --- |
| Given (준비) | 테스트에 필요한 입력 데이터, 엔티티 초기 상태, Stub의 반환값 정의 | 테스트 검증에 꼭 필요한 데이터만 최소한으로 준비 |
| When (실행) | 검증하고자 하는 핵심 비즈니스 메서드 호출 | 가급적 **단 하나의 핵심 동작**만 실행하여 테스트 초점을 명확히 유지 |
| Then (검증) | 반환값 일치 여부, DB 상태 변경, 예외 발생, Mock 호출 횟수 확인 | `assertThat()` 등을 사용해 실패 시 원인을 알 수 있도록 구체적으로 단언 |

#### 장점과 주의점

- 장점: 주석이나 구조만 읽어도 해당 기능의 요구사항(스펙)이 무엇인지 문서처럼 읽히므로 동료 개발자의 리뷰 및 유지보수가 쉬워짐.
- 주의점: 특정 프레임워크나 테스트 종류가 아니라 코드를 읽기 쉽게 나누는 구조적 관습. 단순히 주석(`// given`, `// when`, `// then`)을 다는 것보다, 하나의 테스트 메서드에서 여러 동작(`When`)과 검증(`Then`)을 뒤섞지 않고 '한 번에 하나의 동작만 검증'하도록 분리하는 것이 핵심.

### 회귀 테스트

#### 정의 및 필요성

- 정의: 새로운 기능 추가, 버그 수정, 라이브러리 버전 업그레이드, 리팩터링 등의 변경 이후에도 기존에 정상 동작하던 기능들이 깨지지 않았는지 반복 확인하는 테스트.
- 검증 대상: 수정한 버그가 다시 나타나지 않는지뿐만 아니라, 전혀 무관해 보이는 다른 기능에 의도치 않은 부작용(Side Effect)이 발생했는지까지 포함.

#### 재확인 테스트와의 구분

| 구분 | 실행 시점 및 목적 | 핵심 질문 |
| --- | --- | --- |
| 재확인 테스트 (Confirmation) | 버그를 수정한 직후, 해당 결함이 제대로 고쳐졌는지 확인 | "보고된 그 버그가 이제 해결되었는가?" |
| 회귀 테스트 (Regression) | 코드 변경 전반 이후, 기존의 다른 정상 기능들이 망가지지 않았는지 확인 | "이번 수정 때문에 원래 잘 되던 다른 기능이 고장 나지 않았는가?" |

관계: 버그 수정을 위해 작성한 테스트 코드는 수정 직후에는 재확인 테스트 역할을 하고, 이후 프로젝트가 진행되면서 CI 파이프라인에서 계속 재실행될 때는 회귀 테스트 역할을 수행.

#### 자동화의 중요성과 한계

- 자동화(CI) 연계: 사람이 매 배포마다 모든 기능을 수동으로 눌러보는 것은 불가능하므로, GitHub Actions 등 CI 환경에서 Push/PR 시 자동화된 단위·통합 테스트 스위트를 실행해 회귀 결함을 조기에 차단.
- 한계: 테스트 코드가 작성된 범위 내의 동작만 보장하므로, 테스트 커버리지가 낮거나 예외 케이스 테스트가 누락되어 있다면 회귀 버그를 놓칠 수 있음.
