## 트랜잭션(Transaction)

#### 트랜잭션 (Transaction)

- DB에서 하나의 논리적인 작업 단위로 묶인 여러 개의 쿼리(SQL) 묶음
- 묶인 쿼리들은 모두 성공하거나, 하나라도 실패하면 모두 취소됨
- "여러 번의 DB 변경을 한 번의 변경처럼 다루는 것"

#### 작업 단위 (Unit of Work)

- 비즈니스적으로 반드시 함께 처리되어야 하는 변경들의 묶음
- 예: 계좌 이체 = 출금 + 입금, 주문 = 재고 차감 + 주문 생성 + 결제 기록

#### 트랜잭션 경계

- 트랜잭션이 어디서 시작해서 어디서 끝나는지를 나타내는 범위

```sql
BEGIN;                       -- 트랜잭션 시작
  UPDATE ...;
  INSERT ...;
COMMIT;                      -- 성공: 변경 확정
-- 또는 ROLLBACK;            -- 실패: 변경 취소
```

### 트랜잭션이 필요한 이유

#### 예시: 계좌 이체 (A → B로 10,000원)

```sql
UPDATE account SET balance = balance - 10000 WHERE id = 'A';   -- ① A 출금
UPDATE account SET balance = balance + 10000 WHERE id = 'B';   -- ② B 입금
```

| 상황 | 트랜잭션 없음 | 트랜잭션 있음 |
| --- | --- | --- |
| ① 성공, ② 실패 (서버 다운, 에러) | A의 돈만 빠지고 **B는 받지 못함** → 돈이 사라짐 | ①도 **취소**되어 처음 상태로 돌아감 |
| ①, ② 모두 성공 | 정상 | 정상 (commit) |

- 트랜잭션은 **중간 상태(일부만 반영된 상태)가 DB에 남지 않도록** 보장함

### 트랜잭션이 필요한 상황

| 상황 | 함께 처리되어야 하는 작업 |
| --- | --- |
| 주문 | 재고 차감 + 주문 생성 + 결제 기록 |
| 회원가입 | 회원 생성 + 기본 프로필 생성 + 약관 동의 기록 |
| 게시글 삭제 | 게시글 삭제 + 댓글 삭제 + 작성자의 게시글 수 감소 |
| 포인트 사용 | 포인트 차감 + 사용 내역 기록 |
| 팀 생성 | 팀 생성 + 생성자를 팀장(owner) 멤버로 추가 |

## commit / rollback

#### Commit (커밋)

- 트랜잭션 안에서 실행한 변경 사항을 **DB에 영구적으로 확정**하는 명령
- commit 이후에는
  - 다른 트랜잭션(다른 요청)도 **변경된 데이터를 볼 수 있음**
  - 서버가 꺼져도 **변경 내용이 유지됨**
  - **rollback으로 되돌릴 수 없음**

#### Rollback (롤백)

- 트랜잭션 안에서 실행한 변경 사항을 **모두 취소하고 트랜잭션 시작 전 상태로 되돌리는** 명령
- 에러 발생, 비즈니스 규칙 위반, 서버·연결 장애 시 실행됨

#### Auto Commit (자동 커밋)

- 트랜잭션을 명시하지 않으면 **쿼리 하나하나가 실행되자마자 바로 commit**되는 모드
- MySQL, PostgreSQL 모두 기본값
- 여러 쿼리를 하나로 묶으려면 `BEGIN`(또는 `START TRANSACTION`)으로 트랜잭션을 직접 시작해야 함

#### Savepoint (세이브포인트)

- 트랜잭션 중간에 지정하는 **되돌리기 지점**
- 전체를 취소하지 않고 **특정 지점까지만** rollback할 수 있음

### commit과 rollback 비교

| 구분 | Commit | Rollback |
| --- | --- | --- |
| 의미 | 변경 **확정** | 변경 **취소** |
| 실행 시점 | 트랜잭션의 모든 작업이 성공했을 때 | 에러·규칙 위반·장애가 발생했을 때 |
| 결과 | 변경이 영구 저장, 다른 트랜잭션에 보임 | 트랜잭션 시작 전 상태로 복구 |
| 되돌리기 | 불가능 | - |

### Prisma에서 commit / rollback이 결정되는 방식

- Prisma의 `$transaction`은 `BEGIN`, `COMMIT`, `ROLLBACK`을 **자동으로** 실행함

| 콜백(또는 배열의 쿼리)의 결과 | 동작 |
| --- | --- |
| 정상적으로 끝남 (`return`) | **commit** |
| 예외가 발생함 (`throw`) | **rollback** 후 예외를 다시 던짐 |
| 제한 시간 초과 (`timeout`, 기본 5초) | **rollback** |

### commit 이후에 되돌려야 할 때

- commit된 변경은 rollback할 수 없으므로, **반대 동작을 하는 새 작업(보상 트랜잭션, Compensating Transaction)** 으로 취소함
- 예: 주문 commit 후 결제 실패 → 주문 상태를 `CANCELED`로 바꾸고 재고를 다시 증가시키는 작업 실행

## 원자성(Atomicity)

#### 원자성 (Atomicity)

- 트랜잭션 안의 작업들이 **모두 반영되거나(All), 전혀 반영되지 않아야 한다(Nothing)** 는 성질
- **All or Nothing**
- 트랜잭션을 **더 이상 쪼갤 수 없는 하나의 단위(원자)** 처럼 다룬다는 의미
- ACID의 **A**

#### 부분 반영 (Partial Update)

- 여러 작업 중 **일부만 DB에 반영되고 나머지는 반영되지 않은 상태**
- 원자성이 보장되지 않으면 장애 발생 시 이런 **어중간한 상태**가 남음

### 원자성이 보장될 때와 아닐 때

#### 예시: 주문 처리 (재고 차감 → 주문 생성 → 결제 기록)

```
[원자성 X]
① 재고 차감   ✅ 반영
② 주문 생성   ✅ 반영
③ 결제 기록   ❌ 에러
→ 재고는 줄었고 주문도 있는데 결제 기록이 없음 (데이터 불일치)

[원자성 O]
① 재고 차감   ✅
② 주문 생성   ✅
③ 결제 기록   ❌ 에러
→ ①, ②도 모두 취소 → 주문 전 상태 그대로
```

| 결과 | 원자성 보장 시 가능 여부 |
| --- | --- |
| ①②③ 모두 반영 | ⭕ |
| ①②③ 모두 미반영 | ⭕ |
| ①②만 반영, ③ 미반영 | ❌ (원자성이 막는 상태) |

### DB가 원자성을 보장하는 방법

- DB는 데이터를 변경하기 전에 **변경 전 값을 로그(Undo Log)** 에 기록해 둠
- 트랜잭션이 실패하면 이 로그를 이용해 **변경 전 상태로 되돌림** (rollback)
- 트랜잭션 도중 서버가 갑자기 꺼져도, 재시작할 때 **commit되지 않은 트랜잭션을 취소**해서 부분 반영된 상태가 남지 않게 함

### 원자적 연산 (Atomic Operation)

- 트랜잭션뿐 아니라 **쿼리 하나 수준**에서도 원자성이 중요함
- "조회 → 계산 → 저장"을 애플리케이션에서 나눠 하면, 그 사이에 다른 요청이 끼어들어 값이 꼬일 수 있음

## ACID

#### ACID

- 트랜잭션이 **안전하게 처리되기 위해 보장해야 하는 4가지 성질**의 앞 글자
- **A**tomicity(원자성), **C**onsistency(일관성), **I**solation(격리성), **D**urability(지속성)

| 성질 | 의미 | 한 줄 요약 |
| --- | --- | --- |
| **Atomicity** (원자성) | 트랜잭션의 작업은 모두 반영되거나 전혀 반영되지 않음 | All or Nothing |
| **Consistency** (일관성) | 트랜잭션 전후로 DB가 **정해진 규칙(제약 조건)을 항상 만족**함 | 규칙을 깨는 데이터는 저장되지 않음 |
| **Isolation** (격리성) | 동시에 실행되는 트랜잭션이 **서로의 중간 결과에 영향을 받지 않음** | 동시에 실행해도 따로 실행한 것처럼 |
| **Durability** (지속성) | commit된 결과는 **장애가 발생해도 사라지지 않음** | 확정된 건 영원히 |

### Atomicity (원자성)

- 트랜잭션 중 하나라도 실패하면 **전체를 rollback**
- DB는 **Undo Log**(변경 전 값 기록)로 보장
- 예: 이체 중 입금이 실패하면 출금도 취소

### Consistency (일관성)

- DB에 정의된 **규칙**을 트랜잭션 전후로 항상 지키는 성질
  - 제약 조건: `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL`, `CHECK`
  - 비즈니스 규칙: 잔액은 0 이상, 재고는 음수가 될 수 없음
- 규칙을 위반하는 변경이 있으면 트랜잭션이 실패하고 rollback됨
- DB 제약 조건으로 보장되는 부분도 있지만, **비즈니스 규칙은 애플리케이션 코드**에서도 함께 지켜야 함

```sql
-- 잔액이 음수가 되지 않도록 DB 규칙으로 정의
ALTER TABLE account ADD CONSTRAINT chk_balance CHECK (balance >= 0);
```

### Isolation (격리성)

- 여러 트랜잭션이 동시에 실행될 때, 한 트랜잭션의 **commit되지 않은 중간 변경을 다른 트랜잭션이 보지 못하게** 하는 성질
- DB는 **잠금(Lock)** 과 **MVCC(Multi-Version Concurrency Control, 데이터의 여러 버전을 두고 읽기·쓰기가 서로 막지 않게 하는 방식)** 로 보장
- 완벽하게 격리하면 성능이 떨어지므로, DB는 **격리 수준(Isolation Level)** 을 선택할 수 있게 함

#### 동시성 이상 현상

| 현상 | 의미 |
| --- | --- |
| **Dirty Read** | 다른 트랜잭션이 **commit하지 않은 값**을 읽음 (그 트랜잭션이 rollback되면 존재하지 않는 값을 읽은 셈) |
| **Non-Repeatable Read** | 같은 트랜잭션 안에서 **같은 행을 두 번 읽었는데 값이 다름** (중간에 다른 트랜잭션이 수정·commit) |
| **Phantom Read** | 같은 조건으로 두 번 조회했는데 **행의 개수가 달라짐** (중간에 다른 트랜잭션이 추가·삭제) |

#### 격리 수준

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 특징 |
| --- | --- | --- | --- | --- |
| READ UNCOMMITTED | 발생 | 발생 | 발생 | 가장 느슨함, 거의 사용 안 함 |
| READ COMMITTED | 방지 | 발생 | 발생 | **PostgreSQL 기본값** |
| REPEATABLE READ | 방지 | 방지 | 발생 가능 | **MySQL(InnoDB) 기본값** (InnoDB는 대부분의 Phantom Read도 방지) |
| SERIALIZABLE | 방지 | 방지 | 방지 | 가장 엄격함, 동시 처리 성능 낮음 |

- 격리 수준이 높을수록 **정확하지만 느리고**, 낮을수록 **빠르지만 이상 현상이 생길 수 있음**

```ts
// Prisma에서 트랜잭션 격리 수준 지정
await this.prisma.$transaction(
  async (tx) => {
    // ...
  },
  { isolationLevel: Prisma.TransactionIsolationLevel.Serializable },
);
```

### Durability (지속성)

- commit이 완료되면 **서버가 꺼지거나 장애가 나도 결과가 유지**되는 성질
- DB는 변경 내용을 디스크의 **Redo Log / WAL(Write-Ahead Log)** 에 먼저 기록한 뒤 commit을 완료함
- 장애 후 재시작할 때 이 로그를 다시 적용해서 **commit된 변경을 복구**함
- 디스크 자체가 손상되는 경우까지 대비하려면 **백업, 복제(Replication)** 를 함께 사용

## UNIQUE 제약 조건

#### 제약 조건 (Constraint)

- 테이블에 저장되는 데이터가 지켜야 할 규칙을 **DB가 직접 강제**하는 것
- 규칙을 어기는 INSERT/UPDATE는 DB가 에러를 내고 거부함
- ACID의 **일관성(Consistency)** 을 보장하는 대표적인 수단

#### UNIQUE 제약 조건

- 지정한 컬럼(또는 컬럼 조합)의 값이 테이블 안에서 **중복되지 않도록** 보장하는 제약
- 예: 같은 이메일로 두 번 가입할 수 없음

#### 복합 UNIQUE 제약 조건

- **두 개 이상의 컬럼 조합**이 중복되지 않도록 보장
- 예: `(user_id, post_id)` → 한 사용자는 같은 게시글에 좋아요를 한 번만 누를 수 있음

#### 유니크 인덱스 (Unique Index)

- 중복 여부를 빠르게 확인하기 위해 UNIQUE 제약과 함께 만들어지는 인덱스
- 대부분의 DB(MySQL, PostgreSQL)는 UNIQUE 제약을 만들면 **유니크 인덱스를 자동 생성**함 → 해당 컬럼 조회도 빨라짐

### UNIQUE 제약이 필요한 이유: 동시 요청

- 애플리케이션에서 "이미 있는지 조회 → 없으면 저장"으로 검사해도, **동시에 들어온 요청**은 둘 다 검사를 통과할 수 있음

```
요청 A: 조회 → 없음 ──────────▶ INSERT 성공
요청 B:    조회 → 없음 ──────────▶ INSERT 성공   ← 중복 발생
```

- UNIQUE 제약이 있으면 DB가 **하나만 성공시키고 나머지는 에러로 거부**함 → 데이터 중복의 **최종 방어선**

| 단계 | 역할 |
| --- | --- |
| 사전 조회 | 대부분의 중복을 빠르게 걸러내고 친절한 메시지 제공 |
| UNIQUE 제약 | 동시 요청까지 **DB가 최종 차단** |
| 예외 처리 | UNIQUE 위반 에러를 **409 Conflict**로 변환 |

### UNIQUE 위반 처리

| DB / ORM | 에러 |
| --- | --- |
| MySQL | `1062` (`ER_DUP_ENTRY`) |
| PostgreSQL | `23505` (`unique_violation`) |
| Prisma | `P2002` |

## 낙관적 잠금(Optimistic Locking)

#### 잠금 (Lock)

- 데이터를 수정하는 동안 **다른 트랜잭션이 같은 데이터를 수정하지 못하게 막는 것**

#### 낙관적 잠금 (Optimistic Locking)

- **"충돌은 드물 것"** 이라고 가정하고, **DB 잠금 없이** 수정하되, **저장하는 순간에 다른 사람이 먼저 수정했는지 확인**하는 방식
- 주로 **버전(version) 컬럼**을 사용해서 확인
- 충돌이 감지되면 저장하지 않고 **실패 처리**(에러 응답 또는 재시도)

#### 비관적 잠금 (Pessimistic Locking)

- **"충돌이 자주 일어날 것"** 이라고 가정하고, 데이터를 읽을 때 **DB 잠금을 먼저 걸어** 다른 트랜잭션의 수정을 막는 방식
- 다른 트랜잭션은 잠금이 풀릴 때까지 **기다려야 함**

### 낙관적 잠금 동작 방식

```
게시글 { id: 1, content: "A", version: 3 }

사용자 1: 조회 (version 3)
사용자 2: 조회 (version 3)

사용자 1: UPDATE ... SET content = "A+1", version = 4
          WHERE id = 1 AND version = 3
          → 1행 수정 ✅ (DB version: 4)

사용자 2: UPDATE ... SET content = "A+2", version = 4
          WHERE id = 1 AND version = 3
          → 0행 수정 ❌ (이미 version 4라서 조건 불일치)
```

```sql
UPDATE post
SET content = '새 내용', version = version + 1
WHERE id = 1 AND version = 3;   -- 읽었을 때의 버전과 같을 때만 수정
```

- 수정된 행 수(affected rows)가 **0이면 다른 사람이 먼저 수정한 것**
