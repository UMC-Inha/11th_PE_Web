# Backend Chapter08

## 키워드 정리

### 트랜잭션(Transaction)

- 데이터베이스의 상태를 변화시키는 논리적 작업 단위
- 하나의 트랜잭션에 포함된 여러 SQL은 분리될 수 없으며 전부 반영되거나 전부 취소됨
- 필요한 이유
    - 비즈니스 로직 하나가 여러 SQL로 이루어지는 경우가 대부분
    - 중간에 실패하면 데이터가 어중간한 상태로 남아 정합성이 깨짐

```tsx
생명주기
1. 시작 (BEGIN)
2. SQL 실행 (변경 사항은 아직 임시 상태)
3. 종료: COMMIT 또는 ROLLBACK
```

**스프링의 트랜잭션 관리**

- 선언적 트랜잭션: `@Transactional`을 붙이면 스프링이 AOP 프록시로 메서드 앞뒤에 BEGIN/COMMIT/ROLLBACK을 삽입
- 프록시 기반이라 생기는 제약
    - 같은 클래스 내부 메서드 호출(`this.method()`)은 프록시를 거치지 않아 적용되지 않음
    - `private` 메서드에는 적용되지 않음
    - 스프링이 관리하는 빈이어야 함
- 적용 위치: 비즈니스 로직을 담당하는 Service 계층에 붙이는 것이 원칙

**주요 속성**

| 속성 | 설명 |
| --- | --- |
| `readOnly = true` | 읽기 전용 힌트. 변경 감지(스냅샷 비교)를 생략해 성능에 유리하고 의도치 않은 쓰기를 방지 |
| `rollbackFor` | 롤백 대상 예외 지정. 기본값은 RuntimeException과 Error만 롤백, 체크 예외는 커밋됨 |
| `propagation` | 이미 진행 중인 트랜잭션이 있을 때의 동작. 기본값 `REQUIRED`(있으면 참여, 없으면 새로 생성) |
| `isolation` | 격리 수준 지정. 기본값은 DB 설정을 따름 |
| `timeout` | 제한 시간 초과 시 롤백 |

### commit / rollback

**commit**

- 트랜잭션의 모든 변경을 DB에 영구 반영하고 종료
- 커밋 이후에는 다른 트랜잭션에서도 변경 사항이 보임
- 커밋된 후에는 롤백 불가

**rollback**

- 트랜잭션 시작 이후의 모든 변경을 취소하고 시작 전 상태로 복구
- 예외 발생, 명시적 `setRollbackOnly()`, 타임아웃 시 발생

**내부 동작 원리**

- Undo Log: 변경 전 값을 기록. 롤백 시 이 기록으로 원상 복구 (원자성 보장)
- Redo Log(WAL, Write-Ahead Logging): 변경 내용을 디스크 로그에 먼저 기록. 장애 후 재시작 시 커밋된 내용을 복구 (지속성 보장)

**롤백 관련 주의점**

- 예외를 `catch`로 삼키면 스프링이 예외를 감지하지 못해 롤백되지 않음
- 체크 예외는 `rollbackFor`를 지정하지 않으면 롤백되지 않음
- 이미 `rollback-only`로 표시된 트랜잭션에 참여한 뒤 커밋을 시도하면 `UnexpectedRollbackException` 발생

### 원자성(Atomicity)

- 트랜잭션의 모든 작업이 전부 성공하거나 전부 실패해야 한다는 성질 (All or Nothing)
- 외부에서 보기에 트랜잭션은 한 번에 일어나는 하나의 연산이며 중간 상태는 관찰되지 않음

**보장 방식**

- 실패 시 Undo Log로 변경을 되돌림
- 애플리케이션은 작업 묶음을 하나의 트랜잭션 경계 안에 넣어야 함

**원자성이 깨지는 대표 상황**

- 여러 SQL을 서로 다른 트랜잭션으로 실행 (Service 메서드에 트랜잭션이 없거나 각각 커밋)
- 예외를 삼켜서 롤백이 일어나지 않음
- 체크 예외를 롤백 설정 없이 사용
- `REQUIRES_NEW`로 분리해 부분 커밋이 발생

**범위의 한계**

- DB 작업에만 적용됨. 외부 API 호출, 파일 저장, 메시지 발행은 롤백되지 않음
- 서로 다른 DB나 서비스에 걸친 작업은 분산 트랜잭션이나 보상 트랜잭션이 필요

### ACID

트랜잭션이 신뢰할 수 있으려면 갖춰야하는 4가지 성질

**Atomicity(원자성)**

- 전부 반영 또는 전부 취소

**Consistency(신뢰성)**

- 트랜잭션 전후로 DB가 정의된 규칙(제약 조건, 도메인 규칙)을 만족하는 상태를 유지
- 제약 조건(PK, FK, UNIQUE, NOT NULL, CHECK)을 위반하면 트랜잭션이 거부됨
- 비즈니스 규칙(잔액은 음수가 될 수 없음 등)은 애플리케이션과 DB가 함께 지켜야 함
- 나머지 세 성질(A, I, D)은 일관성을 달성하기 위한 수단이라는 관점도 있음

**Isolation(격리성)**

- 동시에 실행되는 트랜잭션들이 서로의 중간 상태를 볼 수 없고, 마치 순차 실행된 것처럼 동작해야 함
- 완벽한 격리는 성능 비용이 크기 때문에 격리 수준으로 정도를 조절함

**Durability(지속성)**

- 커밋된 데이터는 시스템 장애(정전, 크래시)가 발생해도 유지됨
- Redo Log를 디스크에 먼저 기록(WAL)하는 방식으로 보장

### UNIQUE 제약 조건

한 컬럼 또는 여러 컬럼 조합의 값이 테이블 내에서 중복되지 않도록 DB가 강제하는 무결성 제약

**특징**

- 내부적으로 유니크 인덱스를 생성하여 중복 여부를 빠르게 검사 (조회 성능에도 이점)
- 복합 UNIQUE는 컬럼 하나씩은 중복돼도 되고, 컬럼 조합 전체가 같을 때만 위반
- 컬럼 순서가 인덱스 활용에 영향을 줌
- NULL 처리: 대부분의 DB(MySQL, PostgreSQL 등)는 NULL을 서로 다른 값으로 취급하여 NULL은 여러 개 허용

**애플리케이션 검증과 DB 제약의 역할 분담**

- 사전 체크(`existsBy...`): 사용자에게 의미 있는 에러 응답을 주기 위한 용도
- DB UNIQUE: 데이터 무결성을 보장하는 최종 방어선
- 둘 다 필요한 이유: 사전 체크만으로는 동시 요청의 경쟁 상태(Race Condition)를 막을 수 없음
    - 두 요청이 동시에 "없음"을 확인하고 둘 다 INSERT를 시도
    - 하나는 DB가 거부함 → `DataIntegrityViolationException`
- 대응: 해당 예외를 잡아 도메인 에러(409 등)로 변환

### 낙관적 잠금(Optimistic Locking)

- 동시 수정 충돌이 드물다고 낙관하고, 데이터를 읽을 때 잠금을 걸지 않는 방식
- 수정 후 저장하는 시점에 다른 트랜잭션이 먼저 바꿨는지 검사하여 충돌을 감지
- DB의 락이 아닌 애플리케이션 레벨(버전 컬럼)로 구현

**해결하는 문제**

- Lost Update: 두 사용자가 같은 데이터를 읽고 각자 수정할 때 나중에 저장한 쪽이 앞선 변경을 덮어쓰는 문제

**JPA 구현**

- 엔티티에 `@Version` 필드(Long, Integer, Timestamp 등)를 추가
- 수정 시 UPDATE 쿼리에 버전 조건이 붙고 버전이 자동 증가

```sql
UPDATE rating SET score = ?, version = version + 1
WHERE rating_id = ? AND version = ?
```

- 영향받은 행이 0이면 다른 트랜잭션이 먼저 수정한 것으로 판단 → `ObjectOptimisticLockingFailureException` 발생 후 롤백
- 충돌 처리 방식은 개발자가 결정: 사용자에게 "다른 곳에서 수정됨" 안내(409), 최신 데이터 재조회 후 재시도 등

**비관적 잠금과 비교**

|  | 낙관적 잠금 | 비관적 잠금 |
| --- | --- | --- |
| 전제 | 충돌이 드묾 | 충돌이 잦음 |
| 구현 | 버전 컬럼(`@Version`) | DB 락(`SELECT ... FOR UPDATE`) |
| 충돌 감지 시점 | 저장(커밋) 시점 | 조회 시점부터 대기 |
| 장점 | 락이 없어 처리량이 높고 데드락 위험이 없음 | 충돌을 사전에 확실히 차단 |
| 단점 | 충돌 시 재시도·예외 처리 필요, 충돌이 잦으면 비효율 | 대기 시간 증가, 데드락 가능성 |
| 적합한 경우 | 읽기가 많고 동시 수정이 드문 데이터 (게시글, 프로필 수정) | 충돌이 잦고 정합성이 최우선인 데이터 (재고, 좌석 예약, 잔액) |
