- 트랜잭션(Transaction)

  여러 DB 작업을 하나의 작업 단위로 묶는 것. 같은 트랜잭션에 참여한 변경을 함께 확정하거나 취소하기 위한 경계.

  **이번 워크북에서의 역할**

    - `POST /movie-records`에서 평점과 즐겨찾기를 함께 저장 → 사용자가 요청한 영화 기록 전체를 하나의 작업으로 취급.
    - Repository의 `save()`마다 따로 끝내는 대신, 두 저장을 호출하는 Service 메서드에 `@Transactional` 적용.
    - 같은 트랜잭션 매니저를 사용하고 기본 전파 방식인 `REQUIRED`로 참여하면, 안쪽 Repository 작업도 바깥 Service의 트랜잭션에 합류.

  두 저장을 묶는 간단한 예시

    ```java
    @Transactional
    public void saveTogether(Rating rating, Favorite favorite) {
        ratingRepository.save(rating);
        favoriteRepository.save(favorite);
    }
    ```

  **추가 핵심 정리**

    - 기본 `REQUIRED`: 이미 트랜잭션이 있으면 참여, 없으면 새로 시작. `REQUIRES_NEW`는 독립적인 트랜잭션 → 안쪽에서 커밋한 작업은 바깥 롤백으로 취소되지 않을 수 있음.
    - 조회 메서드의 `@Transactional(readOnly = true)`: 읽기 전용 의도 전달 및 JPA 최적화에 사용. 모든 쓰기를 무조건 차단하는 장치 X.
    - 기본 프록시 방식에서는 같은 객체 안에서 `this.메서드()`로 호출하면 해당 메서드의 트랜잭션 설정이 새로 적용되지 않음. 바깥 호출에서 이미 시작한 트랜잭션은 유지.
    - 트랜잭션이 길면 DB 연결·잠금 점유 시간도 증가 → 느린 외부 API 호출까지 무조건 안에 넣기보다는 필요한 DB 작업 중심으로 범위 설정.

  Spring — @Transactional
  Spring — 트랜잭션 전파
  Spring Data JPA — 읽기 전용 트랜잭션

- commit / rollback

  트랜잭션을 어떻게 끝낼지 결정하는 동작.

    - **commit**: 현재 트랜잭션의 변경 확정.
    - **rollback**: 현재 트랜잭션에서 수행한 변경 취소. 이전에 다른 트랜잭션으로 커밋한 데이터까지 되돌리는 기능 X.

  **Spring에서 처리되는 흐름**

    - 일반적인 Service 트랜잭션은 메서드 실행 후 정상 종료하면 커밋 시도, 롤백 대상 예외가 밖으로 전달되면 롤백.
    - 기본 설정에서 `RuntimeException`과 `Error`는 롤백 대상. Checked Exception은 기본적으로 자동 롤백 대상 X → 필요하면 `@Transactional(rollbackFor = Exception.class)` 등으로 명시.
    - 메서드 안에서 예외를 잡고 정상 반환하면 프록시가 그 예외를 기준으로 롤백할 수 없음. 단, DB 오류 등으로 이미 rollback-only 상태라면 정상 반환해도 커밋 불가.

  **save / flush / commit 구분**

    - `save()`: 엔티티 저장 처리. 호출 한 번이 트랜잭션 전체의 커밋을 의미하는 것은 X.
    - `flush()`: 영속성 컨텍스트의 변경을 SQL로 DB에 반영. SQL이 실행됐어도 아직 커밋 전이면 롤백 가능.
    - 커밋 시점의 flush에서 제약 위반이 드러날 수도 있음 → Service 본문이 끝까지 실행됐다고 최종 저장 성공으로 단정 X.

  직접 SQL로 확인하는 예시

    ```sql
    START TRANSACTION;
    UPDATE rating SET score = 5 WHERE rating_id = 1;
    ROLLBACK; -- 이번 트랜잭션의 변경 취소
    ```

  위에서 `ROLLBACK` 대신 `COMMIT`을 사용하면 변경 확정. MySQL의 기본 autocommit 환경에서 여러 문장을 묶으려면 명시적으로 트랜잭션 시작.

  **주의**

    - 롤백은 DB 트랜잭션 범위에 적용. 이미 전송한 메일·외부 API 요청까지 자동 취소되는 것은 X.
    - MySQL의 `ALTER TABLE` 등은 암묵적 커밋 발생 가능 → 테이블 구조 변경까지 일반 DML처럼 롤백할 수 있다고 가정하면 안 됨.

  Spring — 롤백 규칙
  MySQL — autocommit, Commit, Rollback

- 원자성(Atomicity)

  트랜잭션을 구성하는 작업이 전부 반영되거나, 전부 취소되는 성질. **All or Nothing**.

  **이번 워크북의 예시**

    - `addToFavorites: true` 요청 → 평점 저장과 즐겨찾기 저장이 함께 성공해야 정상 완료.
    - 평점 저장 후 즐겨찾기 저장 실패 → 같은 트랜잭션의 평점 저장도 롤백. 평점만 남는 부분 성공 방지.
    - `addToFavorites: false`라면 평점만 저장하는 것이 정상 요구사항 → 원자성은 모든 테이블을 항상 바꾼다는 의미 X.

  **원자성이 깨지는 구조**

    - 평점 저장은 트랜잭션 A에서 커밋, 즐겨찾기는 별도의 트랜잭션 B에서 실행 → B가 실패해도 이미 커밋한 A는 그대로 유지.
    - 각 Repository에 트랜잭션이 있어도 두 호출을 함께 묶는 바깥 경계가 없으면, 두 저장의 원자성까지 보장하는 것은 X.
    - 같은 DB를 사용해도 독립적인 트랜잭션으로 나누거나, 중간 예외를 삼키면 의도한 전체 취소가 되지 않을 수 있음.

  **추가 핵심 정리**

    - 원자성: 한 트랜잭션의 부분 성공 방지.
    - 격리성: 여러 트랜잭션이 동시에 실행될 때 서로에게 미치는 영향 제어.
    - `@Transactional`을 붙였다고 중복 요청·동시 수정 문제까지 전부 해결되는 것은 X → UNIQUE 제약과 동시성 제어는 별도로 필요.
    - 검증할 때는 첫 저장 이후 두 번째 저장을 실패시키고, 트랜잭션이 끝난 뒤 두 테이블의 데이터를 확인. 저장 전에 하는 중복 검사에서 막힌 것만으로는 첫 저장의 롤백을 확인한 것 X.
    - 이 성질은 DB 트랜잭션의 범위에 해당. 외부 결제·메일처럼 DB 밖의 작업은 별도의 실패 복구 설계 필요.

  PostgreSQL — 트랜잭션의 All or Nothing
  Spring — 트랜잭션 전파와 독립 트랜잭션

- ACID

  트랜잭션이 갖춰야 할 네 가지 성질. **Atomicity · Consistency · Isolation · Durability**의 앞글자.

  | 성질 | 의미 | 이번 워크북에 연결하면 |
      | --- | --- | --- |
  | A — 원자성 | 모두 반영하거나 모두 취소 | 평점·즐겨찾기 중 하나만 저장되는 상황 방지 |
  | C — 일관성 | 정의한 규칙을 만족하는 상태에서 다른 유효한 상태로 전환 | 같은 회원·영화의 즐겨찾기 중복 금지 |
  | I — 격리성 | 동시에 실행되는 트랜잭션 사이의 간섭 제어 | 동시 요청에서 어떤 데이터를 읽고 변경할지 결정 |
  | D — 지속성 | 커밋한 결과를 장애 후에도 보존하도록 보장 | 확정된 영화 기록을 재시작 후에도 유지 |

  **일관성에서 주의할 점**

    - DB의 UNIQUE·외래 키·NOT NULL 같은 제약과 애플리케이션의 업무 검증이 함께 필요.
    - DB는 코드에 없는 업무 규칙까지 알아서 판단하지 않음. 예를 들어 “본인 즐겨찾기만 삭제”는 토큰의 회원 정보와 조회 조건으로 구현해야 하는 규칙.
    - 같은 회원의 평점은 하나만 허용하면서 즐겨찾기는 중복 허용하는 등, 테이블별 규칙이 다르면 그에 맞게 각각 설계.

  **격리성에서 주의할 점**

    - 트랜잭션이 있다고 모든 요청이 완전히 순서대로 실행되는 것은 X.
    - 대표적인 격리 수준: `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`.
    - 격리 수준에 따라 미확정 변경 읽기, 같은 데이터 재조회, 조건에 맞는 행의 증감 등에 대한 동작이 달라짐. 구체적인 구현 차이는 DB별 확인 필요.
    - 더 강한 격리는 동시 처리 성능·대기 시간과 맞교환 가능 → 무조건 가장 강하게 설정하는 것이 정답은 X.

  **추가 핵심 정리**

  원자성은 부분 성공, 일관성은 규칙 위반, 격리성은 동시 실행의 간섭, 지속성은 커밋 결과 유실에 대한 성질. 서로 다른 문제를 다루므로 하나만 만족한다고 나머지까지 자동 해결되는 것은 X.

  MySQL — InnoDB와 ACID
  MySQL — 트랜잭션 격리 수준

- UNIQUE 제약 조건

  지정한 컬럼 또는 컬럼 조합에 중복 값을 저장하지 못하도록 DB가 강제하는 규칙.

  **단일 UNIQUE와 복합 UNIQUE**

    - `UNIQUE(movie_id)`: 서비스 전체에서 같은 영화 ID를 한 번만 저장 가능 → 여러 회원이 같은 영화를 즐겨찾기하는 요구사항과 불일치.
    - `UNIQUE(member_id, movie_id)`: 두 값의 조합이 같을 때만 중복 → 같은 영화라도 회원이 다르면 저장 가능.
    - 예: `(1, 550)`과 `(2, 550)`은 허용, `(1, 550)`을 두 번 저장하는 것은 거부.

  워크북 Favorite 엔티티의 설정

    ```java
    @Table(
        name = "favorite",
        uniqueConstraints = @UniqueConstraint(
            columnNames = {"member_id", "movie_id"}
        )
    )
    ```

  **서버 검사와 DB 제약을 함께 두는 이유**

    - 서버의 `existsBy...`: 저장 전에 중복을 확인해 의도한 오류 code와 message 제공.
    - DB의 UNIQUE: 동시 요청이나 다른 저장 경로에서도 실제 중복 데이터가 들어가지 않도록 최종 방어.
    - 요청 A와 B가 동시에 중복 검사 → 둘 다 “없음” 확인 → 둘 다 저장 시도 가능. 일반적인 `@Transactional`만으로 이 사이의 경쟁이 사라지는 것은 X.
    - 그래서 사전 검사에서 발생한 중복과 DB 저장 시 발생한 중복을 같은 409 응답 형식으로 처리하는 과정도 필요. DB 오류 전체를 무조건 중복으로 분류하면 NOT NULL·외래 키 위반 등을 잘못 처리할 수 있음.

  **추가 핵심 정리**

    - 엔티티 어노테이션은 스키마 생성에 사용하는 정보 → 이미 운영 중인 테이블에 실제 제약이 있는지는 `SHOW CREATE TABLE favorite;` 등으로 별도 확인.
    - MySQL은 UNIQUE 인덱스에서 여러 NULL을 허용 → 반드시 값이 있어야 하는 컬럼에는 NOT NULL도 함께 설정.
    - UNIQUE 인덱스는 중복 검사를 위해 유지되므로 저장 비용도 발생. 실제 업무상 유일해야 하는 값·조합을 기준으로 설정.

  MySQL — UNIQUE 인덱스
  Spring — 무결성 제약 위반 예외

- 낙관적 잠금(Optimistic Locking)

  동시 수정 충돌이 드물다고 가정하고, 읽은 시점의 버전과 저장할 때의 버전을 비교해 충돌을 감지하는 방식. 다른 요청의 변경을 모른 채 덮어쓰는 **Lost Update** 방지에 사용.

  **동작 예시**

    - A와 B가 같은 평점의 version 0을 조회.
    - A가 먼저 수정 → DB의 version이 1로 변경.
    - B가 version 0을 기준으로 수정 시도 → 현재 버전과 불일치하므로 충돌 처리. A의 변경을 그대로 덮어쓰지 않도록 방지.

  JPA에서 버전 필드를 선언하는 예시

    ```java
    @Version
    private Long version;
    ```

  버전은 JPA가 관리. 애플리케이션에서 직접 증가시키는 방식으로 사용 X.

  갱신 SQL의 개념적인 형태

    ```sql
    UPDATE rating
    SET score = 4, version = version + 1
    WHERE rating_id = 6 AND version = 0;
    ```

  ID뿐 아니라 읽었을 때의 version도 조건에 포함. 다른 요청이 이미 버전을 바꿨다면 기대한 행을 갱신할 수 없음.

  **추가 핵심 정리**

    - 버전 충돌 시 `OptimisticLockException`이 발생하고 해당 트랜잭션은 롤백 대상. Spring의 예외 변환을 거치면 낙관적 잠금 관련 DataAccessException으로 전달될 수 있음.
    - 충돌은 flush·커밋 시점에 드러날 수도 있음. 재시도가 필요하면 실패한 트랜잭션을 그대로 이어 쓰지 말고 새 트랜잭션에서 다시 조회한 최신 값으로 판단.
    - 충돌이 잦으면 실패·재시도 비용 증가 → 비관적 잠금이나 조건부 갱신 등도 비교. 비관적 잠금은 DB 행 등을 미리 잠가 다른 작업을 대기시키는 접근.
    - 낙관적 잠금도 UPDATE 실행 시 DB 잠금이 전혀 없는 방식이라는 의미 X. 핵심은 버전으로 변경 충돌을 감지하는 것.
    - **UNIQUE와 역할 구분**: UNIQUE는 중복 행 삽입 방지, 낙관적 잠금은 기존 행의 동시 변경 충돌 감지. 아직 없는 즐겨찾기의 동시 INSERT를 `@Version`만으로 막을 수 있는 것은 X.
    - 이번 워크북의 필수 구현에는 `@Version` 추가 요구 없음. 즐겨찾기 중복 방지는 복합 UNIQUE로, 낙관적 잠금은 동시 수정 제어의 확장 개념으로 구분.

  Jakarta Persistence — 낙관적 잠금과 Version
  Hibernate — 잠금과 버전 관리
  Spring — JPA 낙관적 잠금 예외 변환
