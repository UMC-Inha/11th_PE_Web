# 🎯 핵심 키워드



- 트랜잭션(Transaction)

트랜잭션은 **함께 성공해야 하는 데이터 변경 작업을 하나의 실행 단위로 묶는 것**이다. 트랜잭션의 범위는 사용자가 요청한 업무가 어디까지 완료되어야 하는지를 기준으로 정한다.

예를 들어 영화 기록을 남기는 기능에서는 평점 저장과 즐겨찾기 저장을 하나의 서비스 메서드에서 묶을 수 있다. 같은 HTTP 요청 안에서 실행되더라도 각각 독립적으로 저장하면 전체 작업의 성공과 실패를 함께 처리하기 어렵다.

Spring에서는 다음 특성을 함께 이해해야 한다.

- **기본 전파 방식은 `REQUIRED`이다.** 기존 트랜잭션이 있으면 참여하고, 없으면 새로 시작한다. 따라서 여러 서비스 메서드에 `@Transactional`이 붙어 있어도 하나의 트랜잭션으로 실행될 수 있다.
- **트랜잭션은 필요한 범위만 유지한다.** 오래 실행되면 DB 연결이나 잠금을 오래 점유할 수 있으므로, 느린 외부 API 호출까지 무조건 포함하지 않도록 설계한다.
- **`readOnly = true`는 읽기 작업임을 알려 주는 설정이다.** 읽기 처리의 최적화에 활용되지만, 모든 환경에서 쓰기를 강제로 차단하는 기능은 아니다.

DB 트랜잭션이 되돌릴 수 있는 범위도 구분해야 한다. 트랜잭션 도중 이메일을 발송했다면 이후 DB 저장이 롤백되어도 이미 발송한 이메일은 취소되지 않는다. 외부 작업은 DB 변경과 별도로 실패 처리 방식을 설계해야 한다.

- commit / rollback

**commit은 트랜잭션의 변경 사항을 최종 확정하는 작업**이고, **rollback은 해당 트랜잭션에서 수행한 변경 사항을 취소하는 작업**이다.

JPA에서는 저장 메서드 호출, SQL 실행, 최종 확정이 서로 다른 시점에 이루어질 수 있다는 점이 중요하다.

| 동작 | 의미 |
| --- | --- |
| `save()` | 엔티티를 저장 대상으로 처리한다. SQL 실행 시점은 엔티티 상태나 ID 생성 방식 등에 따라 달라질 수 있다. |
| `flush()` | 영속성 컨텍스트의 변경 사항을 SQL로 DB에 반영한다. 아직 트랜잭션이 확정된 것은 아니다. |
| `commit` | 트랜잭션의 변경 사항을 최종 확정한다. 필요한 변경 사항은 커밋 과정에서 flush된다. |
| `rollback` | 해당 트랜잭션의 변경 사항을 취소한다. 이미 flush된 변경도 커밋 전이라면 취소할 수 있다. |

따라서 `saveAndFlush()`가 성공했다고 해서 저장이 최종 확정된 것은 아니다. 같은 트랜잭션의 뒤쪽 작업에서 실패하면 앞서 실행한 변경도 롤백될 수 있다.

Spring의 기본 롤백 규칙도 확인해야 한다.

- `RuntimeException`과 `Error`가 트랜잭션 경계 밖으로 전달되면 기본적으로 롤백한다.
- `IOException`과 같은 checked exception은 기본 롤백 대상이 아니다.
- checked exception도 롤백해야 한다면 `@Transactional(rollbackFor = IOException.class)`처럼 규칙을 지정할 수 있다.

예외를 `catch`한 뒤 무시하면 트랜잭션 관리자가 실패를 인식하지 못할 수 있다. 실패를 처리할 때는 오류 메시지뿐 아니라 **트랜잭션을 계속 진행할지, 취소할지**도 함께 고려해야 한다.

- 원자성(Atomicity)

원자성은 **트랜잭션의 일부 변경만 확정되는 상태를 허용하지 않는 성질**이다. 여러 저장 작업을 수행하더라도 하나의 작업처럼 성공하거나 취소되어야 한다.

원자성이 있다고 해서 동시 요청이 항상 순서대로 실행되는 것은 아니다. 한 요청 내부의 부분 성공을 막는 문제와 여러 요청 사이의 충돌을 처리하는 문제는 구분해야 한다.

원자성을 검증하려면 **첫 번째 저장 이후에 실패하는 상황**을 만들어야 한다. 저장 전 중복 검사에서 예외가 발생한 경우에는 취소할 변경 자체가 없으므로, 그 결과만으로 롤백 동작을 확인하기 어렵다.

새로운 평점을 저장한 뒤 의도적으로 실패시키는 서비스 메서드의 예시다.

```java
@Transactional
public void verifyRollback(Rating rating) {
    ratingRepository.saveAndFlush(rating);
    throw new IllegalStateException("롤백 동작 확인");
}
```

이 메서드를 Spring이 관리하는 서비스 빈을 통해 외부에서 호출하고, 실패한 트랜잭션이 종료된 뒤 별도 조회로 결과를 확인한다. INSERT가 실행되었어도 새 평점이 DB에 남지 않아야 한다.

롤백 검증에서는 다음 사항을 확인한다.

- 요청이 오류 응답으로 끝났는지 확인한다.
- 먼저 저장한 데이터가 실제로 취소되었는지 확인한다.
- 이전에 정상 저장한 데이터는 유지되는지 확인한다.

테스트용으로 넣은 강제 예외는 검증 후 제거해야 한다.

- ACID

ACID는 트랜잭션이 갖추어야 하는 네 가지 성질이다. 각각 해결하려는 문제가 다르므로 구분해서 이해해야 한다.

| 성질 | 의미 | 영화 서비스에서의 예 |
| --- | --- | --- |
| 원자성 — Atomicity | 작업 전체가 성공하거나 변경 사항이 모두 취소된다. | 즐겨찾기 저장에 실패하면 같은 트랜잭션의 평점 저장도 취소한다. |
| 일관성 — Consistency | 트랜잭션 전후에 데이터가 정해진 규칙을 만족한다. | 같은 회원이 같은 영화를 중복으로 즐겨찾기할 수 없다는 규칙을 유지한다. |
| 격리성 — Isolation | 동시에 실행되는 트랜잭션이 서로에게 미치는 영향을 제어한다. | 다른 요청에서 수정 중인 평점이 언제 조회 결과에 보이는지 제어한다. |
| 지속성 — Durability | 커밋된 결과가 장애 이후에도 유지되도록 보장한다. | 저장이 확정된 즐겨찾기는 서버를 재시작해도 유지된다. |

**일관성을 유지하려면 애플리케이션의 로직과 DB 제약이 함께 필요하다.** 트랜잭션을 적용해도 DB가 ‘평점은 1~5점이어야 한다’는 서비스 규칙을 자동으로 이해하지는 않는다. 입력 검증이나 DB 제약으로 규칙을 표현해야 한다.

격리성은 격리 수준에 따라 보장 범위가 달라진다. 예를 들어 아직 커밋되지 않은 값을 읽는 문제나, 같은 데이터를 다시 조회했을 때 값이 달라지는 문제를 어느 수준까지 허용할지 결정한다.

따라서 `@Transactional`을 붙였다는 사실만으로 모든 동시성 문제가 해결되었다고 판단해서는 안 된다. 업무에 따라 UNIQUE 제약이나 버전 검사 같은 추가 장치가 필요하다.

- UNIQUE 제약 조건

UNIQUE 제약은 특정 컬럼 또는 컬럼 조합의 중복을 DB에서 막는 규칙이다. 즐겨찾기에서는 `(member_id, movie_id)` 조합에 적용하여 회원별로 같은 영화가 한 번만 등록되도록 한다.

서버에서 중복 여부를 먼저 검사해도 다음과 같은 **경쟁 상황**이 발생할 수 있다.

1. 요청 A가 중복 여부를 조회하고, 아직 없다는 결과를 받는다.
2. 요청 B도 같은 조합을 조회하고, 아직 없다는 결과를 받는다.
3. 두 요청이 모두 사전 검사를 통과하여 저장을 시도한다.
4. DB의 UNIQUE 제약이 같은 조합의 데이터가 둘 다 저장되어 확정되는 것을 막는다.

중복 검사와 실제 저장 사이에는 다른 요청이 실행될 수 있다. 따라서 서버 검사는 사용자에게 명확한 오류를 전달하는 역할을 맡고, DB 제약은 여러 요청이 동시에 들어와도 데이터 규칙을 지키는 역할을 맡는다.

추가로 다음 사항을 확인해야 한다.

- **엔티티 선언과 실제 DB 구조를 함께 확인한다.** `@UniqueConstraint`를 작성했어도 기존 DB에 제약이 반드시 추가되는 것은 아니다. 특히 `ddl-auto: validate`는 스키마를 자동으로 수정하지 않는다.
- **필수 값에는 `NOT NULL`도 적용한다.** MySQL의 UNIQUE 인덱스는 NULL을 여러 개 허용하므로, 값의 존재 여부와 중복 여부는 따로 제한해야 한다.
- **DB에서 발생한 중복 오류도 처리한다.** 사전 검사를 통과한 뒤 발생한 중복 충돌도 적절한 오류 응답으로 변환해야 한다.

이때 모든 `DataIntegrityViolationException`을 중복 오류로 취급하면 안 된다. NOT NULL이나 외래 키 제약 위반도 포함될 수 있으므로, 실제로 어떤 제약을 위반했는지 구분해야 한다.

- 금(Optimistic Locking)

낙관적 잠금은 **데이터를 읽은 이후 다른 요청이 먼저 수정했는지 확인하고, 충돌이 발생하면 현재 수정을 실패시키는 방식**이다. 충돌이 자주 발생하지 않을 것이라고 가정하고 수정 시점에 검사한다.

예를 들어 두 요청이 동시에 같은 평점을 읽으면 다음과 같은 일이 발생할 수 있다.

| 순서 | 요청 A | 요청 B |
| --- | --- | --- |
| 1 | 평점 3점, 버전 1을 조회한다. | 평점 3점, 버전 1을 조회한다. |
| 2 | 평점을 5점으로 저장하고 버전을 2로 변경한다. | 기존 조회 결과를 기준으로 수정을 준비한다. |
| 3 | 저장을 완료한다. | 버전 1로 수정하려 하지만 DB의 버전이 2이므로 충돌을 감지한다. |

버전 검사가 없다면 요청 B가 요청 A의 수정 결과를 덮어쓸 수 있다. 이러한 문제를 **갱신 손실(Lost Update)**이라고 한다.

JPA에서는 엔티티에 `jakarta.persistence.Version`의 `@Version`을 적용할 수 있다.

```java
@Version
private Long version;
```

수정할 때는 개념적으로 다음과 같은 SQL이 실행된다.

```sql
UPDATE rating
SET score = 5,
    version = version + 1
WHERE rating_id = 10
  AND version = 1;
```

ID가 같아도 버전이 달라지면 수정할 행이 일치하지 않는다. JPA는 이를 낙관적 잠금 충돌로 처리한다. 버전 값은 일반적으로 JPA가 관리하며, 실제 적용 시에는 DB에도 대응하는 컬럼이 필요하다.

충돌이 발생하면 최신 데이터를 다시 조회하고 재수정 여부를 결정해야 한다. 재시도를 구현하더라도 실패한 트랜잭션을 종료한 뒤 새 트랜잭션에서 처리해야 한다.

| 장치 | 주로 방지하거나 감지하는 문제 |
| --- | --- |
| UNIQUE 제약 | 같은 회원·영화 조합의 중복 생성이다. |
| 낙관적 잠금 | 이미 존재하는 동일 데이터의 동시 수정 충돌이다. |

낙관적 잠금은 읽는 단계에서 미리 행을 잠그는 방식은 아니지만, 실제 UPDATE 과정에서 DB 잠금이 전혀 사용되지 않는다는 의미는 아니다.

또한 사용자가 오래 열어 둔 수정 화면의 충돌까지 확인하려면, 화면에서 조회했던 버전을 수정 요청에도 전달하여 비교하는 설계가 필요할 수 있다.
