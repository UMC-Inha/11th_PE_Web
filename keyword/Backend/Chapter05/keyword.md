- SOP와 CORS
    
    SOP(Same-Origin Policy)는 다른 출처의 자원에 대한 접근을 제한하는 브라우저의 보안 정책이다. 출처는 프로토콜, 호스트, 포트의 조합으로 구분하므로, localhost:5173에서 실행되는 프론트엔드와 localhost:8080에서 실행되는 백엔드는 서로 다른 출처이다. CORS는 서버가 응답 헤더를 통해 허용할 출처를 알려주어, 브라우저가 다른 출처의 응답을 JavaScript에서 사용할 수 있도록 하는 방식이다.
    
    여기서 **요청이 서버에 도착하는 것과 프론트엔드에서 응답을 읽는 것은 별개**라는 점이 중요하다. 단순한 GET 요청은 서버에서 정상 처리되어도 CORS 응답 헤더가 없으면 프론트엔드에서 결과를 읽지 못할 수 있다. 반면 JSON을 전송하거나 Authorization 헤더를 사용하는 등의 요청은 브라우저가 먼저 OPTIONS 방식의 사전 요청인 **프리플라이트**를 보낼 수 있다. 이 검사가 실패하면 실제 요청은 전송되지 않는다. 따라서 워크북의 “요청 자체는 서버에 도착한다”는 설명은 모든 요청에 적용되는 것은 아니다. 
    
    예를 들어 닉네임 중복 확인 API가 Postman에서는 정상 동작하는데 브라우저에서 실패한다면, 브라우저 개발자 도구의 Network 탭에서 요청의 Origin과 서버의 Access-Control-Allow-Origin을 비교해볼 수 있다. 서버가 localhost:5173만 허용했는데 화면을 localhost:5174에서 실행했다면 허용 목록과 실제 출처가 일치하지 않는 것이다.
    
    또한 **CORS는 로그인이나 접근 권한 검사를 대신하지 않는다.** 브라우저 밖의 프로그램도 API를 호출할 수 있으므로, 특정 출처만 허용했다고 해서 API 자체가 보호되는 것은 아니다. 사용자 인증과 데이터 접근 권한은 서버에서 별도로 검사해야 한다.
    
- Same-Origin과 Same-Site의 차이
    
    Same-Origin은 프로토콜, 호스트, 포트가 모두 같은 경우를 의미한다. Same-Site는 현대 브라우저의 schemeful same-site 기준으로 **프로토콜과 등록 가능 도메인**을 비교하며, 서브도메인과 포트는 구분하지 않는다. 따라서 워크북의 “등록 가능 도메인만 같으면 된다”는 설명에는 프로토콜도 확인해야 한다는 조건을 보충할 필요가 있다. 
    
    예를 들어 https://app.example.com과 https://api.example.com은 호스트가 달라 서로 다른 출처이지만, 프로토콜과 등록 가능 도메인인 example.com이 같으므로 같은 사이트이다. 반면 http://app.example.com과https://api.example.com은 프로토콜이 달라 같은 사이트로 보지 않는다.
    
    등록 가능 도메인은 단순히 주소의 마지막 두 부분을 뜻하지 않는다. 예를 들어 app.example.co.kr의 등록 가능 도메인은 co.kr이 아니라 example.co.kr이다.
    
    이 구분이 중요한 이유는 **응답 접근 허용과 쿠키 전송 조건을 서로 다르게 판단하기 때문**이다. 프론트엔드와 API 서버가 같은 사이트라도 출처가 다르면 브라우저의 fetch 요청에 CORS 설정이 필요할 수 있다. 반대로 CORS를 허용했다고 해서 쿠키가 무조건 전송되는 것도 아니다. 쿠키의 Domain, Path, Secure, SameSite와 요청의 credentials 설정 등을 함께 확인해야 한다.
    
- 쿠키의 SameSite 속성
    
    SameSite는 다른 사이트에서 시작된 요청에 쿠키를 함께 전송할지를 제어하는 속성이다. 사용자의 브라우저가 로그인 쿠키를 자동으로 보내는 특성을 악용하는 **CSRF 공격을 줄이는 데 도움**을 준다.
    
    - **Strict**: 같은 사이트에서 발생한 요청에만 쿠키를 전송한다. 외부 사이트의 링크를 눌러 처음 들어오는 요청에는 쿠키가 빠질 수 있어, 사용성이 불편해질 수 있다.
    - **Lax**: 같은 사이트의 요청에는 쿠키를 보내고, 다른 사이트에서 들어오는 경우에는 일반적으로 링크 클릭과 같은 최상위 페이지 이동의 안전한 메서드 요청에 전송한다. 다른 사이트에서 실행한 일반적인 fetch 요청이나 POST 요청에는 전송하지 않는다.
    - **None**: 다른 사이트에서 시작된 요청에도 쿠키를 전송할 수 있도록 허용하며, Secure 속성을 함께 설정해야 한다. 다만 브라우저의 서드파티 쿠키 차단 정책까지 해제하는 것은 아니다.
    
    예를 들어 로그인 쿠키를 사용하는 프론트엔드와 백엔드가 서로 다른 사이트라면, SameSite=None과 Secure 설정을 검토해야 한다. 다른 출처에 대한 fetch에서 쿠키를 포함하려면 credentials를 include로 설정하고, 서버도 명시적인 프론트엔드 출처와 자격 증명 사용을 허용해야 한다. 이 경우 Access-Control-Allow-Origin에 별표(*)를 사용할 수 없다.
    
    SameSite, Secure, HttpOnly는 역할도 다르다. SameSite는 사이트 간 요청에서의 쿠키 전송, Secure는 보안 연결을 통한 전송, HttpOnly는 JavaScript의 쿠키 읽기 제한을 담당한다. 따라서 하나만 설정하면 다른 보안 조건까지 해결된다고 생각하면 안 된다.
    
- 복합 UNIQUE 제약을 사용하는 이유는?
    
    복합 UNIQUE 제약은 여러 컬럼을 묶어서 **그 값의 조합이 중복되지 않도록 보장하는 제약**이다. 워크북에서는 평점과 즐겨찾기 테이블의 member_id와 movie_id를 묶어, 같은 회원이 같은 영화에 데이터를 중복 등록하지 못하도록 한다.
    
    예를 들어 회원 1이 영화 550에 평점을 등록했다면 회원 1과 영화 550의 조합은 다시 저장할 수 없다. 하지만 회원 1이 영화 155에 평점을 남기거나, 회원 2가 영화 550에 평점을 남기는 것은 가능하다. member_id 하나에만 UNIQUE를 걸면 회원이 평점을 하나만 남길 수 있고, movie_id 하나에만 걸면 영화 하나에 한 명만 평점을 남길 수 있어 요구사항과 달라진다.
    
    특히 중요한 점은 **애플리케이션의 중복 확인만으로는 동시 요청을 막기 어렵다**는 것이다. 두 요청이 거의 동시에 들어오면 둘 다 “아직 등록되지 않았다”고 조회한 뒤 저장을 시도할 수 있다. 이때 데이터베이스의 UNIQUE 제약이 최종적으로 중복 저장을 막는다. 사전 중복 검사는 사용자에게 안내하기 위한 과정이고, DB 제약은 데이터의 일관성을 지키는 마지막 방어선인 셈이다.
    
    평점을 수정하는 기능이라면 기존 행을 수정하도록 구현하고, 중복 등록을 오류로 처리할 기능이라면 제약 위반을 잡아 409 Conflict 등의 응답으로 변환할 수 있다. 또한 MySQL의 UNIQUE 인덱스는 NULL을 여러 개 허용하므로, 반드시 값이 있어야 하는 회원 ID와 영화 ID에는 워크북처럼 **NOT NULL도 함께 적용**해야 한다.
    
- 외부 Open API 연동 시 API Key를 프론트/백엔드 중 어디에 두어야 안전한가?
    
    **비밀로 유지해야 하는 API Key는 백엔드에 보관하는 것이 원칙**이다. 브라우저에 전달된 JavaScript와 네트워크 요청은 사용자가 확인할 수 있으므로, 프론트엔드 코드에 포함된 키는 숨겨진 값으로 취급할 수 없다.
    
    프론트엔드의 .env 파일에 저장하면 안전하다고 생각하기 쉽지만, 환경 변수는 그 자체로 비밀 저장소가 아니다. 예를 들어 Vite의 VITE_ 접두사가 붙은 환경 변수는 클라이언트 코드에 노출된다. .gitignore는 Git 저장소에 파일이 올라가는 것을 막을 뿐, 빌드 결과나 브라우저 요청에 포함되는 값까지 숨겨주지는 않는다. 
    
    워크북은 영화 목록과 상세 정보를 프론트엔드가 TMDB에서 직접 조회하도록 구성한다. 이 구조에서는 브라우저에서 사용하는 키나 토큰이 노출될 수 있다는 점을 이해해야 한다. **조회하는 데이터가 공개되어 있다는 것과, 호출에 사용하는 인증 정보가 공개되어도 된다는 것은 별개의 문제**이다.
    
    키를 비밀로 유지해야 한다면 프론트엔드는 우리 백엔드에 영화 검색을 요청하고, 백엔드가 보관한 키로 외부 API를 호출한 뒤 필요한 결과만 반환하도록 구성할 수 있다. 다만 백엔드에 키를 숨기더라도 누구나 우리 API를 무제한 호출할 수 있다면 사용량이 소진될 수 있으므로, 호출 횟수 제한이나 캐시도 함께 고려해야 한다.
    
    반대로 제공자가 브라우저용 공개 키로 설계한 값이라면 프론트엔드에서 사용할 수 있다. 이 경우에도 제공자가 지원하는 도메인 제한, API별 권한 제한, 사용량 제한 등을 적용해야 한다. 실수로 비밀 키를 공개했다면 코드에서 삭제하는 것만으로 끝내지 않고, 기존 키를 폐기하고 새로 발급해야 한다.
