- SOP와 CORS
  - SOP(Same-Origin Policy, 동일 출처 정책)는 브라우저에서 서로 다른 출처의 리소스에 접근하는 것을 제한하는 보안 정책이다.
  - Origin은 프로토콜(Scheme), 호스트(Host), 포트(Port)의 조합으로 결정된다.
  - 예를 들어 **`https://example.com`**과 **`http://example.com`**은 프로토콜이 다르므로 서로 다른 Origin이다.
  - SOP는 한 출처의 스크립트가 다른 출처의 데이터를 임의로 읽는 것을 제한하여 사용자 정보를 보호한다.
  - CORS(Cross-Origin Resource Sharing)는 서버가 다른 Origin의 브라우저 요청을 허용할 수 있도록 하는 규칙이다.
  - 서버는 **`Access-Control-Allow-Origin`** 등의 HTTP 응답 헤더를 통해 허용할 출처를 지정한다.
  - 일부 요청은 실제 요청 전에 **`OPTIONS`** 메서드로 프리플라이트 요청을 수행한다.
  - CORS는 브라우저의 응답 접근을 제어하는 정책이며, 서버의 인증 및 권한 검사를 대체하지 않는다.
  - 따라서 프런트엔드에서 CORS 오류가 발생하면 서버의 CORS 설정과 요청 헤더를 함께 확인해야 한다.
- Same-Origin과 Same-Site의 차이
  - **Same-Origin**은 프로토콜, 호스트, 포트가 모두 같을 때 동일 출처로 판단하는 개념이다.
  - **Same-Site**는 쿠키 보안 등의 맥락에서 사이트 경계를 기준으로 판단하는 개념이다.
  - 일반적으로 Same-Site는 스킴과 등록 가능 도메인(eTLD+1)을 기준으로 판단하며, 포트는 구분하지 않는다.
  - 예를 들어 **`https://app.example.com`**과 **`https://api.example.com`**은 호스트가 다르므로 Same-Origin은 아니지만, 일반적인 조건에서는 Same-Site다.
  - **`https://example.com`**과 **`http://example.com`**은 프로토콜이 다르므로 Same-Origin이 아니다.
  - 또한 스킴을 고려하는 현대적인 Same-Site 판단에서는 HTTPS와 HTTP의 조합을 서로 다른 사이트로 취급한다.
  - Same-Origin은 주로 브라우저의 출처 간 접근 제한과 관련되고, Same-Site는 쿠키 전송 및 CSRF 방어와 관련된다.
  - 따라서 두 개념은 서로 대체할 수 없으며, API 통신과 쿠키 보안을 설계할 때 각각 구분해서 이해해야 한다.
- 쿠키의 SameSite 속성
  - **`SameSite`**는 쿠키를 다른 사이트에서 발생한 요청에 어느 범위까지 포함할지 결정하는 속성이다.
  - **`Strict`**는 기본적으로 Same-Site 요청에만 쿠키를 전송하므로 외부 사이트를 통한 요청에서 쿠키 노출을 줄인다.
  - **`Lax`**는 Same-Site 요청에 쿠키를 전송하며, 일반적으로 외부 사이트에서 시작된 최상위 페이지 이동 중 안전한 HTTP 메서드의 요청에도 쿠키를 허용한다.
  - ***`None`***은 크로스 사이트 요청에도 쿠키를 전송하도록 허용하며, 일반적으로 **`Secure`** 속성을 함께 설정해야 한다.
  - **`Secure`**는 쿠키를 HTTPS 연결에서만 전송하도록 제한하는 속성이다.
  - **`SameSite`** 설정은 CSRF(Cross-Site Request Forgery) 공격의 위험을 줄이는 데 도움이 된다.
  - 다만 **`SameSite`**만으로 모든 CSRF 공격을 방지할 수 있는 것은 아니므로 CSRF 토큰이나 Origin 검증 등을 함께 고려해야 한다.
  - 프런트엔드와 백엔드가 다른 사이트에 있다면 쿠키 설정뿐 아니라 CORS의 자격 증명 설정도 확인해야 한다.
  - 쿠키의 실제 전송 여부는 브라우저 정책, 요청 방식, 도메인 및 경로 설정 등에 따라서도 달라진다.
- 복합 UNIQUE 제약을 사용하는 이유는?
  - **UNIQUE 제약 조건**은 특정 컬럼의 값이 중복되지 않도록 데이터베이스에서 보장하는 제약 조건이다.
  - **복합 UNIQUE 제약**은 두 개 이상의 컬럼을 하나의 조합으로 묶어 중복을 제한하는 방식이다.
  - 단일 컬럼의 값은 중복될 수 있지만, 지정된 컬럼들의 조합은 중복될 수 없도록 설정할 수 있다.
  - 예를 들어 사용자마다 같은 상품을 한 번만 찜할 수 있도록 **`UNIQUE(user_id, product_id)`**를 설정할 수 있다.
  - 이 경우 같은 사용자가 같은 상품을 여러 번 등록하는 것은 막지만, 다른 사용자가 해당 상품을 찜하는 것은 허용한다.
  - 복합 UNIQUE 제약은 애플리케이션 코드만으로 중복을 검사할 때 발생할 수 있는 동시 요청 문제를 방지하는 데 도움이 된다.
  - 중복 검사 후 INSERT를 수행하는 사이에 다른 요청이 들어오더라도 데이터베이스가 제약 조건을 최종적으로 보장한다.
  - 따라서 좋아요, 찜 목록, 사용자별 설정, 특정 그룹 내 이름 등 조합의 유일성이 필요한 데이터에 유용하다.
  - 다만 데이터베이스 종류에 따라 UNIQUE 제약에서 **`NULL`**을 처리하는 방식이 다를 수 있으므로 설계 시 확인해야 한다.
- 외부 Open API 연동 시 API Key를 프론트/백엔드 중 어디에 두어야 안전한가?
  - **일반적으로 비밀 API Key는 백엔드에 보관하는 것이 안전하다.**
  - 프런트엔드에 포함된 API Key는 자바스크립트 번들, 브라우저 개발자 도구, 네트워크 요청 등을 통해 노출될 수 있다.
  - 프런트엔드 환경 변수에 저장하더라도 빌드 과정에서 클라이언트 코드에 포함되면 비밀 정보로 보호되지 않는다.
  - 백엔드에서는 환경 변수나 비밀 관리 서비스를 이용해 API Key를 관리하고, 외부 API 요청을 대신 수행할 수 있다.
  - 이 구조에서는 브라우저가 백엔드에 요청하고, 백엔드가 API Key를 사용해 외부 API를 호출한 뒤 필요한 결과만 반환한다.
  - 백엔드에 API Key를 보관하면 키의 접근 권한, 사용량, 호출 제한, 로그 등을 관리하기도 쉽다.
  - 공개적으로 사용하도록 설계된 클라이언트용 키는 프런트엔드에서 사용할 수 있지만, 허용 도메인 제한과 권한 최소화 등 별도의 보호 설정이 필요하다.
  - **`.env`** 파일을 사용하더라도 프런트엔드 빌드 도구에서 공개용으로 노출되는 환경 변수는 비밀로 취급하면 안 된다.
  - API Key가 이미 외부에 노출되었다면 키를 폐기하거나 재발급하고, 사용 내역을 확인해야 한다.
  - 따라서 **비밀 키는 백엔드에 보관하고, 프런트엔드에는 필요한 API 기능만 제공하는 구조**가 일반적인 보안 설계 원칙이다.
