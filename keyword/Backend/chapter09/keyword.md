- Swagger / OpenAPI
  - OpenAPI는 REST API의 구조와 명세를 표준화된 형식으로 정의하는 규격이다.
    - API의 URL, HTTP 메서드, 요청 파라미터, 응답 데이터, 인증 방식 등을 문서화할 수 있다.
  - Swagger는 OpenAPI 명세를 기반으로 API 문서를 시각화하거나 테스트할 수 있도록 지원하는 도구 모음이다.
    - 개발자는 Swagger UI를 통해 API 명세를 웹 화면에서 확인하고 직접 요청을 실행할 수 있다.
    - 이를 통해 프론트엔드와 백엔드 개발자가 API의 동작 방식과 데이터 형식을 공유할 수 있다.
    - API 문서를 별도로 수작업으로 작성하는 부담을 줄이고 명세와 구현 간의 불일치를 줄일 수 있다.
- 단위 테스트
  - 단위 테스트는 함수, 메서드, 클래스 등 작은 코드 단위가 의도한 대로 동작하는지 검증하는 테스트이다.
  - 특정 기능의 입력값에 대해 기대한 결과값이 반환되는지 확인한다.
  - 일반적으로 테스트 대상 외부의 데이터베이스, API, 다른 객체 등의 의존성은 분리하여 테스트한다.
  - 이를 통해 개별 기능의 오류를 빠르게 발견하고 원인을 쉽게 파악할 수 있다.
  - 테스트 대상이 다른 기능이나 환경에 영향을 받지 않도록 독립적으로 실행하는 것이 중요하다.
  - 단위 테스트는 코드 변경 시 기능의 정확성을 확인하고 유지보수성을 높이는 데 활용된다.
- 통합 테스트
  - 통합 테스트는 여러 모듈이나 구성 요소가 결합되어 함께 동작할 때 정상적으로 작동하는지 검증하는 테스트이다.
  - 개별 기능의 동작뿐 아니라 모듈 간 데이터 전달, 호출 관계, 상호작용 등을 확인한다.
  - 예를 들어 Controller, Service, Repository가 연결되어 요청을 처리하고 데이터베이스에 저장하는 과정 등을 검증한다.
  - 단위 테스트에서 확인하기 어려운 구성 요소 간의 연결 문제나 데이터 처리 오류를 발견할 수 있다.
  - 실제 환경과 유사한 조건에서 테스트하되 외부 시스템에 대한 의존성은 필요에 따라 Mock이나 Stub으로 대체할 수 있다.
  - 통합 테스트는 여러 구성 요소가 실제로 연결되었을 때 발생하는 문제를 확인하는 데 목적이 있다.
- Mock, Stub
  테스트 대상 코드가 DB, 외부 API, 이메일 서비스, 다른 클래스 등에 의존하고 있다면, 이러한 의존성을 실제로 실행하지 않고도 테스트할 수 있도록 가짜 객체를 만들어 사용한다.
  1. Mock : **의존 객체의 상호작용을 검증하기 위한 객체**

     Mock은 테스트 대상이 의존 객체의 메서드를 올바르게 호출했는지 확인하기 위해 사용한다.

     단순히 특정 값을 반환하는 것을 넘어, 특정 메서드가 호출되었는지, 몇 번 호출되었는지, 어떤 인자가 전달되었는지 등을 검증할 수 있다.

  2. Stub : **미리 정해진 결과를 반환하는 객체**

     Stub은 테스트 대상이 의존 객체를 호출했을 때 특정 결과를 반환하도록 미리 설정해 놓은 객체이다.

     테스트 대상이 의존 객체로부터 어떤 결과를 받는지 통제하여, 그 결과에 따른 테스트 대상의 동작을 검증하는 데 목적이 있다.
  **정리하면 Stub은 테스트에 필요한 상황과 데이터를 만들어 주는 역할이고, Mock은 테스트 대상이 의존 객체와 올바르게 상호작용했는지 확인하는 역할이다.**
- given-when-then
  - given-when-then은 테스트 코드를 세 가지 단계로 구분하여 작성하는 테스트 구성 패턴이다.
    - Given은 테스트를 실행하기 위한 조건, 데이터, 환경 등을 준비하는 단계이다.
    - When은 준비된 조건에서 테스트 대상의 특정 동작을 실행하는 단계이다.
    - Then은 동작 실행 후 반환값, 상태 변화, 호출 결과 등이 기대한 결과와 일치하는지 검증하는 단계이다.
  - 각 단계가 명확하게 구분되면 테스트 코드의 의도와 검증 내용을 쉽게 파악할 수 있다.
  - 테스트 코드의 가독성과 유지보수성을 높이며, 일반적으로 단위 테스트와 통합 테스트 모두에 활용된다.
- 회귀 테스트
  - 회귀 테스트는 기존 코드의 수정, 기능 추가, 버그 수정 등으로 인해 기존에 정상적으로 동작하던 기능이 손상되지 않았는지 확인하는 테스트이다.
  - 코드 변경이 새로운 문제를 발생시키거나 기존 기능에 영향을 주는지 검증하는 데 목적이 있다.
  - 기존에 발견했던 버그를 재현하는 테스트를 추가하여 동일한 문제가 다시 발생하지 않는지 확인할 수 있다.
  - 회귀 테스트는 단위 테스트, 통합 테스트, 엔드 투 엔드 테스트 등 다양한 테스트 수준에서 수행할 수 있다.
  - 자동화된 테스트를 활용하면 코드 변경 후 반복적으로 검증할 수 있어 개발 과정에서 안정성을 높일 수 있다.
  ### **1. 단위 테스트 (Unit Test)**
  - 단위 테스트는 함수, 메서드, 클래스 등 작은 단위의 코드가 의도한 대로 동작하는지 검증하는 테스트이다.
  - 외부 의존성을 분리하여 테스트 대상의 로직에 집중한다.
  - 주로 Mock이나 Stub을 활용해 DB, API 등의 의존성을 대체한다.
  - 테스트 속도가 빠르고 오류 발생 시 원인을 파악하기 쉽다.
  ### **2. 통합 테스트 (Integration Test)**
  - 통합 테스트는 여러 모듈이나 구성 요소가 연결되어 함께 정상적으로 동작하는지 검증하는 테스트이다.
  - 개별 구성 요소뿐 아니라 구성 요소 간 데이터 전달과 상호작용을 확인한다.
  - 실제 DB, API, 프레임워크 환경 등을 연결하여 테스트하는 경우가 많다.
  - 예를 들어, Controller, Service, Repository가 연결되어 회원 데이터를 조회하거나 저장하는 과정 등을 검증하는 테스트이다.
  - 단위 테스트에서 발견하기 어려운 구성 요소 간 연결 문제나 설정 오류 등을 확인할 수 있다.
  ### **3. 엔드 투 엔드 테스트 (E2E Test)**
  - 엔드 투 엔드 테스트는 실제 사용자의 행동 흐름을 기준으로 시스템 전체가 정상적으로 동작하는지 검증하는 테스트이다.
  - 사용자 요청부터 처리, 응답, 결과 확인까지 전체 흐름을 검증한다.
  - 실제 환경과 유사하게 구성하여 여러 시스템과 구성 요소가 함께 동작하는지 확인한다.
  - 예를 들어, 사용자가 로그인한 뒤 게시글을 작성하고 작성된 게시글이 화면에 정상적으로 표시되는 과정을 검증하는 테스트이다.
  - 시스템 전체의 기능과 사용자 관점의 동작을 확인할 수 있지만, 실행 속도가 느리고 구성 및 유지 비용이 높은 편이다.
