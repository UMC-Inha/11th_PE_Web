- 3계층 아키텍처 이외에 어떤 아키텍처들이 있을까?
    
    # 3계층 아키텍처 이외의 아키텍처
    
    ## 아키텍처란?
    
    > 소프트웨어를 구성하는 요소들의 **역할을 나누고, 서로 어떻게 연결할지 정하는 구조**
    > 
    
    도서 대여 서비스를 만든다면 사용자 요청을 처리하는 기능, 대여 가능 여부를 판단하는 기능, DB에 데이터를 저장하는 기능 등이 필요하다.
    
    아키텍처는 이러한 기능을 **어디에 배치하고 어떤 방식으로 협력하게 할 것인지** 결정하는 기준이다.
    
    3계층 아키텍처에서는 일반적으로 다음과 같이 책임을 나눈다.
    
    | 계층 | 역할 | 예시 |
    | --- | --- | --- |
    | 표현 계층 | 사용자 입력과 출력 처리 | 요청 수신, 응답 반환 |
    | 비즈니스 계층 | 서비스의 업무 규칙 처리 | 대여 가능 여부 확인 |
    | 데이터 접근 계층 | 데이터 저장소에 접근 | 도서 조회, 대여 기록 저장 |
    
    다만 **논리적인 계층인 Layer**와 **물리적인 실행·배포 단위인 Tier**는 구분할 필요가 있다.
    
    ```
    Layer → 코드의 책임을 어떻게 나누는가?
    Tier  → 시스템을 어떤 실행 환경으로 나누는가?
    ```
    
    예를 들어 Controller, Service, Repository를 나누더라도 하나의 애플리케이션에서 함께 실행할 수 있다.
    
    즉, **코드를 세 계층으로 나누었다고 반드시 서버도 세 개가 필요한 것은 아니다.**
    
    ---
    
    ## 모놀리식 아키텍처
    
    > 여러 기능을 **하나의 애플리케이션 단위로 구성하고 배포**하는 방식
    > 
    
    회원 관리, 도서 조회, 대여 처리 기능을 하나의 애플리케이션에 포함하는 구조이다.
    
    ```
    도서 대여 애플리케이션
    ├─ 회원 관리
    ├─ 도서 조회
    ├─ 대여 처리
    └─ 알림 처리
             ↓
            DB
    ```
    
    기능들이 같은 애플리케이션 안에 있기 때문에 내부 함수나 메서드 호출로 협력할 수 있다.
    
    초기에는 개발 환경과 배포 구성이 비교적 단순하고, 하나의 애플리케이션 안에서 요청의 처리 흐름을 따라가기 쉽다는 장점이 있다.
    
    반면 규모가 커지고 기능 간 의존성이 복잡해지면, 작은 변경이 다른 기능에 영향을 줄 수 있다. 특정 기능만 수정하더라도 애플리케이션 전체를 다시 배포해야 할 수 있다.
    
    | 장점 | 고려할 점 |
    | --- | --- |
    | 초기 개발과 배포 구성이 비교적 단순함 | 기능별 독립 배포가 어려움 |
    | 내부 기능을 직접 호출할 수 있음 | 기능 간 의존성이 복잡해질 수 있음 |
    | 한 애플리케이션 안에서 흐름을 파악하기 쉬움 | 특정 기능만 별도로 확장하기 어려움 |
    
    **모놀리식이라고 해서 모든 코드를 하나의 파일에 작성하는 것은 아니다.**
    
    내부를 회원, 도서, 대여 등의 모듈로 구분하고 각 모듈의 경계를 명확하게 관리할 수도 있다. 이러한 구조를 **모듈러 모놀리스**라고 부른다.
    
    ---
    
    ## 마이크로서비스 아키텍처
    
    > 업무 기능을 **독립적으로 배포할 수 있는 여러 서비스로 분리**하는 방식
    > 
    
    모놀리식에서 하나로 묶여 있던 기능을 업무 단위에 따라 나눈다.
    
    ```
    회원 서비스 <- API 또는 메시지 -> 대여 서비스
                                      <->
                                   도서 서비스
    ```
    
    예를 들어 회원 서비스는 회원 정보를, 도서 서비스는 도서 정보를, 대여 서비스는 대여 업무를 책임진다.
    
    각 서비스는 자신의 데이터를 소유하고, 다른 서비스는 API나 메시지 등 정해진 방식으로 필요한 기능을 요청한다.
    
    여기서 데이터를 독립적으로 관리한다는 것은 **다른 서비스의 테이블에 직접 접근하는 방식으로 강하게 결합하지 않는 것**을 의미한다. 반드시 서비스마다 별도의 물리적 DB 서버를 하나씩 두어야 한다는 뜻은 아니다.
    
    ### 장점
    
    - 서비스별로 독립적인 배포가 가능하다.
    - 부하가 큰 서비스만 별도로 확장할 수 있다.
    - 업무별 책임과 개발 범위를 나누기 쉽다.
    
    ### 고려할 점
    
    - 서비스 사이의 네트워크 통신이 실패할 수 있다.
    - 여러 서비스에 걸친 데이터 일관성을 관리해야 한다.
    - 배포, 모니터링, 장애 추적이 복잡해진다.
    
    예를 들어 대여 서비스의 처리는 성공했지만 알림 서비스 호출은 실패할 수 있다. 이런 상황에서는 재시도나 후속 처리 방법을 설계해야 한다.
    
    → 마이크로서비스는 **서비스를 작게 나누는 것뿐 아니라, 분리된 서비스가 실패 상황에서도 협력하도록 설계하는 방식**이다.
    
    ---
    
    ## 이벤트 기반 아키텍처
    
    > 시스템에서 발생한 사건을 전달하고, 필요한 구성 요소가 이를 받아 처리하는 방식
    > 
    
    이벤트는 `회원 가입 완료`, `도서 대여 완료`처럼 **이미 발생한 사실**을 표현한다.
    
    ```
    대여 처리 완료
          ↓
    '도서 대여 완료' 이벤트 발행
          ↓
    메시지 브로커 등을 통해 전달
          ├─ 알림 기능 → 대여 안내 발송
          └─ 통계 기능 → 대여 통계 갱신
    ```
    
    대여 기능이 알림과 통계의 세부 구현을 직접 알 필요 없이, 이벤트를 발행하면 각 기능이 필요한 작업을 수행할 수 있다.
    
    | 구성 요소 | 역할 |
    | --- | --- |
    | 이벤트 생산자 | 사건이 발생했음을 알림 |
    | 이벤트 전달 경로 | 이벤트를 소비자에게 전달 |
    | 이벤트 소비자 | 이벤트를 받아 필요한 작업 수행 |
    
    이 구조는 기능 사이의 결합을 줄이고, 하나의 사건에 여러 기능이 반응하도록 만들기 좋다.
    
    다만 비동기 처리에서는 대여가 완료된 직후에도 통계가 아직 갱신되지 않았을 수 있다. 또한 전달 방식에 따라 같은 이벤트가 다시 전달될 수도 있다.
    
    따라서 다음을 고려해야 한다.
    
    - 이벤트 처리에 실패했을 때 어떻게 재시도할 것인가?
    - 같은 이벤트를 여러 번 받아도 문제가 없는가?
    - 이벤트 처리 순서가 바뀌어도 괜찮은가?
    
    여기서 **같은 요청이나 이벤트를 반복 처리해도 의도한 결과가 중복으로 발생하지 않도록 하는 성질**을 멱등성이라고 한다.
    
    예를 들어 같은 대여 완료 이벤트를 두 번 받아도 통계가 두 번 증가하지 않도록 처리할 수 있다.
    
    ---
    
    ## 헥사고날 아키텍처
    
    > 핵심 업무 로직과 외부 기술을 포트와 어댑터로 분리하는 방식
    > 
    
    헥사고날 아키텍처는 **Ports and Adapters 아키텍처**라고도 한다.
    
    | 구성 요소 | 역할 | 예시 |
    | --- | --- | --- |
    | 핵심 로직 | 업무 규칙 수행 | 대여 가능 여부 판단 |
    | 포트 | 외부와 상호작용하는 계약 | 도서 조회·저장 인터페이스 |
    | 어댑터 | 특정 기술을 포트에 연결 | MySQL 저장 구현, HTTP 요청 처리 |
    
    예를 들어 대여 로직이 직접 SQL을 작성하고 MySQL 연결을 관리한다면, 업무 규칙과 DB 접근 코드가 밀접하게 연결된다.
    
    이를 분리하면 대여 로직은 다음과 같은 기능만 요구할 수 있다.
    
    ```
    도서를 조회한다.
    대여 기록을 저장한다.
    ```
    
    실제로 MySQL에 접근하는 방법은 별도의 어댑터가 담당한다.
    
    ```
    HTTP 요청 처리 어댑터
              ↓
         입력 포트
              ↓
         대여 업무 로직
              ↓
         출력 포트
              ↑
    MySQL 저장 어댑터가 구현
    ```
    
    이렇게 구성하면 테스트할 때 실제 MySQL 대신 테스트용 저장 구현을 연결하기 쉬워진다.
    
    → 핵심은 육각형이라는 모양 자체가 아니라 **업무 로직을 외부 기술의 세부 구현에서 분리하는 것**이다.
    
    ---
    
    ## 클린 아키텍처
    
    > **업무 규칙을 중심에 두고, 코드의 의존성이 안쪽을 향하도록** 구성하는 방식
    > 
    
    대표적인 구성 요소는 다음과 같다.
    
    | 구성 요소 | 역할 |
    | --- | --- |
    | Entities | 핵심 업무 규칙 |
    | Use Cases | 애플리케이션이 수행하는 작업과 흐름 |
    | Interface Adapters | 외부 데이터와 내부 모델 사이의 변환 |
    | Frameworks & Drivers | DB, 웹 프레임워크 등의 기술 요소 |
    
    예를 들어 도서 대여 서비스에서는 다음과 같이 나눌 수 있다.
    
    ```
    핵심 업무 규칙
    → 대여 가능한 상태인지 판단
    
    유스케이스
    → 도서 조회 → 대여 조건 확인 → 대여 기록 저장
    
    외부 기술
    → HTTP 요청 처리, MySQL 접근
    ```
    
    중요한 것은 **안쪽의 업무 규칙이 바깥쪽의 구체적인 기술을 직접 알아야 하지 않도록 만드는 것**이다.
    
    대여 유스케이스가 DB 저장 기능을 필요로 하더라도, MySQL 구현에 직접 의존하는 대신 안쪽에 정의한 인터페이스를 이용할 수 있다.
    
    이때 **실행 중 호출되는 방향**과 **소스 코드의 의존성 방향**은 다를 수 있다. 외부 구현을 실행하더라도 내부 코드가 그 구현 클래스를 직접 참조하지 않도록 구성할 수 있기 때문이다.
    
    헥사고날 아키텍처와 공통점이 많지만, 클린 아키텍처는 업무 규칙의 계층과 의존성 규칙을 특히 강조한다.
    
    ---
    
    ## 아키텍처를 구분하는 기준
    
    위 아키텍처들은 모두 같은 기준으로 분류된 것은 아니다.
    
    | 구분 기준 | 관련 아키텍처 |
    | --- | --- |
    | 책임을 어떤 계층으로 나누는가? | 계층형 아키텍처 |
    | 어떤 단위로 실행·배포하는가? | 모놀리식, 마이크로서비스 |
    | 구성 요소가 어떻게 소통하는가? | 이벤트 기반 |
    | 업무 로직과 외부 기술의 의존성을 어떻게 관리하는가? | 헥사고날, 클린 |
    
    따라서 하나만 선택해야 하는 관계는 아니다.
    
    예를 들어 **모놀리식 애플리케이션 내부에 클린 아키텍처를 적용**하거나, **마이크로서비스 사이에서 이벤트로 통신**할 수 있다.
    
    아키텍처를 선택할 때는 서비스 규모뿐 아니라 **업무의 복잡성, 배포 방식, 팀 구성, 운영 부담**을 함께 고려해야 한다.
    
- SQL Injection을 포함한 대표적인 웹 보안 공격 기법
    
    # SQL Injection을 포함한 대표적인 웹 보안 공격 기법
    
    웹 애플리케이션은 사용자가 입력한 검색어, 리뷰 내용, URL, 요청 파라미터 등을 처리한다.
    이떄 입력을 코드처럼 실행하거나, 요청자의 권한을 제대로 확인하지 않으면 보안 문제가 발생할 수 있다.
    
    | 공격·취약점 | 핵심 문제 |
    | --- | --- |
    | SQL Injection | 사용자 입력이 SQL 구문으로 해석됨 |
    | XSS | 신뢰할 수 없는 입력이 브라우저에서 코드로 실행됨 |
    | CSRF | 사용자의 인증 상태를 이용해 원하지 않는 요청을 보냄 |
    | SSRF | 서버가 공격자가 유도한 대상으로 요청을 보냄 |
    | IDOR | 식별자를 바꿔 권한 없는 데이터에 접근함 |
    
    ---
    
    ## SQL Injection
    
    > 사용자 입력이 SQL의 일부로 해석되어 **원래 의도와 다른 쿼리가 실행되는 공격**
    > 
    
    예를 들어 사용자가 입력한 책 제목을 SQL 문자열에 직접 붙인다고 하자.
    
    ```
    # 위험한 예시
    sql = (
        "SELECT book_id, title FROM book "
        "WHERE title = '" + user_input + "'"
    )
    ```
    
    이 경우 사용자 입력이 단순한 검색값으로만 처리되지 않고, SQL 문장의 구조에 영향을 줄 수 있다.
    
    취약한 쿼리와 DB 계정의 권한에 따라 데이터가 유출되거나 수정·삭제되는 문제가 발생할 수 있다.
    
    ### 파라미터 바인딩
    
    > SQL 구문과 입력값을 **분리해서 전달**하는 방법
    > 
    
    ```
    # Python SQLAlchemy 예시
    from sqlalchemy import text
    
    statement = text("""
        SELECT book_id, title
        FROM book
        WHERE title = :title
    """)
    
    result = connection.execute(
        statement,
        {"title": user_input}
    )
    ```
    
    → 입력값을 SQL 문자열에 직접 붙이지 않고 별도의 파라미터로 전달함
    
    여기서 `:title`은 SQLAlchemy에서 사용하는 바인딩 표기이다. 실제 표기법은 사용하는 라이브러리와 드라이버에 따라 달라질 수 있다.
    
    또한 테이블 이름, 컬럼 이름, 정렬 방향은 일반적인 값 파라미터로 대체할 수 없는 경우가 많다. 이런 부분은 사용자가 보낸 문자열을 그대로 붙이지 말고 **허용된 값 목록에서 선택하도록 제한**해야 한다.
    
    **ORM을 사용한다는 사실만으로 SQL Injection이 자동으로 방지되는 것은 아니다.** ORM 내부에서 실행할 SQL을 문자열 결합으로 만들면 여전히 취약해질 수 있다.
    
    ---
    
    ## XSS
    
    > 웹페이지에 포함된 악성 코드가 **다른 사용자의 브라우저에서 실행되는 공격**
    > 
    
    도서 리뷰 내용을 화면에 보여줄 때, 입력값을 HTML로 그대로 해석하면 문제가 생길 수 있다.
    
    ```
    // 위험한 예시: 입력값을 HTML로 해석
    reviewElement.innerHTML = userReview;
    ```
    
    단순한 텍스트를 표시하려는 목적이라면 다음과 같이 처리할 수 있다.
    
    ```
    // 입력값을 텍스트로 표시
    reviewElement.textContent = userReview;
    ```
    
    → 리뷰 내용을 실행 가능한 HTML이 아닌 문자열로 표시함
    
    ### 대표적인 형태
    
    | 형태 | 설명 |
    | --- | --- |
    | 저장형 XSS | 악성 입력이 DB 등에 저장된 뒤 다른 사용자에게 전달됨 |
    | 반사형 XSS | 요청에 포함된 악성 입력이 응답에 반영됨 |
    | DOM 기반 XSS | 브라우저의 자바스크립트가 입력을 위험하게 처리하여 발생함 |
    
    이 구분은 완전히 배타적이지 않다. 저장·반사는 입력의 전달 방식에, DOM 기반은 브라우저 측 처리에 초점을 둔다.
    
    ### 방어 방법
    
    - 출력 위치에 맞는 **출력 인코딩**을 사용한다.
    - 일반 문자열 출력에는 `textContent` 같은 안전한 API를 사용한다.
    - HTML 입력을 허용해야 한다면 검증된 도구로 HTML을 정화한다.
    - CSP를 추가적인 방어 수단으로 활용한다.
    
    HTML 본문, 속성, URL, 자바스크립트 코드 안에서는 필요한 처리가 다르다.
    
    따라서 **특수문자를 한 번 바꾸기만 하면 모든 XSS가 방지되는 것은 아니다.**
    
    ---
    
    ## CSRF
    
    > 로그인한 사용자의 브라우저가 **사용자가 의도하지 않은 요청을 보내도록 유도하는 공격**
    > 
    
    쿠키 기반 인증에서는 브라우저가 조건에 맞는 요청에 인증 쿠키를 자동으로 포함한다.
    
    공격자는 이러한 동작을 악용할 수 있다.
    
    ```
    사용자가 도서 서비스에 로그인
                  ↓
    공격자가 만든 페이지 방문
                  ↓
    해당 페이지가 도서 서비스로 변경 요청 유도
                  ↓
    방어가 없다면 사용자 권한으로 처리될 수 있음
    ```
    
    예를 들어 사용자는 대여 취소 버튼을 누르지 않았지만, 다른 페이지에서 유도된 요청으로 대여가 취소되는 상황을 생각할 수 있다.
    
    ### 방어 방법
    
    - 프레임워크의 CSRF 방어 기능 사용
    - 상태를 변경하는 요청에 **CSRF 토큰 검증**
    - `SameSite` 쿠키 설정
    - 상황에 맞는 `Origin` 검증
    - 조회 용도의 `GET` 요청으로 중요한 상태를 변경하지 않기
    
    **POST 요청을 사용한다는 것만으로 CSRF가 방지되지는 않는다.**
    
    또한 XSS와 CSRF는 다르다.
    
    ```
    XSS  → 신뢰하는 사이트 안에서 악성 코드가 실행됨
    CSRF → 인증된 사용자의 브라우저가 원하지 않는 요청을 보냄
    ```
    
    ---
    
    ## SSRF
    
    > 서버가 사용자 입력을 바탕으로 **공격자가 지정한 대상에 요청을 보내도록 만드는 공격**
    > 
    
    사용자가 입력한 URL에서 도서 표지 이미지를 가져오는 기능을 생각해 보자.
    
    ```
    사용자가 이미지 URL 입력
               ↓
    서버가 해당 주소에 접속
               ↓
    이미지를 내려받아 저장
    ```
    
    접속 대상을 제대로 제한하지 않으면 서버가 내부 관리 시스템 등 의도하지 않은 주소에 접근할 수 있다.
    
    서버는 일반 사용자가 직접 접근할 수 없는 내부 네트워크에 연결되어 있을 수 있기 때문에 문제가 된다.
    
    ### 방어 방법
    
    - 요청 가능한 주소와 프로토콜 제한
    - 가능한 경우 허용 목록 사용
    - 내부 주소 등 접근하면 안 되는 대상 차단
    - 리다이렉트로 다른 주소에 이동하는 경우 검증
    - DNS 해석 결과 검증
    - 네트워크 수준에서 서버의 외부 요청 제한
    
    단순히 URL 문자열의 시작 부분만 확인하는 방식으로는 충분하지 않을 수 있다.
    
    → 외부 URL을 처리할 때는 **입력된 문자열뿐 아니라 실제로 서버가 접속하게 되는 대상**까지 고려해야 한다.
    
    ---
    
    ## IDOR와 접근 제어 취약점
    
    > 데이터 식별자를 변경했을 때 **접근 권한이 없는 다른 사용자의 데이터까지 조회·수정할 수 있는 문제**
    > 
    
    예를 들어 다음 주소로 대여 내역을 조회한다고 하자.
    
    ```
    /rentals/100
    ```
    
    사용자가 주소를 `/rentals/101`로 바꾸었을 때 다른 사람의 대여 내역이 조회된다면 접근 제어에 문제가 있는 것이다.
    
    여기서는 **인증과 인가**를 구분해야 한다.
    
    | 구분 | 확인하는 내용 |
    | --- | --- |
    | 인증 | 이 사용자가 누구인가? |
    | 인가 | 이 사용자가 해당 작업을 수행할 권한이 있는가? |
    
    로그인한 사용자라고 해서 모든 대여 내역에 접근할 수 있는 것은 아니다.
    
    일반 사용자의 본인 기록 조회라면 다음과 같은 조건을 사용할 수 있다.
    
    ```
    -- 바인딩 파라미터를 사용하는 개념 예시
    WHERE rental_id = :rental_id
      AND user_id = :authenticated_user_id
    ```
    
    `authenticated_user_id`는 사용자가 임의로 보낸 값이 아니라 **서버가 인증 정보에서 확인한 값**이어야 한다.
    
    또한 화면에서 버튼을 숨기거나 식별자를 UUID로 바꾸는 것만으로는 충분하지 않다. 서버에서 요청마다 해당 데이터에 대한 접근 권한을 검증해야 한다.
    
- 커넥션 풀(Connection Pool)이란?
    
    # 커넥션 풀(Connection Pool)이란?
    
    ## 커넥션
    
    > 애플리케이션이 DB와 통신하기 위해 사용하는 **연결**
    > 
    
    애플리케이션이 SQL을 실행하려면 DB에 연결해야 한다.
    
    새 연결을 생성하는 과정에는 네트워크 연결, 인증 등의 작업이 필요하다.
    
    ```
    DB 연결 생성
         ↓
    SQL 실행
         ↓
    DB 연결 종료
    ```
    
    요청마다 이 과정을 반복하면 연결 생성과 종료에 드는 비용이 계속 발생한다.
    
    ---
    
    ## 커넥션 풀
    
    > DB 연결을 관리하면서 **필요할 때 빌려주고, 사용이 끝나면 돌려받아 재사용하는 방식**
    > 
    
    ```
    애플리케이션 요청
           ↓
    풀에서 연결 대여
           ↓
    SQL 및 트랜잭션 처리
           ↓
    풀에 연결 반환
    ```
    
    반환된 연결은 다음 요청에서 다시 사용할 수 있다.
    
    이때 커넥션 풀은 **쿼리 결과를 저장하는 캐시가 아니라 DB 연결을 재사용하는 장치**이다. 같은 연결을 사용하더라도 SQL은 필요에 따라 다시 실행된다.
    
    또한 모든 커넥션 풀이 시작할 때 최대 개수만큼 연결을 만드는 것은 아니다. 구현과 설정에 따라 미리 생성하거나, 필요할 때 생성할 수 있다.
    
    ---
    
    ## 연결 대여와 반환
    
    예를 들어 사용할 수 있는 연결이 3개 있다고 하자.
    
    ```
    커넥션 풀
    ├─ 연결 A → 요청 1이 사용 중
    ├─ 연결 B → 요청 2가 사용 중
    └─ 연결 C → 대기 중
    ```
    
    새 요청은 연결 C를 빌려 사용할 수 있다. 요청 1이 작업을 끝내고 연결 A를 반환하면 다른 요청이 다시 사용할 수 있다.
    
    풀에서 빌린 연결의 `close()`는 보통 실제 DB 연결을 끊는 대신 **풀에 반환하는 동작**을 한다.
    
    다만 사용할 수 없는 연결이나 폐기 조건에 해당하는 연결은 실제로 종료될 수 있다.
    
    → 연결을 재사용하려면 **사용한 연결을 반드시 반환해야 한다.**
    
    ---
    
    ## 커넥션 누수
    
    > 빌린 연결을 반환하지 않아 **다른 요청이 사용할 수 있는 연결이 줄어드는 문제**
    > 
    
    정상 처리에서는 연결을 반환하더라도, 예외가 발생한 경로에서 반환을 빠뜨릴 수 있다.
    
    ```
    연결 대여
        ↓
    SQL 실행 중 오류
        ↓
    반환 코드가 실행되지 않음
        ↓
    연결이 계속 사용 중인 상태로 남음
    ```
    
    이런 상황이 반복되면 풀의 연결이 고갈되어 새 요청이 기다리거나 실패할 수 있다.
    
    따라서 `finally`, 컨텍스트 매니저, 프레임워크의 자원 관리 기능 등을 사용하여 **성공과 실패 모두에서 반환이 이루어지도록** 해야 한다.
    
    ---
    
    ## 연결이 모두 사용 중이면?
    
    풀에서 추가 연결을 생성할 수 있다면 새 연결을 만들 수 있다.
    
    하지만 최대 연결 수에 도달했다면, 새 요청은 연결이 반환될 때까지 기다리게 된다. 설정된 대기 시간을 넘기면 시간 초과 오류가 발생할 수 있다.
    
    | 설정 개념 | 의미 |
    | --- | --- |
    | 최대 연결 수 | 풀에서 허용하는 연결 개수의 상한 |
    | 연결 대기 시간 | 연결을 빌리기 위해 기다리는 최대 시간 |
    | 유휴 연결 관리 | 사용하지 않는 연결을 유지하거나 정리하는 기준 |
    | 연결 수명 | 오래된 연결을 교체하는 기준 |
    
    구체적인 설정 이름과 동작은 사용하는 커넥션 풀에 따라 달라진다.
    
    ---
    
    ## 풀 크기가 클수록 좋을까?
    
    연결 수가 많으면 더 많은 작업이 DB에 동시에 접근할 수 있지만, DB가 감당할 수 있는 처리량에는 한계가 있다.
    
    따라서 연결을 지나치게 늘리면 DB의 자원 사용과 경합이 증가할 수 있다.
    
    반대로 연결이 너무 적으면 DB에 여유가 있어도 애플리케이션 요청이 연결을 기다릴 수 있다.
    
    ```
    너무 적은 연결
    → 애플리케이션의 연결 대기 증가
    
    지나치게 많은 연결
    → DB의 동시 작업 부담 증가 가능
    ```
    
    또한 애플리케이션 인스턴스마다 별도의 풀이 있다면 전체 연결 수를 함께 계산해야 한다.
    
    ```
    애플리케이션 인스턴스 4개
    각 풀의 최대 연결 수 10개
    
    → 설정상 전체 최대 연결 수는 40개
    ```
    
    이 계산은 각 인스턴스에 풀이 하나씩 있고 추가 연결 허용이 없다는 가정이다.
    
    풀 크기는 **DB의 연결 한도, 쿼리 처리 시간, 동시 요청 수, 애플리케이션 인스턴스 수**를 함께 고려하여 정해야 한다.
    
- Raw SQL vs ORM
    
    # Raw SQL vs ORM
    
    ## Raw SQL
    
    > 개발자가 **SQL 문장을 직접 작성**하여 DB에 전달하는 방식
    > 
    
    예를 들어 대여 가능한 책을 조회하려면 다음과 같이 작성한다.
    
    ```
    SELECT book_id, title
    FROM book
    WHERE is_available = TRUE
    ORDER BY book_id DESC
    LIMIT 10;
    ```
    
    애플리케이션에서도 SQL을 직접 작성해 실행할 수 있다.
    
    ```
    # Python SQLAlchemy 예시
    from sqlalchemy import text
    
    statement = text("""
        SELECT book_id, title
        FROM book
        WHERE is_available = :available
        ORDER BY book_id DESC
        LIMIT 10
    """)
    
    rows = connection.execute(
        statement,
        {"available": True}
    ).all()
    ```
    
    → SQL 구조는 직접 작성하고 입력값은 별도로 바인딩함
    
    **Raw SQL은 사용자 입력을 문자열로 붙인다는 뜻이 아니다.** SQL을 직접 작성하더라도 파라미터 바인딩을 사용할 수 있다.
    
    ---
    
    ## ORM
    
    > 객체와 관계형 DB의 테이블을 **매핑하여 데이터를 다루는 기술**
    > 
    
    ORM은 **Object-Relational Mapping**의 약자이다.
    
    기본적인 매핑 관계는 다음과 같이 이해할 수 있다.
    
    | 애플리케이션 | 관계형 DB |
    | --- | --- |
    | 클래스 | 테이블 |
    | 객체의 속성 | 컬럼 |
    | 객체 인스턴스 | 행 |
    
    실제 ORM은 상속이나 여러 테이블에 걸친 매핑도 지원할 수 있으므로, 위 표는 기본적인 이해를 위한 구조이다.
    
    예를 들어 `Book` 클래스가 `book` 테이블에 매핑되어 있다고 가정하자.
    
    ```
    # Python SQLAlchemy ORM 예시
    # Book 모델과 session이 준비되어 있다고 가정
    from sqlalchemy import select
    
    statement = (
        select(Book)
        .where(Book.is_available.is_(True))
        .order_by(Book.book_id.desc())
        .limit(10)
    )
    
    books = session.scalars(statement).all()
    ```
    
    → ORM이 SQL을 생성해 실행하고, 조회 결과를 `Book` 객체로 제공함
    
    조회한 객체의 속성을 통해 데이터에 접근할 수 있다.
    
    ```
    for book in books:
        print(book.title)
    ```
    
    ---
    
    ## Raw SQL과 ORM의 차이
    
    | 구분 | Raw SQL | ORM |
    | --- | --- | --- |
    | 작성 방식 | SQL 직접 작성 | 모델과 ORM API 사용 |
    | 결과 처리 | 행을 필요한 데이터 구조로 변환 | 매핑된 객체로 제공 가능 |
    | 쿼리 제어 | SQL 구조를 직접 제어 | 생성된 SQL을 확인해야 함 |
    | 반복 작업 | 직접 작성할 부분이 많을 수 있음 | 매핑과 일반적인 데이터 처리 코드 감소 |
    | 학습 요소 | SQL과 DB 동작 | SQL·DB 동작과 ORM의 사용 방식 |
    | DB 변경 | DB별 SQL 차이를 직접 처리할 수 있음 | 일부 차이를 추상화하지만 완전한 호환을 보장하지는 않음 |
    
    Raw SQL은 복잡한 조회 조건과 DB 고유 기능을 직접 표현하기 좋다.
    
    ORM은 객체 중심의 애플리케이션 코드와 DB 데이터를 연결하고, 반복적인 데이터 처리 코드를 줄이는 데 도움이 된다.
    
    ---
    
    ## ORM을 사용하면 SQL을 몰라도 될까?
    
    ORM을 사용하더라도 DB에서는 SQL이 실행된다.
    
    따라서 다음과 같은 내용을 확인할 수 있어야 한다.
    
    - 어떤 조건으로 데이터를 조회하는가?
    - 어떤 테이블을 JOIN하는가?
    - 한 요청에서 SQL이 몇 번 실행되는가?
    - 필요한 것보다 많은 데이터를 가져오지는 않는가?
    - 인덱스를 활용할 수 있는 조건인가?
    
    객체 몇 개를 조회하는 간단한 코드처럼 보여도 실제로는 많은 쿼리가 실행될 수 있다.
    
    → ORM은 SQL 작성을 도와주는 기술이지만 **SQL과 DB 동작에 대한 이해를 대신하지는 않는다.**
    
    ---
    
    ## N+1 문제
    
    > 목록을 조회한 뒤 연관 데이터를 개별 조회하면서 **추가 쿼리가 반복되는 문제**
    > 
    
    예를 들어 책 목록을 조회한 뒤 각 책의 카테고리 이름을 출력한다고 하자.
    
    ```
    for book in books:
        print(book.category.name)
    ```
    
    `category`가 필요할 때 조회되는 지연 로딩으로 설정되어 있다면, 속성에 접근할 때 추가 쿼리가 실행될 수 있다.
    
    ```
    책 목록 조회                    → 1번
    첫 번째 책의 카테고리 조회        → 추가 조회
    두 번째 책의 카테고리 조회        → 추가 조회
    ...
    ```
    
    N개 책이 각각 별도의 카테고리를 참조하고 해당 데이터가 미리 로딩되지 않았다면, 목록 조회 1번에 추가 조회 N번이 발생하는 형태가 될 수 있다.
    
    다만 캐시, 이미 로딩된 객체, 중복된 연관 관계 등에 따라 실제 쿼리 수는 달라진다.
    
    ### 해결 방향
    
    - 필요한 연관 데이터를 JOIN으로 함께 조회
    - 연관 데이터를 여러 건 묶어서 조회
    - ORM의 적절한 로딩 전략 사용
    
    무조건 모든 관계를 한 번에 가져오는 것도 좋은 방법은 아니다. 불필요한 데이터가 늘거나 JOIN 결과의 행 수가 크게 증가할 수 있기 때문이다.
    
    따라서 **화면에 필요한 데이터와 실제 쿼리 수를 기준으로 로딩 방식을 선택**해야 한다.
    
    ---
    
    ## 성능과 사용 방식
    
    Raw SQL이라고 항상 빠른 것도 아니고, ORM이라고 항상 느린 것도 아니다.
    
    성능은 실제 실행되는 SQL, 인덱스, 조회량, 네트워크 왕복 횟수, 객체 생성 비용 등에 영향을 받는다.
    
    두 방식을 함께 사용하는 것도 가능하다.
    
    ```
    일반적인 등록·조회·수정
    → ORM 활용
    
    복잡한 통계나 특수한 조회
    → 직접 작성한 SQL 활용
    ```
    
    이때 같은 작업 안에서 두 방식을 섞는다면 **트랜잭션 범위와 ORM이 관리하는 객체 상태**가 어긋나지 않도록 주의해야 한다.
    
- INSERT 외에 데이터를 다루는 핵심 SQL 문법
    
    # INSERT 외에 데이터를 다루는 핵심 SQL 문법
    
    SQL에서 `INSERT`는 새로운 행을 추가한다.
    
    그 외에 데이터를 다루는 기본 명령어는 다음과 같다.
    
    | 명령어 | 역할 |
    | --- | --- |
    | `SELECT` | 데이터 조회 |
    | `UPDATE` | 기존 데이터 수정 |
    | `DELETE` | 기존 행 삭제 |
    
    조회할 때는 `WHERE`, `JOIN`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT` 등을 함께 사용한다.
    
    아래 SQL 예제는 **MySQL 기준**이다.
    
    ---
    
    ## SELECT
    
    > 테이블에서 **필요한 데이터를 조회**한다.
    > 
    
    ```
    SELECT book_id, title
    FROM book
    WHERE is_available = TRUE
    ORDER BY book_id DESC
    LIMIT 10;
    ```
    
    → 대여 가능한 책을 `book_id`가 큰 순서대로 최대 10개 조회함
    
    | 구성 요소 | 역할 |
    | --- | --- |
    | `SELECT` | 가져올 컬럼 지정 |
    | `FROM` | 조회할 테이블 지정 |
    | `WHERE` | 조회할 행의 조건 지정 |
    | `ORDER BY` | 정렬 기준 지정 |
    | `LIMIT` | 결과 개수 제한 |
    
    여기서 `book_id DESC`는 **ID 내림차순**이다. 등록 시각 기준의 최신순이 필요하다면 등록 시각 컬럼을 사용해야 한다.
    
    예를 들어 `created_at` 컬럼이 있다면 다음과 같이 정렬할 수 있다.
    
    ```
    ORDER BY created_at DESC, book_id DESC
    ```
    
    → 등록 시각이 같을 때는 고유한 `book_id`로 순서를 구분함
    
    ---
    
    ## UPDATE
    
    > 기존 행의 **컬럼 값을 수정**한다.
    > 
    
    ```
    UPDATE book
    SET title = '새로운 책 제목'
    WHERE book_id = 10;
    ```
    
    → `book_id`가 10인 책의 제목을 변경함
    
    여러 컬럼을 함께 수정할 수도 있다.
    
    ```
    UPDATE book
    SET
        title = '새로운 책 제목',
        description = '변경된 책 설명'
    WHERE book_id = 10;
    ```
    
    `SET`에는 변경할 컬럼과 값을 작성하고, `WHERE`에는 수정할 대상을 작성한다.
    
    ```
    UPDATE book
    SET is_available = FALSE;
    ```
    
    위처럼 `WHERE`가 없으면 **모든 행이 수정 대상**이 된다.
    
    변경 전에 같은 조건으로 조회하면 어떤 행이 대상인지 확인하는 데 도움이 된다.
    
    ```
    SELECT book_id, title, is_available
    FROM book
    WHERE book_id = 10;
    ```
    
    단, 조회 후 수정 사이에 다른 트랜잭션이 데이터를 바꿀 수 있으므로, 사전 조회만으로 동시성 문제가 해결되는 것은 아니다.
    
    ---
    
    ## DELETE
    
    > 조건에 맞는 **행을 삭제**한다.
    > 
    
    ```
    DELETE FROM rental
    WHERE rental_id = 100;
    ```
    
    → `rental_id`가 100인 대여 기록을 삭제함
    
    `WHERE` 없이 실행하면 테이블의 모든 행이 삭제 대상이 된다.
    
    ```
    DELETE FROM rental;
    ```
    
    `DELETE`는 테이블의 행을 삭제하지만 **테이블 구조는 남겨 둔다.**
    
    ```
    DELETE FROM rental;
    → 테이블 안의 행 삭제
    
    DROP TABLE rental;
    → 테이블 자체 삭제
    ```
    
    또한 다른 테이블이 해당 데이터를 FK로 참조하고 있다면, 제약조건 설정에 따라 삭제가 제한되거나 관련 행에 영향이 갈 수 있다.
    
    ---
    
    ## WHERE와 조건 연산자
    
    > 전체 데이터 중에서 **조건에 맞는 행만 선택**한다.
    > 
    
    | 연산자 | 의미 | 예시 |
    | --- | --- | --- |
    | `=` | 같음 | `category_id = 1` |
    | `<>` | 다름 | `category_id <> 1` |
    | `>`, `<` | 크거나 작음 | `book_id > 100` |
    | `IN` | 여러 값 중 하나와 일치 | `category_id IN (1, 2)` |
    | `BETWEEN` | 양 끝을 포함하는 범위 | `book_id BETWEEN 10 AND 20` |
    | `LIKE` | 문자열 패턴 비교 | `title LIKE '%도서관%'` |
    | `IS NULL` | NULL 여부 확인 | `returned_at IS NULL` |
    
    예를 들어 제목에 `도서관`이 포함된 책을 조회하려면,
    
    ```
    SELECT book_id, title
    FROM book
    WHERE title LIKE '%도서관%';
    ```
    
    처럼 작성한다.
    
    `LIKE`에서 `%`는 0개 이상의 문자를, `_`는 한 문자를 나타낸다.
    
    여러 조건을 결합할 때는 괄호로 의도를 명확하게 표현할 수 있다.
    
    ```
    WHERE is_available = TRUE
      AND (category_id = 1 OR category_id = 2)
    ```
    
    → 대여 가능하면서 카테고리가 1 또는 2인 책만 조회함
    
    ---
    
    ## JOIN
    
    > 서로 다른 테이블의 **관련 데이터를 연결하여 조회**한다.
    > 
    
    ```
    SELECT
        b.book_id,
        b.title,
        c.name AS category_name
    FROM book b
    JOIN category c
        ON b.category_id = c.category_id;
    ```
    
    → 책과 카테고리를 `category_id` 기준으로 연결함
    
    위의 `JOIN`은 `INNER JOIN`으로, 연결 조건을 만족하는 데이터만 반환한다.
    
    반면 `LEFT JOIN`은 왼쪽 테이블의 행을 유지한다.
    
    ```
    SELECT
        b.book_id,
        b.title,
        c.name AS category_name
    FROM book b
    LEFT JOIN category c
        ON b.category_id = c.category_id;
    ```
    
    → 연결되는 카테고리가 없어도 책은 조회되며, 오른쪽 카테고리 컬럼은 `NULL`로 표시됨
    
    주의할 점은 `LEFT JOIN` 이후 오른쪽 테이블의 컬럼을 `WHERE`로 제한하면, 연결되지 않은 행이 제외될 수 있다는 것이다.
    
    ```
    WHERE c.name = '문학'
    ```
    
    연결되지 않은 행의 `c.name`은 `NULL`이므로 위 조건을 만족하지 못한다.
    
    또한 올바르게 JOIN했더라도 **일대다 관계에서는 기준 행이 여러 결과 행으로 나타날 수 있다.** 결과 행이 늘어났다는 이유만으로 JOIN 조건이 잘못되었다고 단정할 수는 없다.
    
    ---
    
    ## GROUP BY와 집계 함수
    
    > 여러 행을 **같은 기준으로 묶어 개수나 합계 등을 계산**한다.
    > 
    
    카테고리별 도서 수를 조회하려면 다음과 같이 작성한다.
    
    ```
    SELECT
        category_id,
        COUNT(*) AS book_count
    FROM book
    GROUP BY category_id;
    ```
    
    → 같은 `category_id`를 가진 책을 묶어 개수를 계산함
    
    | 집계 함수 | 역할 |
    | --- | --- |
    | `COUNT(*)` | 행의 개수 |
    | `COUNT(column)` | 해당 컬럼이 NULL이 아닌 행의 개수 |
    | `SUM(column)` | 합계 |
    | `AVG(column)` | 평균 |
    | `MAX(column)` | 최댓값 |
    | `MIN(column)` | 최솟값 |
    
    예를 들어 다음 쿼리는 전체 대여 건수와 반납 완료 건수를 함께 계산한다.
    
    ```
    SELECT
        COUNT(*) AS total_rentals,
        COUNT(returned_at) AS returned_rentals
    FROM rental;
    ```
    
    → `returned_at`이 NULL이면 `COUNT(returned_at)`에 포함되지 않음
    
    `SUM`, `AVG` 등도 일반적으로 NULL을 제외하고 계산한다. 특히 평균을 계산할 때 **NULL을 0으로 취급하는 것과 제외하는 것은 결과가 다르다.**
    
    ---
    
    ## WHERE와 HAVING
    
    > `WHERE`는 그룹화할 **행을 필터링**하고, `HAVING`은 **그룹 결과를 필터링**한다.
    > 
    
    대여 가능한 책이 5권 이상인 카테고리를 찾는다면 다음과 같이 작성한다.
    
    ```
    SELECT
        category_id,
        COUNT(*) AS available_book_count
    FROM book
    WHERE is_available = TRUE
    GROUP BY category_id
    HAVING COUNT(*) >= 5;
    ```
    
    논리적으로 다음과 같이 이해할 수 있다.
    
    ```
    대여 가능한 책만 선택
             ↓
    카테고리별로 묶음
             ↓
    각 그룹의 책 개수 계산
             ↓
    개수가 5 이상인 그룹만 선택
    ```
    
    | 구분 | 적용 대상 | 예시 |
    | --- | --- | --- |
    | `WHERE` | 개별 행 | 대여 가능한 책 |
    | `HAVING` | 그룹 결과 | 책이 5권 이상인 카테고리 |
    
    위 흐름은 쿼리의 의미를 설명한 것이며, DB가 실제로 수행하는 실행 계획과 항상 같은 것은 아니다.
    
    ---
    
    ## DISTINCT
    
    > 조회 결과에서 **선택한 컬럼 조합의 중복을 제거**한다.
    > 
    
    책이 존재하는 카테고리 ID 목록을 중복 없이 조회하려면,
    
    ```
    SELECT DISTINCT category_id
    FROM book;
    ```
    
    처럼 작성할 수 있다.
    
    여러 컬럼을 선택하면 그 조합을 기준으로 중복을 판단한다.
    
    ```
    SELECT DISTINCT category_id, is_available
    FROM book;
    ```
    
    → `category_id`와 `is_available`이 모두 같은 결과끼리 중복을 제거함
    
    다만 JOIN 결과가 예상보다 많을 때 무조건 `DISTINCT`를 추가하면, 잘못된 JOIN 조건을 가릴 수 있다.
    
    먼저 **결과가 늘어난 이유가 정상적인 일대다 관계인지, 잘못된 연결 조건인지** 확인해야 한다.

    ## 트랜잭션: COMMIT과 ROLLBACK
    
    > 여러 데이터 변경을 **하나의 작업 단위로 묶어서 처리**한다.
    > 
    
    MySQL의 InnoDB처럼 트랜잭션을 지원하는 테이블에서는 다음과 같이 사용할 수 있다.
    
    ```
    START TRANSACTION;
    
    UPDATE book
    SET title = '수정된 제목'
    WHERE book_id = 10;
    
    UPDATE book
    SET description = '수정된 설명'
    WHERE book_id = 10;
    
    COMMIT;
    ```
    
    → 두 변경을 하나의 트랜잭션으로 확정함
    
    변경을 확정하기 전에 취소하려면 `COMMIT` 대신 `ROLLBACK`을 실행한다.
    
    ```
    START TRANSACTION;
    
    UPDATE book
    SET title = '임시 제목'
    WHERE book_id = 10;
    
    ROLLBACK;
    ```
    
    → 해당 트랜잭션에서 변경한 제목을 취소함
    
    | 명령어 | 역할 |
    | --- | --- |
    | `START TRANSACTION` | 트랜잭션 시작 |
    | `COMMIT` | 변경 확정 |
    | `ROLLBACK` | 아직 확정하지 않은 변경 취소 |
    
    **이미 `COMMIT`한 변경을 이후의 `ROLLBACK`으로 되돌릴 수는 없다.**
    
    또한 오류가 발생했다고 항상 전체 트랜잭션이 자동 취소되는 것은 아니다. 애플리케이션에서 실패를 감지하고 필요한 경우 `ROLLBACK`하도록 처리해야 한다.
    
    MySQL의 일부 DDL은 암묵적인 커밋을 발생시키므로, 테이블 구조 변경까지 일반적인 데이터 수정과 같은 방식으로 되돌릴 수 있다고 생각해서는 안 된다.
