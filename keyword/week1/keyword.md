- PK, FK란?
    
     
    
    PK(Primary Key)는 테이블의 각 데이터를 고유하게 식별하기 위한 기본키이다.
    
    - 값이 중복될 수 없다.
    - NULL이 될 수 없다.
    - 하나의 행을 구분하는 기준이 된다.
    
    FK(Foreign Key)는 다른 테이블의 PK를 참조하여 테이블 간 관계를 연결하는 외래키이다. FK를 이용하면 존재하지 않는 데이터를 참조하는 것을 막아 참조 무결성을 유지할 수 있다.
    
    핵심적으로 PK는 자신의 데이터를 식별하고, FK는 다른 테이블의 데이터를 가리킨다.
    
- ERD란?
    
    ERD(Entity Relationship Diagram)는 데이터베이스의 테이블, 속성, 그리고 테이블 사이의 관계를 시각적으로 표현한 설계도이다.
    
    ERD에는 주로 다음 내용이 들어간다.
    
    - 테이블과 각 테이블의 속성
    - PK와 FK
    - 테이블 사이의 관계
    - 컬럼의 제약조건
    
    서비스의 요구사항이나 와이어프레임을 분석해 필요한 데이터를 찾고, 이를 어떤 테이블과 관계로 저장할 것인지 설계할 때 사용한다.
    
- 연관관계란? 그리고 연관관계를 설정하는 방법은?
    
     
    
    연관관계는 한 테이블의 데이터와 다른 테이블의 데이터가 어떤 관계를 가지는지를 의미한다.
    
    대표적으로 다음 세 가지가 있다.
    
    - 1:1 : 하나의 데이터가 하나의 데이터와 연결된다.
    - 1:N : 하나의 데이터가 여러 데이터와 연결된다.
    - N:M : 양쪽 모두 여러 데이터와 연결될 수 있다.
    
    1:N 관계에서는 일반적으로 N 쪽 테이블에 FK를 둔다. N:M 관계는 두 테이블을 직접 연결하지 않고 중간 매핑 테이블을 만들어 두 개의 1:N 관계로 표현한다. 워크북의 사용자-책 대여, 책-해시태그, 책-좋아요가 이에 해당한다.
    
- 정규화란?
    
    정규화는 데이터 중복을 줄이고 데이터의 일관성과 무결성을 유지하기 위해 테이블을 적절하게 분리하는 과정이다.
    
    같은 회원 정보를 여러 주문에 반복해서 저장하면 회원 정보가 변경될 때 여러 데이터를 모두 수정해야 한다. 이를 회원 테이블과 주문 테이블로 분리하고 FK로 연결하면 하나의 정보만 관리하면 된다.
    
    대표적인 정규형은 다음과 같다.
    
    - 1NF : 하나의 컬럼에는 하나의 값만 저장한다.
    - 2NF : 복합키의 일부에만 의존하는 속성을 분리한다.
    - 3NF : 일반 속성끼리의 불필요한 의존 관계를 제거한다.
    
    이번 단계에서는 데이터 중복을 최소화하고 반복되는 데이터를 별도 테이블로 분리하는 과정이라고 이해하면 충분하다.
    
- 반 정규화란?
    
    반 정규화는 조회 성능이나 구현 편의성을 위해 정규화된 데이터를 의도적으로 중복해서 저장하는 방법이다.
    예를 들어 좋아요 수를 매번 좋아요 테이블에서 계산하지 않고 책 테이블에 좋아요 수를 따로 저장하면 조회 속도를 높일 수 있다. 워크북에서도 읽기 성능이 중요한 경우 이러한 방식을 사용할 수 있다고 설명한다.
    다만 데이터가 여러 곳에 저장되기 때문에 값이 서로 달라질 위험이 있다.
    즉, 정규화는 데이터 정합성과 중복 최소화에 초점을 두고, 반 정규화는 일부 중복을 허용하여 성능을 높이는 데 초점을 둔다.
    
- DB에서의 상속 관계 표현은 어떻게 하는가?
    
     
    
    관계형 데이터베이스에는 객체지향 언어처럼 직접적인 상속 개념이 없기 때문에 테이블 구조로 표현한다.
    
    대표적인 방법은 다음과 같다.
    
    - 부모와 자식의 모든 데이터를 하나의 테이블에 저장하는 방식
    - 부모 테이블과 자식 테이블을 각각 만들고 PK와 FK로 연결하는 방식
    - 각 자식 타입마다 별도의 테이블을 만드는 방식
    
    어떤 방식이 항상 좋은 것은 아니며 데이터 구조, 중복 여부, JOIN 비용 등을 고려하여 선택한다.
    
- 인덱스란?
    
     
    
    인덱스(Index)는 데이터베이스에서 원하는 데이터를 빠르게 찾기 위해 사용하는 자료구조이다. 책의 맨 뒤에 있는 색인과 비슷한 역할을 한다.
    장점은 검색과 JOIN 등의 조회 속도를 높일 수 있다는 점이다. 반면 인덱스 자체가 저장 공간을 사용하고 데이터가 추가·수정·삭제될 때 인덱스도 함께 갱신해야 하므로 쓰기 성능이 떨어질 수 있다.
    따라서 모든 컬럼에 만드는 것이 아니라 검색, JOIN, 정렬 등에 자주 사용되는 컬럼을 중심으로 설정하는 것이 중요하다.


- TypeScript와 정적 타입 검사
    - JavaScript와 비교했을 때 TypeScript는 오류를 언제, 어떤 방식으로 확인하나요?
        
         JavaScript는 타입이 맞지 않아도 실행 자체는 허용하는 경우가 많아 예상과 다른 결과가 런타임에 나타날 수 있다. 반면 TypeScript는 코드를 실행하기 전에 컴파일 과정에서 타입을 검사하여 잘못된 타입의 값 전달, 존재하지 않는 프로퍼티 사용 등의 실수를 미리 발견한다.
        
    - 컴파일 타임 오류와 런타임 오류는 어떤 차이가 있나요?
        
         컴파일 타임 오류는 TypeScript 코드를 JavaScript로 변환하기 전에 타입이나 문법을 검사하는 과정에서 발생하는 오류이다. 런타임 오류는 컴파일을 통과한 JavaScript가 실제로 실행되는 중에 발생하는 오류이다. TypeScript가 모든 런타임 오류까지 막아 주는 것은 아니다.
        
    - TypeScript의 타입 정보가 실행되는 JavaScript에 남지 않는 이유는 무엇일까요?
        
          TypeScript의 타입 정보는 개발 단계에서 정적 타입 검사를 하기 위해 사용된다. 실제 실행 환경인 브라우저나 Node.js는 JavaScript를 실행하므로, 컴파일 과정에서 `string`, `number` 같은 타입 정보는 제거되고 JavaScript 코드만 남는다.
        
- 타입 추론과 타입 모델링
    - TypeScript가 타입을 추론하도록 두는 경우와 타입을 직접 작성하는 경우는 각각 언제 알맞을까요?
        
        값만 보고 TypeScript가 타입을 명확하게 판단할 수 있다면 타입 추론에 맡기는 것이 편리하다. 반면 함수의 매개변수처럼 어떤 값이 들어와야 하는지 명확히 정해야 하거나, 객체의 구조를 명확하게 표현해야 하는 경우에는 타입을 직접 작성하는 것이 좋다.
        
    - 객체와 함수의 형태를 타입으로 표현하면 어떤 실수를 미리 찾을 수 있을까요?
        
        객체에서는 필수 프로퍼티 누락이나 잘못된 타입의 값 할당을 미리 찾을 수 있다. 함수에서는 잘못된 타입의 인자를 전달하거나 의도한 반환 타입과 다른 값을 반환하는 등의 실수를 컴파일 단계에서 발견할 수 있다.
        
    - `type`과 `interface`는 표현 범위와 확장 방식에서 어떤 차이가 있을까요?
        
        `type`은 객체뿐 아니라 원시 타입의 별칭, 유니언 타입 등 다양한 타입을 표현할 수 있으며 `&`를 이용해 타입을 조합할 수 있다. `interface`는 주로 객체의 구조를 정의하는 데 사용하며 `extends`로 확장할 수 있다. 또한 같은 이름의 `interface`는 서로 호환된다면 선언이 합쳐질 수 있지만, `type`은 같은 이름으로 다시 선언할 수 없다. 
        
- 유니언 타입과 타입 좁히기
    - 여러 타입 중 하나가 될 수 있는 값을 유니언 타입으로 표현하면 어떤 장점이 있나요?
        
         유니언 타입을 사용하면 하나의 값이 가질 수 있는 여러 타입을 명확하게 제한하면서도 다양한 경우를 처리할 수 있다. 예를 들어 `string | number`는 문자열 또는 숫자만 허용한다는 의미이므로 가능한 값의 범위를 코드에서 명확하게 표현할 수 있다.
        
    - 조건문, `typeof`와 판별 프로퍼티는 타입을 어떻게 좁히나요?
        
         조건문을 통해 특정 조건이 참이라는 것이 확인되면 TypeScript는 해당 범위에서 타입을 더 구체적으로 판단한다. `typeof`를 사용하면 문자열, 숫자 등 현재 값의 타입을 확인할 수 있고, 객체에서는 `status`와 같은 공통 프로퍼티의 값을 이용하여 어떤 객체 타입인지 구분할 수 있다. 이를 타입 좁히기라고 한다.
        
    - `null`과 `undefined`가 포함된 값을 안전하게 다룰 때 옵셔널 체이닝과 널 병합 연산자는 어떤 역할을 하나요?
        
        옵셔널 체이닝 `?.`은 앞의 값이 `null` 또는 `undefined`일 경우 오류를 발생시키지 않고 `undefined`를 반환한다. 널 병합 연산자 `??`는 값이 `null` 또는 `undefined`일 때만 지정한 기본값을 사용한다. `0`이나 빈 문자열처럼 유효할 수 있는 falsy 값은 그대로 유지한다는 점에서 `||`와 차이가 있다. 
        
         
        
- 타입 안전성과 제네릭
    - `any`와 `unknown`은 타입 검사를 허용하는 방식이 어떻게 다른가요?
        
         `any`는 타입 검사를 거의 비활성화하므로 어떤 값이든 저장하고 바로 사용할 수 있지만 잘못된 코드도 컴파일러가 발견하지 못할 수 있다. `unknown`도 어떤 값이든 받을 수 있지만, 사용하기 전에 `typeof` 등의 방법으로 타입을 확인해야 하므로 더 안전하다. 
        
    - 여러 타입을 받을 때 `unknown`과 제네릭은 각각 어떤 상황에 알맞을까요?
        
         `unknown`은 외부에서 들어오는 값처럼 실제 타입을 미리 알 수 없는 데이터를 안전하게 받을 때 적합하다. 제네릭은 여러 타입을 받을 수 있으면서도 입력 타입과 출력 타입 또는 여러 매개변수 사이의 타입 관계를 유지해야 할 때 적합하다.
        
    - 제네릭은 입력 타입과 출력 타입의 관계를 어떻게 유지하나요?
        
        제네릭의 타입 매개변수 `T`는 함수에 전달된 타입 정보를 저장하고 그 타입을 반환값에도 그대로 연결한다. 따라서 문자열을 전달하면 결과도 문자열 타입으로, 숫자를 전달하면 결과도 숫자 타입으로 유지된다. `unknown`처럼 타입 정보를 잃지 않고 입력과 출력의 관계를 보존할 수 있다는 것이 핵심이다.
