- PK, FK란?
    
    PK(Primary Key)
    
    - 테이블에서 각 행을 유일하게 식별할 수 있는 대표 식별자
    - 중복된 값을 가질 수 없고(Unique), 빈 값을 허용하지 않음(NOT NULL)
    - 테이블 당 하나의 기본키만 지정(2개 이상의 컬럼을 묶은 복합키도 가능!)
    
    FK(Foreign Key)
    
    - 다른 테이블의 기본키(PK) 또는 UNIQUE 제약이 걸린 후보키를 참조하는 컬럼
    - 자기 자신을 참조하는 경우도 있으며, DBMS에 따라 다른 테이블의 PK뿐 아니라 UNIQUE 제약이 걸린 컬럼도 참조할 수 있음
    - 테이블 간의 관계를 맺어주고, FK 값이 NULL이 아닌 경우에는 참조하는 테이블에 실제 존재하는 값만 입력 받도록 참조 무결성을 보장함
    - FK 컬럼이 NULL을 허용하면 참조 행 없이 NULL을 저장할 수 있으므로, 참조 무결성은 보통 NULL이 아닌 값에 대해 적용됨
- ERD란?
    
    ERD(Entity Relationship Diagram)
    
    - 데이터베이스의 구조와 테이블 간의 관계를 시각적으로 표현한 개체-관계 모델 다이어그램
    - 요구사항 분석 단계 이후 데이터 모델링 시 설계도 형태로 정리하여 데이터 구조의 무결성과 확장성을 점검하는 데 사용됨
- 연관관계란? 그리고 연관관계를 설정하는 방법은?
    
    연관관계
    
    - 두 개 이상의 테이블이 서로 어떻게 연결되어 있는지를 나타내는 관계
    - 1:1, 1:N, N:M
    - 관계를 구현하는 방법:
        - 1:N: N쪽 테이블에 FK를 두어 연결
        - 1:1: 한쪽 테이블에 FK를 두고, 해당 컬럼에 UNIQUE 제약을 적용
        - N:M: 연결 테이블을 만들고 각 테이블의 PK를 FK로 저장
        - 필수 관계라면 FK 컬럼에 NOT NULL을 적용하여 반드시 값이 있어야 함
- 정규화란?
    
    정규화(Normalization)
    
    - 데이터 중복을 줄이고, 삽입·수정·삭제 이상(anomaly)을 방지해 데이터의 무결성과 유지보수성을 높이는 과정
    - 중복을 완전히 없애는 것이 아니라, 중복을 최소화하고 이상 현상을 줄이는 것이 목적
    - 제 1 정규화: 테이블의 컬럼이 원자값을 갖도록 분해하는 것
    - 제 2 정규화: 제 1 정규화를 진행한 테이블에 대해 부분 함수 종속을 제거하고 완전 함수 종속을 만족하도록 분해하는 것
        - 완전 함수 종속: 기본키의 전체 집합이 결정자가 되어야 하며, 기본키의 일부만으로 다른 속성이 결정되어서는 안 됨
        - 복합 키를 사용할 때 특히 중요하며, 단일 컬럼 기본키를 가진 테이블은 보통 자동으로 만족함
    - 제 3 정규화: 제 2 정규화를 진행한 테이블에 대해 비키 속성 간의 이행적 종속을 제거하도록 분해하는 것
        - 예: A → B, B → C일 때 A → C가 성립하면 비키 속성 간의 이행적 종속이 발생한다고 봄
- 반 정규화란?
    
    반정규화
    
    - 성능 향상을 위해 일부 데이터 중복이나 계산 결과를 허용하고 조인을 줄이는 설계 기법
    - 조회 속도는 향상되지만 데이터 일관성 유지와 모델의 유연성이 상대적으로 낮아질 수 있음
    - 계산된 컬럼 추가: 자주 조회되는 값을 미리 계산해 저장
    - 테이블 병합: 자주 함께 조회되는 테이블을 합쳐 조회 비용을 줄임
    - 반정규화와 분할 개념을 구분하면:
        - 테이블 수직 분할: 하나의 테이블을 여러 테이블로 나누는 설계
        - 테이블 수평 분할: 하나의 테이블을 값 기준으로 여러 파티션으로 나누는 방식
        - 위 두 방식은 일반적으로 반정규화라기보다 파티셔닝 또는 물리적 설계 기법에 가깝다
- DB에서의 상속 관계 표현은 어떻게 하는가?
    
    일반 데이터베이스에는 객체 상속 개념이 없고, 보통 ORM(특히 JPA)에서 설명하는 Super-Type Sub-Type 모델을 세 가지 전략 중 하나로 매핑한다.
    
    - 조인 전략: 슈퍼타입-서브타입 각각 테이블 생성
        - 공통 속성을 가진 슈퍼타입 테이블과 서브타입 테이블을 따로 만들고, 자식의 PK이자 FK로 부모의 PK를 공유하는 구조
        - 정규화가 잘 되어 있으나, 서브타입의 전체 정보를 조회할 때 주로 JOIN이 필요해 쿼리가 복잡해질 수 있음
    - 단일 테이블 전략
        - 자식 클래스의 모든 속성을 부모 테이블에 몰아 넣고, 어떤 타입인지 구분하는 컬럼을 두는 방식
        - JOIN이 필요 없어 조회가 빠르나, 다른 자식의 컬럼들은 NULL을 허용해야 하고 테이블 크기가 비대해짐
    - 구현 클래스마다 테이블 생성
        - 공통 부모 테이블 없이 각 자식마다 필요한 모든 컬럼을 복사해 각각 별개의 테이블로 만드는 방식
        - 자식 테이블을 묶어서 조회할 때 UNION이 필요할 수 있으며, 다형성 조회를 자주 사용하지 않는다면 적합할 수 있음
    
- 인덱스란?
    
    인덱스(Index)
    
    - 테이블의 데이터 검색 속도를 빠르게 하기 위해 특정 컬럼의 값을 기준으로 정렬하여 생성해두는 자료구조
    - WHERE, JOIN, ORDER BY 연산의 탐색 속도가 향상
    - INSERT, UPDATE, DELETE 시 인덱스 트리도 정렬해야하므로 쓰기 속도가 저하



- TypeScript와 정적 타입 검사
    - JavaScript와 비교했을 때 TypeScript는 오류를 언제, 어떤 방식으로 확인하나요?
        - javascript는 코드가 실제로 실행되는 시점에 오류를 발견하는데 비해, typescript는 javascript 코드가 실행되기 전 컴파일 타임에 타입 검사기를 통해 타입 일치 여부를 미리 검증한다
    - 컴파일 타임 오류와 런타임 오류는 어떤 차이가 있나요?
        - 컴파일 오류는 코드가 실행되기 전, 런타임 오류는 javascript를 실제로 실행하는 동안 발생한다.
        - 컴파일 타임 오류는 타입 오류를 검사하고 javascript 파일을 만들고,
        - 런타임 오류는 실제 값을 계산하고 console에 결과를 출력한다.
    - TypeScript의 타입 정보가 실행되는 JavaScript에 남지 않는 이유는 무엇일까요?
        - JavaScript 런타임이 타입을 이해하지 못하고, 타입 검사는 오직 실행 전 단계에서만 필요하기 때문
- 타입 추론과 타입 모델링
    - TypeScript가 타입을 추론하도록 두는 경우와 타입을 직접 작성하는 경우는 각각 언제 알맞을까요?
        - TypeScript는 초기화된 값, 함수의 반환값 등을 매우 정확하게 추론함. 불필요한 타입 명시를 줄이면 코드가 간결해지고 유지보수가 쉬워짐
        - 코드의 안정성을 확보하거나 TypeScript가 내 의도를 알지 못할 때 직접 작성해주어야함
    - 객체와 함수의 형태를 타입으로 표현하면 어떤 실수를 미리 찾을 수 있을까요?
        - 객체 타입을 잘못 정의하거나 필수 속성을 누락했을 때
        - 함수 선언 시 인자 오류나 반환값 오류
    - `type`과 `interface`는 표현 범위와 확장 방식에서 어떤 차이가 있을까요?
        - interface: 객체의 구조를 정의하고 결합하는 데 특화
        - type: 객체 뿐만 아니라 원시 타입, 유니온, 튜플 등 다양한 타입을 표현하고 조합하는데 특화
- 유니언 타입과 타입 좁히기
    - 여러 타입 중 하나가 될 수 있는 값을 유니언 타입으로 표현하면 어떤 장점이 있나요?
        - 허용되지 않은 타입을 차단하고
        - 타입 좁히기를 통해 예외 처리하지 않고 추론할 수 있다
    - 조건문, `typeof`와 판별 프로퍼티는 타입을 어떻게 좁히나요?
        - 조건문은 값의 존재 여부와 참/거짓 여부를 기준으로 타입을 더 구체적으로 좁힐 수 있다
        - `typeof`는 변수의 런타임 타입을 문자열로 반환하며, 예를 들어 `"string"`, `"number"`, `"boolean"` 등을 판별한다
        - 여러 객체 타입이 묶인 유니온 타입일 때, 공통 프로퍼티를 이용하거나 각 객체가 갖는 고유한 리터럴 값을 비교해 타입을 구분한다
        - 단, `if (value)`는 `null`/`undefined`만 검증하는 것이 아니라 `0`, `""`, `false`, `NaN`도 거짓으로 처리하므로 널 체크와 동일하지 않다
        - `strictNullChecks`를 켜두면 null/undefined 처리 여부를 타입 시스템이 강제하며, 사용자 정의 타입 가드 `value is T`로 더 명확하게 타입을 좁힐 수 있다
    - `null`과 `undefined`가 포함된 값을 안전하게 다룰 때 옵셔널 체이닝과 널 병합 연산자는 어떤 역할을 하나요?
        - 옵셔널 체이닝: 좌측 값이 null 혹은 undefined이면 에러를 내지 않고 undefined를 반환
        - 널 병합 연산자: 좌측 값이 null 또는 undefined이면 우측의 기본값을 반환하고, 아니면 좌측의 원래 값을 반환
- 타입 안전성과 제네릭
    - `any`와 `unknown`은 타입 검사를 허용하는 방식이 어떻게 다른가요?
        - any는 타입 검사를 완전히 비활성화하고, unknown은 모든 타입을 허용하지만 사용하기 전 타입 검사를 강제한다
    - 여러 타입을 받을 때 `unknown`과 제네릭은 각각 어떤 상황에 알맞을까요?
        - unknown은 어떤 값이 들어올지 전혀 알 수 없을 때 사용하고,
        - 제네릭은 어떤 값이 들어올지는 모르지만 그 타입을 유지하고 추적해야할 때 사용한다
    - 제네릭은 입력 타입과 출력 타입의 관계를 어떻게 유지하나요?
        - 컴파일러가 함수를 호출할 때 들어온 인자의 타입을 추론하여 T에 고정하기 때문에, 입력과 출력의 타입 관계가 깨지지 않고 그대로 유지된다.
