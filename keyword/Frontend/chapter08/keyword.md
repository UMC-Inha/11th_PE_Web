- 클라이언트 상태와 서버 상태
  - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.
    **① 입력값**
    - 검색어, 게시글 작성 내용, 로그인 폼의 입력값 등은 클라이언트 상태로 관리하는 것이 적절하다. 사용자가 입력하는 순간마다 서버에 저장할 필요가 없으며 화면 내부에서 즉시 변경되어야 하기 때문이다.
    - 일반적으로 React의 `useState`를 사용하고 여러 컴포넌트에서 공유해야 한다면 전역 상태 관리 도구를 사용할 수 있다.
    - 입력값의 원본은 사용자가 현재 입력하고 있는 클라이언트에 있다.
    **② 로그인 토큰**
    - 로그인 토큰은 인증 과정에서 서버가 발급하는 데이터이므로 원본은 인증 서버에서 발급하고 검증하는 데 있다.
    - 클라이언트는 이후 API 요청에서 토큰을 사용하기 위해 이를 보관해야 한다.
    - 웹 애플리케이션에서는 HttpOnly, Secure, SameSite 속성을 설정한 쿠키에 토큰을 저장하는 방식을 고려할 수 있다.
    - HttpOnly 쿠키는 JavaScript에서 직접 읽을 수 없으므로 XSS를 통한 토큰 탈취 위험을 줄이는 데 도움이 된다.
    - 쿠키를 사용하는 경우 CSRF 방어도 함께 고려해야 한다.
    - 토큰을 일반 전역 store에 저장하면 페이지 새로고침 시 상태가 사라질 수 있으며, 영속화하면 XSS에 의한 탈취 위험도 고려해야 한다.
    **③ 회원 정보**
    - 회원 이름, 이메일, 프로필 이미지 등은 서버가 원본 데이터를 관리하므로 서버 상태로 취급하는 것이 적절하다.
    - 클라이언트는 API를 통해 회원 정보를 조회하고 Query Cache에 저장하여 재사용할 수 있다.
    - 회원 정보가 변경되면 서버에서 데이터를 수정하고 Query Cache를 갱신해야 한다.
    - Zustand와 같은 전역 store에 회원 정보를 별도로 저장하면 Query Cache의 데이터와 서로 달라지는 문제가 발생할 수 있다.
  - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?
    - 전역 store와 Query Cache에 동일한 회원 정보를 저장하면 데이터의 원본이 두 곳으로 나뉘는 문제가 발생한다.
    - 예를 들어 Query Cache에는 회원 이름이 '홍길동'으로 저장되어 있고 전역 store에는 '김철수'로 저장될 수 있다.
    - 회원 정보를 수정했을 때 한쪽 상태만 갱신하면 두 저장소의 데이터가 서로 달라지는 불일치 문제가 발생한다.
    - 이를 상태 동기화 문제(State Synchronization Problem)라고 한다.
    - 두 저장소를 모두 갱신하려면 추가적인 코드와 관리 로직이 필요하며, 한쪽이라도 갱신에 실패하면 불일치가 발생할 수 있다.
    - 또한 동일한 데이터를 여러 곳에서 관리하면 불필요한 메모리 사용과 디버깅 복잡도가 증가한다.
    - 따라서 서버에서 가져온 회원 정보는 Query Cache를 단일 관리 지점으로 사용하는 것이 좋다.
    - 전역 store에는 모달 상태, 선택한 탭, 임시 UI 상태처럼 서버와 무관한 데이터를 저장하는 것이 적절하다.
- 캐시 일관성
  - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?
    - 서버에서 데이터를 수정하더라도 클라이언트에 저장된 Query Cache가 자동으로 변경되는 것은 아니다.
    - TanStack Query는 성능을 위해 기존 캐시 데이터를 재사용하므로 캐시가 유효한 상태라면 서버에 다시 요청하지 않을 수 있다.
    - 또한 회원 정보 조회에 사용한 Query Key와 수정 후 갱신한 Query Key가 서로 다르면 기존 캐시가 갱신되지 않을 수 있다.
    - 다른 컴포넌트에서 별도의 전역 store에 이전 회원 정보를 저장하고 있다면 해당 화면에서도 오래된 데이터가 표시될 수 있다.
    - 즉, 서버 데이터 변경과 클라이언트 캐시 갱신은 별개의 작업이므로 둘 사이의 동기화가 필요하다.
  - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?
    **① 변경한 데이터를 다시 조회하는 방식 (Refetch / Invalidation)**
    - 서버에서 데이터를 수정한 후 기존 캐시를 무효화하고 서버에 다시 요청하여 최신 데이터를 가져오는 방식이다.
    - TanStack Query에서는 `invalidateQueries()`를 사용하여 특정 Query Key에 해당하는 캐시를 무효화할 수 있다.
    - 캐시가 무효화되면 해당 쿼리는 다시 조회되어 서버의 최신 데이터로 갱신된다.
    - 서버에서 계산하거나 여러 데이터가 결합되어 반환되는 경우에도 최신 결과를 가져올 수 있다는 장점이 있다.
    - 반면 서버에 추가 요청을 보내야 하므로 네트워크 비용과 응답 대기 시간이 발생한다.
    - 따라서 게시글 목록, 주문 내역, 여러 조건에 따라 달라지는 검색 결과처럼 서버에서 최신 데이터를 다시 계산해야 하는 경우에 적합하다.
    **② 캐시를 직접 수정하는 방식 (Cache Update)**
    - 서버에서 데이터를 수정한 후 다시 조회하지 않고 클라이언트의 Query Cache를 직접 변경하는 방식이다.
    - TanStack Query에서는 `setQueryData()`를 사용하여 캐시에 저장된 데이터를 갱신할 수 있다.
    - 서버에서 수정된 결과를 응답으로 반환하면 해당 응답 데이터를 캐시에 바로 반영할 수 있다.
    - 추가적인 서버 조회 요청이 필요하지 않으므로 네트워크 비용을 줄이고 화면을 빠르게 갱신할 수 있다.
    - 하지만 수정된 데이터가 관련된 여러 캐시에 존재한다면 각각의 캐시를 정확하게 갱신해야 한다.
    - 따라서 회원 이름 변경처럼 수정 결과가 명확하고 다른 데이터에 영향을 주지 않는 단순한 작업에 적합하다.
