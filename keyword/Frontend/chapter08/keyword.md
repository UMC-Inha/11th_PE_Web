- 클라이언트 상태와 서버 상태
    - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.
        
        > 상태를 어디에 둘지 정할 때는 그 값을 누가 결정하는지, 누가 함께 사용하는지, 언제까지 유지해야 하는지를 살펴본다.
        > 
        
        **프로필 수정 화면**을 예로 들어 본다면, 
        
        화면에는 **서버**에서 받은 **닉네임이** 표시되고, **사용자**가 입력창에서 **새 닉네임**을 작성할 수 있다.
        **저장** 버튼을 누르면 로그인한 사용자임을 확인하기 위한 **인증 정보**도 사용한다.
        → 세 값은 같은 기능에 쓰이지만 각각 **역할이 다르다.**
        
        | 데이터 | 원본 또는 신뢰 기준 | 관리 위치 예시 | 수명 |
        | --- | --- | --- | --- |
        | 수정 중인 닉네임 | 사용자가 현재 입력한 값 | 컴포넌트의 `useState` 또는 폼 라이브러리 | 편집을 완료하거나 취소할 때까지 |
        | 액세스 토큰 또는 세션 식별자 | 서버나 인증 제공자가 발급하고 API 서버가 검증 | 서버가 설정한 쿠키 또는 인증 설계에 따른 앱 메모리 | 만료, 갱신, 로그아웃 등 인증 수명에 따름 |
        | 저장된 회원 정보 | 서버에서 관리하는 회원 데이터 | `GET /me`의 응답을 TanStack Query 캐시에 보관 | 다시 조회하거나 캐시가 갱신될 때까지 이전 응답 재사용 |
        | 모달 열림 여부 | 현재 화면에서 일어난 사용자 조작 | 컴포넌트 상태. 여러 화면에서 제어한다면 전역 UI 상태 | 화면 또는 기능의 사용 범위에 따름 |
        
        ### 입력값은 사용자가 편집하는 곳 가까이 둔다
        
        프로필의 현재 닉네임이 `영화팬`이고, 사용자가 입력창에서 `시네마팬`으로 바꿨다고 하자.
        
        ```
        서버에 저장된 닉네임 → 영화팬
        입력창에서 수정 중인 닉네임 → 시네마팬
        ```
        
        저장 버튼을 누르기 전까지 헤더에는 `영화팬`이 표시되고 입력창에는 `시네마팬`이 표시되어도 자연스럽다. 하나는 확정된 프로필이고, 다른 하나는 사용자가 작성 중인 초안이기 때문이다. 취소 버튼을 누르면 폼의 초안만 버리면 된다.
        
        ```tsx
        import { useState } from "react";
        
        type ProfileFormProps = {
          savedNickname: string;
          onSave: (nickname: string) => void;
        };
        
        function ProfileForm({
          savedNickname,
          onSave,
        }: ProfileFormProps) {
          const [draftNickname, setDraftNickname] =
            useState(savedNickname);
        
          return (
            <form
              onSubmit={(event) => {
                event.preventDefault();
                onSave(draftNickname);
              }}
            >
              <label>
                닉네임
                <input
                  value={draftNickname}
                  onChange={(event) =>
                    setDraftNickname(event.target.value)
                  }
                />
              </label>
              <button type="submit">저장</button>
            </form>
          );
        }
        ```
        
        이 예시에서는 회원 정보를 받은 뒤 폼을 처음 렌더링한다고 가정한다. `useState(savedNickname)`의 초기값은 폼이 마운트될 때 사용된다. 이후 백그라운드 조회로 `savedNickname`이 바뀌어도 편집 중인 값은 그대로 유지된다. 계정이 바뀌거나 사용자가 편집을 취소했을 때는 폼을 초기화하는 시점을 별도로 정할 수 있다.
        
        입력값도 사용 범위에 따라 위치가 달라진다. 한 폼에서 쓰는 닉네임은 그 폼에 두면 충분하다. 여러 단계에 걸쳐 작성하는 가입 폼이라면 공통 부모나 폼 상태를 사용해 다음 단계에도 값을 유지할 수 있다. 검색어와 페이지 번호처럼 새로고침 후 복원하거나 링크로 공유할 값은 URL의 검색 파라미터로 관리할 수 있다.
        
        ### 로그인 토큰은 API 요청의 인증에 사용한다
        
        로그인 토큰은 회원의 이름이나 프로필 사진을 표시하기 위한 정보와 성격이 다르다. 서버에 보호된 API를 호출할 때 제시하는 자격 증명이다.
        
        ```
        로그인 성공
            ↓
        서버 또는 인증 제공자가 자격 증명 발급
            ↓
        이후 API 요청에서 자격 증명 전달
            ↓
        API 서버가 유효성 확인
        ```
        
        브라우저 앱에서 인증 정보를 관리하는 방식은 서버의 인증 설계에 따라 달라진다.
        
        | 방식 | 프론트엔드에서의 동작 | 함께 고려할 점 |
        | --- | --- | --- |
        | 서버가 `HttpOnly` 쿠키 설정 | 브라우저가 조건에 맞는 요청에 쿠키를 포함 | `Secure`, `SameSite`, 쿠키 범위, CSRF 방어 |
        | 액세스 토큰을 앱 메모리에 보관 | 요청을 보낼 때 `Authorization` 헤더에 토큰 추가 | 새로고침 시 토큰이 사라지므로 세션 복원이나 갱신 흐름 필요 |
        | 토큰을 Web Storage에 보관 | JavaScript가 저장하고 다시 읽음 | 같은 출처에서 실행된 스크립트가 접근할 수 있어 XSS 발생 시 노출 가능 |
        
        서버가 `HttpOnly` 쿠키로 세션을 관리한다면 React에서 쿠키 값을 읽어 Zustand에 복사할 필요가 없다. 앱이 현재 회원을 알고 싶을 때는 `GET /me`를 호출하고, 서버가 쿠키를 검사해 현재 회원 정보를 응답하는 구조를 사용할 수 있다. Bearer 토큰 방식을 사용한다면 앱 메모리에 보관하는 액세스 토큰과 조회한 회원 프로필의 관리 책임을 구분할 수 있다.
        
        토큰 문자열이 브라우저에 남아 있어도 이미 만료되었을 수 있다. 화면에서 사용하는 로그인 상태는 인증 요청 결과나 `/me` 응답을 바탕으로 관리하고, 실제 접근 허용 여부는 API 서버가 요청마다 판단한다.
        
        ### 회원 정보는 서버 상태로 관리한다
        
        닉네임, 프로필 사진, 계정 상태처럼 서버에 저장되는 회원 정보의 원본은 서버에 있다. 프론트엔드에서 `useQuery`로 읽은 값은 서버가 응답한 시점의 데이터를 보관한 것이다.
        
        ```
        서버의 회원 데이터
            ↓ GET /me
        TanStack Query 캐시
            ├─ 헤더에서 닉네임 표시
            └─ 마이페이지에서 프로필 표시
        ```
        
        여러 화면이 같은 회원 정보를 사용해도, 하나의 QueryClient 안에서 같은 query key를 사용하면 같은 캐시 데이터를 읽을 수 있다. 컴포넌트가 여러 개라는 사실만으로 회원 정보를 별도의 전역 store에 다시 저장할 필요가 생기는 것은 아니다.
        
    - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?
        
        > 같은 프로필을 Zustand와 TanStack Query에 각각 저장하고 화면마다 읽는 곳이 다르면, 갱신 시점 차이로 서로 다른 프로필이 표시될 수 있다.
        > 
        
        예를 들어 로그인 응답을 `authStore.user`에 저장하고, 마이페이지에서는 `GET /me`를 호출해 `["me"]`에 저장했다고 하자.
        
        | 화면 | 표시할 닉네임을 읽는 곳 | 처음 표시되는 값 |
        | --- | --- | --- |
        | 헤더 | `authStore.user.nickname` | 영화팬 |
        | 마이페이지 | `["me"]` 쿼리의 `data.nickname` | 영화팬 |
        
        처음에는 두 값이 같아 문제가 드러나지 않는다. 이후 마이페이지에서 닉네임을 수정하고 쿼리 캐시만 갱신하면 다음처럼 된다.
        
        ```
        서버                 → 시네마팬
        TanStack Query 캐시   → 시네마팬
        Zustand의 user        → 영화팬
        
        마이페이지 → 시네마팬
        헤더      → 영화팬
        ```
        
        ### 변경 경로마다 두 저장소를 맞춰야 한다
        
        닉네임 수정 한 곳에서 두 저장소를 모두 갱신해도, 회원 정보가 바뀌는 경로가 늘면 같은 처리를 반복해야 한다.
        
        - 프로필 수정 요청의 응답을 받았을 때
        - 창으로 돌아와 `/me`가 백그라운드에서 다시 조회되었을 때
        - 로그인하거나 다른 계정으로 전환했을 때
        - 로그아웃해 기존 회원 데이터를 화면에서 제거할 때
        
        예를 들어 TanStack Query가 `/me`를 재조회해 최신 데이터를 받더라도, 결과를 별도로 Zustand에 쓰는 코드가 없다면 Zustand의 프로필은 이전 버전에 머문다. 반대로 Zustand만 최신으로 바꾸면 쿼리 캐시를 보는 화면에서 이전 값이 남는다.
        
        Zustand의 `persist`로 프로필까지 저장하면 새로고침 후 문제가 더 눈에 띌 수 있다. 이전에 저장했던 닉네임이 먼저 복원되고 `/me`에서 다른 값이 도착할 수 있기 때문이다. 로그아웃과 계정 전환을 다룰 때는 현재 앱의 인증 상태와 이전 계정의 개인 데이터 캐시를 함께 정리해야 한다.
        
        ### 회원 정보를 읽는 곳을 통일한다
        
        한 가지 방법은 현재 회원 정보를 조회하는 `useMe()`를 만들고, 헤더와 마이페이지가 모두 사용하는 것이다. 이 예시의 `getMe`는 `GET /me`를 호출하는 프로젝트의 API 함수다.
        
        ```tsx
        import { useQuery } from "@tanstack/react-query";
        
        export type Member = {
          id: string;
          nickname: string;
          avatarUrl: string | null;
        };
        
        export const meQueryKey = ["me"] as const;
        
        export function useMe(enabled: boolean) {
          return useQuery({
            queryKey: meQueryKey,
            queryFn: getMe,
            enabled,
          });
        }
        ```
        
        ```tsx
        function Header({ canLoadProfile }: { canLoadProfile: boolean }) {
          const { data: member } = useMe(canLoadProfile);
        
          return <span>{member?.nickname ?? "게스트"}</span>;
        }
        
        function MyPage({ canLoadProfile }: { canLoadProfile: boolean }) {
          const { data: member, isPending, isError } =
            useMe(canLoadProfile);
        
          if (!canLoadProfile) return <p>로그인이 필요합니다.</p>;
          if (isPending) return <p>회원 정보를 불러오는 중입니다.</p>;
          if (isError || !member) return <p>회원 정보를 불러오지 못했습니다.</p>;
        
          return <h1>{member.nickname}님의 마이페이지</h1>;
        }
        ```
        
        `canLoadProfile`은 앱이 `/me` 요청을 시작해도 되는 조건이라고 가정한다. 쿠키 기반 인증에서 `/me` 자체로 로그인 여부를 확인하는 앱이라면, 초기부터 요청을 실행하고 응답에 따라 세션 상태를 판단할 수도 있다.
        
        `["me"]`가 현재 로그인 계정에 따라 다른 결과를 반환한다는 점도 고려해야 한다. 이 키를 재사용할 경우 로그아웃이나 계정 전환 시 이전 세션의 진행 중인 조회를 취소하고 개인 데이터 캐시를 정리하는 흐름이 필요하다. 앱이 계정 ID를 조회 전에 확실히 알고 있다면 `["me", accountId]`처럼 계정별로 키를 구분할 수도 있다. `enabled: false`는 자동 조회만 끄기 때문에 기존 캐시에 남은 회원 정보를 지우지는 않는다.
        
        ### 같은 닉네임이 두 곳에 있는 게 필요한 경우도 있다
        
        `member.nickname`과 `draftNickname`처럼 의미가 다른 값은 따로 관리할 수 있다.
        
        | 값 | 의미 | 값을 바꾸는 시점 |
        | --- | --- | --- |
        | `member.nickname` | 서버가 확정한 닉네임 | 수정 성공 응답을 반영하거나 다시 조회했을 때 |
        | `draftNickname` | 사용자가 입력 중인 닉네임 | 입력창 값이 바뀔 때 |
        | `isEditorOpen` | 수정 화면이 열려 있는지 | 사용자가 편집을 시작하거나 닫을 때 |
        
        같은 문자열이 있어도 세 값은 서로 다른 변화를 표현한다. 문제가 되는 경우는 `authStore.user.nickname`과 `query.data.nickname`이 둘 다 현재 서버의 닉네임을 대표하면서 각각 독립적으로 갱신될 때다.
        
- 캐시 일관성
    - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?
        
        > 서버에 변경 사항을 저장하는 작업과, 프론트엔드가 이미 받은 응답을 갱신하는 작업은 별도로 이루어진다.
        > 
        
        `PATCH /me`가 성공하면 서버의 회원 데이터는 바뀐다. 하지만 브라우저가 앞서 `GET /me`로 받아 둔 응답까지 서버가 자동으로 교체하지는 않는다.
        
        ```
        1. GET /me 실행
           → 서버가 닉네임 "영화팬" 반환
           → ["me"] 캐시에 "영화팬" 저장
        
        2. PATCH /me 실행
           → 서버가 닉네임을 "시네마팬"으로 변경
        
        3. 기존 캐시를 읽는 헤더
           → ["me"]에 남아 있는 "영화팬" 표시
        ```
        
        TanStack Query에서 `useMutation()`으로 데이터를 수정해도 어떤 조회 결과가 영향을 받는지 자동으로 연결하지 않는다. 수정 요청이 닉네임 하나를 바꿀 수도 있고, 회원 상세, 회원 목록, 리뷰 작성자 표시처럼 여러 응답에 영향을 줄 수도 있기 때문이다. 수정이 성공한 뒤 어떤 쿼리를 어떻게 갱신할지는 애플리케이션에서 지정한다.
        
        ### 같은 화면을 다시 열어도 캐시가 재사용될 수 있다
        
        새로 마운트된 화면이 같은 query key의 데이터를 읽으면 이전 캐시를 곧바로 표시할 수 있다. 해당 데이터가 `staleTime` 기준으로 fresh라면 기본 설정에서 마운트만으로 재조회가 일어나지 않을 수 있다.
        
        ```
        12:00:00  GET /me 성공, 닉네임 "영화팬"
        12:00:20  PATCH /me 성공, 닉네임 "시네마팬"
        12:00:30  마이페이지 다시 열기
                  → staleTime이 1분이라면 기존 캐시는 여전히 fresh로 판단될 수 있음
        ```
        
        여기서 fresh는 앱이 설정한 시간 기준이다. 서버에서 그사이 수정이 있었다는 사실을 프론트엔드가 자동으로 알 수는 없다. 반대로 시간이 지나 캐시가 stale이 되더라도 기존 데이터가 즉시 삭제되거나 그 순간 네트워크 요청이 시작되지는 않는다. 활성 쿼리 무효화, 컴포넌트 마운트, 창에 다시 포커스가 오는 등 재조회 계기가 있어야 한다.
        
        ### 같은 회원이라도 응답마다 별도 캐시에 들어갈 수 있다
        
        다음 예시에서는 7번 회원의 닉네임이 세 가지 응답에 포함된다.
        
        | query key | 캐시에 담긴 결과 |
        | --- | --- |
        | `["me"]` | 로그인한 7번 회원의 프로필 |
        | `["members", "detail", "7"]` | 7번 회원의 상세 정보 |
        | `["reviews", "list", { page: 1 }]` | 리뷰 목록과 각 리뷰의 작성자 닉네임 |
        
        `["me"]` 캐시를 새 응답으로 교체하면 이 키를 읽는 헤더와 마이페이지에는 변경이 반영된다. 회원 상세나 리뷰 목록은 별도 키로 저장된 응답이므로, 해당 응답에 포함된 닉네임은 그대로 남을 수 있다. TanStack Query는 각 응답에서 `id`가 같은 객체를 찾아 공통 데이터로 합치는 캐시를 기본 제공하지 않는다.
        
        이때 먼저 확인할 것은 화면에 이전 값이 보이는 경로다.
        
        | 확인할 내용 | 이전 값이 보이는 경우 |
        | --- | --- |
        | 화면이 회원 정보를 어디서 읽는가? | 헤더는 Zustand를 읽고 수정 화면은 Query 캐시를 읽음 |
        | 정확히 어떤 query key를 사용하는가? | `["me"]`만 갱신했지만 문제 화면은 회원 상세 키를 사용함 |
        | 다른 응답에 해당 필드가 들어 있는가? | 리뷰 목록 응답의 작성자 닉네임이 별도로 저장되어 있음 |
        | 입력창의 값인가, 조회 화면의 값인가? | 조회 데이터는 갱신됐지만 폼은 사용자가 수정 중인 초안을 유지함 |
        | 다시 조회한 API 응답은 무엇인가? | 새 요청은 발생했지만 응답 본문에 여전히 이전 값이 들어 있음 |
        
        마지막 경우에는 프론트엔드 캐시를 정리하는 것만으로 원인을 설명할 수 없다. 브라우저 네트워크 탭에서 실제로 새 요청이 나갔는지, 응답에 어떤 값이 들어왔는지 보면 재조회가 안 된 경우와 서버 응답 자체가 이전 값인 경우를 구분할 수 있다.
        
        ### 화면이 최신 데이터를 알게 되는 시점
        
        현재 탭에서 직접 프로필을 수정했다면 수정 성공 시점에 관련 캐시를 갱신할 수 있다. 다른 탭, 다른 기기 또는 관리자에 의해 수정되었다면 현재 화면에는 그 성공 콜백이 실행되지 않는다. 그런 변경을 반영해야 하는 화면은 필요한 최신성에 따라 다시 방문할 때 조회하거나, 일정 간격으로 재조회하거나, 서버가 보낸 변경 알림을 받아 갱신하는 방식 등을 사용할 수 있다.
        
    - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?
        
        > 수정 응답만으로 화면에 필요한 최종 결과를 알기 어렵다면 다시 조회하기 좋다. 수정 응답이 화면에서 쓰는 최신 데이터 전체를 제공한다면 그 결과로 캐시를 바로 갱신할 수 있다.
        > 
        
        예를 들어 같은 `PATCH /me`라도 API 계약은 다음처럼 다를 수 있다.
        
        ```
        경우 A  204 No Content
                → 저장 성공 여부만 확인할 수 있음
        
        경우 B  200 OK + 수정된 회원 정보 전체
                → 화면에 필요한 최신 프로필을 응답에서 얻을 수 있음
        
        경우 C  200 OK + 변경된 닉네임 한 필드
                → 해당 필드는 알 수 있지만, 전체 프로필에 미친 영향은 응답만으로 알기 어려울 수 있음
        ```
        
        ### 방법 1. `invalidateQueries()`로 관련 데이터 다시 조회하기
        
        `invalidateQueries()`는 지정한 쿼리를 무효화한다. 기본적으로 일치하는 쿼리 중 활성 쿼리는 백그라운드에서 다시 조회한다. 화면에서 사용하지 않는 쿼리는 보통 캐시에 남아 있다가 이후 사용 조건을 충족할 때 조회한다. 비활성화된 쿼리에는 일반 활성 쿼리와 같은 자동 재조회 동작을 기대할 수 없으므로 `enabled`와 재조회 설정도 함께 확인한다.
        
        ```
        import {
          useMutation,
          useQueryClient,
        } from "@tanstack/react-query";
        
        type UpdateProfileInput = {
          nickname: string;
        };
        
        function useUpdateProfile() {
          const queryClient = useQueryClient();
        
          return useMutation({
            // PATCH /me가 성공 시 204를 반환한다고 가정
            mutationFn: (input: UpdateProfileInput) =>
              updateProfile(input),
        
            onSuccess: async () => {
              await queryClient.invalidateQueries({
                queryKey: ["me"],
                exact: true,
              });
            },
          });
        }
        ```
        
        `exact: true`는 정확히 `["me"]`에 해당하는 쿼리를 지정한다. 반대로 `queryKey: ["members", "list"]`를 일치 조건으로 사용하고 `exact`를 생략하면, 그 키로 시작하는 검색·페이지별 회원 목록 쿼리를 함께 무효화할 수 있다.
        
        `onSuccess`에서 무효화의 Promise를 기다리면 해당 재조회 과정이 끝날 때까지 mutation의 대기 상태를 유지할 수 있다. 재조회가 끝나기 전에도 기존 캐시는 남아 있을 수 있어서, 조회 화면에서는 현재 내용을 유지하고 작은 갱신 표시를 추가하는 식으로 표현할 수 있다.
        
        다시 조회하기 적절한 경우는 다음과 같다.
        
        - 수정 API가 `204`를 반환하거나 성공 여부만 알려준다.
        - 서버가 닉네임의 앞뒤 공백을 제거하는 등 최종 값을 가공한다.
        - 필드 하나의 변경으로 권한 표시, 합계, 집계 값 등 다른 필드도 달라진다.
        - 목록의 필터, 정렬, 페이지 경계가 달라져서 변경된 항목이 어느 위치에 들어갈지 서버가 결정한다.
        
        예를 들어 닉네임으로 정렬된 회원 목록에서는 닉네임이 바뀌면 회원의 위치가 다른 페이지로 이동할 수 있다. 캐시에서 해당 행의 이름만 바꾸면 이름은 최신이지만 정렬 순서와 페이지 구성은 이전 상태에 머문다. 회원 목록 쿼리를 다시 조회하면 서버가 결정한 순서와 구성까지 받을 수 있다.
        
        ### 방법 2. `setQueryData()`로 수정 응답을 반영하기
        
        `setQueryData()`는 지정한 query key의 캐시를 직접 갱신한다. 수정 API가 `GET /me`와 같은 형태의 최신 프로필을 반환한다면 추가 GET 없이 그 응답을 사용할 수 있다.
        
        ```
        import {
          useMutation,
          useQueryClient,
        } from "@tanstack/react-query";
        
        type Member = {
          id: string;
          nickname: string;
          avatarUrl: string | null;
        };
        
        function useUpdateProfile() {
          const queryClient = useQueryClient();
        
          return useMutation({
            // 서버가 확정한 최신 Member 객체를 반환하는 API 함수
            mutationFn: updateProfileAndReturnMember,
        
            onSuccess: (updatedMember: Member) => {
              queryClient.setQueryData<Member>(
                ["me"],
                updatedMember,
              );
            },
          });
        }
        ```
        
        ```
        PATCH /me 성공
            ↓
        서버가 최신 프로필 반환
            ↓
        setQueryData로 ["me"] 교체
            ↓
        같은 키를 읽는 헤더와 마이페이지가 최신 닉네임 표시
        ```
        
        중요한 것은 `setQueryData()`에 어떤 값을 넣느냐다. 사용자가 보낸 폼 값은 요청 내용이고, 수정 응답은 서버가 반영한 결과다. 예를 들어 `" 시네마팬 "`을 보냈지만 서버가 공백을 제거해 `"시네마팬"`을 응답했다면, 캐시에는 서버가 확정한 값을 넣는 편이 일관된다.
        
        응답에 수정된 닉네임만 포함된다면, 해당 필드만 바뀐다는 API 계약을 바탕으로 기존 프로필과 합칠 수 있다.
        
        ```
        queryClient.setQueryData<Member>(
          ["me"],
          (previous) => {
            if (previous === undefined) {
              return undefined;
            }
        
            return {
              ...previous,
              nickname: response.nickname,
            };
          },
        );
        ```
        
        위 코드는 기존 회원 객체를 직접 변경하지 않고 새 객체를 만들어 반환한다. 기존 캐시가 없는 경우에는 닉네임만으로 완전한 회원 객체를 만들 수 없으므로 갱신을 건너뛴다. 유효한 프로필 전체가 필요한 화면에서는 다시 조회해 채울 수 있다.
        
        ### 방법 3. 상세는 직접 반영하고, 목록은 다시 조회하기
        
        같은 수정에서도 화면별로 다른 방법을 적용할 수 있다. 서버가 수정된 회원 객체 전체를 응답한다면 내 프로필과 회원 상세를 즉시 갱신할 수 있다. 반면 이름순으로 정렬되거나 검색어에 따라 구성되는 목록은 다시 조회하는 편이 정확하다.
        
        ```
        onSuccess: async (updatedMember: Member) => {
          queryClient.setQueryData<Member>(
            ["me"],
            updatedMember,
          );
        
          queryClient.setQueryData<Member>(
            ["members", "detail", updatedMember.id],
            updatedMember,
          );
        
          await queryClient.invalidateQueries({
            queryKey: ["members", "list"],
          });
        },
        ```
        
        이 코드는 `["me"]`와 회원 상세 쿼리가 둘 다 같은 `Member` 구조를 사용한다고 가정한다. 회원 상세 응답에 추가 필드가 있다면 프로필 객체로 그대로 교체할 경우 그 필드가 사라질 수 있다. 그런 경우에는 알려진 필드만 병합하거나 회원 상세를 별도로 무효화할 수 있다.
        
        ### 서버 성공 후 반영과 낙관적 업데이트
        
        위의 직접 갱신 예시는 서버가 성공 응답을 준 뒤 캐시를 수정한다. 북마크 버튼처럼 클릭 즉시 결과를 보여주고 싶다면, 응답이 오기 전에 성공을 가정해 화면을 변경하는 낙관적 업데이트를 사용할 수 있다.
        
        ```
        서버 성공 후 반영
        저장 요청 → 성공 응답 → 캐시 갱신
        
        낙관적 업데이트
        저장 요청과 함께 화면 갱신 → 성공하면 확정
                                 → 실패하면 복구 또는 재조회
        ```
        
        캐시를 직접 변경하는 낙관적 업데이트에서는 이전 값을 저장하고, 진행 중인 조회가 임시 값을 덮지 않도록 처리하며, 수정이 실패하면 이전 값으로 되돌리는 흐름이 필요하다. 프로필의 여러 필드를 한 번에 저장하고 서버 검증 결과를 보여줘야 하는 폼이라면 성공 응답을 받은 시점에 반영하는 방식이 더 단순하다.
