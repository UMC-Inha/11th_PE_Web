- 클라이언트 상태와 서버 상태
  - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.
    - **입력값 (Client State)**
      - 관리 위치: useState, Zustand
      - 예시: 로그인 폼의 이메일, 비밀번호, 검색어
      - 원본: 사용자가 현재 브라우저에서 입력한 값
      - 특징: 서버에 저장되기 전까지 클라이언트에서 관리하는 상태
      - 컴포넌트 내부에서만 사용한다면 useState, 여러 컴포넌트에서 공유한다면 Zustand 등을 사용할 수 있음
    - **로그인 토큰 (Authentication State)**
      - 관리 위치: 인증 전용 Store 또는 쿠키
      - 예시: Access Token, Refresh Token
      - 원본: 인증 서버에서 발급한 토큰
      - 특징: 사용자의 인증 여부를 확인하기 위한 자격 증명
      - Access Token은 메모리 등에 저장할 수 있고, Refresh Token은 보안상 HttpOnly, Secure 쿠키에 저장하는 방식을 고려할 수 있음
    - **회원 정보 (Server State)**
      - 관리 위치: TanStack Query의 Query Cache
      - 예시: 회원 이름, 이메일, 프로필 이미지, 회원 등급
      - 원본: 서버 DB
      - 특징: 서버에서 데이터를 가져와 클라이언트에 캐싱하여 사용하는 상태
      - 여러 컴포넌트에서 회원 정보가 필요하더라도 Query Cache를 통해 공유할 수 있음
  - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?
    - 동일한 데이터를 두 곳에서 관리하면 데이터 불일치 문제가 발생할 수 있음
    - 예를 들어 Zustand와 Query Cache에 모두 회원 이름을 저장했다고 가정함
      - Zustand: 철수
      - Query Cache: 철수
      - 회원 이름을 영희로 수정했을 때 Query Cache만 갱신하면 Zustand에는 여전히 철수가 남아 있음
    - 주요 문제
      - **데이터 불일치:** 화면마다 서로 다른 회원 정보가 표시될 수 있음
      - **동기화 비용 증가:** 데이터가 변경될 때마다 두 저장소를 모두 업데이트해야 함
      - **버그 발생 가능성:** 로그아웃, 회원 정보 수정, 재조회 등의 상황에서 어떤 데이터가 최신인지 판단하기 어려워짐
    - 권장 구조
      - Zustand: Access Token, 인증 관련 상태
      - TanStack Query: 회원 정보, 게시글 목록, 상세 정보 등 서버 데이터
- 캐시 일관성
  - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?
    - 서버 DB와 클라이언트의 Query Cache가 서로 독립적으로 동작하기 때문
    - TanStack Query는 서버에서 가져온 데이터를 캐시에 저장하고 재사용함
    - 따라서 서버 DB의 데이터가 변경되더라도 기존 Query Cache가 자동으로 변경되는 것은 아님
    - 예시
      - 마이페이지에서 회원 이름 철수를 조회함.
      - 회원 정보 수정 API를 호출해 서버 DB의 이름을 영희로 변경함.
      - 다른 화면에서 기존 Query Cache를 사용함.
      - 서버 DB에는 영희가 저장되어 있지만 화면에는 이전 값인 철수가 표시될 수 있음.
    - 주요 원인
      - 서버 데이터를 수정한 후 관련 Query Cache를 갱신하지 않은 경우
      - 화면마다 서로 다른 Query Key를 사용해 별도의 캐시가 존재하는 경우
      - staleTime 등 캐시 정책에 따라 기존 데이터가 재사용되는 경우
  - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?
    - **변경한 데이터를 다시 조회하는 방식**
      - 기존 캐시를 오래된 데이터로 표시하고 서버에서 다시 조회하도록 유도하는 방식
      - 예시

        ```tsx
        queryClient.invalidateQueries({
          queryKey: ["me"],
        });
        ```

      - 주요 특징
        - 기존 캐시를 무효화 상태로 표시함
        - 활성화된 관련 Query는 기본적으로 다시 요청함
        - 비활성 Query는 나중에 사용될 때 다시 조회할 수 있음
      - 적절한 상황
        - 서버에서 계산한 최신 결과를 다시 가져와야 할 때
        - 여러 데이터가 함께 변경되어 정확한 캐시 갱신이 어려울 때
        - 목록의 정렬, 페이지네이션, 데이터 개수 등이 영향을 받을 때
      - 장점: 서버의 최신 데이터를 다시 가져오므로 데이터 일관성을 유지하기 쉬움
      - 단점: 추가 API 요청이 발생하고 네트워크 비용이 증가할 수 있음
    - **캐시를 직접 수정하는 방식**
      - 서버에 다시 요청하지 않고 Query Cache의 데이터를 직접 변경하는 방식임
      - 예시

        ```tsx
        queryClient.setQueryData(
          ["me"],
          updatedMember
        );
        ```

      - 주요 특징
        - 캐시에 저장된 데이터를 직접 수정함
        - 서버에 추가 요청을 보내지 않음
        - 변경된 데이터를 즉시 화면에 반영할 수 있음
      - 적절한 상황
        - 수정 API가 변경된 데이터를 응답으로 반환할 때
        - 어떤 데이터가 어떻게 변경됐는지 명확할 때
        - 추가 조회 없이 빠르게 화면을 갱신하고 싶을 때
      - 장점: 불필요한 API 요청을 줄이고 빠르게 화면에 반영할 수 있음
      - 단점: 관련된 다른 캐시까지 직접 관리해야 하므로 데이터 불일치가 발생하지 않도록 주의해야 함
    - **두 방식을 함께 사용하는 경우**
      - 모든 데이터를 반드시 한 가지 방식으로만 갱신할 필요는 없음
      - 예를 들어 회원 정보를 수정했다면 다음과 같이 처리할 수 있음
        - 회원 상세 정보: setQueryData로 즉시 갱신
        - 회원 목록: invalidateQueries로 다시 조회
      - 수정된 데이터는 바로 반영하면서, 영향을 받는 다른 데이터는 서버에서 다시 가져오는 방식
    - **추가 개념: 낙관적 업데이트**
      - 서버의 응답을 기다리지 않고 요청이 성공할것이라고 가정해 캐시를 먼저 변경하는 방식
      - 예를 들어 좋아요 버튼을 누르면 서버 응답을 기다리지 않고 좋아요 수를 먼저 증가
      - 실제 요청이 실패하면 이전 캐시 데이터로 되돌리는 롤백 처리가 필요
      - 사용자에게 빠른 반응을 제공할 수 있지만, 실패 상황까지 고려해야 함
