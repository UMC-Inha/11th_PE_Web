- 클라이언트 상태와 서버 상태

  클라이언트 상태 : 브라우저(프론트엔드) 내부에서 관리되는 데이터

  useState, Zustand, Context 등

  네트워크 요청이 필요 X → 서버 상태보다 접근 및 업데이트 속도 빠름

  세션간 지속성이 유지되진 않음, but 로컬 스토리지나 세션 스토리지를 이용하면 세션이 끝나도 유지 가능

  ex) 다크모드 여부, input 값 등

  서버 상태 : 서버에 저장되어 있고, 네트워크를 통해 가져오는 데이터

  React-Query, SWR 등

  동기 요청이 필요하다

  캐싱, 재요청, 동기화 문제가 존재

  인증, 암호화로 보호할 수 있어 더 안전하다.

  세션 간 지속성이 항상 유지 → 서버에서 데이터를 다시 요청하면 언제든 불러올 수 있다.

  ex) 게시글 목록, 상품 정보

    - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.

      입력값 : 클라이언트 상태로 관리

      → 사용자가 입력하는 동안 해당 화면에서만 필요

      로그인 토큰 : 클라이언트 상태로 관리

      → 여러 화면, 기능들에서 사용하고 Authorization 헤더에 넣어야하기 때문

      회원 정보 : 서버 상태

      → 실제 데이터는 서버 DB에 있고 이를 조회, 캐싱해서 보여준다.

    - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?

      데이터 원본이 두 개가 된다

      → 화면마다 회원 정보가 다름, 수정할 때 두 곳 모두 수정을 해야 하는 등의 문제가 생긴다.

- 캐시 일관성

  캐시 일관성 : 여러 로컬 캐시에 저장된 공유 리소스 데이터의 균일성

  → 여러 클라이언트가 공유 메모리 리소스의 동일한 영역에 대한 캐시된 복사복을 갖고 있다면 모든 복사본은 동일하다. (→ 깊은 복사 느낌. 같진 않다)

![image1.png](images/image1.png)

  캐시 일관성을 위해선 “쓰기 전파"와 “트랜잭션 직렬화”가 필요하다

  쓰기 전파 : 모든 캐시의 데이터 변경은 피어 캐시에 있는 다른 복사본에 전파되어야 한다.

  → 같은 데이터의 복사본이 여러 캐시에 있다면, 한 곳에서 수정한 내용을 다른 캐시에서도 같이 바꿔야 한다.

  트랜잭션 직렬화 : 단일 메모리 위치에 대한 읽기/쓰기는 모든 프로세서에 의해 동일한 순서로 보여야 한다.

  → 여러 프로세서가 같은 데이터를 동시에 읽고 수정할 때, 누가 먼저 수정했는지 순서를 모두 똑같이 봐야 한다.

  일관성을 보장하는 메커니즘 : 스누핑, 디렉터리 기반

  스누핑 : 개별 캐시가 아닌 자신이 캐시한 메모리 위치에 대한 접근을 위해 주소 라인을 모니터링하는 과정

  디렉터리 기반 : 기렉터리 기반 시스템에서 공유되는 데이터는 캐시 간의 일관성을 유지하는 공통 디렉터리에 배치

    - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?

      서버 데이터는 수정되었지만, 다른 화면은 이전 캐시 데이터를 보여주고 있기 때문이다.

      해결법 → 캐시의 해당 데이터를 새 응답값으로 갱신 OR 관련 Query를 무효화해서 다시 조회하게 한다.

    - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?

      다시 조회하는 방식 → 서버가 수정 후 어떤 값을 최종적으로 저장했는지 다시 받아와야할 때

      →정확성, 단순함이 우선일 때

      캐시 직접 수정 방식 → 수정 성공 응답에 최신 데이터가 포함되어 있고, 무엇이 바꼈는지 명확할 때

      →즉시 반영, 요청 감소가 우선일 때
