- 클라이언트 상태와 서버 상태
    - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.

      #### **1. 원본이 어디에 있느냐로 나눈다**

        - 클라이언트 상태는 원본이 브라우저(내 화면)에 있는 값이다. 서버에 물어보지 않아도 지금 값을 정확히 안다.
        - 서버 상태는 원본이 서버 DB에 있는 값이다. 화면이 가진 것은 잠깐 받아 온 복사본이라 그사이 서버에서 바뀌었을 수 있다.
        - 도서관에 비유하면, 내 공책에 쓴 메모는 내가 원본을 가진 클라이언트 상태이고, 도서관에서 빌려 온 책은 원본이 도서관에 있는 서버 상태이다.

      | **데이터** | **원본 위치** | **관리하는 곳** | **이유** |
              | --- | --- | --- | --- |
      | 입력값 (회원가입, 로그인 폼) | 지금 이 화면 | useState | 그 화면에서만 쓰고, 화면을 떠나면 필요 없다. |
      | 로그인 토큰 | 브라우저 (서버가 준 것을 내가 보관) | Zustand persist | 여러 화면과 요청에서 쓰고, 새로고침해도 남아야 한다. 서버에 다시 달라고 할 수 없다. |
      | 회원 정보 (닉네임, 이메일) | 서버 DB | TanStack Query 캐시 | 원본이 서버에 있어서 언제든 다시 받을 수 있고, 최신인지 관리해야 한다. |

      #### **2. 우리 코드에서**

        ```tsx
        const [form, setForm] =useState(DEFAULT_LOGIN_FORM);
        
        const accessToken =useAuthStore((state) => state.accessToken);
        
        const meQuery =useQuery({
          queryKey: ["members", "me"],
          queryFn: getMe,
          enabled: Boolean(accessToken),
          staleTime: 5 *60 *1000,
        });
        ```

        - 위 코드는 세 가지 상태를 각자 맞는 곳에서 꺼낸다. 로그인 폼 입력값은 useState, 토큰은 auth-store, 회원 정보는 useQuery이다.
        - 토큰은 서버가 로그인할 때 한 번 준 값이라 클라이언트가 원본처럼 들고 있어야 한다. 반면 닉네임은 서버에 계속 있으니 필요할 때 받아 와 캐시에 둔다.

    - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?

      #### **1. 복사본이 두 개가 되어 서로 달라진다**

        - 같은 닉네임이 Zustand store에도, query 캐시에도 있으면 복사본이 두 개가 된다.
        - 닉네임을 수정하고 한쪽만 바꾸면, store를 읽는 화면과 캐시를 읽는 화면에 서로 다른 닉네임이 보인다.
        - 단톡방 공지를 두 군데에 적어 두었다가 한 곳만 고치면, 어느 쪽이 맞는지 헷갈리는 것과 같다.

      | **상황** | **store에 저장한 닉네임** | **query 캐시의 닉네임** | **결과** |
              | --- | --- | --- | --- |
      | 로그인 직후 | zerozero | zerozero | 같음 |
      | 내 정보 수정 후 setQueryData만 함 | zerozero (그대로) | 새닉네임 | 헤더와 마이페이지가 서로 다르게 보임 |
      | 다른 기기에서 닉네임 수정 | zerozero (모름) | 다시 조회하면 새닉네임 | store 쪽은 계속 옛날 값 |

      #### **2. 그래서 한 곳에만 둔다**

        - 서버에 원본이 있는 회원 정보는 query 캐시 한 곳에만 둔다. 모든 화면이 같은 queryKey로 같은 칸을 읽는다.
        - 우리 코드에서는 헤더, 마이페이지, 내 정보 수정 화면이 모두 ["members", "me"]를 읽는다. 그래서 닉네임을 수정하고 setQueryData를 한 번 하면 세 화면이 동시에 바뀐다.
        - store에는 서버에서 다시 받을 수 없는 토큰만 둔다.

- 캐시 일관성
    - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?

      #### **1. 화면은 캐시에 있는 복사본을 보여 준다**

        - TanStack Query는 한 번 받아 온 데이터를 캐시에 저장하고, staleTime 동안은 최신이라고 믿고 다시 요청하지 않는다.
        - 서버에서 데이터가 바뀌어도 캐시는 그 사실을 모른다. 그래서 캐시를 읽는 화면에는 이전 값이 그대로 보인다.
        - 이렇게 서버의 원본과 캐시의 복사본이 서로 다른 상태를 캐시 일관성이 깨졌다고 한다.

      | **순서** | **서버 DB** | **캐시 ["members", "me"]** | **마이페이지** |
              | --- | --- | --- | --- |
      | 1. 내 정보 조회 | zerozero | zerozero | zerozero |
      | 2. 닉네임 수정 요청 성공 | 새닉네임 | zerozero | zerozero |
      | 3. 캐시를 갱신하지 않으면 | 새닉네임 | zerozero (staleTime 5분 동안 그대로) | zerozero (이전 값) |

      #### **2. 해결은 수정 뒤에 캐시를 맞춰 주는 것**

        - 데이터를 바꾸는 요청이 성공하면, 그 데이터를 담고 있는 캐시도 같이 갱신해야 한다.
        - 방법은 두 가지이다. 캐시를 낡았다고 표시해서 다시 받아 오게 하거나(invalidateQueries), 새 값을 캐시에 직접 넣는다(setQueryData).
        - 이때 조회할 때 쓴 queryKey와 같은 key를 써야 같은 칸이 갱신된다.

    - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?

      #### **1. 두 방식의 차이**

        - invalidateQueries는 지정한 key의 캐시를 낡았다고 표시한다. 그 데이터를 쓰는 화면이 있으면 staleTime이 남아 있어도 바로 다시 요청한다.
        - setQueryData는 지정한 key의 캐시 값을 직접 바꾼다. 서버에 다시 묻지 않는다.

      | **구분** | **invalidateQueries (다시 조회)** | **setQueryData (직접 수정)** |
              | --- | --- | --- |
      | 요청 수 | 변경 요청 + 다시 조회 요청 | 변경 요청만 |
      | 화면이 바뀌는 시점 | 다시 조회한 응답이 도착한 뒤 | 변경 응답이 도착하자마자 |
      | 정확성 | 서버 원본을 다시 받으니 항상 정확하다. | 넣는 값이 정확해야 한다. |
      | 적절한 상황 | 응답에 새 데이터가 없을 때, 바뀐 데이터가 여러 곳일 때 | 응답에 바뀐 결과가 그대로 담겨 올 때 |

      #### **2. 우리 코드에서**

        ```tsx
        onSuccess: (response) => {
          setAccessToken(response.result.accessToken);
          queryClient.invalidateQueries({ queryKey: ["members", "me"] });
          navigate({ to: "/" });
        },
        ```

        - 위 코드는 로그인 성공 처리이다. 로그인 응답에는 닉네임과 토큰만 있고 이메일, 가입 시각은 없다. 그래서 내 정보를 직접 만들 수 없어 다시 조회하는 방식을 쓴다.

        ```tsx
        onSuccess: (response) => {
          queryClient.setQueryData<MemberInfo>(["members", "me"], response.result);
        },
        ```

        - 위 코드는 닉네임 수정 성공 처리이다. 수정 응답의 result에 이메일, 바뀐 닉네임, 가입 시각이 모두 담겨 와서, 내 정보 조회 응답과 같은 모양이다. 그래서 다시 조회하지 않고 캐시에 바로 넣는다.
        - Network 탭에서 확인하면 수정 요청 뒤에 내 정보 조회 요청이 추가로 나가지 않는다.
        - 요청에 보낸 값으로 캐시를 바꿀 수도 있지만, 서버가 값을 바꾸어 저장하거나 다른 값도 함께 바꾸면 보낸 값과 실제 값이 달라진다. 이럴 때는 응답 값을 쓰거나 다시 조회한다.
