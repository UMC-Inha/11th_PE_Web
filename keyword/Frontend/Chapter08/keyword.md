- 클라이언트 상태와 서버 상태
    - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.
    
    상태를 관리할 때는 **데이터의 원본이 어디에 있는지, 여러 컴포넌트에서 공유해야 하는지**를 기준으로 구분하는 것이 좋다.
    
    - **입력값 (useState)**: 이메일이나 비밀번호처럼 사용자가 직접 입력하는 값은 컴포넌트 내부에서 관리하는 것이 적절하다. 다른 화면과 공유할 필요가 없다면 전역 상태로 관리할 이유가 없다.
    - **로그인 토큰 (Zustand + persist)**: 서버에서 발급하지만 클라이언트가 API 요청에 사용하기 위해 보관하는 값이다. 여러 컴포넌트에서 인증 상태를 참조하므로 전역 store로 관리할 수 있다.
    - **회원 정보 (TanStack Query)**: 닉네임, 이메일처럼 서버 DB에 원본이 존재하는 데이터는 query 캐시로 관리하는 것이 적절하다. 동일한 query key를 사용하면 여러 컴포넌트에서 데이터를 공유할 수 있다.
    
    추가로 **토큰이 저장되어 있다는 사실이 유효한 로그인 상태를 보장하는 것은 아니다.** 토큰이 만료되었거나 서버에서 무효화되었을 수도 있기 때문에 실제 인증 여부는 서버에서 확인해야 한다.
    
    - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?
    
    가장 큰 문제는 **동일한 데이터가 서로 다른 값을 가지는 상태 불일치**가 발생할 수 있다는 점이다.
    
    예를 들어 마이페이지에서 닉네임을 변경한 후 TanStack Query의 캐시만 갱신했다고 가정한다. 헤더가 Zustand의 닉네임을 참조하고 있다면 마이페이지에는 새로운 닉네임이 표시되지만 헤더에는 이전 닉네임이 남아 있을 수 있다.
    
    이처럼 동일한 데이터를 중복 저장하면 동기화 코드가 추가로 필요하고, 어느 값이 최신인지 판단하기 어려워진다.
    
    따라서 **전역 store에는 인증 정보나 UI 상태를, query 캐시에는 서버 데이터를 저장하는 방식**으로 역할을 구분하는 것이 좋다.
    
    또한 로그아웃하거나 다른 계정으로 로그인할 때는 이전 사용자의 데이터가 캐시에 남지 않도록 관리해야 한다.
    
- 캐시 일관성
    - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?
    
    TanStack Query는 서버에서 받아온 데이터를 캐시에 저장하고 재사용한다. 따라서 서버의 데이터가 변경되더라도 **기존 캐시가 자동으로 수정되는 것은 아니다.**
    
    예를 들어 영화 상세 페이지에서 즐겨찾기를 추가했는데 마이페이지의 즐겨찾기 목록에는 해당 영화가 보이지 않을 수 있다. 서버에서는 추가가 완료되었지만 목록 조회에 사용되는 캐시는 갱신되지 않았기 때문이다.
    
    여기서 중요한 개념은 **staleTime과 데이터의 실제 최신성은 다르다**는 점이다.
    
    `staleTime`은 캐시 데이터를 얼마 동안 최신으로 취급할지 결정하는 설정일 뿐, 서버 데이터가 변경되었는지를 실시간으로 확인하는 기능은 아니다.
    
    또한 query key가 다르면 별도의 캐시로 관리되므로, 동일한 데이터를 여러 화면에서 사용한다면 query key를 일관되게 설계해야 한다.
    
    - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?
    
    **invalidateQueries는 정확성, setQueryData는 불필요한 재요청을 줄이는 데 장점이 있다.**
    
    - **invalidateQueries**: 데이터 변경 후 서버에서 최신 결과를 다시 확인해야 하는 경우에 적절하다. 예를 들어 즐겨찾기 추가 후 목록의 순서나 전체 개수가 서버에서 결정되는 경우에 사용할 수 있다.
    - **setQueryData**: 서버의 성공 응답에 변경된 데이터가 충분히 포함되어 있다면 적절하다. 별도의 GET 요청 없이 기존 캐시를 변경할 수 있어 화면을 빠르게 갱신할 수 있다.
    
    예를 들어 다음과 같이 사용할 수 있다.
    
    ```tsx
    queryClient.invalidateQueries({
      queryKey: ["favorites"],
    });
    ```
    
    즐겨찾기 목록을 다시 확인해야 하는 경우다. 해당 캐시를 무효화하여 활성화된 query가 최신 데이터를 다시 조회하도록 한다.
    
    ```tsx
    queryClient.setQueryData(
      ["members", "me"],
      response.result
    );
    ```
    
    닉네임 수정 API가 수정된 회원 정보를 반환하는 경우다. 응답 데이터를 그대로 캐시에 저장하여 추가 조회 없이 화면에 반영할 수 있다.
    
    추가로 알아두면 좋은 개념은 **낙관적 업데이트(Optimistic Update)**다. 서버 응답을 기다리지 않고 변경 결과를 화면에 먼저 보여주는 방식이다.
    
    예를 들어 즐겨찾기 버튼을 누르자마자 하트 아이콘을 활성화할 수 있다. 다만 서버 요청이 실패하면 기존 상태로 되돌리는 **롤백(Rollback)** 처리가 필요하다.
    
    즉, 단순히 화면을 빠르게 갱신하는 것뿐만 아니라 **서버 데이터와 캐시가 최종적으로 같은 상태를 유지하도록 만드는 것**이 캐시 관리의 핵심이다.
