- 클라이언트 상태와 서버 상태
    - 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.
        - **입력값**: 사용자가 브라우저에서 작성 중인 값 → 컴포넌트의 `useState`로 관리. 서버에 저장하기 전의 닉네임 수정 초안 등이 해당.
        - **로그인 토큰**: 서버가 발급하고 프론트에서 보관하는 인증 수단. 이 실습에서는 Zustand store로 공유하고 `persist`로 새로고침 후 복원. 실제 유효성은 서버에서 판단.
        - **회원 정보**: 원본은 서버에 있고 프론트에는 조회한 사본이 존재 → TanStack Query 캐시로 관리. `useQuery`로 데이터·로딩·오류와 재조회를 함께 처리.
    - 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?
        - 같은 정보의 복사본이 두 곳에 생겨 둘 다 갱신해야 하는 부담 증가. 한쪽만 수정하면 화면마다 다른 닉네임을 표시할 수 있음.
        - 예: `setQueryData`로 캐시의 닉네임을 바꿔도 Zustand에 복사해 둔 닉네임까지 자동 변경되는 것은 X.
        - 조회한 회원 정보는 query 캐시를 공통 출처로 사용하고, 전역 store는 토큰 등 별도로 공유할 상태에 사용.

  **추가 핵심 정리**

    - **편집 초안 분리**: 서버에서 조회한 값과 저장 전 입력값은 역할이 다름. 폼 초안을 로컬 상태로 관리하면 취소·검증이 편리하고, 저장 성공 후 서버 응답으로 캐시 갱신.
    - **파생값**: `canSubmit`처럼 기존 상태에서 계산할 수 있는 값은 매 렌더링에서 계산. 별도 상태로 중복 저장할 필요 X.

- 캐시 일관성
    - 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?
        - 서버 데이터와 브라우저의 query 캐시는 별개. 수정 요청에 성공해도 관련된 모든 캐시가 자동으로 바뀌는 것은 X.
        - 예: 서버 닉네임은 변경됐지만 `["members", "me"]` 캐시에 이전 응답이 남아 있으면 조회 화면도 이전 값을 표시.
        - `staleTime`은 캐시를 최신으로 취급하는 시간이며, 그동안 서버와 자동으로 동기화한다는 뜻은 X.
    - 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?
        - **다시 조회 — invalidateQueries**: 변경의 영향 범위가 넓거나 수정 응답만으로 최신 상태를 구성하기 어려울 때 사용. 일반적인 설정에서 대상 query를 stale로 표시하고, 화면에서 사용 중인 활성 query는 백그라운드 재조회. 서버의 최종 값을 가져오는 대신 추가 요청과 응답 대기 발생.
        - **직접 수정 — setQueryData**: 수정 응답에 필요한 최신 데이터가 담겨 있을 때 적합. 워크북에서는 닉네임 수정 응답의 `result`가 내 정보와 같은 형태이므로 그대로 캐시에 저장 → 갱신을 위한 GET 요청을 줄이고 즉시 반영.
        - 직접 수정은 어느 캐시를 어떻게 바꿀지 판단해야 하는 부담이 있음. 목록·상세 등 다른 query에도 영향이 있다면 해당 캐시의 갱신도 고려.

        ```tsx
        queryClient.setQueryData(["members", "me"], response.result);
        ```


    **추가 핵심 정리**
    
    - **캐시 공유**: 같은 QueryClient 안에서 동일한 query key를 사용해야 같은 데이터를 공유. 화면도 고정값 대신 query 데이터를 표시해야 갱신 결과가 보임.
    - **불변성**: 기존 캐시 객체를 직접 수정하지 않고 새 객체로 갱신. 수정 응답이 최신 전체 값을 제공한다면 그 응답을 사용하는 방식이 간단.
