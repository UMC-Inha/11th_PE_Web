# Frontend Chapter08

## 키워드 정리

### 클라이언트 상태와 서버 상태

#### 입력값, 로그인 토큰과 회원 정보는 각각 어디에서 관리하는 것이 적절할까요? 각 상태의 원본이 어디에 있는지도 함께 생각해 보세요.

**판단 기준: 값의 원본이 어디에 있는지 + 값의 사용 목적**

| 상태 | 원본 또는 판단 기준 | 관리 위치 |
| --- | --- | --- |
| 폼 입력값 | 사용자가 현재 입력한 값 | 컴포넌트 상태(useState) 또는 폼 라이브러리 |
| 로그인 토큰 | 서버가 발급하고 유효성을 판단하는 인증 정보 | 인증 구조에 따라 쿠키 또는 메모리 등에서 관리 |
| 회원 정보 | 서버에 저장된 회원 데이터 | useQuery로 조회하고 Query 캐시에서 관리 |

- 폼 입력값: 서버에서 가져온 닉네임을 초기값으로 사용하더라도, 수정 중인 값은 저장 전까지 클라이언트의 초안
- 회원 정보: Query 캐시에 있는 값은 마지막으로 확인한 서버 데이터의 사본
- 로그인 토큰: 화면에 표시하는 조회 데이터가 아니라 요청에 사용하는 인증 정보. 일반적인 Query 캐시 관리 대상과 구분

#### 같은 회원 정보를 전역 store와 query 캐시에 각각 저장하면 어떤 문제가 생길 수 있을까요?

- 값 불일치: 한쪽만 갱신하면 화면마다 다른 정보 표시
- 관리 부담: 회원 정보 수정이나 로그아웃 시 두 곳을 각각 갱신·정리해야 함
- 권장 구조: 헤더와 프로필에서 동일한 `['me']` Query Key를 사용해 하나의 캐시 공유. 전역 store는 공통 UI 상태 등 별도 용도로 사용

→ 여러 화면에서 같은 데이터를 사용하는 것이 아니라, 따로 관리해야 하는 사본이 여러 개 생기는 것이 문제

### 캐시 일관성

#### 서버에서 데이터를 수정했는데 다른 화면에는 이전 값이 보이는 이유는 무엇인가요?

- 수정 API의 성공 ≠ 조회 캐시의 갱신
- TanStack Query는 수정 요청의 결과만으로 어떤 Query Key가 영향을 받았는지 자동으로 판단하지 못함
- 같은 Query Key를 사용하는 화면은 캐시를 공유하지만, 서로 다른 Query Key에 들어 있는 정보는 자동으로 동기화되지 않음

예) 닉네임 변경 후 `['me']`만 갱신 → `['posts']`에 별도로 저장된 작성자 닉네임은 이전 값으로 남을 수 있음

#### 변경한 데이터를 다시 조회하는 방식과 캐시를 직접 수정하는 방식은 각각 어떤 상황에 적절할까요?

**변경한 데이터를 다시 조회 / `invalidateQueries`**

- 동작: 관련 캐시를 stale로 표시. 기본적으로 현재 사용 중인 관련 쿼리는 백그라운드에서 재조회
- 적절한 상황: 수정 응답에 최신 데이터가 없거나, 변경이 목록·검색·집계 등 여러 결과에 영향을 줄 때

**캐시 직접 수정 / `setQueryData`**

- 동작: 추가 요청 없이 지정한 Query Key의 캐시를 즉시 갱신
- 적절한 상황: 수정 응답에 최신 데이터가 있고, 어느 캐시를 어떻게 바꿀지 명확할 때

```tsx
최신 회원 정보가 응답에 포함 -> 응답 값으로 ['me'] 직접 갱신

204 No Content로 응답하고 최종 저장값 확인이 필요 -> ['me'] 무효화 후 재조회

두 방식 병행 -> ['me']는 직접 갱신하고, 작성자 정보가 담긴 ['posts']는 무효화
```
