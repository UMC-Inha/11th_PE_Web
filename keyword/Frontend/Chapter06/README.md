## 키워드 정리

### query key와 요청 상태

#### 목록, 검색과 상세에 같은 query key를 쓰면 어떤 문제가 생길까요? 페이지 번호, 검색어와 영화 ID를 포함하는 이유도 함께 생각해 보세요.

**같은 Query Key를 사용하면?**

TanStack Query는 Query Key를 기준으로 데이터를 캐시에 저장하고 찾아온다. 따라서 같은 Query Key를 사용한다는 것은 TanStack Query에 "이 요청들은 같은 데이터를 사용한다"라고 알려주는 것과 같다. 요청하는 API 주소나 함수가 다르다고 해서 자동으로 별개의 캐시로 나누어주지는 않는다.

예를 들어 다음 세 가지 요청에 모두 `['movies']`를 사용했다고 가정한다.

- 인기 영화 목록 조회
- 특정 검색어에 대한 영화 검색
- 특정 영화의 상세 정보 조회

이 요청들은 서로 다른 데이터를 반환하지만, 같은 캐시를 공유하여 다음과 같은 문제가 발생한다.

- 다른 화면의 데이터가 표시될 수 있다.
- 캐시 데이터가 서로 덮어써질 수 있다.
- 데이터 구조가 달라 오류가 발생할 수 있다.
- 요청 조건이 바뀌어도 별개의 요청으로 인식되지 않는다.

**페이지 번호, 검색어, 영화 ID를 포함하는 이유**

→ 요청 결과를 바꾸는 값은 Query Key에도 포함한다.

| 구분 | Query Key 예시 | 포함하는 이유 |
| --- | --- | --- |
| 영화 목록 | `['movies', 'list', page]` | 페이지마다 영화 목록이 다르기 때문 |
| 영화 검색 | `['movies', 'search', keyword, page]` | 검색어와 페이지에 따라 결과가 달라지기 때문 |
| 영화 상세 | `['movies', 'detail', movieId]` | 영화마다 상세 정보가 다르기 때문 |

각 Query Key는 서로 다른 캐시여서 정보를 따로 저장하고, 다시 방문 시 해당 영화의 캐시를 재사용할 수 있다.

#### `enabled: false`인데도 `isPending`이 참일 수 있는 이유는 무엇이며, 이때 `isLoading`은 어떤 값일까요?

**데이터 상태와 요청 상태는 다르다**

TanStack Query에서는 데이터가 준비되었는지와 현재 네트워크 요청 중인지를 구분한다.

- `isPending`: 아직 성공한 데이터가 없는 초기 상태인지를 나타낸다.
- `isFetching`: 현재 요청을 실행 중인지를 나타낸다.
- `isLoading`: 초기 데이터를 기다리는 상태이면서, 실제 요청도 진행 중인지를 나타낸다.

```tsx
isLoading = isPending && isFetching
```

**`enabled: false`는 쿼리가 자동으로 요청되지 않도록 하는 설정이다**

캐시 데이터가 없는 상태에서 요청까지 비활성화하면 다음과 같은 상태가 된다. → "아직 데이터는 없지만, 요청도 하고 있지 않다."

| 속성 | 값 | 이유 |
| --- | --- | --- |
| status | 'pending' | 아직 성공한 데이터가 없음 |
| fetchStatus | 'idle' | 요청을 실행하고 있지 않음 |
| isPending | true | 초기 데이터가 준비되지 않음 |
| isFetching | false | 요청 중이 아님 |
| isLoading | false | true && false의 결과 |

```tsx
검색어가 비어 있음
→ enabled: false
→ 캐시가 없다면 isPending: true
→ 실제 요청은 없으므로 isLoading: false
```

### 캐시 수명과 재조회

#### `staleTime`과 `gcTime`은 각각 언제부터 계산하며, 시간이 지난 뒤 캐시에 어떤 차이가 생길까요?

**`staleTime`**

`staleTime`은 데이터를 최신 상태로 간주하는 시간이다. 일반적으로 데이터를 성공적으로 받아 캐시를 갱신한 시점부터 계산한다.

- 시간이 지나기 전: fresh 상태
- 시간이 지난 후: stale 상태

데이터가 stale 상태가 되어도 캐시는 삭제되지 않는다. 또한 `staleTime`이 끝났다는 이유만으로 즉시 재조회하지는 않는다.

일반적인 기본 설정에서는 stale 상태에서 다음과 같은 계기가 생기면 재조회한다.

- 해당 쿼리를 사용하는 컴포넌트가 새로 마운트됨
- 다른 창을 보다가 현재 창으로 돌아옴
- 네트워크가 다시 연결됨

**`gcTime`**

`gcTime`은 쿼리를 관찰하는 컴포넌트가 없어진 뒤 캐시를 보관하는 시간이다. 마지막 관찰자가 제거된 시점부터 계산한다.

시간이 지나도록 사용되지 않으면 캐시가 제거된다. 반대로 해당 쿼리를 계속 관찰하고 있다면, `gcTime`이 지났다는 이유만으로 캐시가 삭제되지 않는다.

| 구분 | staleTime | gcTime |
| --- | --- | --- |
| 목적 | 데이터의 신선도 판단 | 사용하지 않는 캐시 제거 |
| 계산 시작 | 데이터가 성공적으로 갱신된 시점 | 마지막 관찰자가 제거된 시점 |
| 시간이 지난 결과 | stale 상태로 변경 | 사용하지 않는 캐시 삭제 |
| 기본값 | 0 | 5분 |

#### 전역 기본값과 개별 `useQuery`의 `staleTime`은 어떤 기준으로 정하면 좋을까요?

**전역 기본값: 서비스의 공통 정책**

전역 `staleTime`은 대부분의 쿼리에 공통으로 적용할 기준으로 정한다.

- 데이터가 얼마나 자주 변경되는가?
- 오래된 데이터를 보여 주었을 때 문제가 얼마나 큰가?
- 네트워크 요청 비용과 서버 부담은 어느 정도인가?
- 사용자가 같은 화면에 얼마나 자주 재방문하는가?

최신성이 중요하면 짧게, 변경이 드물고 반복 조회가 많으면 길게 설정하는 것이 적절하다.

**개별 설정: 데이터 특성에 따른 조정**

전역 기본값과 다른 정책이 필요한 데이터는 개별 `useQuery`에서 설정한다. 개별 설정은 해당 쿼리에서 전역 기본값보다 우선한다.

예를 들어 영화 서비스에서 전역 기본값을 1분으로 정하더라도, 변경이 드문 장르 목록은 더 길게 설정할 수 있다. 반면 잔여 좌석처럼 빠르게 바뀌는 데이터는 짧게 설정해야 한다.

단, `staleTime`을 짧게 설정하는 것만으로 실시간 갱신이 이루어지지는 않는다. 주기적인 갱신이 필요하면 별도 재조회 설정이 필요하다.

→ 전역 `staleTime`은 서비스의 일반적인 데이터 특성에 맞추고, 개별 `useQuery`에서는 변경 빈도와 최신성 요구에 따라 조정한다.
