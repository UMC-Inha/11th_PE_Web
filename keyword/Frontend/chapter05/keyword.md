- HTTP와 API
  - API, endpoint, HTTP method와 status code는 요청과 응답에서 각각 어떤 역할을 할까요?
    - **API**는 클라이언트와 서버가 데이터를 주고받기 위해 정해 놓은 통신 규칙이다.
    - **Endpoint**는 API를 통해 특정 기능이나 자원에 접근하는 URL이다.
    - **HTTP method**는 요청의 목적을 나타내며, GET은 조회, POST는 생성, PUT은 전체 수정, PATCH는 일부 수정, DELETE는 삭제에 사용된다.
    - 클라이언트는 endpoint에 HTTP method와 필요한 데이터, 헤더 등을 담아 요청한다.
    - 서버는 요청을 처리한 뒤 상태 코드와 응답 데이터를 반환한다.
    - **Status code**는 요청 처리 결과를 나타내며, 200번대는 성공, 300번대는 리다이렉션, 400번대는 클라이언트 오류, 500번대는 서버 오류를 의미한다.
    - 예를 들어 **`GET /users`**는 사용자 목록을 조회하고, **`POST /users`**는 새로운 사용자를 생성하는 요청이다.
  - 브라우저와 API 서버의 origin이 다를 때 CORS는 어떤 역할을 할까요?
    - **Origin**은 프로토콜, 호스트, 포트의 조합으로 결정된다.
    - 예를 들어 **`http://localhost:3000`**과 **`http://localhost:8080`**은 포트가 다르므로 서로 다른 origin이다.
    - 브라우저는 다른 origin으로 요청할 때 보안 정책인 동일 출처 정책(Same-Origin Policy)을 적용한다.
    - CORS(Cross-Origin Resource Sharing)는 서버가 다른 origin의 브라우저 요청을 허용할 수 있도록 하는 HTTP 헤더 기반의 규칙이다.
    - 서버는 **`Access-Control-Allow-Origin`** 등의 응답 헤더로 허용할 origin을 지정한다.
    - 일부 요청은 실제 요청 전에 OPTIONS 메서드를 사용하는 프리플라이트 요청을 수행한다.
    - CORS는 브라우저가 응답을 사용할 수 있는지 판단하는 정책이며, 서버 자체의 인증이나 권한 검사를 대체하지 않는다.
    - CORS 오류가 발생하면 프런트엔드 코드만 수정하기보다 서버의 CORS 설정도 확인해야 한다.
- Promise와 비동기 처리
  - Promise의 pending, fulfilled와 rejected 상태는 각각 무엇을 의미할까요?
    - **Promise**는 비동기 작업의 결과가 나중에 결정될 것을 나타내는 객체다.
    - **`pending`**은 비동기 작업의 결과가 아직 결정되지 않은 상태다.
    - **`fulfilled`**는 작업이 성공적으로 완료되어 결과값이 확정된 상태다.
    - **`rejected`**는 작업이 실패하여 거부 사유가 확정된 상태다.
    - **`fulfilled`**와 **`rejected`**는 Promise의 완료 상태이며, 두 상태를 합쳐 settled 상태라고 한다.
    - 성공한 결과는 **`.then()`**으로 처리하고, 실패 사유는 **`.catch()`**로 처리할 수 있다.
    - Promise는 한 번 완료 상태가 되면 다른 상태로 다시 변경되지 않는다.
    - 이러한 상태를 구분하면 비동기 작업의 진행 상황과 결과에 따른 처리를 명확하게 작성할 수 있다.
  - `.then().catch()`와 `async/await`는 같은 비동기 흐름을 어떻게 다르게 표현하나요?
    - **`.then().catch()`**와 **`async/await`**는 모두 Promise를 기반으로 비동기 작업을 처리하는 방법이다.
    - **`.then()`**은 Promise가 성공적으로 완료되었을 때 실행할 콜백을 등록한다.
    - **`.catch()`**는 앞선 Promise 체인에서 발생한 거부를 처리하며, 체인 안의 오류도 전달받을 수 있다.
    - **`async`** 함수는 항상 Promise를 반환하며, 함수 내부에서 **`await`**를 사용해 Promise의 결과를 기다릴 수 있다.
    - **`async/await`**는 비동기 코드를 동기 코드와 비슷한 순서로 표현해 가독성을 높인다.
    - **`async/await`**에서 오류는 일반적으로 **`try...catch`**로 처리한다.
    - **`.then().catch()`**는 체인 형태의 데이터 변환과 연속 처리를 표현하기에 편리하다.
    - 두 방식은 같은 비동기 흐름을 표현할 수 있으며, 코드 구조와 팀의 작성 방식에 따라 선택할 수 있다.
  - `await`를 사용해도 브라우저 전체가 멈추지 않는 이유는 무엇일까요?
    - **`await`**는 Promise의 결과가 준비될 때까지 해당 **`async`** 함수의 실행을 일시 중단한다.
    - 이때 브라우저 전체나 자바스크립트 실행 환경이 멈추는 것은 아니다.
    - 비동기 네트워크 요청은 브라우저의 네트워크 처리 기능 등을 통해 진행된다.
    - Promise가 완료되면 대기하던 함수의 나머지 부분이 마이크로태스크로 예약되어 실행된다.
    - 그동안 브라우저는 다른 자바스크립트 작업이나 렌더링, 사용자 입력 처리를 진행할 수 있다.
    - 따라서 **`await`**는 결과를 기다리는 동안 현재 함수의 실행 흐름만 중단하는 역할을 한다.
    - 다만 **`await`**를 사용하더라도 CPU를 오래 점유하는 동기 작업은 브라우저 화면을 멈추게 할 수 있다.
    - **`await`**는 비동기 작업을 읽기 쉽게 작성하는 문법이지, 모든 작업을 자동으로 백그라운드에서 실행하는 기능은 아니다.
- fetch와 HTTP 요청 라이브러리
  - `fetch`에서 네트워크 오류와 HTTP 오류를 따로 처리해야 하는 이유는 무엇일까요?
    - **`fetch`**는 HTTP 요청을 보내고 응답을 Promise로 반환하는 브라우저 기본 API다.
    - 네트워크 연결 실패, DNS 오류, 요청 중단 등의 상황에서는 일반적으로 Promise가 거부된다.
    - 반면 서버가 404나 500 같은 HTTP 오류 상태를 반환해도 **`fetch`**는 보통 정상적으로 Response 객체를 반환한다.
    - 따라서 **`fetch`**에서는 **`response.ok`** 또는 **`response.status`**를 확인해 HTTP 오류를 직접 처리해야 한다.
    - **`response.ok`**는 상태 코드가 200~299 범위일 때 **`true`**를 반환한다.
    - 네트워크 오류와 HTTP 오류를 구분하면 사용자에게 더 정확한 오류 메시지를 제공할 수 있다.
    - 예를 들어 네트워크 오류는 연결 상태를 확인하도록 안내하고, 404 오류는 요청한 자원을 찾을 수 없다고 안내할 수 있다.
    - 요청 취소나 응답 본문 파싱 오류도 별도로 고려하면 더욱 안정적인 오류 처리가 가능하다.
  - 순수 `fetch`로 여러 API 함수를 작성하면 어떤 설정과 처리가 반복될까요?
    - 여러 API 함수를 순수 **`fetch`**로 작성하면 기본 URL과 공통 헤더 설정이 반복될 수 있다.
    - 인증 토큰이나 **`Content-Type`** 등의 헤더를 각 요청에 추가해야 할 수 있다.
    - POST나 PATCH 요청에서는 데이터를 JSON 문자열로 변환하는 작업이 반복된다.
    - 응답을 **`response.json()`**으로 변환하고 HTTP 상태 코드를 확인하는 과정도 반복될 수 있다.
    - 네트워크 오류와 HTTP 오류를 구분하고, 오류 메시지를 정리하는 코드도 필요하다.
    - 인증 만료 처리, 요청 취소, 타임아웃 등의 기능을 추가하면 중복 코드가 더 늘어난다.
    - 이러한 공통 처리를 함수로 분리하면 코드 중복을 줄이고 유지보수를 쉽게 할 수 있다.
    - API 함수가 많아질수록 공통 요청 유틸리티나 HTTP 클라이언트 라이브러리를 사용하는 것이 유리하다
  - ky와 Axios는 JSON 응답을 읽고 공통 요청 처리를 추가하는 방식이 어떻게 다를까요?
    - **ky**와 **Axios**는 반복적인 HTTP 요청 처리를 줄이기 위한 라이브러리다.
    - ky는 **`fetch`**를 기반으로 하며, **`.json()`** 메서드로 응답 JSON을 읽을 수 있다.
    - ky는 **`prefixUrl`**, **`headers`**, **`timeout`**, **`hooks`** 등의 설정을 통해 공통 요청 처리를 구성할 수 있다.
    - ky는 기본적으로 HTTP 오류 상태에서 예외를 발생시키므로 **`HTTPError`** 등을 이용해 오류를 처리할 수 있다.
    - Axios는 **`axios.create()`**로 기본 URL, 헤더, 타임아웃 등을 설정한 인스턴스를 만들 수 있다.
    - Axios는 응답 데이터를 기본 설정에 따라 변환하며, 일반적인 JSON 응답은 **`response.data`**로 접근한다.
    - Axios는 요청 인터셉터와 응답 인터셉터를 통해 인증 토큰 추가나 공통 오류 처리를 구현할 수 있다.
    - 두 라이브러리 모두 공통 설정과 오류 처리를 재사용할 수 있으며, ky는 Fetch API와 유사한 사용 방식, Axios는 인스턴스와 인터셉터를 활용한 구조가 특징이다.
- 비동기 데이터의 UI 상태
  - 서버 데이터를 보여 주는 화면에서 로딩, 오류, 빈 결과와 성공 상태를 구분해야 하는 이유는 무엇일까요?
    - 서버 데이터를 사용하는 화면은 요청이 진행되는 동안에도 다양한 상태를 가질 수 있다.
    - **로딩 상태**는 아직 데이터를 받는 중이므로 사용자에게 기다려야 한다는 정보를 제공한다.
    - **오류 상태**는 요청 실패를 알리고 사용자가 다음 행동을 선택할 수 있도록 한다.
    - **빈 결과 상태**는 요청은 성공했지만 표시할 데이터가 없는 상황을 나타낸다.
    - **성공 상태**는 데이터가 정상적으로 도착하여 화면에 표시할 수 있는 상황이다.
    - 이 상태들을 구분하지 않으면 데이터가 없는 화면이 로딩 중인지, 오류인지, 실제로 결과가 없는지 알기 어렵다.
    - 상태를 명확하게 관리하면 불필요한 재요청이나 사용자 혼란을 줄일 수 있다.
    - 따라서 비동기 UI는 데이터 유무뿐 아니라 요청의 진행 상태와 결과를 함께 고려해야 한다.
  - 각 상태를 사용자가 이해할 수 있게 표현하려면 어떤 정보와 동작이 필요할까요?
    - **로딩 상태**에서는 스피너나 스켈레톤과 함께 데이터를 불러오는 중이라는 안내를 표시한다.
    - **오류 상태**에서는 무엇이 실패했는지 설명하고, 가능한 경우 다시 시도하기 버튼을 제공한다.
    - 인증이 필요한 오류라면 로그인 안내를 제공하고, 권한 오류라면 접근 권한이 없다는 점을 알려 준다.
    - **빈 결과 상태**에서는 검색 결과가 없거나 아직 등록된 데이터가 없다는 사실을 명확하게 표현한다.
    - 검색 화면이라면 검색어 변경이나 필터 초기화처럼 결과를 찾을 수 있는 다음 행동을 제안한다.
    - **성공 상태**에서는 데이터 목록이나 상세 정보를 표시하고, 필요한 경우 페이지 이동이나 정렬 기능을 제공한다.
    - 재요청 중에는 기존 데이터를 유지할지, 로딩 화면으로 대체할지 상황에 맞게 결정한다.
    - 사용자에게 상태와 다음 행동을 함께 제공하면 화면의 예측 가능성과 사용성이 높아진다.
  - API 응답 타입과 화면에서 사용하는 타입을 분리하면 어떤 상황에서 도움이 될까요?
    - **API 응답 타입**은 서버가 실제로 반환하는 데이터의 구조를 나타내는 타입이다.
    - **화면에서 사용하는 타입**은 UI에서 필요한 형태로 가공한 데이터를 나타내는 타입이다.
    - 서버 응답에는 화면에서 사용하지 않는 필드나 중첩된 객체, 문자열 형태의 날짜가 포함될 수 있다.
    - 화면에서는 날짜를 **`Date`** 객체로 변환하거나 여러 필드를 조합해 하나의 표시용 값을 만들 수 있다.
    - API 응답 타입과 화면 타입을 분리하면 서버의 데이터 구조가 변경되어도 UI에 미치는 영향을 줄일 수 있다.
    - 응답 데이터를 화면 타입으로 변환하는 매핑 함수를 두면 데이터 변환 로직을 한곳에서 관리할 수 있다.
    - TypeScript에서는 **`ApiUser`**와 **`UserViewModel`**처럼 타입을 구분해 각 계층의 역할을 명확하게 나타낼 수 있다.
    - 이러한 분리는 서버와 화면 사이의 의존성을 낮추고 테스트와 유지보수를 쉽게 만든다.
    - 단, 타입 선언만으로 실제 응답 데이터의 유효성이 보장되는 것은 아니므로 필요하면 런타임 검증도 수행해야 한다.
