- 인증과 인가
    - 인증과 인가는 무엇을 확인하는 과정인가요?
        
        ## 인증(Authentication)과 인가(Authorization)
        
        ### 1. 용어 정의
        
        #### 인증 (Authentication, AuthN)
        
        - "너 누구야?" 를 확인하는 과정
        - 요청을 보낸 사용자가 스스로 주장하는 그 사람이 맞는지 확인하는 것
        - 확인 수단
            - 인지(지식) 기반 인증: 비밀번호, PIN
            - 소유 기반 인증: 휴대폰 인증번호(OTP), 보안 키
            - 생체 기반 인증: 지문, 얼굴
            - 외부 서비스의 확인: 소셜 로그인(카카오, 구글)
        - 예: 로그인 시 이메일·비밀번호가 맞는지 확인
        
        #### 인가 (Authorization, AuthZ)
        
        - "너 이거 해도 돼?" 를 확인하는 과정
        - 인증된 사용자가 특정 리소스에 접근하거나 특정 동작을 할 권한이 있는지 확인하는 것
        - 예: 관리자 페이지에 들어갈 수 있는지, 이 게시글을 수정·삭제할 수 있는지
        
        ### 2. 인증과 인가의 차이
        
        | 구분 | 인증 (Authentication) | 인가 (Authorization) |
        | --- | --- | --- |
        | 확인하는 것 | **신원** (누구인가) | **권한** (무엇을 할 수 있는가) |
        | 순서 | 먼저 | 인증 이후 |
        | 확인 방법 | 비밀번호, OTP, 소셜 로그인, 토큰 검증 | 역할(Role), 소유자 여부, 권한 목록 |
        | 실패 시 상태 코드 | **401 Unauthorized** | **403 Forbidden** |
        | 예시 | 로그인, 토큰이 유효한지 확인 | 관리자 메뉴 접근, 남의 글 삭제 시도 |
        - 인증 없이 인가는 불가능: 누구인지 알아야 그 사람의 권한을 판단할 수 있음
        - 401의 이름은 "Unauthorized"지만 실제 의미는 인증 실패(인증 필요) 이고, 권한 부족은 403
        
        ### 3. 요청 흐름에서 보기
        
        ```
        [로그인]
        클라이언트 ── 이메일·비밀번호 ──▶ 서버: 인증 성공 → 토큰(또는 세션) 발급
        
        [이후 요청]
        클라이언트 ── 요청 + 토큰 ──▶ 서버
                                         │
                                         ├─ ① 인증: 토큰이 유효한가? 누구의 토큰인가?
                                         │      └ 실패 → 401 Unauthorized
                                         │
                                         ├─ ② 인가: 이 사용자가 이 동작을 할 권한이 있는                                             가?
                                         │      └ 실패 → 403 Forbidden
                                         │
                                         └─ ③ 둘 다 통과 → 요청 처리 (200, 201, 204                                        ...)
        ```
        
        #### 예시: 게시글 삭제 `DELETE /posts/10`
        
        | 상황 | 결과 |
        | --- | --- |
        | 토큰 없이 요청 | 인증 실패 → **401** |
        | 만료된 토큰으로 요청 | 인증 실패 → **401** |
        | 로그인했지만 다른 사람의 글 | 인가 실패 → **403** |
        | 로그인했고 본인 글 | 삭제 성공 → **204** |
        
        ### 4. 인가 방식의 종류
        
        | 방식 | 의미 | 예시 |
        | --- | --- | --- |
        | **역할 기반 (RBAC)** | 사용자의 **역할(Role)** 에 따라 권한 부여 | `ADMIN`만 회원 관리 가능, `USER`는 일반 기능만 |
        | **소유자 기반** | 리소스의 **작성자·소유자**인지 확인 | 본인이 작성한 글·댓글만 수정·삭제 |
        | **속성 기반 (ABAC)** | 사용자·리소스·상황의 **여러 속성**을 조합해서 판단 | 같은 팀 멤버만 프로젝트 조회, 업무 시간에만 접근 |
        
        ### 5. 프론트엔드에서의 인증·인가
        
        #### 인증 상태 관리
        
        - 로그인 성공 시 받은 토큰(또는 세션 쿠키)을 저장하고, 이후 API 요청에 함께 보냄
            - 쿠키 방식: 브라우저가 자동으로 전송 (`credentials: 'include'`)
            - 토큰 방식: `Authorization: Bearer 토큰` 헤더에 담아 전송 (axios 인터셉터 등으로 공통 처리)
        - 현재 로그인한 사용자 정보(이름, 역할 등)를 전역 상태로 관리해 화면에 활용
        
        #### 화면에서 인가 처리
        
        - **보호된 라우트(Protected Route)**: 로그인하지 않은 사용자가 마이페이지 등에 접근하면 로그인 페이지로 이동
        - **역할에 따른 UI 분기**: 관리자에게만 관리 메뉴 표시, 작성자에게만 수정·삭제 버튼 표시
        
        ```tsx
        // 로그인이 필요한 페이지 보호 (React Router)
        function ProtectedRoute({ children }: { children: React.ReactNode }) {
          const { user } = useAuth();
          if (!user) return <Navigate to="/login" replace />;
          return children;
        }
        
        // 관리자만 접근 가능한 페이지
        function AdminRoute({ children }: { children: React.ReactNode }) {
          const { user } = useAuth();
          if (!user) return <Navigate to="/login" replace />;
          if (user.role !== 'ADMIN') return <Navigate to="/forbidden" replace />;
          return children;
        }
        ```
        
        ```tsx
        // 작성자에게만 수정·삭제 버튼 표시
        {post.authorId === user?.id && (
          <>
            <button onClick={onEdit}>수정</button>
            <button onClick={onDelete}>삭제</button>
          </>
        )}
        ```
        
        #### 서버 응답에 따른 처리
        
        | 응답 | 의미 | 프론트 처리 |
        | --- | --- | --- |
        | **401** | 인증 실패 (로그인 안 됨, 토큰 만료) | 토큰 재발급 시도 → 실패하면 로그인 페이지로 이동 |
        | **403** | 인가 실패 (권한 없음) | "접근 권한이 없어요" 안내, 이전 페이지나 홈으로 이동 |
        
        #### 프론트엔드의 인가는 "사용자 경험"을 위한 것
        
        - 버튼을 숨기거나 페이지 이동을 막는 것은 잘못된 동작을 미리 안내하기 위한 UI 처리일 뿐
        - 브라우저 코드는 사용자가 개발자 도구로 수정하거나, API를 직접 호출해서 우회할 수 있음
        - 따라서 실제 인증·인가 검사는 반드시 서버에서 해야 하고, 프론트는 서버의 401·403 응답에 맞춰 화면을 처리함
    - 로그인한 사용자도 특정 기능을 이용하지 못할 수 있는 이유는 무엇인가요?
        
        ### 1. 용어 정의
        
        #### 로그인 (인증 완료 상태)
        
        - 서버가 요청을 보낸 사용자가 누구인지 확인한 상태
        - 로그인은 "가입된 사용자 OO님이다"라는 신원 확인까지만 보장함
        
        #### 인가 (Authorization)
        
        - 인증된 사용자가 요청한 동작에 대한 권한이 있는지 판단하는 과정
        - 로그인 여부와 별개로, 기능을 쓸 때마다 따로 검사함
        
        ### 2. 인증과 인가는 별개의 검사
        
        | 단계 | 확인하는 것 | 로그인한 사용자의 경우 |
        | --- | --- | --- |
        | 인증 | 누구인가? | ⭕ 통과 |
        | 인가 | 이 기능을 써도 되는가? | ❓ 사용자·리소스·상황에 따라 다름 |
        - 로그인은 인증만 통과한 것이고, 기능 사용 여부는 인가 단계에서 따로 결정됨
        - 그래서 같은 로그인 사용자라도 기능마다 허용·차단이 달라질 수 있음
        
        ### 3. 이용하지 못하는 이유
        
        #### 이유 1. 역할(Role)이 다르다
        
        - 서비스는 사용자를 역할별로 나누고, 역할마다 쓸 수 있는 기능을 다르게 정함
        
        | 역할 | 가능한 기능 예시 |
        | --- | --- |
        | 일반 사용자 (`USER`) | 글 작성, 댓글, 좋아요 |
        | 운영자 (`MANAGER`) | 신고된 글 숨김, 공지 작성 |
        | 관리자 (`ADMIN`) | 회원 정지, 전체 통계 조회 |
        - 일반 사용자가 관리자 페이지에 접근하면 → **403 Forbidden**
        
        #### 이유 2. 리소스의 소유자가 아니다
        
        - 다른 사람이 만든 리소스는 조회는 가능해도 수정·삭제는 불가능한 경우가 많음
        - 예: 남의 게시글 삭제, 남의 주문 내역 조회, 남의 프로필 수정
        - 서버는 요청한 사용자 id와 리소스의 작성자 id를 비교해서 판단
        
        #### 이유 3. 그룹·팀의 멤버가 아니거나 멤버 권한이 부족하다
        
        - 협업 서비스에서는 리소스가 속한 그룹 안에서의 역할에 따라 권한이 달라짐
        - 예: 프로젝트에 초대받지 않은 사용자는 해당 프로젝트 조회 불가
        - 예: 같은 팀이어도 `뷰어(viewer)`는 보기만 가능, `편집자(editor)`는 수정 가능, `소유자(owner)`만 삭제·멤버 관리 가능
        
        #### 이유 4. 계정 상태가 조건을 만족하지 않는다
        
        | 계정 상태 | 제한되는 기능 예시 |
        | --- | --- |
        | 이메일·휴대폰 미인증 | 글 작성, 결제 |
        | 이용 정지된 계정 | 대부분의 쓰기 기능 |
        | 필수 정보 미입력 (약관 동의, 프로필) | 서비스 주요 기능 |
        | 연령·지역 제한 | 성인 인증이 필요한 콘텐츠, 특정 국가 미지원 기능 |
        
        #### 이유 5. 요금제·구독 등급이 부족하다
        
        - 무료 사용자는 기본 기능만, 유료 플랜 사용자만 고급 기능 사용 가능
        - 예: 무료 플랜은 프로젝트 3개까지, 파일 업로드 용량 제한, 프리미엄 전용 기능
        
        #### 이유 6. 리소스나 서비스의 상태 때문에 지금은 불가능하다
        
        - 사용자 권한은 충분해도 대상의 현재 상태가 동작을 허용하지 않는 경우
        - 예: 마감된 모집글에 지원, 이미 배송 시작된 주문 취소, 삭제된 게시글에 댓글 작성, 정원이 찬 이벤트 신청
        - 이런 경우는 주로 409 Conflict 등으로 응답
        
        #### 이유 7. 인증이 만료되었거나 추가 인증이 필요하다
        
        - 로그인했던 상태여도 토큰·세션이 만료되면 다시 인증이 필요 → 401 Unauthorized
        - 비밀번호 변경, 계정 삭제, 결제처럼 민감한 기능은 로그인 상태여도 비밀번호 재입력·추가 인증을 요구하기도 함
        
        #### 이유 8. 사용량 제한에 걸렸다
        
        - 짧은 시간에 요청을 너무 많이 보내거나 일일 사용 한도를 넘기면 일시적으로 차단
        - 예: 인증번호 재전송 횟수 제한, AI 기능 하루 사용 횟수 제한 → 429 Too Many Requests
        
        ### 4. 이유별 응답 상태 코드
        
        | 이유 | 상태 코드 |
        | --- | --- |
        | 역할·소유자·멤버 권한 부족, 계정 상태 제한, 요금제 부족 | **403 Forbidden** |
        | 토큰·세션 만료, 재인증 필요 | **401 Unauthorized** |
        | 리소스 상태와 충돌 (마감, 이미 처리됨) | **409 Conflict** |
        | 사용량 초과 | **429 Too Many Requests** |
        | 권한이 없는 리소스의 존재 자체를 숨기고 싶을 때 | **404 Not Found** (비공개 저장소 등) |
        
        ### 5. 프론트엔드에서 처리하기
        
        #### 사용자가 이해할 수 있게 이유와 다음 행동 안내
        
        | 이유 | 화면 처리 예시 |
        | --- | --- |
        | 역할 부족 | 메뉴·버튼을 표시하지 않음, 직접 접근 시 "접근 권한이 없어요" |
        | 소유자 아님 | 수정·삭제 버튼을 작성자에게만 표시 |
        | 미인증 계정 | "이메일 인증 후 이용할 수 있어요" + **인증하러 가기** 버튼 |
        | 요금제 부족 | 기능에 잠금 아이콘 표시 + **플랜 업그레이드** 안내 |
        | 리소스 상태 | "모집이 마감되었어요" + 버튼 비활성화 |
        | 인증 만료 | 토큰 재발급 시도 → 실패 시 로그인 페이지로 이동 |
        | 사용량 초과 | "잠시 후 다시 시도해주세요", 남은 시간 표시 |
        
        ```tsx
        // 버튼을 숨기기보다 이유를 알려줘야 하는 경우: 비활성화 + 안내 문구
        <button disabled={!canApply}>지원하기</button>
        {!canApply && <p>{getDisabledReason(post, user)}</p>}
        ```
        
        ```tsx
        // 서버 응답에 따른 공통 처리 (axios 응답 인터셉터)
        api.interceptors.response.use(
          (res) => res,
          (error) => {
            const status = error.response?.status;
            if (status === 401) {
              // 토큰 재발급 시도 후 실패하면 로그인 페이지로 이동
            }
            if (status === 403) {
              toast.error('이 기능을 사용할 권한이 없어요.');
            }
            return Promise.reject(error);
          }
        );
        ```
        
        - 프론트에서 버튼을 숨기거나 비활성화하는 것은 **안내를 위한 UI 처리**이고, 실제 차단은 서버의 인가 검사로 이루어짐
        - 서버가 권한 정보(역할, 소유 여부, 가능한 동작 목록)를 응답에 함께 내려주면, 프론트는 그 값을 기준으로 화면을 그리는 것이 좋음
            
            ```json
            { 
            	"id": 10, 
            	"title": "모집글", 
            	"canEdit": true, 
            	"canDelete": false, 
            	"canApply": false 
            }
            ```
            
- JWT
    - header, payload, signature는 각각 어떤 역할을 하나요?
        
        ### 1. 용어 정의
        
        #### JWT (JSON Web Token)
        
        - 사용자 정보와 권한 같은 데이터를 JSON 형태로 담아, 서명해서 주고받는 토큰
        - 로그인 성공 시 서버가 발급하고, 클라이언트는 이후 요청마다 토큰을 보내 "내가 누구인지" 증명함
            
            ```
            Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
            ```
            
        - 서버가 세션을 저장하지 않고 토큰 자체만 검증해서 사용자를 확인할 수 있음 (Stateless)
        
        #### JWT의 구조
        
        - **header, payload, signature** 세 부분을 `.`으로 이어 붙인 문자열
        
        ```
        eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIiwiZXhwIjoxNzk0MDAwMDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
        └──────────────── header ───────────┘└──────────────────────── payload ─────────────────────────┘└────────────── signature ──────────────┘
        ```
        
        #### Base64URL 인코딩
        
        - 데이터를 URL·헤더에 안전하게 넣을 수 있는 문자(`A-Z`, `a-z`, `0-9`, , `_`)로 바꾸는 인코딩 방식
        - header와 payload는 JSON을 Base64URL로 인코딩한 것 → 누구나 디코딩해서 내용을 볼 수 있음 (암호화가 아님)
        
        #### 클레임 (Claim)
        
        - payload 안에 담기는 하나하나의 정보(키-값 쌍)
        - 예: `"sub": "42"`, `"role": "USER"`
        
        ### 2. 각 부분의 역할
        
        | 부분 | 역할 | 한눈에 |
        | --- | --- | --- |
        | **Header** | 토큰의 타입과 서명 알고리즘 정보 | "이 토큰은 어떻게 서명됐는가" |
        | **Payload** | 전달하려는 데이터(클레임) | "이 토큰은 누구의, 어떤 정보인가" |
        | **Signature** | header와 payload가 위조·변조되지 않았음을 증명 | "이 토큰은 진짜인가" |
        
        ### 3. Header
        
        #### 역할
        
        - 토큰의 메타 정보를 담음
        - 서버는 header를 보고 어떤 알고리즘으로 서명을 검증할지 알 수 있음
        
        #### 디코딩한 내용
        
        ```json
        {
          "alg": "HS256",
          "typ": "JWT"
        }
        ```
        
        | 필드 | 의미 |
        | --- | --- |
        | `alg` | 서명 알고리즘 (`HS256`, `RS256`, `ES256` 등) |
        | `typ` | 토큰 타입 (`JWT`) |
        | `kid` | (선택) 서명에 사용한 키의 ID → 키를 여러 개 쓰거나 교체할 때 사용 |
        
        #### 대표 서명 알고리즘
        
        | 알고리즘 | 방식 | 특징 |
        | --- | --- | --- |
        | `HS256` | HMAC + SHA-256, 하나의 비밀 키로 서명·검증 | 간단함. 발급 서버와 검증 서버가 같은 비밀 키를 공유 |
        | `RS256` | RSA, 개인 키로 서명하고 공개 키로 검증 | 검증하는 쪽에 공개 키만 주면 되어서 여러 서비스가 검증할 때 유리 |
        
        ### 4. Payload
        
        #### 역할
        
        - 토큰에 담아 전달할 실제 데이터(클레임) 를 담음
        - 서버는 payload를 보고 누구의 토큰인지, 언제 만료되는지, 어떤 권한이 있는지 판단함
        - DB를 매번 조회하지 않아도 사용자 식별·인가에 필요한 기본 정보를 얻을 수 있음
        
        #### 디코딩한 내용
        
        ```json
        {
          "sub": "42",
          "role": "USER",
          "iat": 1793990000,
          "exp": 1794000000
        }
        ```
        
        #### 클레임 종류
        
        | 종류 | 의미 | 예시 |
        | --- | --- | --- |
        | **등록된 클레임 (Registered)** | 표준으로 이름과 의미가 정해진 클레임 | `sub`, `exp`, `iat` 등 |
        | **공개 클레임 (Public)** | 충돌을 피하도록 공개적으로 정의해 쓰는 클레임 | `email`, `name` 등 |
        | **비공개 클레임 (Private)** | 서비스끼리 약속해서 쓰는 커스텀 클레임 | `role`, `userId` |
        
        #### 주요 등록된 클레임
        
        | 클레임 | 이름 | 의미 |
        | --- | --- | --- |
        | `iss` | Issuer | 토큰 발급자 |
        | `sub` | Subject | 토큰의 주체 (보통 **사용자 id**) |
        | `aud` | Audience | 토큰을 사용할 대상 (어떤 서버용 토큰인지) |
        | `exp` | Expiration Time | **만료 시각** (초 단위 Unix 시간) |
        | `nbf` | Not Before | 이 시각 이전에는 사용 불가 |
        | `iat` | Issued At | 발급 시각 |
        | `jti` | JWT ID | 토큰 고유 id (중복 사용·재사용 방지에 활용) |
        
        #### payload에 넣으면 안 되는 정보
        
        - payload는 인코딩만 되어 있어서 누구나 읽을 수 있음
        - 비밀번호, 주민등록번호, 카드 정보 같은 민감 정보는 절대 넣지 않음
        - 토큰이 커지면 매 요청마다 전송량이 늘어나므로 필요한 최소한의 정보만 담음
        
        ### 5. Signature
        
        #### 역할
        
        - header와 payload가 발급 이후 변경되지 않았는지(무결성) 증명
        - 이 토큰을 비밀 키를 가진 서버가 발급했는지(발급자 확인) 증명
        - 내용을 숨기는 것이 아니라 위조를 막는 것이 목적
        
        #### 만드는 방법 (HS256 기준)
        
        ```
        signature = HMACSHA256(
          base64UrlEncode(header) + "." + base64UrlEncode(payload),
          서버의 비밀 키
        )
        ```
        
        #### 위조를 막는 원리
        
        ```
        [공격자가 payload를 수정]
        { "sub": "42", "role": "USER" }  →  { "sub": "42", "role": "ADMIN" }
        
        [서버 검증]
        ① 받은 header + 수정된 payload로 비밀 키를 사용해 서명을 다시 계산
        ② 토큰에 붙어 있는 signature와 비교
        ③ 비밀 키를 모르는 공격자는 올바른 서명을 만들 수 없음 → 서명 불일치 → 401
        ```
        
        - payload를 한 글자만 바꿔도 서명 결과가 완전히 달라짐
        - 비밀 키가 유출되면 누구나 유효한 토큰을 만들 수 있으므로 비밀 키는 서버에서만 안전하게 보관
        
        ### 6. 서버의 토큰 검증 흐름
        
        ```
        토큰 수신
           │
           ├─ ① 형식 확인: header.payload.signature 세 부분인가?
           │
           ├─ ② 서명 검증: 비밀 키(또는 공개 키)로 계산한 서명과 일치하는가?   ← Signature
           │       └ 불일치 → 401
           │
           ├─ ③ 클레임 검증: exp(만료), iss(발급자), aud(대상) 등이 맞는가?    ← Payload
           │       └ 만료·불일치 → 401
           │
           └─ ④ 통과 → payload의 sub, role로 사용자 식별·인가 진행
        ```
        
        ### 7. 프론트엔드에서의 JWT
        
        #### payload 읽기
        
        - 프론트에서도 payload를 디코딩해서 화면 표시용으로 활용할 수 있음
            - 예: 만료 시각(`exp`)을 확인해 만료 직전에 토큰 재발급 요청, 역할(`role`)에 따라 메뉴 표시
        
        ```tsx
        import { jwtDecode } from 'jwt-decode';
        
        interface TokenPayload {
          sub: string;
          role: 'USER' | 'ADMIN';
          exp: number;
        }
        
        const payload = jwtDecode<TokenPayload>(accessToken);
        const isExpired = payload.exp * 1000 < Date.now();   // exp는 초 단위
        ```
        
        #### 프론트에서는 서명을 검증하지 않음
        
        - 서명 검증에는 서버의 비밀 키가 필요하고, 비밀 키는 브라우저에 둘 수 없음
        - 따라서 프론트에서 디코딩한 payload는 UI 편의용으로만 사용하고, 실제 인증·인가 판단은 서버가 서명을 검증한 결과를 따름
        - 토큰을 직접 수정해서 `role`을 `ADMIN`으로 바꿔도, 서버의 서명 검증에서 걸려 401이 됨
    - JWT를 디코딩하는 것과 서명을 검증하는 것은 어떻게 다른가요?
        
        ### 1. 용어 정의
        
        #### 디코딩 (Decoding)
        
        - Base64URL로 **인코딩된 header와 payload를 원래 JSON으로 되돌리는 것**
        - 비밀 키가 필요 없어서 **누구나** 할 수 있음
        - 토큰에 **무슨 내용이 적혀 있는지 읽는 것**일 뿐, 그 내용이 진짜인지는 알 수 없음
        
        #### 서명 검증 (Signature Verification)
        
        - header와 payload로 **서명을 다시 계산해서, 토큰에 붙은 signature와 일치하는지 확인하는 것**
        - 서명에 사용한 **비밀 키(HS256) 또는 공개 키(RS256)** 가 있어야 할 수 있음
        - 토큰이 **신뢰할 수 있는 서버가 발급했고, 이후 변조되지 않았는지** 확인하는 과정
        
        #### 무결성 (Integrity)
        
        - 데이터가 만들어진 이후 **중간에 바뀌지 않았음**을 보장하는 성질
        - 서명 검증은 JWT의 무결성을 확인하는 수단
        
        ### 2. 차이 비교
        
        | 구분 | 디코딩 | 서명 검증 |
        | --- | --- | --- |
        | 하는 일 | header·payload를 **읽기** | 서명이 맞는지 **확인하기** |
        | 필요한 것 | 토큰만 있으면 됨 | **비밀 키 또는 공개 키** |
        | 할 수 있는 주체 | 누구나 (브라우저, 공격자 포함) | 키를 가진 **서버** |
        | 알 수 있는 것 | 토큰에 **적힌 내용** | 그 내용이 **위조·변조되지 않았는지** |
        | 위조된 토큰을 넣으면 | 문제없이 내용이 읽힘 | **실패** (서명 불일치) |
        | 만료 확인 | 하지 않음 (`exp` 값을 읽을 수만 있음) | 보통 라이브러리가 `exp`까지 함께 검사 |
        | 결과를 믿을 수 있나 | ❌ | ⭕ |
        | 주 사용 위치 | 프론트엔드 (UI 표시용) | 백엔드 (인증·인가 판단) |
        
        ### 3. 비유
        
        - 디코딩: 봉투 없이 온 편지를 읽는 것 → 누가 썼는지는 편지에 적힌 이름을 믿을 수밖에 없음
        - 서명 검증: 편지에 찍힌 도장(인감)이 진짜인지 대조하는 것 → 도장 원본(키)을 가진 사람만 대조 가능, 진짜 발신자인지 확인됨
        
        ### 4. 동작 과정
        
        #### 디코딩
        
        ```
        eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIn0 . (signature)
                │                            │
                ▼ Base64URL 디코딩            ▼ Base64URL 디코딩
        { "alg": "HS256" }        { "sub": "42", "role": "USER" }
        
        → signature는 사용하지 않음. 내용만 읽고 끝
        ```
        
        #### 서명 검증
        
        ```
        ① 받은 header와 payload를 그대로 사용
        ② 서버의 비밀 키로 서명을 새로 계산
             HMACSHA256(header + "." + payload, 비밀 키)
        ③ 새로 계산한 서명 === 토큰에 붙은 signature ?
             ├─ 일치   → 변조되지 않은 진짜 토큰 → exp 등 클레임 검사 후 사용
             └─ 불일치 → 위조·변조된 토큰 → 401 Unauthorized
        ```
        
        ### 5. 디코딩만으로는 안 되는 이유
        
        ```
        [원래 토큰 payload]          [공격자가 수정한 payload]
        { "sub": "42",               { "sub": "1",
          "role": "USER" }    →        "role": "ADMIN" }
        ```
        
        | 서버가 하는 일 | 결과 |
        | --- | --- |
        | **디코딩만** 하고 payload를 믿음 | 공격자가 **1번 사용자(관리자)로 인식**됨 → 권한 탈취 |
        | **서명 검증** 후 payload를 사용 | 수정된 payload로 계산한 서명이 기존 signature와 달라서 **거부(401)** |
        - 공격자는 payload를 얼마든지 수정할 수 있지만, 비밀 키가 없어서 그에 맞는 올바른 서명은 만들 수 없음
        - 그래서 서버는 반드시 서명을 검증한 뒤에 payload를 신뢰해야 함
        
        ### 6. 코드로 보기
        
        #### 프론트엔드: 디코딩 (jwt-decode)
        
        ```tsx
        import { jwtDecode } from 'jwt-decode';
        
        const payload = jwtDecode<{ sub: string; role: string; exp: number }>(accessToken);
        
        // UI 편의용으로만 사용
        const isExpired = payload.exp * 1000 < Date.now();   // 만료 직전 재발급 요청 판단
        const isAdmin = payload.role === 'ADMIN';            // 관리자 메뉴 표시 여부
        ```
        
        - 서명을 검증하지 않으므로 이 값으로 보안 판단을 하면 안 됨
        - 사용자가 토큰을 수정하면 화면은 바뀔 수 있지만, 서버 API는 서명 검증에서 거부함
        
        #### 백엔드: 서명 검증 (NestJS `@nestjs/jwt`)
        
        ```tsx
        import { Injectable, UnauthorizedException } from '@nestjs/common';
        import { JwtService } from '@nestjs/jwt';
        
        @Injectable()
        export class AuthService {
          constructor(private readonly jwtService: JwtService) {}
        
          async verifyAccessToken(token: string) {
            try {
              // 서명 + exp 등 클레임까지 검증, 성공하면 payload 반환
              return await this.jwtService.verifyAsync<{ sub: string; role: string }>(token, {
                secret: process.env.JWT_SECRET,
              });
            } catch {
              throw new UnauthorizedException('유효하지 않은 토큰입니다.');
            }
          }
        }
        ```
        
        #### 라이브러리 함수 비교 (`jsonwebtoken` 기준)
        
        | 함수 | 동작 | 사용처 |
        | --- | --- | --- |
        | `jwt.decode(token)` | 디코딩만 (서명·만료 검사 X) | 로그, 디버깅, `kid` 등 header 정보 미리 확인 |
        | `jwt.verify(token, key)` | 서명 + 만료 등 클레임 검증 후 payload 반환 | **인증 처리** |
        - 서버에서 인증할 때 `decode`를 쓰면 위조된 토큰도 통과하므로, 반드시 `verify`를 사용
        - 검증 시 허용할 알고리즘을 지정해서(`algorithms: ['HS256']`), header의 `alg`를 조작한 토큰을 받아들이지 않게 함
        
        ### 7. 역할 정리
        
        | 위치 | 하는 일 | 목적 |
        | --- | --- | --- |
        | 프론트엔드 | **디코딩** | 만료 시각 확인, 사용자 이름·역할에 따른 화면 표시 |
        | 백엔드 | **서명 검증** + 클레임 검증 | 진짜 사용자인지 확인 (인증), 권한 판단 (인가) |
    - payload에 비밀번호를 담으면 안 되는 이유는 무엇인가요?
        
        ### 1. 용어 정의
        
        #### Payload
        
        - JWT에서 사용자 식별 정보, 권한, 만료 시각 같은 데이터(클레임) 를 담는 부분
        - JSON을 Base64URL로 인코딩한 문자열
        
        #### 인코딩 (Encoding)과 암호화 (Encryption)
        
        | 구분 | 인코딩 | 암호화 |
        | --- | --- | --- |
        | 목적 | 데이터를 **전송·저장하기 좋은 형식**으로 바꾸기 | 데이터를 **허가된 사람만 읽을 수 있게** 숨기기 |
        | 원래 값으로 되돌리기 | **누구나** 가능 (키 필요 없음) | **키가 있는 사람만** 가능 |
        | 예시 | Base64, Base64URL, URL 인코딩 | AES, RSA |
        - JWT의 payload는 인코딩만 되어 있고 암호화되어 있지 않음
        
        #### 민감 정보 (Sensitive Data)
        
        - 노출되면 사용자에게 피해를 주거나 계정 탈취로 이어질 수 있는 정보
        - 예: 비밀번호, 주민등록번호, 카드 번호, 계좌 정보, 상세 주소, 건강 정보
        
        ### 2. 안 되는 이유
        
        #### 이유 1. payload는 누구나 읽을 수 있다
        
        - Base64URL 디코딩은 키 없이 누구나 할 수 있음
            - 브라우저 콘솔의 `atob()`, jwt.io 같은 사이트, 디코딩 라이브러리로 바로 확인 가능
        - 토큰을 손에 넣은 사람은 payload 안의 비밀번호를 그대로 볼 수 있음
        
        ```jsx
        // 브라우저 콘솔에서 바로 확인 가능
        const payload = token.split('.')[1];
        JSON.parse(atob(payload.replace(/-/g, '+').replace(/_/g, '/')));
        // { sub: "42", email: "woods@x.com", password: "myPassword123!" }  ← 그대로 노출
        ```
        
        #### 이유 2. 서명은 "변조 방지"이지 "내용 숨김"이 아니다
        
        - signature는 payload가 바뀌지 않았는지 확인할 뿐, payload 내용을 가려주지 않음
        - "서명된 토큰이니 안전하다"는 것은 위조에 대한 안전이지 노출에 대한 안전이 아님
        
        | 보장하는 것 | 서명 (Signature) |
        | --- | --- |
        | 내용이 바뀌지 않았음 (무결성) | ⭕ |
        | 신뢰할 수 있는 서버가 발급함 | ⭕ |
        | 내용을 다른 사람이 못 읽음 (기밀성) | ❌ |
        
        #### 이유 3. 토큰은 여러 곳에 노출되고 오래 남는다
        
        - JWT는 매 요청마다 전송되고 여러 곳에 저장되기 때문에, 유출될 수 있는 지점이 많음
        
        | 노출 지점 | 예시 |
        | --- | --- |
        | 브라우저 저장소 | `localStorage`에 저장된 토큰을 **XSS 공격** 스크립트가 탈취 |
        | 개발자 도구 | Network 탭의 요청 헤더, Application 탭 |
        | 서버·프록시 로그 | 요청 헤더나 URL을 기록하는 로그, 에러 모니터링 도구 |
        | URL 쿼리 스트링 | `?token=...`으로 전달하면 **브라우저 기록, Referer 헤더**에 남음 |
        | 공유·캡처 | 디버깅하면서 토큰을 메신저·이슈에 붙여넣기 |
        - 비밀번호가 들어 있으면, 이 중 한 곳만 노출돼도 비밀번호까지 유출됨
        
        #### 이유 4. 토큰 유출보다 비밀번호 유출의 피해가 훨씬 크다
        
        | 유출된 것 | 피해 범위 |
        | --- | --- |
        | 토큰만 | 토큰이 **만료될 때까지** 해당 서비스에서만 악용 가능 |
        | 비밀번호 | 만료 없음. 비밀번호를 바꾸기 전까지 **계속 로그인 가능** |
        | 비밀번호 (재사용) | 같은 비밀번호를 쓰는 **다른 서비스 계정까지** 탈취 가능 (크리덴셜 스터핑) |
        
        #### 이유 5. 비밀번호는 로그인 이후에 필요 없다
        
        - 비밀번호는 로그인할 때 한 번 인증하는 용도로만 사용됨
        - 인증에 성공한 뒤에는 토큰 자체가 인증 수단 역할을 하므로, 이후 요청에서 비밀번호를 확인할 일이 없음
        - 필요 없는 정보를 담는 것은 노출 위험만 늘리는 것
        
        #### 이유 6. 해시된 비밀번호도 마찬가지로 위험하다
        
        - bcrypt로 해시한 값이라도 공격자가 얻으면 오프라인에서 무차별 대입 공격을 시도할 수 있음
        - 해시 알고리즘·cost 정보까지 해시 문자열에 포함되어 있어 공격에 필요한 정보를 그대로 넘겨주는 셈
        - 비밀번호 해시는 DB 안에서만 다뤄야 함
        
        ### 3. payload에 담아도 되는 정보 / 안 되는 정보
        
        | 담아도 되는 정보 | 담으면 안 되는 정보 |
        | --- | --- |
        | 사용자 id (`sub`) | 비밀번호, 비밀번호 해시 |
        | 역할·권한 (`role`) | 주민등록번호, 여권 번호 |
        | 만료·발급 시각 (`exp`, `iat`) | 카드 번호, 계좌 정보 |
        | 발급자·대상 (`iss`, `aud`) | API Key, 비밀 키, 내부 시스템 정보 |
        | 화면 표시용 최소 정보 (닉네임 등) | 상세 주소, 전화번호, 건강 정보 같은 개인정보 |
        - 기준: "이 토큰이 공개되어도 괜찮은 정보인가?"
        - 상세한 사용자 정보가 필요하면 토큰에는 id만 넣고, 서버가 그 id로 DB를 조회해서 사용
        
        ```json
        // ⭕ 좋은 예
        { "sub": "42", "role": "USER", "iat": 1793990000, "exp": 1794000000 }
        
        // ❌ 나쁜 예
        { "sub": "42", "email": "woods@x.com", "password": "myPassword123!", "phone": "010-1234-5678" }
        ```
        
        ### 4. 정말 숨겨야 하는 정보를 토큰에 담아야 한다면
        
        - JWE (JSON Web Encryption) 처럼 토큰 내용을 암호화하는 방식을 사용할 수 있음
        - 하지만 대부분의 서비스에서는 민감 정보를 토큰에 넣지 않고 서버에서 조회하는 방식으로 해결함
