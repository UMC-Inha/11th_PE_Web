- 인증과 인가
    - 인증과 인가는 무엇을 확인하는 과정인가요?
    
    **인증은 요청한 사용자가 누구인지 확인하는 과정이고, 인가는 그 사용자가 해당 작업을 해도 되는지 판단하는 과정이다.** 두 과정은 연결되어 있지만, 인증에 성공했다고 모든 요청이 허용되는 것은 아니다.
    
    영화 리뷰 수정 기능을 예로 들면 다음처럼 구분할 수 있다.
    
    | 구분 | 서버가 확인하는 내용 | 예시 |
    | --- | --- | --- |
    | 인증 | 요청한 사용자가 누구인지 | 로그인한 회원이 7번 회원인지 확인한다. |
    | 인가 | 그 회원이 해당 리뷰를 수정할 수 있는지 | 리뷰 작성자가 7번 회원인지 확인한다. |
    
    인증은 로그인 버튼을 누르는 순간에만 필요한 것이 아니다. **로그인 이후 보호된 API를 요청할 때도 서버는 세션이나 토큰을 확인해서 요청자를 식별해야 한다.** HTTP 요청 자체에는 이전에 로그인했다는 사실이 자동으로 포함되지 않기 때문이다.
    
    또한 **회원가입과 로그인은 별개의 과정이다.** 회원가입은 계정 정보를 등록하는 것이고, 로그인은 등록된 계정의 주인인지 확인하는 것이다. 따라서 회원가입에 성공했더라도 서비스가 자동 로그인 처리를 제공하지 않는다면 아직 로그인한 상태는 아니다.
    
    - 로그인한 사용자도 특정 기능을 이용하지 못할 수 있는 이유는 무엇인가요?
    
    로그인은 사용자의 신원을 확인할 뿐이고, 기능을 사용할 수 있는지는 별도의 권한 조건으로 결정된다. 권한은 관리자 여부뿐 아니라 **데이터의 소유자, 소속, 구독 상태, 계정 상태** 등에 따라서도 달라질 수 있다.
    
    | 상황 | 접근이 제한되는 이유 |
    | --- | --- |
    | 일반 회원이 회원 삭제 기능을 실행한다. | 관리자 권한이 필요하다. |
    | 다른 회원이 작성한 리뷰를 수정한다. | 해당 리뷰의 작성자가 아니다. |
    | 다른 조직의 내부 문서를 조회한다. | 문서가 속한 조직의 구성원이 아니다. |
    | 정지된 계정으로 리뷰를 작성한다. | 계정 상태에 따른 제한이 있다. |
    
    특히 **요청에 담긴 회원 번호를 그대로 믿으면 안 된다.** 예를 들어 로그인한 회원이 7번인데 요청 URL의 회원 번호를 9번으로 바꿨다고 해서 9번 회원의 정보를 수정할 수 있어서는 안 된다. 서버는 인증으로 확인한 회원 정보와 수정하려는 데이터의 소유자를 비교해야 한다.
    
    화면에서 수정 버튼을 숨기거나 페이지 이동을 막는 것은 사용 편의를 위한 처리이다. 사용자가 직접 API 요청을 보낼 수도 있으므로, **최종 권한 판단은 서버에서 요청마다 수행해야 한다.**
    
    인증과 인가의 실패는 응답 상태로도 구분할 수 있다.
    
    - **401 Unauthorized:** 인증 정보가 없거나 유효하지 않은 경우이다. 토큰이 없거나 만료된 상황이 대표적이다.
    - **403 Forbidden:** 요청을 이해했지만 접근을 허용하지 않는 경우이다. 로그인한 일반 회원이 관리자 기능을 요청하는 상황이 대표적이다.
    
    401이 발생했다고 항상 로그인 화면으로 보내고, 403이 발생했다고 다시 로그인을 시키는 식으로 동일하게 처리하면 안 된다. **인증이 필요한 상황과 권한 자체가 없는 상황을 구분해서 안내해야 한다.**
    
- JWT
    - header, payload, signature는 각각 어떤 역할을 하나요?
    
    일반적으로 로그인에 사용하는 **서명된 JWT**는 header, payload, signature의 세 부분으로 구성된다.
    
    | 구성 요소 | 역할 | 추가로 알아둘 점 |
    | --- | --- | --- |
    | Header | 서명 알고리즘과 토큰 유형 등의 정보를 담는다. | 토큰에 적힌 알고리즘을 무조건 믿지 않고, 서버가 허용한 알고리즘인지 확인해야 한다. |
    | Payload | 사용자 식별자, 만료 시간 등의 정보를 담는다. | 정보의 각 항목을 클레임이라고 하며, 필요한 정보만 최소한으로 넣는 것이 좋다. |
    | Signature | header와 payload의 변조 여부를 검증하는 데 사용한다. | 내용을 숨기는 기능이 아니라, 검증에 성공한 내용이 변경되지 않았는지 확인하는 기능이다. |
    
    Payload는 다음과 같은 형태가 될 수 있다.
    
    ```json
    {
      "sub": "7",
      "role": "USER",
      "iss": "umcine-api",
      "aud": "umcine-web",
      
      
      
      "exp": 1893456000
    }
    ```
    
    - **sub:** 토큰의 주체를 나타낸다. 회원 번호처럼 사용자를 안정적으로 식별할 수 있는 값을 넣을 수 있다.
    - **role:** 서비스에서 정의한 권한 정보이다. 이 예시에서는 일반 회원을 의미한다.
    - **iss:** 토큰을 발급한 주체이다.
    - **aud:** 토큰을 사용하도록 의도된 대상이다.
    - **exp:** 만료 시각이다. 일반적인 JWT에서는 Unix 시간을 **초 단위**로 사용한다.
    
    자바스크립트의 Date.now()는 밀리초 단위이므로 만료 시간과 비교할 때 단위를 맞춰야 한다. 다만 프론트엔드에서 만료 여부를 확인하는 것은 화면 처리를 위한 보조 수단이고, **서버에서도 반드시 만료 여부를 검증해야 한다.**
    
    또한 payload에 담긴 권한은 보통 **토큰 발급 당시의 정보이다.** 관리자를 일반 회원으로 변경해도 이미 발급한 토큰 내용이 자동으로 바뀌지는 않는다. 권한 변경을 빠르게 반영해야 하는 서비스에서는 짧은 유효기간이나 별도의 서버 상태 확인 같은 처리가 필요하다.
    
    - JWT를 디코딩하는 것과 서명을 검증하는 것은 어떻게 다른가요?
    
    **디코딩은 토큰에 무엇이 적혀 있는지 읽는 것이고, 서명 검증은 그 내용을 신뢰할 수 있는지 확인하는 과정이다.**
    
    서명된 JWT의 header와 payload는 Base64URL 방식으로 인코딩되어 있다. 이는 암호화가 아니므로, 토큰을 가진 사람은 비밀키 없이도 내용을 읽을 수 있다.
    
    예를 들어 누군가 payload의 권한을 USER에서 ADMIN으로 바꾸고 다시 인코딩했다고 가정해 볼 수 있다.
    
    - 디코딩만 하면 ADMIN이라는 값이 정상적으로 보인다.
    - 기존 서명은 변경 전 내용을 기준으로 만들어졌기 때문에, 올바른 서버 검증에서는 실패한다.
    
    따라서 **프론트엔드에서 디코딩한 권한을 보고 관리자 메뉴를 표시하는 것과 서버가 관리자 요청을 허용하는 것은 별개이다.** 디코딩 결과만으로 실제 접근 권한을 부여하면 안 된다.
    
    또한 **서명이 유효하다는 것만으로 사용 가능한 토큰이라고 판단할 수는 없다.** 서버는 다음 조건도 함께 확인해야 한다.
    
    - 토큰이 만료되지 않았는지 확인한다.
    - 아직 사용하면 안 되는 시각으로 설정되어 있지 않은지 확인한다.
    - 기대한 발급자가 발급한 토큰인지 확인한다.
    - 현재 서비스에서 사용할 목적으로 발급된 토큰인지 확인한다.
    
    다른 서비스용으로 발급된 토큰이나 이미 만료된 토큰도 서명 자체는 정상일 수 있기 때문이다.
    
    - payload에 비밀번호를 담으면 안 되는 이유는 무엇인가요?
    
    **일반적인 서명된 JWT의 payload는 암호화되지 않아 토큰을 얻은 사람이 내용을 읽을 수 있기 때문이다.** 서명은 변조를 확인하는 기능이지, 비밀번호를 감추는 기능이 아니다.
    
    비밀번호 원문뿐 아니라 **비밀번호 해시도 payload에 넣으면 안 된다.** 해시는 서버에서 비밀번호를 대조하기 위해 보관하는 값이고, 외부로 노출되면 비밀번호를 추측하는 공격에 악용될 수 있다.
    
    로그인 이후에는 비밀번호를 매번 전달할 필요가 없다. 서버가 로그인 시 비밀번호를 확인한 뒤 토큰을 발급하고, 이후 요청에서는 그 토큰을 검증하면 된다. Payload에는 회원 식별자, 만료 시간 등 필요한 정보만 담는 편이 좋다.
    
    토큰 자체도 주의해서 다뤄야 한다. 일반적인 **Bearer 토큰은 가진 사람이 사용할 수 있는 인증 정보**이므로, 토큰을 탈취한 사람이 유효기간 동안 사용자를 대신해 요청할 수 있다. 서명 검증은 토큰 변조를 막는 것이지 토큰 도난까지 막는 기능은 아니다.
    
    실제로는 다음 사항을 함께 고려해야 한다.
    
    - 토큰 전체를 콘솔, 서버 로그, 공유 캡처 등에 노출하지 않는다.
    - HTTPS를 사용해 전송 중 정보가 노출되는 위험을 줄인다.
    - Payload에 개인정보를 불필요하게 많이 넣지 않는다.
    - 프론트엔드에서 토큰을 삭제하는 것과 서버에서 토큰을 무효화하는 것은 구분한다.
    
    특히 **로그아웃하면서 브라우저의 토큰을 지웠다고 해서 이미 복사된 토큰까지 자동으로 무효화되는 것은 아니다.** 즉시 사용을 막아야 한다면 서버에서도 토큰 폐기 여부를 확인하는 등의 별도 처리가 필요하다.
