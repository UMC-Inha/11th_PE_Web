- 인증과 인가
    - 인증과 인가는 무엇을 확인하는 과정인가요?
        
        ### 인증(Authentication)
        
        인증은 **사용자가 누구인지 확인하는 과정**이다.
        
        사용자가 로그인할 때 이메일과 비밀번호를 확인하거나, 요청에 포함된 세션·JWT·Access Token을 검증하여 사용자의 신원을 확인한다.
        
        ```
        이메일·비밀번호 입력
        → 서버가 회원 정보 확인
        → 일치하면 로그인 성공
        → 사용자 신원 확인 완료
        ```
        
        예를 들어 Spring Security에서는 인증에 성공한 사용자의 ID, 이름과 권한 정보를 `Authentication` 객체에 저장하여 현재 요청을 보낸 사용자가 누구인지 확인한다.
        
        인증 실패는 일반적으로 `401 Unauthorized`로 응답한다.
        
        ### 인가(Authorization)
        
        인가는 **인증된 사용자가 특정 기능이나 데이터에 접근할 권한이 있는지 확인하는 과정**이다.
        
        ```
        로그인한 사용자 확인
        → 사용자의 역할과 권한 확인
        → 해당 기능에 접근 가능한지 판단
        ```
        
        예를 들어 관리자만 회원 목록을 조회할 수 있도록 제한할 수 있다.
        
        ```java
        @PreAuthorize("hasRole('ADMIN')")
        @GetMapping("/members")
        public List<MemberResponse> findMembers() {
            return memberService.findMembers();
        }
        ```
        
        일반 사용자가 로그인에 성공했더라도 `ADMIN` 권한이 없다면 이 기능을 사용할 수 없다. 인가 실패는 일반적으로 `403 Forbidden`으로 응답한다.
        
        | 구분 | 인증 | 인가 |
        | --- | --- | --- |
        | 영어 | Authentication | Authorization |
        | 확인 내용 | 사용자가 누구인가 | 무엇을 할 수 있는가 |
        | 대표 예시 | 로그인, 토큰 검증 | 관리자 기능, 게시글 수정 권한 |
        | 실패 응답 | 주로 `401 Unauthorized` | 주로 `403 Forbidden` |
        | 처리 순서 | 먼저 수행 | 인증 후 수행 |
    - 로그인한 사용자도 특정 기능을 이용하지 못할 수 있는 이유는 무엇인가요?
        
        로그인은 인증에 성공했다는 뜻일 뿐, 모든 기능에 접근할 권한을 얻었다는 뜻은 아니다. 로그인 후에도 별도의 인가 검사를 통과해야 한다.
        
        ### 역할이 다른 경우
        
        관리자 기능은 `ADMIN` 역할을 가진 사용자만 이용할 수 있다.
        
        ```
        로그인한 일반 사용자
        → 인증 성공
        → ADMIN 권한 없음
        → 관리자 페이지 접근 거부
        ```
        
        ### 리소스의 소유자가 아닌 경우
        
        로그인한 사용자라도 다른 사용자가 작성한 게시글을 임의로 수정하거나 삭제할 수 없어야 한다.
        
        ```java
        if (!post.isWrittenBy(currentMemberId)) {
            throw new AccessDeniedException(
                    "게시글을 수정할 권한이 없습니다."
            );
        }
        ```
        
        ```
        사용자 A가 로그인
        → 사용자 B의 게시글 수정 요청
        → 게시글 소유자가 아님
        → 접근 거부
        ```
        
        ### 세부 권한이 없는 경우
        
        같은 역할을 가진 사용자라도 담당 업무에 따라 권한이 다를 수 있다.
        
        ```
        회원 조회 권한은 있음
        회원 삭제 권한은 없음
        ```
        
        단순히 `USER`, `ADMIN` 같은 역할만 검사하지 않고 `MEMBER_READ`, `MEMBER_DELETE`처럼 세부 권한을 구분할 수 있다.
        
        ### 리소스 상태상 허용되지 않는 경우
        
        사용자에게 기본적인 권한이 있어도 현재 데이터 상태에 따라 작업이 제한될 수 있다.
        
        ```
        이미 취소된 주문을 다시 취소
        이미 반납한 책을 다시 반납
        마감된 신청을 수정
        ```
        
        이 경우는 사용자 권한 문제라기보다 현재 리소스 상태와의 충돌이므로 `409 Conflict`로 처리할 수도 있다.
        
        ### 계정이나 인증 상태에 추가 제한이 있는 경우
        
        다음과 같은 상황에서도 일부 기능을 제한할 수 있다.
        
        - 이메일 인증을 완료하지 않은 사용자
        - 정지되거나 휴면 상태인 계정
        - 추가 본인 인증이 필요한 기능
        - 결제 비밀번호나 2단계 인증이 필요한 작업
        - 특정 조직이나 서비스에 가입하지 않은 사용자
        
        > 로그인은 “누구인지 확인했다”는 의미이고, 특정 기능을 사용할 수 있는지는 역할, 권한, 리소스 소유권과 현재 상태를 추가로 확인해야 한다.

- JWT
    - header, payload, signature는 각각 어떤 역할을 하나요?
        
        JWT는 점(`.`)을 기준으로 세 부분으로 구성된다.
        
        ```
        Header.Payload.Signature
        ```
        
        ```
        xxxxx.yyyyy.zzzzz
        ```
        
        ### Header
        
        Header에는 토큰의 종류와 서명 생성에 사용한 알고리즘 정보가 들어간다.
        
        ```json
        {
          "typ": "JWT",
          "alg": "HS256"
        }
        ```
        
        | 필드 | 의미 |
        | --- | --- |
        | `typ` | 토큰의 종류 |
        | `alg` | 서명에 사용한 알고리즘 |
        | `kid` | 여러 키 중 어떤 키를 사용했는지 나타내는 식별자 |
        
        Header는 암호화되지 않고 Base64URL 방식으로 인코딩된다.
        
        ### Payload
        
        Payload에는 사용자 정보와 토큰의 유효 기간 등을 나타내는 Claim이 들어간다.
        
        ```json
        {
          "sub": "10",
          "role": "USER",
          "iat": 1794297600,
          "exp": 1794301200
        }
        ```
        
        | Claim | 의미 |
        | --- | --- |
        | `sub` | 토큰의 주체, 일반적으로 사용자 식별자 |
        | `iss` | 토큰 발급자 |
        | `aud` | 토큰을 사용할 대상 |
        | `iat` | 토큰 발급 시간 |
        | `exp` | 토큰 만료 시간 |
        | `role` | 사용자의 역할 또는 권한 |
        
        Payload도 암호화된 것이 아니라 Base64URL로 인코딩된 것이므로 누구나 내용을 확인할 수 있다.
        
        사용자 ID처럼 서버가 사용자를 식별하는 데 필요한 최소한의 정보만 넣는 것이 좋다.
        
        ### Signature
        
        Signature는 Header와 Payload가 발급 이후 변경되지 않았는지 확인하기 위한 전자서명이다.
        
        HS256을 사용하는 경우 개념적으로 다음과 같이 생성한다.
        
        ```
        HMAC-SHA256(
            Base64Url(Header) + "." + Base64Url(Payload),
            Secret Key
        )
        ```
        
        공격자가 Payload의 `role`을 `USER`에서 `ADMIN`으로 바꿀 수는 있지만, 비밀키를 모르기 때문에 올바른 Signature를 다시 만들 수 없다. 서버가 서명을 검증하면 토큰이 조작되었다는 사실을 알 수 있다.
        
        | 구성 요소 | 역할 |
        | --- | --- |
        | Header | 토큰 종류와 서명 알고리즘 표시 |
        | Payload | 사용자 정보와 토큰 관련 Claim 저장 |
        | Signature | Header와 Payload의 위조·변조 여부 확인 |
        
        > Signature는 데이터의 무결성과 발급자를 확인하지만, Header와 Payload의 내용을 숨겨주지는 않는다.
        > 
    - JWT를 디코딩하는 것과 서명을 검증하는 것은 어떻게 다른가요?
        
        ### 디코딩
        
        디코딩은 Base64URL로 표현된 Header와 Payload를 읽을 수 있는 형태로 변환하는 것이다.
        
        ```
        JWT 문자열
        → Base64URL 디코딩
        → Header와 Payload 확인
        ```
        
        디코딩에는 비밀키나 공개키가 필요하지 않다. 따라서 jwt.io 같은 도구나 브라우저에서도 Payload 내용을 확인할 수 있다.
        
        ```json
        {
          "sub": "10",
          "role": "ADMIN"
        }
        ```
        
        하지만 디코딩만으로는 다음 내용을 알 수 없다.
        
        - 신뢰할 수 있는 서버가 발급한 토큰인지
        - Payload가 중간에 변경되었는지
        - 공격자가 임의로 만든 토큰인지
        
        따라서 디코딩한 Payload의 내용을 바로 신뢰하면 안 된다.
        
        ### 서명 검증
        
        서명 검증은 서버의 키를 이용하여 JWT의 Signature가 올바른지 확인하는 과정이다.
        
        ```
        받은 Header와 Payload로 서명을 다시 계산
        → JWT에 포함된 Signature와 비교
        → 같으면 서명 유효
        → 다르면 위조되거나 변조된 토큰
        ```
        
        사용하는 알고리즘에 따라 필요한 키가 다르다.
        
        | 방식 | 서명 생성 | 서명 검증 |
        | --- | --- | --- |
        | HS256 | 비밀키 | 같은 비밀키 |
        | RS256 | 개인키 | 공개키 |
        
        실제 인증에서는 서명만 확인하는 것으로 끝나지 않고 다음 Claim도 함께 검사해야 한다.
        
        - `exp`: 토큰이 만료되지 않았는가
        - `iss`: 신뢰하는 서버가 발급했는가
        - `aud`: 현재 서비스에서 사용하도록 발급됐는가
        - `nbf`: 현재 사용할 수 있는 시간이 되었는가
        
        | 구분 | 디코딩 | 검증 |
        | --- | --- | --- |
        | 목적 | 토큰 내용 확인 | 토큰의 신뢰성 확인 |
        | 키 필요 여부 | 필요 없음 | 비밀키 또는 공개키 필요 |
        | 위조 확인 | 불가능 | 가능 |
        | 인증에 사용 | 단독 사용 불가 | 반드시 필요 |
        
        > 디코딩은 JWT의 내용을 읽는 것이고, 검증은 해당 JWT를 신뢰할 수 있는지 확인하는 것이다.
        > 
    - payload에 비밀번호를 담으면 안 되는 이유는 무엇인가요?
        
        JWT의 Payload는 암호화되지 않고 Base64URL로 인코딩될 뿐이다. 따라서 JWT를 가진 사람은 누구나 Payload를 디코딩하여 내용을 확인할 수 있다.
        
        ```json
        {
          "email": "user@example.com",
          "password": "password123!"
        }
        ```
        
        이런 토큰이 유출되면 비밀번호도 그대로 노출된다.
        
        ```
        JWT 탈취
        → Payload 디코딩
        → 비밀번호 확인 가능
        ```
        
        JWT는 다음과 같은 여러 위치에 남을 수도 있다.
        
        - 브라우저 저장소
        - 서버 로그
        - 프록시 및 네트워크 로그
        - 오류 추적 시스템
        - 개발자 도구
        - 외부 모니터링 서비스
        
        따라서 비밀번호뿐만 아니라 다음과 같은 민감 정보도 Payload에 넣지 않는 것이 좋다.
        
        - 평문 비밀번호
        - 비밀번호 해시값
        - 주민등록번호
        - 카드번호
        - 계좌 비밀번호
        - API Secret Key
        - 불필요한 개인정보
        
        비밀번호 해시값도 넣으면 안 된다. 해시값은 평문이 아니지만 공격자가 오프라인에서 비밀번호를 추측하는 공격에 사용할 수 있고, 비밀번호가 변경될 때마다 토큰 내용과 DB 상태가 어긋날 수 있다.
        
        Payload에는 인증과 인가에 필요한 최소 정보만 넣는다.
        
        ```json
        {
          "sub": "10",
          "role": "USER",
          "exp": 1794301200
        }
        ```
        
        > JWT Payload는 누구나 읽을 수 있으므로 비밀번호 같은 비밀 정보를 저장하면 안 된다. JWT는 정보를 숨기는 수단이 아니라, 정보가 변조되지 않았음을 확인하는 수단이다.
        >
