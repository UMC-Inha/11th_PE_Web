- 인증과 인가
    - 인증과 인가는 무엇을 확인하는 과정인가요?
        - **인증(Authentication)**: 사용자가 주장하는 신원이 맞는지 확인. 예: 이메일·비밀번호를 확인해 로그인 처리.
        - **인가(Authorization)**: 해당 사용자가 요청한 기능·데이터에 접근할 권한이 있는지 판단. 예: 관리자만 영화 삭제 가능.
    - 로그인한 사용자도 특정 기능을 이용하지 못할 수 있는 이유는 무엇인가요?
        - 로그인 성공은 모든 권한을 얻었다는 뜻은 X. 역할·이용 플랜·데이터 소유자에 따라 접근 범위가 달라짐.
        - 예: 일반 회원은 관리자 메뉴 이용 불가, 본인 정보 수정은 가능해도 다른 회원 정보 수정은 불가.
        - 프론트에서 버튼을 숨기는 것은 화면 처리. 서버에서도 매 요청의 권한을 검사해야 직접 API를 호출하는 접근까지 통제 가능.

  **추가 핵심 정리**

    - **최소 권한**: 필요한 권한만 부여하고, 허용 규칙이 없는 접근은 기본 거부.
    - **상태 코드**: `401`은 유효한 인증 정보가 없는 경우, `403`은 권한 부족 등으로 서버가 접근을 거부하는 경우.

- JWT
    - header, payload, signature는 각각 어떤 역할을 하나요?
        - 워크북에서 다루는 **서명형 JWT**는 `header.payload.signature` 형태.
        - **header**: 서명 알고리즘(`alg`)과 토큰 유형(`typ`) 등 메타데이터.
        - **payload**: 사용자 식별자(`sub`), 만료 시각(`exp`) 등 클레임. 클레임은 토큰에 담긴 정보 항목을 의미.
        - **signature**: header와 payload를 기반으로 만든 서명. 검증 키를 이용해 데이터 변조 여부와 서명 유효성 확인.
    - JWT를 디코딩하는 것과 서명을 검증하는 것은 어떻게 다른가요?
        - **디코딩**: Base64URL로 표현된 내용을 읽을 수 있게 변환. 키 없이도 가능하며 내용이 진짜라는 보장은 X.
        - **서명 검증**: 허용된 알고리즘과 신뢰하는 키로 서명 유효성 확인.
        - 예: payload의 `role`을 `USER → ADMIN`으로 바꿔 읽을 수는 있어도, 기존 서명 검증은 실패.
    - payload에 비밀번호를 담으면 안 되는 이유는 무엇인가요?
        - 서명형 JWT의 payload는 암호화되지 않아 토큰을 가진 사람이 읽을 수 있음. Base64URL 인코딩은 암호화와 구분.
        - 서명은 변조 검증용이며 내용 숨김 기능은 X → 비밀번호·비밀키 등 민감한 값은 payload에 포함하지 않기.

  **추가 핵심 정리**

    - **사용 흐름 예시**: 로그인 성공 → 서버가 JWT 발급 → 이후 요청의 `Authorization: Bearer <token>`으로 전달 → 서버가 검증 후 접근 권한 판단.
    - **검증 범위**: 서명뿐 아니라 서비스 정책에 맞춰 만료 시각·발급자(`iss`)·대상(`aud`)도 확인. 디코딩한 사용자 정보만으로 로그인·권한을 신뢰하는 것은 X.
