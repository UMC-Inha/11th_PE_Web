# Frontend Chapter07

## 키워드 정리

### 인증과 인가

#### 인증과 인가는 무엇을 확인하는 과정인가요?

**인증(Authentication)**

- 인증은 요청한 사용자가 누구인지 확인하는 과정
- 로그인 시 이메일과 비밀번호를 확인하거나, 이후 요청에서 토큰을 검증해 사용자를 식별하는 과정이 해당한다.

**인가(Authorization)**

- 인가는 해당 사용자가 특정 기능이나 데이터에 접근할 권한이 있는지 확인하는 과정이다.
- 관리자 권한이 있는지, 수정하려는 게시글의 작성자인지 등을 확인한다.

일반적으로 사용자를 인증한 뒤, 요청한 작업을 수행할 수 있는지 판단한다.

#### 로그인한 사용자도 특정 기능을 이용하지 못할 수 있는 이유는 무엇인가요?

로그인은 인증에 성공했다는 의미이지, 모든 기능에 대한 권한을 얻었다는 의미는 아니다.

기능이나 데이터마다 접근 조건이 다르기 때문에, 로그인 이후에도 별도의 인가 과정이 필요하다.

- 일반 회원은 관리자 전용 기능을 사용할 수 없다.
- 다른 사용자가 작성한 게시글은 수정할 수 없다.
- 구매하지 않은 유료 콘텐츠는 이용할 수 없다.

### JWT

#### header, payload, signature는 각각 어떤 역할을 하나요?

일반적으로 사용하는 서명된 JWT는 다음 세 부분으로 구성되며, 각 부분은 점(.)으로 구분된다.

```tsx
Header.Payload.Signature
```

**Header: 토큰과 서명 방식에 대한 정보**

```tsx
{
	"alg": "HS256", //서명 알고리즘
	"typ": "JWT"    //토큰의 종류
}
```

- Header에는 서명 알고리즘 등 토큰을 처리하는 데 필요한 정보가 들어간다.
- 서버는 토큰에 적힌 알고리즘을 무조건 따르는 것이 아니라, 서버에서 허용한 알고리즘과 키를 기준으로 검증해야 한다.

**Payload: 전달할 정보**

```tsx
{
	"sub": "123",      //토큰의 대상 식별자
	"role": "USER",    //서비스에서 정의한 권한 정보의 예시
	"exp": 1839456000  //만료 시각
}
```

- **Claim 종류**

    | Claim | 의미 |
    | --- | --- |
    | sub | 토큰의 대상 식별자. 사용자 ID 등으로 사용 |
    | exp | 만료 시각 |
    | iat | 발급 시각 |
    | iss | 발급자 |
    | add | 토큰을 사용할 대상 |
    | role | 서비스에서 정의한 권한 정보의 예시 |

- Payload에는 사용자 식별자, 만료 시각 등의 정보가 들어간다. 이 안의 개별 정보 항목을 Claim(클레임)이라고 한다.
- Payload는 일반적인 서명 JWT에서 암호화되지 않으므로 내용을 읽을 수 있다.

**Signature: 내용의 무결성과 서명 확인**

- Signature는 Header와 Payload가 변경되지 않았는지, 신뢰하는 키로 서명되었는지 검증하는 데 사용한다.
- 사용자가 Payload의 권한을 USER 에서 ADMIN으로 바꾸면 기존 서명과 일치하지 않으므로 검증에 실패한다.
- 다만 서명이 유효하더라도 만료 시각, 발급자, 대상 등 필요한 조건을 추가로 확인해야 한다.

#### JWT를 디코딩하는 것과 서명을 검증하는 것은 어떻게 다른가요?

**디코딩**

디코딩은 BASE64URL로 인코딩된 Header와 Payload를 읽을 수 있는 형태로 변환하는 과정이다.

일반적인 서명 JWT는 비밀 키 없이도 내용을 디코딩할 수 있다. 따라서 디코딩에 성공했다는 사실만으로 그 내용이 신뢰할 수 있다는 뜻은 아니다.

**서명 검증**

서명 검증은 신뢰하는 키를 사용해 서명이 유효한지 확인하는 과정이다.

이를 통해 서명 대상 내용이 변경되지 않았는지 확인할 수 있다.

| 구분 | 디코딩 | 서명 검증 |
| --- | --- | --- |
| 목적 | 내용을 읽기 | 서명의 유효성 확인 |
| 키 필요 여부 | 필요 없음 | 검증 키 필요 |
| 위조·변조 확인 | 불가능 | 올바른 검증 설정에서 가능 |
| 인증 판단 | 이것만으로 불가능 | 만료 등 추가 조건도 확인 필요 |

#### payload에 비밀번호를 담으면 안 되는 이유는 무엇인가요?

일반적인 서명 JWT의 Payload는 암호화가 아니라 Base64URL 인코딩되어 있다. 따라서 토큰을 가진 사람은 누구나 디코딩하여 내용을 읽을 수 있다.

Signature는 내용의 변경 여부를 확인하기 위한 것이지, 내용을 숨기는 기능이 아니다.

Payload에 비밀번호를 넣으면 토큰이 노출되었을 때 비밀번호까지 함께 노출된다. 비밀번호 해시 역시 클라이언트에 전달할 필요가 없으며, 노출되면 비밀번호 추측 공격에 악용될 수 있다.

JWT에는 사용자 식별자와 만료 시각 등 요청 처리에 필요한 정보만 최소한으로 포함해야 한다.
