# 핵심 키워드

## 1. URL과 라우팅

### Q. URI, URL, path와 route는 각각 무엇이며 어떤 차이가 있을까요?

#### 1) URI (Uniform Resource Identifier)

⇒ 인터넷상의 자원을 **고유하게 식별**하기 위한 문자열

**식별 방법**에 따라 두 종류로 나뉨

- **URL(Uniform Resource Locator)**: 위치로 식별 → `https://example.com/users/1`
- **URN(Uniform Resource Name)**: 이름으로 식별 → `urn:isbn:9788966262281`

#### 2) URL (Uniform Resource Locator)

- 자원이 **어디에 있고 어떤 방식(프로토콜)으로 접근하는지**를 나타내는 주소
- 구조 예시

```
https://www.example.com:443/users/1?sort=desc#profile
└─┬─┘   └──────┬──────┘ └┬┘└───┬──┘└───┬───┘└──┬──┘
scheme       host      port  path   query  fragment
```

| 구성 요소 | 예시 | 의미 |
| --- | --- | --- |
| scheme | `https` | 사용할 프로토콜 |
| host | `www.example.com` | 서버 주소(도메인/IP) |
| port | `443` | 서버의 포트 (https 기본값이라 보통 생략) |
| path | `/users/1` | 서버 내 자원의 경로 |
| query | `?sort=desc` | 추가 파라미터 (key=value) |
| fragment | `#profile` | 페이지 내 특정 위치 (서버로 전송 안 됨) |

#### 3) Path

⇒ URL에서 host 뒤, query(`?`) 앞에 오는 부분

⇒ 서버 안에서 어떤 자원을 요청하는지를 계층적으로 표현

#### 4) Route (라우트)

⇒ "이 path(패턴)로 요청이 오면 이 코드/화면이 처리한다"는 매핑 규칙

#### 5) Path와 Route의 차이점

⇒ path는 요청에 담긴 **구체적인 값**이고, route는 그 값을 처리 로직과 연결하는 **규칙**

### Q. path param과 search param은 각각 어떤 값을 표현할 때 사용하는 것이 좋을까요?

#### 1) Path Param (경로 파라미터)

⇒ URL의 path 안에 들어가는 **동적인 값**

- 형태: `/users/:id` → `/users/42`
- 특정 자원 하나를 가리키는 **식별자**를 표현할 때 적합
- 없으면 자원 자체를 특정할 수 없으므로 보통 **필수값**

#### 2) Search Param (쿼리 파라미터, Query String)

⇒ URL에서 `?` 뒤에 `key=value` 형태로 붙는 값, 여러 개는 `&`로 연결

- 형태: `/posts?category=react&sort=latest&page=2`
- 같은 자원(목록)을 **어떤 조건**으로 조회·표시할지를 표현할 때 적합
- 없어도 페이지는 동작해야 하므로 보통 **선택값** (없으면 기본값 사용)

#### 3) 판단 기준

**이 값이 없으면 어떤 자원인지 모르는가?**

- ⭕ ⇒ **Path Param**
- ✖️, 보여주는 방식만 달라진다 ⇒ **Search Param**

### Q. 검색어, 필터나 현재 화면의 상태를 URL에 포함하면 공유와 새로고침에 어떤 장점이 있을까요?

1. URL만 있으면 언제 어디서든 같은 화면을 다시 만들 수 있음
2. 공유·새로고침·뒤로 가기·북마크가 모두 기대한 대로 동작함

#### if) 상태를 컴포넌트에만 저장할 때

상태가 메모리(자바스크립트 변수)에만 존재

⇒ 새로고침하면 컴포넌트가 다시 마운트되면서 초기값으로 리셋

⇒ 링크를 공유해도 받은 사람은 초기 화면을 보게 됨

#### 상태를 URL에 저장할 때

⇒ 링크를 공유해도 받은 사람이 바로 같은 화면을 볼 수 있고 새로고침해도 상태가 유지됨

## 2. SPA와 MPA

### Q. SPA와 MPA는 각각 무엇이며 화면을 이동하는 방식에 어떤 차이가 있을까요?

#### 1) SPA (Single Page Application)

- 최초 접속 시 index.html 하나와 JS 번들을 받음
- 이후 화면 이동은 서버에 HTML을 요청하지 않고, JS가 URL에 맞는 컴포넌트를 렌더링
- 서버와는 주로 필요한 데이터(JSON)만 주고받음

#### 2) MPA (Multi Page Application)

- 여러 개의 HTML 페이지로 구성된 전통적인 웹 방식
- 링크를 클릭하면 브라우저가 서버에 새 페이지를 요청하고, 서버는 완성된 HTML을 응답
- 브라우저는 기존 페이지를 버리고 전체를 새로 로드

#### 3) 이동 방식의 차이

⇒ **MPA**: 이동할 때마다 서버에서 새 페이지를 받아 통째로 교체

⇒ **SPA**: 한 페이지 안에서 JS가 URL만 바꾸고 필요한 컴포넌트만 교체

### Q. SPA의 클라이언트 내비게이션은 새로운 HTML 문서를 받는 일반적인 페이지 이동과 어떻게 다를까요?

#### 일반 페이지 이동 (Document Navigation)

⇒ 브라우저가 문서 자체를 교체 ⇒ 서버에서 새 HTML을 받아 처음부터 다시 로드

⇒ 이동의 주체가 브라우저

#### 클라이언트 내비게이션 (Client-side Navigation)

⇒ 문서는 그대로 두고, JS가 URL과 화면 일부만 바꿈

⇒ 이동의 주체가 라우터

### Q. SPA와 MPA는 각각 어떤 서비스나 화면에 적합할까요?

#### MPA 특징

- 첫 화면이 빠르다.
- 구조가 단순하고, 페이지별로 독립적이다.
- 이동할 때마다 전체 로드 → 느리다.

#### SPA 특징

- 이동이 빠르고 앱처럼 부드러운 사용자 경험이 가능하다.
- 첫 로딩이 느릴 수 있다.

**MPA**: 콘텐츠를 보여주는 것이 중심이고, 검색 노출·첫 화면 속도가 중요한 서비스

ex) 뉴스, 블로그, 랜딩 페이지

**SPA**: 사용자와 상호작용이 많고, 화면 이동이 잦으며 상태를 유지해야 하는 서비스

ex) 채팅, 메신저, SNS 피드, Notion, Figma

## 3. Tailwind CSS

### Q. CSS 규칙을 직접 작성하는 방식과 비교했을 때 Tailwind CSS의 특징은 무엇일까요?

**직접 CSS 작성**

: 클래스 이름을 직접 짓고, 별도 CSS 파일에 스타일 규칙을 정의한 뒤 HTML에 적용

**Tailwind CSS**

: 미리 만들어진 유틸리티 클래스(한 가지 역할만 하는 작은 클래스)를 HTML/JSX에 조합해서 스타일링

#### 특징

- 파일을 오가지 않고 한 곳에서 작업
  - 컴포넌트 코드와 스타일이 같은 곳에 있어, 요소를 보면 스타일을 바로 알 수 있음
- 디자인 일관성이 유지
  - 간격, 색상, 글자 크기 등이 정해진 단계로 제공 → `p-2`(8px), `text-sm`, `blue-500` 등
- 반응형 처리가 간단
- 스타일 충돌·부작용이 적음
  - 클래스가 각 요소에만 붙으므로, 한 곳을 고쳐도 다른 컴포넌트에 영향이 가지 않음
- 클래스가 길어짐
  - 요소 하나에 클래스가 줄줄이 붙어 마크업 가독성이 떨어질 수 있음

### Q. styled-components와 Tailwind CSS는 스타일을 작성하고 생성하는 방식이 어떻게 다를까요?

#### styled-components

- JS/TS 안에 CSS 문법 그대로 스타일을 작성
- **런타임**(브라우저 실행 중)에 CSS를 만들어 페이지에 생성

#### Tailwind CSS

- 미리 정의된 유틸리티 클래스를 조합
- **빌드 타임**에 사용된 클래스만 모아 정적 CSS 파일 생성

### Q. Tailwind CSS에서 `bg-${color}-500`처럼 class 이름을 동적으로 조합하면 스타일이 생성되지 않을 수 있는 이유는 무엇일까요?

Tailwind는 빌드할 때 소스 코드를 실행하지 않고 텍스트로만 읽어서 클래스 이름을 찾음

⇒ `bg-${color}-500`은 코드를 실행해야 `bg-red-500`처럼 완성되는 문자열이라 빌드 시점에는 완전한 클래스 이름이 코드에 존재하지 않음

⇒ 해당 CSS가 생성되지 않음

### Q. 상태에 따라 달라지는 스타일은 완성된 class 이름의 매핑이나 CSS 변수를 이용해 어떻게 표현할 수 있을까요?

#### 1) 상태 값이 정해져 있을 때 (success / error)

⇒ **완성된 class 이름 매핑**

상태별로 적용할 클래스를 객체에 온전한 이름으로 정의해 두고, 상태 값으로 꺼내 쓰는 방식

#### 2) 값이 연속적이거나 미리 정할 수 없을 때 (진행률 %)

⇒ **CSS 변수 이용**

클래스 이름은 고정해 두고, 바뀌는 값만 CSS 변수로 전달하는 방식
