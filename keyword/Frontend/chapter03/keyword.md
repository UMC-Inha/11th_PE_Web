- URL과 라우팅
  - URI, URL, path와 route는 각각 무엇이며 어떤 차이가 있을까요?
    | 개념  | 의미                                                     | 예시                                       |
    | ----- | -------------------------------------------------------- | ------------------------------------------ |
    | URI   | 자원을 식별하는 문자열 전체를 가리키는 상위 개념         | URL, `urn:isbn:9788966260959` 등           |
    | URL   | URI 중 자원의 위치와 접근 방법(scheme, host)까지 담은 것 | `https://shop.example.com/products/42?...` |
    | path  | URL 안에서 자원의 계층적 위치를 나타내는 부분            | `/products/42`                             |
    | route | path 패턴을 특정 화면이나 핸들러에 연결하는 앱의 규칙    | `/products/:id` → `ProductDetail`          |
    path는 주소에 실제로 들어 있는 값이고 route는 개발자가 정의한 매핑 규칙이다. 위의 표에서 `/products/42` 같은 path들이 `/products/:id` 라는 하나의 route에 매칭되고 이때 42가 id 파라미터로 추출된다.
  - path param과 search param은 각각 어떤 값을 표현할 때 사용하는 것이 좋을까요?
    path param은 무엇을 보여줄지(특정 리소스 자체를 식별하는 값) , search param은 어떻게 보여줄지(필터링, 정렬) 를 표현할 때 사용하는것이 좋다.
    판단하는 간단한 기준은 이 값이 없어도 페이지가 기본값으로 성립하면 search param, 성립하지 않으면 path param을 사용한다.
    ex) /user/123 → 값이 없으면 어떤 리소스를 요청할 지 결정할 수 없음 (path param)
    /user?page=2 → 값이 없어도 기본 목록이나 페이지가 성립하고 값이 있으면 조회 조건이 달라짐(Search param)
  - 검색어, 필터나 현재 화면의 상태를 URL에 포함하면 공유와 새로고침에 어떤 장점이 있을까요?
    링크를 받은 사람이 보낸 사람과똑같은 화면을 볼 수 있다. 또한 새로고침하거나 브라우저를 껐다 켜도 같은 화면으로 돌아올 수 있다.
- SPA와 MPA
  - SPA와 MPA는 각각 무엇이며 화면을 이동하는 방식에 어떤 차이가 있을까요?
    - SPA : 하나의 HTML 페이지를 기반으로 JS가 화면을 동적으로 변경하는 방식
    - MPA : 페이지마다 별도의 HTML 문서를 서버에서 받아오는 방식
      |                      | **SPA**             | **MPA**                   |
      | -------------------- | ------------------- | ------------------------- |
      | HTML 문서            | 초기 로드 후 재사용 | 페이지마다 새로 받음      |
      | 화면 이동            | JS가 처리           | 브라우저가 새 페이지 요청 |
      | 서버 요청            | API 요청 중심       | 페이지 이동마다 HTML 요청 |
      | 페이지 전체 새로고침 | 일반적으로 없음     | 일반적으로 발생           |
      | 화면 전환            | 상대적으로 부드러움 | 페이지가 다시 로드됨      |
      |                      |                     |                           |
  - SPA의 클라이언트 내비게이션은 새로운 HTML 문서를 받는 일반적인 페이지 이동과 어떻게 다를까요?
    SPA는 페이지 이동 시 새 HTML문서를 다시 받지 않는다는 것이 핵심이다.
    일반적인 페이지 이동은 새 URL로 요청하여 새로운 HTML 문서 전체를 받아 페이지를 교환한다. 그러나 SPA는 JS가 URL 화면을 변경한다. 즉 SPA는 같은 문서 안에서 UI만 변경하여 업데이트 하는 것이도 MPA는 문서를 교체하는 것이다.
  - SPA와 MPA는 각각 어떤 서비스나 화면에 적합할까요?
    SPA는 화면 내 상호작용이 많고 앱처럼 동작하는 서비스에 적합하다.
    MPA는 뉴스, 블로그처럼 각 페이지가 독립적인 콘텐츠를 제공하는 서비스에 적합하다.
- Tailwind CSS
  - CSS 규칙을 직접 작성하는 방식과 비교했을 때 Tailwind CSS의 특징은 무엇일까요?
    Tailwind CSS는 CSS 규칙을 직접 작성하기보다 미리 제공되는 유틸리티 클래스를 조합해 스타일을 적용하는 방식이다.
    예를 들어 margin, padding 등을 CSS 파일에 직접 작성하는 대신 p-4, mt-2 같은 클래스를 HTML에 적용한다. 따라서 별도의 CSS파일을 작성하는 작업을 줄일 수 있다.
  - styled-components와 Tailwind CSS는 스타일을 작성하고 생성하는 방식이 어떻게 다를까요?
    - styled-components는 JS안에서 CSS를 작성하고 컴포넌트 단위로 스타일을 정의하는 방식이다. 반면 Tailwind CSS는 미리 정의된 유틸리티 클래스를 HTML에 조합하여 스타일을 적용한다. 즉 styled-components는 CSS를 JS에서 작성, 관리하고 Tailwind CSS는 제공되는 CSS유틸리티를 조합해 사용하는 방식이다.
  - Tailwind CSS에서 `bg-${color}-500`처럼 class 이름을 동적으로 조합하면 스타일이 생성되지 않을 수 있는 이유는 무엇일까요?
    Tailwind CSS는 빌드 시점에 소스 코드를 분석해 실제로 사용되는 클래스 이름을 찾아 필요한 CSS만 생성한다. 그런데 클래스 이름을 동적으로 조합하면 빌드 도구가 완성된 클래스 이름을 미리 알기 어렵다. 만약 color가 red라면 실제로는 bg-red-500이지만 소스에는 완성된 문자열이 존재하지 않는다. 따라서 Tailwind가 bg-red-500같은 클래스를 감지하지 못해 CSS를 생성하지 못할 수 있다.
    따라서 완성된 클래스 이름을 코드에 명시적으로 작성하는것이 중요하다.
  - 상태에 따라 달라지는 스타일은 완성된 class 이름의 매핑이나 CSS 변수를 이용해 어떻게 표현할 수 있을까요?
    상태에 따라 스타일이 달라진다면 완성된 클래스 이름을 미리 매핑하는 방식이 필요하다.
    예를 들어 status에 따라 { active:”bg-green-500”, error: “ bg-red-500”} 처럼 클래스를 선택한다. 이렇게 하면 Tailwind가 빌드 시점에 실제 클래스 이름을 인식할 수 있다.
