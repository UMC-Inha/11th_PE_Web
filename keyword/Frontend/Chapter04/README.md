# Frontend Chapter04

## 키워드 정리

### Web Storage

#### localStorage와 sessionStorage는 저장값의 수명과 공유 범위가 어떻게 다른가요? (쿠키와의 비교 포함)

- **수명 (Persistence)**
    - **localStorage:** 사용자가 직접 삭제하지 않는 한 브라우저를 닫거나 컴퓨터를 재부팅해도 **영구적으로 보관**됩니다.
    - **sessionStorage:** 데이터를 생성한 **해당 브라우저 탭을 닫는 순간 즉시 삭제**됩니다.
- **공유 범위 (Scope)**
    - **localStorage:** 동일한 Origin(도메인+프로토콜+포트) 내라면 **모든 탭과 창에서 전역으로 공유**됩니다.
    - **sessionStorage:** 동일한 Origin이라도 **각 브라우저 탭마다 독립된 영역**으로 격리되어 서로 공유되지 않습니다.
- **쿠키(Cookie)와의 차이점 및 Web Storage의 장점**
    - **네트워크 트래픽 절감:** 쿠키는 모든 HTTP 요청마다 서버로 자동 전송되어 네트워크 비용을 늘리지만, Web Storage는 완전히 클라이언트(브라우저)에만 존재하며 **서버로 자동 전송되지 않습니다.**
    - **용량 확충:** 쿠키(약 4KB)에 비해 Web Storage(약 5MB 이상)가 훨씬 넓은 저장 공간을 제공합니다.

#### 객체나 배열을 저장할 때 JSON 문자열로 바꿔야 하는 이유는 무엇일까요?

- **Web Storage의 구조적 한계:** Web Storage API는 오직 **문자열(String) 데이터 타입만 저장**하도록 설계된 단순 Key-Value 텍스트 저장소입니다.
- **문자열로 전환해야 하는 이유:**
    - 자바스크립트 객체나 배열을 변환 없이 그대로 넣으면 브라우저 내부에서 `.toString()`이 강제로 실행되어 `"[object Object]"`나 `"1,2,3"` 같은 원본 구조가 손실된 글자로 변형되어 버립니다.
    - 따라서 저장 시에는 `JSON.stringify()`를 통해 데이터 구조를 유지한 JSON 문자열로 직렬화(Serialize)해야 하며, 읽어올 때는 `JSON.parse()`로 복원해야 합니다.

#### Web Storage에는 어떤 데이터를 저장하는 것이 적절할까요?

- **적절한 데이터 (유출되어도 보안상 치명적이지 않고 유지되어야 하는 데이터)**
    - UI 테마 설정 (다크모드 / 라이트모드)
    - 사용자 편의 기능 데이터 (최근 검색어, 최근 본 상품, 북마크 ID 목록)
    - 작성 중인 임시 폼/임시글 데이터
- **저장하면 안 되는 데이터 (쿠키/세션 활용 필요)**
    - 로그인 인증 토큰(Access Token), 비밀번호, 주민등록번호, 결제 카드 정보 등 개인/보안 정보
    - **이유:** Web Storage는 자바스크립트 코드만으로 손쉽게 읽고 쓸 수 있어 **XSS(Cross-Site Scripting) 공격** 시 해커에게 쉽게 탈취됩니다. 보안 정보는 `HttpOnly` 옵션이 설정된 쿠키 등을 활용해야 안전합니다.

### 상태 관리 (Zustand)

#### 컴포넌트 상태와 전역 상태는 사용하는 범위가 어떻게 다른가요?

- **컴포넌트 지역 상태 (Local State)**
    - **범위:** 특정 컴포넌트 내부 및 해당 컴포넌트의 자식 컴포넌트
    - **특징:** 해당 UI 조각(화면)에서만 쓰이고 사용이 끝나면 사라지는 일회성 상태입니다. (예: 모달 팝업 열림/닫힘, 드롭다운 메뉴, 텍스트 입력 폼의 input 값)
- **전역 상태 (Global State)**
    - **범위:** 애플리케이션 전체 (모든 페이지 및 컴포넌트 트리)
    - **특징:** 부모-자식 관계와 상관없이 여러 컴포넌트나 여러 화면에서 공통으로 접근하고 업데이트해야 하는 핵심 데이터입니다. (예: 로그인한 유저 정보, 장바구니, 북마크 목록)

#### 여러 화면에서 사용하는 북마크 상태를 전역으로 관리하면 어떤 장점과 비용이 생길까요?

- **장점**
    - **데이터 일관성:** 영화 목록, 상세 페이지, 검색 결과 등 어느 화면에서 북마크를 토글하든 앱 전체의 UI가 **실시간으로 즉시 동기화**됩니다.
    - **Prop Drilling 방지:** 부모에서 자식으로 Props를 수십 단계씩 깊게 전달해야 하는 불필요한 코드 복잡성을 제거합니다.
    - **컴포넌트 간 직접 통신:** 서로 완전히 분리된 독립된 컴포넌트끼리도 손쉽게 상태를 공유할 수 있습니다.
- **비용 (단점/고려사항)**
    - **메모리 지속 사용:** 애플리케이션이 켜져 있는 동안 전역 상태가 브라우저 자바스크립트 메모리(RAM)를 계속 점유합니다.
    - **불필요한 리렌더링:** Selector 설정을 제대로 하지 않으면 전역 상태 변경 시 관련 없는 컴포넌트까지 계속 다시 그려지는 성능 저하가 발생할 수 있습니다.
    - **설계 복잡도 증가:** 전역 스토어(Zustand 등) 세팅을 위한 보일러플레이트 코드가 추가됩니다.

#### Zustand와 Web Storage는 북마크 상태를 관리할 때 각각 어떤 역할을 할까요?

- **Zustand (메모리상 전역 상태 관리자)**
    - 자바스크립트 **메모리(RAM)** 상에서 북마크 상태를 들고 있으면서, 상태가 바뀔 때 이에 연결된 React 컴포넌트들을 **실시간으로 UI 렌더링 및 동기화**합니다.
    - 새로고침하거나 브라우저를 닫으면 메모리가 초기화되는 한계가 있습니다.
- **Web Storage (브라우저 영속성 저장소)**
    - 브라우저 디스크(Storage)에 북마크 데이터를 지속적으로 저장합니다.
    - 새로고침을 하거나 브라우저를 껐다 켜도 이전 북마크 데이터를 잃어버리지 않고 복원(Persist)하는 역할을 담당합니다.
- **역할 결합:** Zustand가 빠른 UI 반응과 동기화를 맡고, Web Storage가 데이터의 지속성을 책임지는 **보완적 관계**로 동작합니다.
