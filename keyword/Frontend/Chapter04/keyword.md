- Web Storage
    - localStorage와 sessionStorage는 저장값의 수명과 공유 범위가 어떻게 다른가요?
    
    둘 다 브라우저의 Web Storage에 값을 저장하지만, **값이 유지되는 기간이 다르다.**
    
    - localStorage: 브라우저를 닫았다 다시 열어도 값이 유지된다.
    - sessionStorage: 현재 탭이 열려 있는 동안만 유지되고, 탭을 닫으면 사라진다.
    
    예를 들어 영화 북마크처럼 **다음 방문에도 남아 있어야 하는 값은 localStorage**가 적합하다. 반대로 현재 탭에서만 잠시 필요한 검색 조건이나 임시 입력값은 sessionStorage에 더 잘 맞는다. 
    
    핵심은 **오래 기억해야 하면 localStorage, 현재 탭에서만 필요하면 sessionStorage**라고 이해하면 된다.
    
    - 객체나 배열을 저장할 때 JSON 문자열로 바꿔야 하는 이유는 무엇일까요?
    
    Web Storage는 값을 **문자열 형태로만 저장**한다.
    
    그래서 배열이나 객체를 저장하려면:
    
    - 저장할 때 JSON.stringify로 문자열로 변환
    - 읽을 때 JSON.parse로 다시 JavaScript 값으로 복원
    
    하는 과정이 필요하다. 
    
    예를 들어 북마크한 영화 ID가 2와 7이라면, 배열 구조를 유지하기 위해 JSON 문자열로 바꿔 저장한 뒤 앱이 다시 실행될 때 배열로 복원한다.
    
    또 하나 중요한 점은 **저장된 값을 그대로 믿으면 안 된다는 것**이다. 사용자가 개발자 도구에서 값을 바꿀 수 있기 때문에, 배열인지 확인하거나 잘못된 값이면 빈 배열 같은 기본값으로 복구하는 처리가 필요하다.
    
    - Web Storage에는 어떤 데이터를 저장하는 것이 적절할까요?
    
    Web Storage에는 **작고, 브라우저에서만 사용하며, 민감하지 않은 데이터**를 저장하는 것이 적절하다.
    
    예시:
    
    - 북마크한 영화 ID
    - 테마 설정
    - 최근 선택한 필터
    - 간단한 화면 설정
    
    반대로 다음과 같은 값은 적절하지 않다.
    
    - 비밀번호
    - 개인정보
    - 중요한 인증 정보
    - 매우 큰 데이터
    
    Web Storage의 값은 사용자가 개발자 도구에서 직접 확인하거나 수정할 수 있기 때문에, 민감한 정보는 저장하지 않는 것이 좋다. 
    
    또한 읽기와 쓰기가 동기적으로 처리되므로 큰 데이터를 자주 저장하는 용도에도 적합하지 않다.
    
- 클라이언트 상태와 전역 상태 관리
    - 컴포넌트 상태와 전역 상태는 사용하는 범위가 어떻게 다른가요?
    
    차이는 **상태를 사용하는 범위**에 있다.
    
    ### 컴포넌트 상태
    
    특정 컴포넌트나 가까운 범위에서만 사용하는 값이다.
    
    예시:
    
    - 검색창 입력값
    - 모달이 열려 있는지 여부
    - 특정 버튼의 토글 상태
    
    이런 값은 보통 useState로 관리한다.
    
    ### 전역 상태
    
    여러 컴포넌트나 여러 화면에서 같은 값을 사용해야 할 때 관리하는 상태이다.
    
    예를 들어 UMCine의 북마크는 영화 목록, 검색 결과, 상세 화면에서 모두 같은 상태를 보여줘야 하므로 전역 상태로 관리하기 적합하다. 
    
    핵심은 **모든 값을 전역으로 만드는 것이 아니라, 실제로 공유가 필요한 상태만 전역으로 관리하는 것**이다.
    
    - 여러 화면에서 사용하는 북마크 상태를 전역으로 관리하면 어떤 장점과 비용이 생길까요?
    
    ### 장점
    
    여러 화면이 하나의 동일한 상태를 사용할 수 있다.
    
    예를 들어:
    
    - 영화 목록에서 북마크 추가
    - 검색 화면에서도 북마크 상태 유지
    - 상세 화면에서도 같은 상태 확인
    
    처럼 모든 화면의 결과가 일치하게 된다.
    
    또 상태와 변경 함수를 여러 단계의 props로 계속 전달하는 구조도 줄일 수 있다.
    
    ### 비용
    
    전역 상태가 많아지면:
    
    - 상태가 어디에서 변경됐는지 찾기 어려워질 수 있다.
    - 관련 없는 컴포넌트까지 같은 store에 의존할 수 있다.
    - 상태 구조 자체가 복잡해질 수 있다.
    
    따라서 **여러 화면이 정말 함께 사용해야 하는 값만 전역 상태로 두는 것이 좋다.**
    
    - Zustand와 Web Storage는 북마크 상태를 관리할 때 각각 어떤 역할을 할까요?
    
    두 기술은 서로 대신하는 관계가 아니라 **역할이 다르다.**
    
    ### Zustand
    
    앱이 실행되는 동안 여러 컴포넌트가 같은 상태와 함수를 공유하게 해주는 전역 상태 관리 도구이다.
    
    예를 들어 하나의 store에서:
    
    - 북마크된 영화 ID 목록
    - 북마크를 추가하거나 제거하는 함수
    
    를 함께 관리할 수 있다. 
    
    ### Web Storage
    
    상태를 브라우저에 저장해서 **새로고침하거나 브라우저를 다시 실행한 뒤에도 유지**하게 한다.
    
    즉 역할을 나누면:
    
    - Zustand: 앱 내부에서 상태를 공유
    - localStorage: 상태를 브라우저에 저장
    
    Zustand의 persist 기능을 사용하면 이 둘을 연결할 수 있다.
    
    한 줄로 정리하면:
    
    **Zustand는 현재 상태를 관리하고, Web Storage는 그 상태를 기억한다.**
