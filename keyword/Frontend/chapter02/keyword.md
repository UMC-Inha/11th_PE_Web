- React 컴포넌트와 JSX
    - JSX는 HTML과 어떤 점이 다르며 React 컴포넌트 안에서 어떤 역할을 하나요?

      ### JSX는 HTML과 무엇이 다르며, 어떤 역할을 하나?

      JSX는 **JavaScript 안에서 HTML처럼 UI를 작성하는 문법**이다. 브라우저가 직접 읽지 못하고, 빌드 시 `React.createElement()` 호출로 변환된다. 즉 생긴 건 HTML이지만 실체는 JavaScript다.

      | 구분 | HTML | JSX |
              | --- | --- | --- |
      | 클래스 | `class` | `className` |
      | 이벤트 | `onclick="..."` (문자열) | `onClick={함수}` (함수 전달) |
      | 스타일 | `style="color: red"` | `style={{ color: 'red' }}` (객체) |
      | 값 삽입 | 불가 | `{변수}`, `{표현식}` |
      | 닫는 태그 | `<img>` 허용 | `<img />` 필수 |
      | 최상위 요소 | 여러 개 가능 | 하나로 감싸야 함 (`<>...</>`) |

      **컴포넌트 안에서의 역할** — 컴포넌트가 반환하는 "화면의 설계도"다. `{}` 안에 JS 표현식을 넣어 데이터를 화면에 연결한다.

        ```jsx
        function Greeting({ name }) {
          return <h1 className="title">안녕, {name}</h1>;
        }
        ```

    - 하나의 화면을 여러 컴포넌트로 나누면 어떤 장점이 있으며, 분리 기준은 어떻게 정할 수 있을까요?

      ### 화면을 컴포넌트로 나누면 좋은 점과 분리 기준

      **장점**

        - **재사용** — 버튼·카드 같은 UI를 여러 화면에서 다시 쓴다
        - **유지보수** — 문제가 생긴 부분만 찾아 고치면 된다
        - **가독성** — 큰 화면을 이름 붙은 조각으로 읽을 수 있다
        - **역할 분리** — 각 컴포넌트가 자기 데이터와 동작만 책임진다

      **분리 기준**

        - **반복되는가** — 같은 모양이 여러 번 나오면 분리 (영화 카드 목록의 카드 하나)
        - **역할이 하나인가** — 한 컴포넌트가 두 가지 일을 하면 쪼갠다 (헤더 / 목록 / 상세)
        - **독립적으로 바뀌는가** — 따로 상태가 변하는 영역은 분리
        - **너무 길어졌는가** — 한 파일이 길어져 읽기 힘들면 신호

        ```
        MoviePage
        ├── Header
        ├── MovieList
        │   └── MovieCard (반복)
        └── Footer
        ```

    - 조건부 렌더링과 목록 렌더링은 데이터에 따라 보여 줄 컴포넌트를 어떻게 결정하나요?

      ### **조건부 렌더링**

      데이터 상태에 따라 **무엇을 보여줄지** 결정한다.

        ```jsx
        {isLoading ? <Spinner /> : <MovieList />}   // 둘 중 하나
        {error && <ErrorMessage />}                  // 조건이 참일 때만
        ```

      | 방식 | 용도 |
              | --- | --- |
      | `조건 ? A : B` | 둘 중 하나 |
      | `조건 && A` | 참일 때만 표시 |
      | `if` + early return | 분기가 복잡할 때 |

      `&&` 사용 시 주의: `{count && <List />}`에서 count가 0이면 화면에 `0`이 찍힌다. `{count > 0 && ...}`처럼 불리언으로 만든다.

      → `&&`가 **true/false를 돌려주는 게 아니라, 피연산자 값 자체를 돌려줌**

      ### 목록 렌더링

      배열 데이터를 **몇 개 보여줄지** 결정한다. `map()`으로 배열을 컴포넌트 배열로 바꾼다.

        ```jsx
        {movies.map((movie) => (
          <MovieCard key={movie.id} movie={movie} />
        ))}
        ```

      **`key`는 필수다.** React가 어떤 항목이 추가·삭제·이동됐는지 구분하는 기준이다. 배열 인덱스 대신 **고유한 id**를 쓴다. 인덱스를 쓰면 순서가 바뀔 때 엉뚱한 항목이 갱신된다.

- props와 단방향 데이터 흐름
    - 부모와 자식 컴포넌트 사이에서 props는 어떤 역할을 하나요?

      ### 부모와 자식 사이에서 props의 역할

      props는 **부모가 자식에게 전달하는 입력값**이다. 함수의 매개변수와 같다. 자식은 받은 props로 화면을 그리며, **직접 수정할 수 없다** (읽기 전용).

        ```jsx
        // 부모
        <MovieCard title="인셉션" rating={9.1} />
        
        // 자식
        function MovieCard({ title, rating }) {
          return <div>{title} ⭐ {rating}</div>;
        }
        ```

      자식이 부모의 데이터를 바꾸고 싶으면, 부모가 **함수를 props로 내려주고** 자식은 그 함수를 호출한다. 데이터를 바꾸는 권한은 여전히 부모에게 있다.

        ```jsx
        <LikeButton onLike={() => setLiked(true)} />
        ```

      | 방향 | 방법 |
              | --- | --- |
      | 부모 → 자식 (데이터) | props 값 |
      | 자식 → 부모 (요청) | props로 받은 함수 호출 |
    - 데이터가 부모에서 자식으로만 흐르면 화면의 변화를 추적하는 데 어떤 도움이 되나요?

      ### 단방향 흐름이 변화 추적에 주는 도움

      데이터가 **위에서 아래로만** 흐르므로, 화면이 이상하면 **데이터의 출처를 위로 거슬러 올라가면** 원인이 나온다.

        ```
        App (state 보유)
         └── MovieList (props 전달)
              └── MovieCard (props 표시)
        ```

      MovieCard의 값이 틀렸다면 → MovieList가 뭘 넘겼나 → App의 state는 뭔가, 순서로 확인하면 된다.

      **양방향이었다면** 자식이 값을 몰래 바꿀 수 있어서, 어떤 컴포넌트가 언제 바꿨는지 추적하기 어렵다. 단방향에서는 **데이터를 바꿀 수 있는 곳이 state를 가진 컴포넌트 하나**로 정해져 있어 예측 가능하다.

    - props에 TypeScript 타입을 붙이면 컴포넌트를 잘못 사용하는 실수를 어떻게 찾을 수 있나요?

      ### props에 TypeScript 타입을 붙이면 좋은 점

      props의 **이름·타입·필수 여부를 미리 정해두면**, 잘못 사용했을 때 실행 전에 에디터가 빨간 줄로 알려준다.

        ```tsx
        type MovieCardProps = {
          title: string;
          rating: number;
          onLike?: () => void;   // ?는 선택
        };
        
        function MovieCard({ title, rating, onLike }: MovieCardProps) { ... }
        ```

      | 실수 | 타입이 잡아주는 것 |
              | --- | --- |
      | `<MovieCard />` | 필수 props `title` 누락 |
      | `<MovieCard title="인셉션" rating="9.1" />` | number 자리에 string |
      | `<MovieCard titel="인셉션" />` | 오타 난 props 이름 |
- 상태와 리렌더링
    - 일반 변수와 state(상태)는 값이 바뀐 뒤 화면을 다시 보여 주는 방식이 어떻게 다른가요?

      #### 1. 일반 변수와 state는 값이 바뀐 뒤 화면을 다시 보여주는 방식이 어떻게 다른가?

      일반 변수는 값이 바뀌어도 **React가 모르므로 화면을 다시 그리지 않는다.** state는 `setState`로 바꾸면 React에 변경이 알려지고 **컴포넌트가 다시 실행되며 화면이 갱신된다.**

      |  | 일반 변수 | state |
              | --- | --- | --- |
      | 값 변경 | 직접 대입 | `setState` |
      | 화면 갱신 | 안 됨 | 리렌더링됨 |
      | 리렌더링 후 값 | 초기값으로 리셋 | 유지 |

        ```jsx
        let a = 0;
        const [b, setB] = useState(0);
        
        <button onClick={() => a++}>{a}</button>          // 화면 그대로 0
        <button onClick={() => setB(b + 1)}>{b}</button>  // 1, 2, 3 갱신
        ```

      컴포넌트는 함수라서 리렌더링 때마다 처음부터 다시 실행된다. 일반 변수는 매번 새로 만들어져 값이 사라지고, state는 React가 컴포넌트 밖에 보관해 값이 유지된다.

    - React에서 원본 상태를 직접 수정하지 않고 새로운 값으로 업데이트해야 하는 이유는 무엇일까요?

      #### 원본 상태를 직접 수정하지 않고 새 값으로 업데이트해야 하는 이유는?

      React는 **이전 값과 새 값의 참조(주소)를 비교**해 변경 여부를 판단한다. 원본을 직접 고치면 주소가 같아 **변화를 감지하지 못하고 화면이 바뀌지 않는다.**

        ```jsx
        movies.push(newMovie);
        setMovies(movies);                 // 주소 동일 → 리렌더링 안 됨
        
        setMovies([...movies, newMovie]);  // 새 배열 → 리렌더링됨
        ```

      | 작업 | 새 값 만드는 법 |
              | --- | --- |
      | 배열 추가 | `[...arr, item]` |
      | 배열 삭제 | `arr.filter(...)` |
      | 배열 수정 | `arr.map(...)` |
      | 객체 수정 | `{ ...obj, key: 값 }` |

      `push`, `splice`, `sort`, `obj.a = 1`처럼 원본을 바꾸는 방식은 state에 쓰지 않는다.

    - 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 사용하는 이유는 무엇일까요?

      #### 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 쓰는 이유는?

      `setState`는 즉시 반영되지 않고 **모아서 한 번에 처리**된다. 같은 이벤트 안에서 state는 계속 **이전 값**이라, 여러 번 호출해도 같은 값을 기준으로 계산된다.

        ```jsx
        setCount(count + 1);   // 0 + 1
        setCount(count + 1);   // 0 + 1
        setCount(count + 1);   // 0 + 1  → 결과 1
        ```

      업데이터 함수는 React가 **직전 결과를 받아** 순서대로 계산하므로 의도대로 누적된다.

        ```jsx
        setCount(prev => prev + 1);   // 0 → 1
        setCount(prev => prev + 1);   // 1 → 2
        setCount(prev => prev + 1);   // 2 → 3
        ```

      **기준** — 새 값이 이전 값에 의존하면(`+1`, 토글, 배열 추가) 업데이터 함수를, 이전 값과 무관하게 덮어쓰면 값을 바로 넣는다.

- 상태 공유와 Context
    - 여러 컴포넌트가 같은 상태를 사용해야 할 때 상태를 어느 컴포넌트에 두는 것이 좋을까요?

      #### 여러 컴포넌트가 같은 상태를 사용할 때 상태를 어디에 두는가?

      **그 상태를 사용하는 컴포넌트들의 가장 가까운 공통 부모**에 둔다. 이를 **상태 끌어올리기(Lifting State Up)**라고 한다.

        ```
        MoviePage          ← 여기에 selectedId 상태
        ├── MovieList      (선택 변경)
        └── MovieDetail    (선택된 영화 표시)
        ```

      `MovieList`와 `MovieDetail`이 각자 상태를 가지면 서로 값이 달라진다. 공통 부모가 하나만 들고 props로 나눠주면 **값의 출처가 하나**가 되어 항상 일치한다.

      너무 위(예: `App`)에 두면 관련 없는 컴포넌트까지 리렌더링되고 props 전달 경로가 길어진다. **필요한 만큼만 끌어올린다.**

    - props 전달, 상태 끌어올리기와 Context는 각각 어떤 상황에 알맞을까요?

      ### props 전달, 상태 끌어올리기, Context는 각각 언제 쓰는가?

      | 방법 | 알맞은 상황 | 예시 |
              | --- | --- | --- |
      | **props 전달** | 부모 → 바로 아래 자식, 1~2단계 | 카드에 영화 제목 전달 |
      | **상태 끌어올리기** | 형제 컴포넌트가 같은 값을 공유·변경 | 목록에서 고르면 상세에 표시 |
      | **Context** | 깊이 떨어진 여러 컴포넌트가 공통으로 쓰는 전역 값 | 로그인 유저, 테마, 언어 |

      **판단 순서** — 기본은 props → 형제끼리 공유가 필요하면 끌어올리기 → 전달 단계가 너무 깊어져 중간 컴포넌트들이 쓰지도 않는 props를 넘겨주기만 하면(**props drilling**) Context를 고려한다.

        ```jsx
        const ThemeContext = createContext('light');
        
        <ThemeContext.Provider value="dark">
          <App />
        </ThemeContext.Provider>
        
        const theme = useContext(ThemeContext);   // 깊은 곳에서 바로 꺼내 씀
        ```

    - 모든 값을 Context로 전달하면 어떤 문제가 생길 수 있을까요?

      ### 모든 값을 Context로 전달하면 생기는 문제

      **불필요한 리렌더링** — Context 값이 바뀌면 그 Context를 쓰는 **모든 컴포넌트가 다시 렌더링**된다. 여러 값을 한 Context에 몰아넣으면 하나만 바뀌어도 전부 다시 그려진다.

      **데이터 흐름 추적이 어려워진다** — props는 부모를 따라 올라가면 출처가 보이지만, Context는 어디서든 꺼내 쓸 수 있어 누가 값을 바꾸는지 찾기 어렵다. 단방향 흐름의 장점이 약해진다.

      **재사용성이 떨어진다** — 컴포넌트가 특정 Context에 의존하면 그 Provider 없이는 동작하지 않아 다른 곳에 가져다 쓰기 어렵고 테스트도 번거롭다.

      **정리** — Context는 **자주 바뀌지 않고 앱 전반에서 쓰는 값**(로그인 정보, 테마, 언어)에 쓴다. 자주 바뀌거나 일부 컴포넌트만 쓰는 값은 props와 상태 끌어올리기로 처리하고, Context가 커지면 **관심사별로 나눈다** (AuthContext, ThemeContext).
