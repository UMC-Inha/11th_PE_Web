- React 컴포넌트와 JSX
    - JSX는 HTML과 어떤 점이 다르며 React 컴포넌트 안에서 어떤 역할을 하나요?
        - JSX는 **JavaScript 안에서 HTML처럼 UI 구조를 작성할 수 있게 해주는 문법**
        - HTML과 비슷하게 생겼지만 실제 HTML은 아니고, Babel·SWC·TypeScript 같은 도구에 의해 일반 JavaScript 코드로 변환된 뒤 React에서 사용됨
            - html과 다르게 `{}` 안에 JavaScript 값을 바로 넣을 수 있다
        - React 컴포넌트에서는 JSX를 이용해 **화면에 어떤 요소를 보여줄지 표현**
    - 하나의 화면을 여러 컴포넌트로 나누면 어떤 장점이 있으며, 분리 기준은 어떻게 정할 수 있을까요?
        - 하나의 화면을 여러 컴포넌트로 나누면 **코드를 역할별로 관리할 수 있어서 읽고 수정하기 용이해짐**
        - 같은 UI를 여러 곳에서 사용해야 할 때 **컴포넌트를 재사용할 수 있어 중복 코드를 줄일 수 있음**
        - 화면이 복잡해져도 Header, MovieList, MovieCard처럼 나누면 **전체 구조를 파악하기 쉬워짐**
        - 컴포넌트를 나누는 기준
            - 반복해서 사용하는 UI
            - 한 가지 역할이 분명한 UI
            - 코드가 길어져 따로 읽고 싶은 부분
            - **컴포넌트 함수 안에 다른 컴포넌트 함수를 정의하지 않도록 주의**
    - 조건부 렌더링과 목록 렌더링은 데이터에 따라 보여 줄 컴포넌트를 어떻게 결정하나요?
        - **조건부 렌더링**
            - 데이터의 조건에 따라 어떤 JSX나 컴포넌트를 보여줄지 결정
            - 삼항 연산자 (조건)?(참):(거짓), (조건)&&(결과) 등
        - **목록 렌더링**
            - 배열 데이터를 돌면서 map()으로 돌면서 각 데이터를 컴포넌트로 바꿔서 보여줌
            - map으로 요소를 변환할 때에는 요소마다 고유한 key가 필요함
              - key는 배열 index보다는 데이터의 고유한 id를 사용하는 것이 적절
              - index를 사용하면 중간 값이 삭제 되었을 때 뒤에 값들의 key 값이 변경되므로 문제 발생 가능
- props와 단방향 데이터 흐름
    - 부모와 자식 컴포넌트 사이에서 props는 어떤 역할을 하나요?
        - **props**
            - 부모가 자식 컴포넌트를 사용할 때 전달하는 입력의 값 지정
            - 전달받은 props 객체를 읽어 서로 다른 화면을 만든다
            - 부모가 넘겨준 함수를 실행할 수 있음
            - 자식은 전달받은 데이터 바꾸기 불가
    - 데이터가 부모에서 자식으로만 흐르면 화면의 변화를 추적하는 데 어떤 도움이 되나요?
        - 데이터가 **부모 → 자식 한 방향으로만 흐르면**, 값이 어디서 왔는지 찾기 쉬움
        - 화면이 바뀌었을 때도 **어떤 부모의 상태가 바뀌었는지 따라가면 되기 때문에 원인을 추적하기 쉬워짐**
        - 코드의 흐름이 단순해서 디버깅하기 편해짐
    - props에 TypeScript 타입을 붙이면 컴포넌트를 잘못 사용하는 실수를 어떻게 찾을 수 있나요?
        - TypeScript로 props에 미리 타입을 정해두면 TypeScript가 컴파일 단계에서 오류를 찾아준다
            - VS Code에서는 보통 코드 아래에 **빨간 줄**로 바로 보여줌
        - 그래서 컴포넌트를 잘못 사용하는 실수를 빠르게 찾을 수 있음
- 상태와 리렌더링
    - 일반 변수와 state(상태)는 값이 바뀐 뒤 화면을 다시 보여 주는 방식이 어떻게 다른가요?
        - 일반 변수의 값 바꾸는 것만으로는 화면이 리렌더링이 요청 불가
        - **state**는 setState 함수로 값을 바꾸면 React가 변화를 감지해서 **컴포넌트를 다시 렌더링하고 화면을 업데이트**

        ```jsx
        const [count, setCount] = useState(0);
        ```

    - React에서 원본 상태를 직접 수정하지 않고 새로운 값으로 업데이트해야 하는 이유는 무엇일까요?
        - React에서는 상태를 바꿀 때 **기존 배열이나 객체를 직접 수정하지 않고 새로운 값으로 만들어 교체**
        - 객체는 주로 안의 값보다 메모리 주소를 통해 비교되는 경우가 많음
        - 원본을 직접 수정하면 **이전 상태와 새로운 상태를 구분하기 어려워지고**, React가 변경을 추적하기 어려워짐
        - 그래서 배열은 map, filter, 전개 문법 등을 사용해서 **새 배열을 만들고** 객체도 { ...movie, isBookmarked: !movie.isBookmarked }처럼 **새 객체를 만들어 업데이트**
    - 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 사용하는 이유는 무엇일까요?
        - setCount(count + 1)은 현재 렌더링 시점의 count 값을 사용하기 때문에, 여러 상태 업데이트가 연속으로 일어나면 **같은 값을 반복해서 사용**할 수 있음
        - 반면 setCount((current) => current + 1)처럼 **업데이터 함수**를 사용하면 React가 전달한 **가장 최신 상태값을 기준으로 다음 상태를 계산**
        - → 증가·감소처럼 **이전 상태를 이용해 다음 상태를 정할 때는 업데이터 함수를 사용하는 것이 더 안전**
- 상태 공유와 Context
    - 여러 컴포넌트가 같은 상태를 사용해야 할 때 상태를 어느 컴포넌트에 두는 것이 좋을까요?
        - 컴포넌트들의 **가장 가까운 공통 부모 컴포넌트**에 상태를 두어야 함
            - 부모가 상태를 관리하고 자식들에게 props로 값과 변경 함수를 전달
            - **→ 상태 끌어올리기**
        - **같은 데이터를 여러 곳에 따로 저장하지 않고 한 곳에서 관리하는 것**이 중요
    - props 전달, 상태 끌어올리기와 Context는 각각 어떤 상황에 알맞을까요?
        - **props 전달**: 부모가 자식에게 값이나 함수를 넘길 때 / 컴포넌트 관계가 단순할 때
        - **상태 끌어올리기**: 여러 자식 컴포넌트가 같은 상태를 함께 사용하거나 변경해야 할 때, **가장 가까운 공통 부모**가 상태를 관리하도록
        - **Context**: 여러 단계 아래에 있는 컴포넌트들이 같은 값을 사용해서 props를 계속 전달하기 번거로울 때 사용 예: 로그인 정보, 테마, 언어 설정.

      **→ 가까운 관계는 props, 여러 자식이 공유하면 상태 끌어올리기, 멀리 떨어진 여러 컴포넌트가 공통으로 쓰면 Context**

    - 모든 값을 Context로 전달하면 어떤 문제가 생길 수 있을까요?
        - Context로 전달하면 **어떤 값이 어디에서 오는지 파악하기 어려워져서 코드의 흐름을 이해하기 힘들어질 수 있음**
        - Context 값이 바뀌면 그 값을 사용하는 여러 컴포넌트가 다시 렌더링될 수 있어서, 너무 많이 사용하면 **불필요한 렌더링**이 생길 수도 있음
        - 가까운 부모와 자식 사이의 값까지 Context로 전달하면 오히려 구조가 복잡해짐
            - 가까우면 props 전달
## React 컴포넌트와 JSX

### JSX는 HTML과 어떤 점이 다르며 React 컴포넌트 안에서 어떤 역할을 하나요?
* JSX는 자바스크립트 안에서 UI 구조를 표현하기 위한 문법으로 HTML과 비슷하지만 HTML 자체라고는 볼 수 없다.
* HTML에서 사용할 수 있던 속성 이름도 JSX에서는 예약어 충돌 문제로 이름이 달라질 수 있고 속성 표기법이 서로 다르다.
* JSX는 React 컴포넌트에서 HTML과 비슷한 문법으로 UI를 표현할 수 있게 해주는 역할을 한다.

### 하나의 화면을 여러 컴포넌트로 나누면 어떤 장점이 있으며, 분리 기준은 어떻게 정할 수 있을까요?
* 나누어져 있으면 수정할 때에 수정할 부분을 찾고 고치기에 간편하다.
* 컴포넌트를 재사용하여 같은 컴포넌트를 여러 곳에서 사용할 수 있다.
* 각 컴포넌트별로 수행하는 일에 따라 역할을 부여하여 자신의 일만 집중적으로 처리하도록 설계할 수 있다.
* **기준** → 반복해서 사용하는가 / 역할이 명확한가 / 특정 부분을 독립적으로 나눌 수 있는

### 조건부 렌더링과 목록 렌더링은 데이터에 따라 보여 줄 컴포넌트를 어떻게 결정하나요?
* **조건부 렌더링**: 데이터에 따라 무엇을 보여줄 지 결정하는 것이다. 카운터에 제한을 추가하는 실습에서 `{count < 5 && <button>+1</button>}` 코드로 5 이상 시 버튼이 비활성화되는 코드를 작성하였는데 이처럼 조건식이나 불리언 값으로 랜더링을 결정한다. 따라서 key값은 일반적으로 불필요하다.
* **목록 렌더링**: 배열 형태의 크기만큼 동일한 구조의 UI를 반복 출력하는 것이다. 각 요소를 구분하기 위한 key를 사용하여 어떤 항목이 삭제되었는지, 수정되었는지, 존재하는지 식별하고 데이터를 순회하며  랜더링한다.

## props와 단방향 데이터 흐름

### 부모와 자식 컴포넌트 사이에서 props는 어떤 역할을 하나요?
* props는 부모에서 자식으로 데이터를 전달하는 방법으로 부모에서 자식 방향으로 데이터가 전달죈다.
* 모든 부모 컴포넌트는 props를 줌으로써 몇몇의 정보를 자식 컴포넌트에게 전달할 수 있다.

### 데이터가 부모에서 자식으로만 흐르면 화면의 변화를 추적하는 데 어떤 도움이 되나요?
* 부모 → 자식 방향으로의 단방향 데이터 전달은 부모 컨포넌트만 값을 변경할 수 있어 예측 가능성이 높다.
* 따라서 화면의 변화를 추적할 때 상태를 정의하고 내려주는 부모 컴포넌트만 확인하면 되어서 용이하다.

### props에 TypeScript 타입을 붙이면 컴포넌트를 잘못 사용하는 실수를 어떻게 찾을 수 있나요?
* TS는 코드 실행 전 컴파일 타임에서 검증하므로 런타임 오류가 발생하기 전 필수 props를 누락하거나 객체의 구조가 어긋나거나 컴포넌트 내부에서 props를 변경하거나 등등.. 문제를 미리 발견할 수 있다.

## 상태와 리렌더링

### 일반 변수와 state(상태)는 값이 바뀐 뒤 화면을 다시 보여 주는 방식이 어떻게 다른가요?
* 일반 변수는 값이 바뀌었을 때 화면을 다시 그리라고 요청하지 않는다.
* 그러나 state는 상태가 바뀌었음을 알리고 필요한 컴포넌트를 다시 호출하여서 리랜더링한다.

### React에서 원본 상태를 직접 수정하지 않고 새로운 값으로 업데이트해야 하는 이유는 무엇일까요?
* 여러 컴포넌트가 동일한 props를 공유하고 있을 때 한 곳에서 직접 변형하면 다른 곳에서 원치 않는 데이터 변형이 일어난다.
* 특히 배열이나 객체를 직접 수정하면 예상치 못한 문제가 생길 수 있다.

### 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 사용하는 이유는 무엇일까요?
* 리엑트는 불필요한 렌더링을 줄이기 위해 여러 요청을 한번에 묶어서 처리한다.
* 묶어서 한번에 처리될 때 업데이터 함수를 사용하면 함수들을 큐에 등록하고 순차적으로 실행된다.
* 따라서 각 함수가 앞에서 계산된 최신의 값을 받아 다음 값을 계산할 수 있어서 안전하게 여러 상태 업데이트를 연속해서 처리할 수 있다.

## 상태 공유와 Context

### 여러 컴포넌트가 같은 상태를 사용해야 할 때 상태를 어느 컴포넌트에 두는 것이 좋을까요?
* 그 상태를 사용하는 컴포넌트들의 가장 가까운 부모 컴포넌트에 두어서 단방향 데이터 흐름을 깨지 않고, 모든 하위 컴포넌트들이 일관되게 랜더링되도록 한다. → 이를 상태끌어올리기라고 한다.

### props 전달, 상태 끌어올리기와 Context는 각각 어떤 상황에 알맞을까요?
* props 전달은 부모-자식 간의 관계가 직접적이고 얕은 경우 알맞다.
* 서로 다른 형제 컴포넌트끼리 상태를 동기화 해야 할 때 상태 끌어올리기를 사용한다.
* 컴포넌트 트리가 깊어져서 props를 여러 단계를 거쳐서 전달해야 할 때 중간 컴포넌트들이 직접 값을 사용하지 않는다면 Context를 사용하기에 알맞다.

### 모든 값을 Context로 전달하면 어떤 문제가 생길 수 있을까요?
* 데이터 추적에 어려움이 생긴다.
* Context의 값이 변경되면 그 Context를 사용하는 모든 컴포넌트들이 강제로 리렌더링된다. 따라서 자주 값이 바뀌는 곳에 Context를 사용하면 성능 저하가 일어난다.
* Context가 너무 많아지면 의존 관계가 복잡해질 수 있다.
