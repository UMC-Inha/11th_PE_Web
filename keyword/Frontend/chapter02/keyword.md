    # React 컴포넌트와 JSX
    
    React에서는 하나의 화면을 하나의 큰 코드로 작성하기보다, 화면을 구성하는 요소를 **컴포넌트(Component)**로 나누어 관리한다.
    
    JSX는 JavaScript 코드 안에서 HTML과 비슷한 문법으로 UI를 작성할 수 있도록 해주며, React 컴포넌트가 **어떤 화면을 보여줄지 표현하는 역할**을 한다.
    
    ---
    
    ## JSX
    
    > JavaScript 안에서 **UI 구조를 작성할 수 있도록 해주는 문법**
    > 
    
    JSX는 HTML과 비슷하게 생겼지만 실제로는 JavaScript 코드 안에서 사용되는 문법이라는 점에서 HTML과 차이가 있다.
    
    ```tsx
    const userName = "세라";
    
    function Greeting() {
      return <h1>Hello, {userName}!</h1>;
    }
    ```
    
    → `{}`를 사용하여 JavaScript의 변수나 표현식을 JSX 안에 넣을 수 있다.
    
    HTML에서는 `class`를 사용하지만 JSX에서는 `className`을 사용하는 것처럼 일부 속성의 이름이나 문법도 다르다.
    
    또한 JSX에서는 하나의 컴포넌트가 반환할 수 있는 최상위 요소가 하나여야 하므로 여러 요소를 반환할 때 Fragment 등을 사용할 수 있다.
    
    JSX는 단순히 화면을 꾸미기 위한 문법이 아니라 **컴포넌트가 화면에 어떤 UI를 렌더링할지 표현하는 역할**을 한다.
    
    ---
    
    ## React 컴포넌트
    
    > UI를 구성하는 **독립적인 단위**
    > 
    
    React 컴포넌트는 화면의 특정 부분을 하나의 단위로 분리하여 재사용할 수 있도록 만든다.
    
    ```tsx
    function Button() {
      return <button>확인</button>;
    }
    ```
    
    → `Button`이라는 컴포넌트가 만들어지고, 필요한 곳에서 사용할 수 있다.
    
    하나의 화면을 여러 컴포넌트로 나누면 **코드의 재사용성과 가독성이 높아지고, 각 부분을 독립적으로 수정하고 관리하기 쉬워진다.**
    
    ---
    
    ## 컴포넌트를 나누는 기준
    
    컴포넌트를 나눌 때는 단순히 코드의 길이만 보고 나누기보다는 **하나의 역할을 담당하는지**, **재사용할 가능성이 있는지**, **독립적으로 관리할 필요가 있는지** 등을 고려할 수 있다.
    
    예를 들어 영화 목록 화면이라면,
    
    ```tsx
    MoviePage
    ├── Header
    ├── MovieList
    │   └── MovieCard
    └── Pagination
    ```
    
    처럼 화면의 역할에 따라 컴포넌트를 나눌 수 있다.
    
    너무 작은 단위로 무조건 나누기보다는 **하나의 컴포넌트가 하나의 명확한 역할을 가지도록 분리하는 것**이 중요하다.
    
    ---
    
    ## 조건부 렌더링
    
    > 조건에 따라 **다른 UI를 보여주는 것**
    > 
    
    JavaScript의 조건문이나 삼항 연산자 등을 이용하여 데이터의 상태에 따라 다른 컴포넌트를 보여줄 수 있다.
    
    ```tsx
    {isLoggedIn ? <MyPage /> : <Login />}
    ```
    
    → 로그인 상태라면 `MyPage`, 그렇지 않으면 `Login`을 보여준다.
    
    예를 들어 로딩 중인지, 데이터가 존재하는지, 로그인되어 있는지 등에 따라 화면을 다르게 보여줄 수 있다.
    
    ---
    
    ## 목록 렌더링
    
    > 배열과 같은 여러 데이터를 **반복하여 여러 컴포넌트로 보여주는 것**
    > 
    
    React에서는 주로 `map()`을 이용하여 목록을 렌더링한다.
    
    ```tsx
    {movies.map((movie) => (
      <MovieCard key={movie.id} movie={movie} />
    ))}
    ```
    
    → `movies` 배열의 각 데이터를 `MovieCard` 컴포넌트로 만들어 화면에 표시한다.
    
    이때 각 항목을 구분하기 위해 `key`를 지정해야 한다.
    
    ---
    
    ## 정리
    
    React에서는 **컴포넌트가 UI를 구성하는 단위**가 되고, JSX를 통해 컴포넌트가 보여줄 화면을 작성한다.
    
    - JSX → JavaScript 안에서 UI를 표현
    - 컴포넌트 → UI를 역할별로 분리하고 재사용
    - 조건부 렌더링 → 데이터나 상태에 따라 보여줄 UI 결정
    - 목록 렌더링 → 배열 등의 데이터를 반복하여 여러 UI 생성
    
    따라서 React에서 화면을 만들 때는 **화면을 적절한 컴포넌트로 나누고, 데이터에 따라 어떤 컴포넌트를 보여줄지 결정하는 것**이 중요하다.
    
- props와 단방향 데이터 흐름
    - 부모와 자식 컴포넌트 사이에서 props는 어떤 역할을 하나요?
    - 데이터가 부모에서 자식으로만 흐르면 화면의 변화를 추적하는 데 어떤 도움이 되나요?
    - props에 TypeScript 타입을 붙이면 컴포넌트를 잘못 사용하는 실수를 어떻게 찾을 수 있나요?
    
    # props와 단방향 데이터 흐름
    
    React에서는 컴포넌트가 서로 데이터를 주고받을 때 **props**를 사용한다.
    
    특히 React의 데이터 흐름은 기본적으로 **부모 컴포넌트에서 자식 컴포넌트 방향으로 흐르는 단방향 데이터 흐름**을 따른다.
    
    ---
    
    ## props
    
    > 부모 컴포넌트가 자식 컴포넌트에게 **데이터나 기능을 전달하는 방법**
    > 
    
    부모 컴포넌트에서 자식 컴포넌트를 사용할 때 props를 전달할 수 있다.
    
    ```tsx
    function MovieCard({ title }: { title: string }) {
      return <h2>{title}</h2>;
    }
    
    function MovieList() {
      return <MovieCard title="인터스텔라" />;
    }
    ```
    
    → `MovieList`가 `MovieCard`에게 `title`이라는 데이터를 전달한다.
    
    자식 컴포넌트는 전달받은 props를 사용하여 화면을 구성할 수 있다.
    
    props는 데이터를 전달할 뿐만 아니라 **함수를 전달하여 자식 컴포넌트에서 부모의 동작을 요청하도록 만드는 데에도 사용**할 수 있다.
    
    ---
    
    ## 단방향 데이터 흐름
    
    > 데이터가 **부모 → 자식 방향으로 흐르는 구조**
    > 
    
    React에서는 부모가 가지고 있는 데이터를 자식에게 props로 전달한다.
    
    예를 들어 부모가 영화 목록을 가지고 있다면,
    
    ```tsx
    <MovieList movies={movies} />
    ```
    
    처럼 자식에게 전달할 수 있다.
    
    이러한 구조에서는 **어떤 데이터가 어디에서 관리되고 어디로 전달되는지 추적하기 쉽다.**
    
    반대로 여러 컴포넌트가 서로 자유롭게 데이터를 변경하도록 만들면 데이터가 어디서 변경되었는지 파악하기 어려워질 수 있다.
    
    따라서 단방향 데이터 흐름은 **데이터의 흐름과 화면 변화의 원인을 추적하기 쉽게 만든다.**
    
    ---
    
    ## Props에 TypeScript 타입 적용
    
    > 컴포넌트가 전달받아야 하는 props의 **형태와 타입을 명확하게 정의**하는 것
    > 
    
    ```tsx
    type MovieCardProps = {
      title: string;
      rating: number;
    };
    
    function MovieCard({ title, rating }: MovieCardProps) {
      return (
        <div>
          <h2>{title}</h2>
          <p>{rating}</p>
        </div>
      );
    }
    ```
    
    이렇게 타입을 지정하면 `title`에 숫자를 전달하거나 `rating`을 빠뜨리는 등의 실수를 개발 과정에서 확인할 수 있다.
    
    ```tsx
    <MovieCard title={123} rating="5" />
    ```
    
    → TypeScript가 `title`과 `rating`의 타입이 잘못되었다고 알려준다.
    
    따라서 props에 타입을 지정하면 **컴포넌트 사용 방법을 명확하게 만들고 잘못된 데이터 전달을 미리 발견할 수 있다.**
    
    ---
    
    ## 정리
    
    - `props` → 부모가 자식에게 데이터나 함수를 전달
    - 단방향 데이터 흐름 → 데이터가 부모에서 자식 방향으로 흐름
    - TypeScript 타입 → 전달해야 하는 props의 형태를 명확하게 정의
    - 단방향 구조 → 데이터가 어디에서 전달되고 변경되는지 추적하기 쉬움
    
    결국 React에서는 **부모가 데이터를 관리하고 필요한 자식에게 props로 전달하는 구조**를 기본적인 데이터 흐름으로 사용한다.
    
- 상태와 리렌더링
    - 일반 변수와 state(상태)는 값이 바뀐 뒤 화면을 다시 보여 주는 방식이 어떻게 다른가요?
    - React에서 원본 상태를 직접 수정하지 않고 새로운 값으로 업데이트해야 하는 이유는 무엇일까요?
    - 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 사용하는 이유는 무엇일까요?
    
    # 상태와 리렌더링
    
    React에서는 화면에 표시되는 값이 변경될 때 UI도 함께 변경되어야 한다.
    
    이를 위해 React에서는 **state(상태)**를 사용하며, state가 변경되면 React가 해당 컴포넌트를 다시 렌더링하여 변경된 값을 화면에 반영한다.
    
    ---
    
    ## 일반 변수와 state
    
    > 일반 변수와 달리 **state는 값이 변경되었을 때 React의 리렌더링을 발생**시킨다.
    > 
    
    일반 변수를 변경하는 것만으로는 React가 해당 값이 변경되었다는 사실을 알고 화면을 다시 렌더링하지 않는다.
    
    반면 `useState`를 사용하면 상태를 만들 수 있다.
    
    ```tsx
    const [count, setCount] = useState(0);
    
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
    ```
    
    → `setCount`를 호출하여 state가 변경되면 컴포넌트가 다시 렌더링되고 화면에 새로운 `count`가 표시된다.
    
    따라서 화면에 영향을 주는 값이라면 일반 변수보다 **React의 state로 관리하는 것이 적절하다.**
    
    ---
    
    ## State를 직접 수정하지 않는 이유
    
    > React에서는 기존 state를 직접 변경하기보다 **새로운 값으로 업데이트**하는 방식을 사용한다.
    > 
    
    배열이나 객체와 같은 state를 직접 수정하면 React가 변경을 제대로 감지하지 못할 수 있다.
    
    예를 들어 배열에 데이터를 추가할 때 기존 배열을 직접 수정하기보다 새로운 배열을 만들어 업데이트한다.
    
    ```tsx
    setMovies([...movies, newMovie]);
    ```
    
    → 기존 `movies` 배열을 변경하는 것이 아니라 기존 데이터를 복사한 새로운 배열을 생성한다.
    
    이처럼 state를 직접 변경하지 않고 새로운 값을 만들어 업데이트하는 방식을 **불변성(Immutability)을 유지한다**고 한다.
    
    ---
    
    ## 이전 상태를 이용한 업데이트
    
    > 다음 상태가 **이전 상태를 기반으로 결정되는 경우**, 업데이트 함수를 사용한다.
    > 
    
    예를 들어 버튼을 클릭할 때마다 숫자를 1씩 증가시키려면,
    
    ```tsx
    setCount((prev) => prev + 1);
    ```
    
    처럼 작성할 수 있다.
    
    여기서 `prev`는 React가 가지고 있는 **가장 최신의 이전 state 값**이다.
    
    여러 번의 상태 업데이트가 예약되거나 이전 상태를 기반으로 값을 변경해야 하는 경우, 현재 변수에 의존하는 것보다 업데이트 함수를 사용하는 것이 안전하다.
    
    ---
    
    ## 리렌더링
    
    > state나 props 등의 변화에 따라 **컴포넌트를 다시 실행하여 변경된 UI를 반영하는 과정**
    > 
    
    state가 변경되면 React는 해당 컴포넌트를 다시 렌더링한다.
    
    리렌더링은 화면 전체를 무조건 처음부터 새로 만드는 것이 아니라, React가 변경된 부분을 확인하고 필요한 UI를 업데이트하는 방식으로 이루어진다.
    
    따라서 state를 적절하게 관리하면 **데이터의 변화와 화면의 변화를 연결**할 수 있다.
    
    ---
    
    ## 정리
    
    - 일반 변수 → 값이 변경되어도 React의 리렌더링을 발생시키지 않음
    - state → 업데이트 함수를 통해 변경하면 리렌더링이 발생
    - 불변성 → 기존 state를 직접 수정하지 않고 새로운 값으로 업데이트
    - 업데이트 함수 → 이전 state를 기반으로 다음 state를 계산할 때 사용
    - 리렌더링 → 변경된 state나 props 등을 반영하여 UI를 다시 계산하는 과정
    
    즉, React의 state는 **화면에 영향을 주는 데이터를 관리하고, 데이터의 변화가 UI에 반영되도록 연결하는 역할**을 한다.
    
- 상태 공유와 Context
    - 여러 컴포넌트가 같은 상태를 사용해야 할 때 상태를 어느 컴포넌트에 두는 것이 좋을까요?
    - props 전달, 상태 끌어올리기와 Context는 각각 어떤 상황에 알맞을까요?
    - 모든 값을 Context로 전달하면 어떤 문제가 생길 수 있을까요?
    
    # 상태 공유와 Context
    
    하나의 컴포넌트에서만 사용하는 상태도 있지만, 여러 컴포넌트가 **같은 데이터를 함께 사용해야 하는 경우**도 있다.
    
    이때 상태를 어디에 둘지 결정하고, 필요한 컴포넌트에 적절한 방법으로 전달해야 한다.
    
    ---
    
    ## 상태를 어디에 둘까?
    
    > 여러 컴포넌트가 사용하는 상태라면 **공통 부모 컴포넌트에 상태를 두는 것**을 기본적으로 고려한다.
    > 
    
    예를 들어 형제 컴포넌트인 `SearchBar`와 `MovieList`가 검색어를 함께 사용해야 한다면, 검색어를 두 컴포넌트의 공통 부모에서 관리할 수 있다.
    
    ```tsx
    function MoviePage() {
      const [keyword, setKeyword] = useState("");
    
      return (
        <>
          <SearchBar keyword={keyword} setKeyword={setKeyword} />
          <MovieList keyword={keyword} />
        </>
      );
    }
    ```
    
    → `MoviePage`가 상태를 관리하고 필요한 자식에게 전달한다.
    
    이처럼 상태를 필요한 컴포넌트들의 **가장 가까운 공통 부모로 올리는 것**을 상태 끌어올리기라고 한다.
    
    ---
    
    ## Props 전달
    
    > 부모 컴포넌트가 자식 컴포넌트에게 **직접 데이터를 전달**하는 방식
    > 
    
    컴포넌트 사이의 관계가 단순하고 전달해야 할 데이터가 많지 않다면 props를 사용하는 것이 가장 간단하다.
    
    ```
    부모
     ↓ props
    자식
    ```
    
    하지만 컴포넌트가 여러 단계로 중첩되어 있다면 중간 컴포넌트를 거쳐 계속 props를 전달해야 하는 문제가 생길 수 있다.
    
    이것을 **props drilling**이라고 한다.
    
    ---
    
    ## 상태 끌어올리기
    
    > 여러 컴포넌트가 같은 상태를 사용해야 할 때 **공통 부모로 상태를 이동시키는 것**
    > 
    
    예를 들어 `SearchBar`에서 검색어를 변경하고 `MovieList`에서 그 검색어를 사용해야 한다면, 두 컴포넌트의 공통 부모가 상태를 관리하도록 만들 수 있다.
    
    상태를 한 곳에서 관리하기 때문에 **데이터의 출처가 명확하고 컴포넌트 간 상태를 동기화하기 쉽다.**
    
    ---
    
    ## Context
    
    > 컴포넌트 트리를 통해 **공통으로 사용되는 값을 여러 컴포넌트에 전달**할 수 있는 기능
    > 
    
    Context를 사용하면 부모에서 자식으로 여러 단계에 걸쳐 props를 전달하지 않고도 필요한 컴포넌트에서 값을 사용할 수 있다.
    
    대표적으로 로그인 사용자 정보, 테마, 언어 설정처럼 **여러 컴포넌트에서 공통으로 사용하는 값**에 활용할 수 있다.
    
    ---
    
    ## Props와 Context는 언제 사용할까?
    
    Props는 부모와 자식 사이에서 직접 데이터를 전달할 때 적합하다.
    
    상태 끌어올리기는 **서로 가까운 컴포넌트들이 같은 상태를 공유해야 할 때** 사용할 수 있다.
    
    Context는 여러 단계에 걸쳐 많은 컴포넌트가 같은 값을 사용해야 해서 props를 계속 전달하기 복잡한 경우 고려할 수 있다.
    
    따라서 단순히 여러 컴포넌트에서 사용한다고 해서 무조건 Context를 사용하는 것이 아니라, **상태의 사용 범위와 컴포넌트 구조를 보고 적절한 방법을 선택하는 것이 중요하다.**
    
    ---
    
    ## Context를 무조건 사용하면 안 되는 이유
    
    > 모든 데이터를 Context로 관리하면 오히려 **데이터의 출처와 흐름을 파악하기 어려워질 수 있다.**
    > 
    
    Context에 너무 많은 상태를 넣으면 해당 값을 사용하는 컴포넌트가 많아지고, Context의 값이 변경될 때 관련 컴포넌트들이 다시 렌더링되는 범위도 커질 수 있다.
    
    또한 부모 → 자식으로 직접 전달하면 쉽게 확인할 수 있는 데이터도 Context를 사용하면 별도의 Provider와 Context를 찾아야 하기 때문에 코드 구조를 이해하기 어려워질 수 있다.
    
    따라서 Context는 **여러 컴포넌트에서 공통으로 사용하는 값**에 선택적으로 사용하는 것이 좋다.
    
    ---
    
    ## 정리
    
    - 상태를 사용하는 범위가 작음 → 해당 컴포넌트에서 관리
    - 형제 컴포넌트가 같은 상태를 사용 → 공통 부모로 상태 끌어올리기
    - 부모 → 자식의 직접적인 데이터 전달 → props
    - 여러 단계의 컴포넌트에서 공통으로 사용하는 값 → Context 고려
    - 모든 상태를 Context로 관리하는 것은 지양 → 데이터 흐름과 리렌더링 범위를 복잡하게 만들 수 있음
    
    결국 상태 공유에서는 **“어떤 상태를 어디에서 관리하고, 어디까지 공유해야 하는가”**를 먼저 판단한 뒤 props, 상태 끌어올리기, Context 중 적절한 방법을 선택하는 것이 중요하다.
