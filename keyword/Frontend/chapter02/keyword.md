- React 컴포넌트와 JSX
    - JSX는 HTML과 어떤 점이 다르며 React 컴포넌트 안에서 어떤 역할을 하나요?
        
        JSX: JavaScript 안에서 HTML과 비슷한 마크업(UI)을 작성할 수 있게 해주는 JavaScript 문법 확장.
        
        Vite와 같은 빌드 도구가 JSX → JavaScript 변환 후 React가 화면을 만들 때 사용
        
        HTML과 유사하지만 JavaScript 코드이다
        
        JSX + JavaScript = .jsx
        
        JSX + TypeScript = .tsx
        
        !스크린샷 2026-09-19 오후 11.23.07.png
        
        React: **UI(JSX가 읽기 쉽게 작성한 UI)**를 만들고 갱신하는 라이브러리
        
        React에선 하나의 어플리케이션을 여러 개의 작은 컴포넌트로 나누어 관리한다.
        
        그중 main.jsx, App.jsx가 핵심
        
        main.jsx : React 어플리케이션을 실행하는 진입점
        
        App.jsx : 실제 화면을 구성하는 메인 컴포넌트(메인 UI)
        
    - 하나의 화면을 여러 컴포넌트로 나누면 어떤 장점이 있으며, 분리 기준은 어떻게 정할 수 있을까요?
        
        컴포넌트 : React UI를 이루는 기본 단위(버튼, 영화 카드, 영화 목록, 페이지 등..)
        
                 화면에 보여줄 JSX를 반환하는 JavaScript 함수.
        
        컴포넌트를 분리할 시 **장점**
        
        - 코드의 재사용성 증가
        - 복잡한 로직의 쉬운 관리
        - 개별 컴포넌트의 테스트가 쉬워져 전체 애플리케이션의 안정성 향상
        
        컴포넌트를 분리할 시 **단점**
        
        - 각 컴포넌트들의 관계와 영향의 파악이 어려움
        - 데이터의 경로와 변화 파악이 어려움.
        - 하나의 컴포넌트가 특정 컴포넌트 하위에서만 사용될 수 있는 역할에 국한될 수 있음.
        
        컴포넌트를 나누는 기준
        
        - 반복 사용
        - 역할이 명확
        - 코드가 길어질 때
        
        외에도 기능의 효율성, 코드의 유지보수, 확장할때의 대처 등을 생각하여 적절히 나눠야 한다.
        
        ex) Header, MovieGrid, MovieCard, Pagination
        
        컴포넌트를 나눌 때 원칙
        
        - 각각의 컴포넌트들은 **단일 책임 원칙**을 지켜야 한다
        - 여러번 쓸 요소의 경우 재사용이 가능하게 해야한다
        - 여러 기능을 수행하는 컴포넌트는 하위 컴포넌트들로 분리해서 관리
    - 조건부 렌더링과 목록 렌더링은 데이터에 따라 보여 줄 컴포넌트를 어떻게 결정하나요?
        
        조건부 렌더링: 보유줄지 말지 결정하는 것
        
        목록 렌더링: 배열을 반복해서 그리기
        
        조건부 렌더링 방법
        
        - if 조건문 사용
        - 삼항 연산자
        - &&(AND)
        
        목록 렌더링 방법
        
        - map() : 배열의 각 값을 하나씩 받아 원하는 값으로 바꾸고 그 결과를 새 배열로 반환하는 메서드
            
            이 경우 React가 각 항목을 구분할 수 있도록 고유한 key가 있어야 한다.
            
            key를 정할 때 주의할 점
            
            - 안정적이고 고유한 값
            - 배열 index가 key가 되면 안된다. → 순서가 바뀌거나 항목이 추가, 삭제될 시 문제가 됨

- props와 단방향 데이터 흐름
    - 부모와 자식 컴포넌트 사이에서 props는 어떤 역할을 하나요?
        
        props : 부모 컴포넌트가 자식 컴포넌트를 사용할 때 전달하는 입력 값 (부모→자식)
        
        props 객체를 받으면 객체에서 필요한 속성을 꺼내주는 구조 분해 할당.
        
        props 타입으로 코드 검사 뿐 아닌 컴포넌트를 사용할 때 어떤 값이 필요한지 알려주는 역할도 한다
        
        !스크린샷 2026-09-20 오전 12.06.34.png
        
        위 경우 MovieCard에 props 객체를 받으면 어떤식으로 출력할지 미리 정해두고 App()에서 값을 받아서 해당되는 속성을 꺼내서 출력되게 된다.
        
    - 데이터가 부모에서 자식으로만 흐르면 화면의 변화를 추적하는 데 어떤 도움이 되나요?
        
        부모에서 자식으로만 내려가는 것을 **단방향 데이터 흐름**이라고 한다. 
        
        이렇게 되면 데이터 흐름이 예측 가능하고 추적하기 쉬워지며 디버깅이나 테스트시에 유용하다. 
        
    - props에 TypeScript 타입을 붙이면 컴포넌트를 잘못 사용하는 실수를 어떻게 찾을 수 있나요?
        
        원래 들어와야할 타입이 아닌 다른 타입이 들어올 경우 TypeScript 오류를 통해 알 수 있다.
        
        ```jsx
        interface MovieCardProps {
          title: string;
          releaseDate: string;
          isBookmarked: boolean;
        }
        
        <MovieCard
                title="오디세이"
                releaseDate="2026.08.05"
                isBookmarked="book"
              />
        ```
        
        예를 들어 위같은 경우 isBookmarked에 boolean만 들어와야하는데 string이 들어온 경우 TypeScript 오류가 나게 된다.
        
- 상태와 리렌더링
    - 일반 변수와 state(상태)는 값이 바뀐 뒤 화면을 다시 보여 주는 방식이 어떻게 다른가요?
        
        state: react 컴포넌트 내에서 동적인 데이터를 관리하기 위해 사용하는 객체
        
        - 로컬 데이터 관리
        - 불변성 : 직접 수정 불가(set, use함수 사용)
        - UI와 동기화 : 상태가 변경될 시 React는 컴포넌트를 리렌더링하여 UI를 최신화한다
        
        일반 변수의 경우 사용하였을 때 데이터가 **리턴되지 않아 React가 변화를 알지 못해 화면이 자동으로 렌더링 되지 않아** UI에서 확인이 불가하다.
        
        하지만 state는 변경되면 React가 이를 감지해 useState를 사용할 시 UI 화면과 동기화되어 수정사항을 확인할 수 있다.
        
        렌더링: React가 App 컴포넌트를 호출하여 새 JSX를 계산하는 것
        
    - React에서 원본 상태를 직접 수정하지 않고 새로운 값으로 업데이트해야 하는 이유는 무엇일까요?
        
        이는 **불변성**을 유지하기 위해서 이다.
        
        불변성: 값이나 상태를 변경 불가. JavaScript에선 메모리 영역의 값을 변경 불가하다.
        
        state의 변경을 감지하여 컴포넌트를 리랜더링하게 되는데 이때 **state의 변경 기준이 콜스택 값**이다.
        
        !스크린샷 2026-09-20 오전 1.11.47.png
        
        JavaScript는 메모리 구조를 call stack, memory heap 두 가지를 사용하게 된다. 
        
        원시타입 → Call Stack에 저장
        
        참조타입 → 실제 데이터는 메모리 힙에 저장, 콜스택에 메모리 힙의 주소 저장.
        
        React에선 효율성을 위해 상태 값을 변경할 때 얕은 비교를 한다. 
        
        얕은 비교: 값이 아닌 참조값(콜스택에 저장된 메모리 힙 영역을 가리키는 주소 값)을 비교
        
        원시타입은 콜스택에 값을 저장하므로 데이터의 값을 비교하게 됨.
        
        원시 타입 변수에 새로운 값을 할당할 시 기존에 Call Stack에 저장된 데이터는 그대로 둔 채 새로운 값을 할당하게 된다.
        
        참조 타입 변수에 값을 재할당하면 Call Stack의 주소 값은 변경되지 않고 메모리 힙 영역의 데이터가 변경된다 → 상태 변경을 감지하지 못함→ 불변성이 지켜지지 않음
        
        따라서 배열이나 객체같은 참조타입의 데이터를 변경할 땐 원본 데이터를 직접 수정하는 것이 아닌 새로운 참조 값을 가진 새로운 배열이나 객체를 생성해야 한다.
        
    - 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 사용하는 이유는 무엇일까요?
        
        useState를 사용할 땐 비동기적으로 동작하여 상태 값이 즉시 변경되는 것이 아닌 다음 렌더링 때 반영되게 된다 → 여러 상태의 업데이트가 동시에 발생되게 되면 결과가 달라질 수 있다.
        
        다음 렌더링 때 반영 : React는 상태 업데이트를 내부 큐에 저장 후 한번에 처리하기 때문에 여러 상태의 업데이트가 겹치더라도 한번에 렌더링된다.

- 상태 공유와 Context
    - 여러 컴포넌트가 같은 상태를 사용해야 할 때 상태를 어느 컴포넌트에 두는 것이 좋을까요?
        
        가장 가까운 공통 부모 컴포넌트에 상태를 둬야한다.
        
        **공통 부모로 상태 끌어올리기**
        
        데이터를 여러 곳에 복사하지 않고 한 컴포넌트만 기준 값을 관리하고 그 상태를 하위 컴포넌트에 props로 전달한다
        
        Single Source of Truth(SSoT)(단일 진실 공급원): 같은 데이터를 여러 곳에 복사하지 않고 한 컴포넌트 기준 값을 관리하는 원칙 → **동일한 데이터를 나타내는 상태는 오직 한 곳에만 존재해야한다.**
        
    - props 전달, 상태 끌어올리기와 Context는 각각 어떤 상황에 알맞을까요?
        
        **props 전달**
        
        가까운 컴포넌트 한두 개에 값을 전달할 때 사용(읽기 전용)
        
        데이터를 깊게 전달해야 하거나 동일한 props를 필요로 하는 경우 좋지 않다. 
        
        prop drilling: 데이터가 필요한 컴포넌트까지 멀리 떨어져있고 해당 높이까지 상태를 끌어올리는 것
        
        실제로 필요 없는 props를 계속 전달함.
        
        !스크린샷 2026-09-20 오전 1.47.33.png
        
        **상태 끌어올리기**
        
        동일한 상태를 여러 컴포넌트에서 사용해야할 때
        
        상태를 가장 가까운 공통 상위 컴포넌트에 끌어올린다.
        
        **Context**
        
        같은 값이 멀리 떨어진 여러 컴포넌트가 필요로 할 때
        
        애플리케이션 전체에서 공유되는 데이터에 접근이 필요한 경우
        
        부모가 해당 트리 아래의 전체에 데이터 제공 가능 → 전역 상태 관리에 좋다.
        
        1. 컨텍스트 생성
        2. 데이터를 필요로 하는 컴포넌트에서 Context 사용
        3. 데이터를 제공하는 컴포넌트에서 Context 제공
        
        서로 멀리있는 컴포넌트들 사이의 모든 컴포넌트에 데이터를 제공할 수 있다.
        
    - 모든 값을 Context로 전달하면 어떤 문제가 생길 수 있을까요?
        
        상위에서 key를 기반으로 여러 데이터를 상태로 관리할 경우, 특정 key가 업데이트될시 같은 context를 사용하는 컴포넌트들 또한 함께 리렌더링이 된다. → 불필요한 리렌더링이 발생한다.
