- React 컴포넌트와 JSX
    - JSX는 HTML과 어떤 점이 다르며 React 컴포넌트 안에서 어떤 역할을 하나요?
        - JSX(JavaScript XML)는 JavaScript 안에서 UI 구조를 작성하는 문법 확장, 빌드 과정에서 React 엘리먼트를 만드는 JavaScript로 변환됨
        - HTML과 비슷하지만 HTML 자체는 아님
        - class 대신 className 사용, JavaScript 표현식은 중괄호 안에 작성, 태그는 모두 닫아야 함
    - 하나의 화면을 여러 컴포넌트로 나누면 어떤 장점이 있으며, 분리 기준은 어떻게 정할 수 있을까요?
        - 컴포넌트(Component) : UI를 독립적인 단위로 나눈 것, 함수로 작성하는 경우가 일반적
        - 반복되는 UI, 독립적으로 바뀌는 부분, 하나의 역할을 맡는 부분을 기준으로 분리
        - 재사용성⬆️, 수정 범위와 책임 명확
    - 조건부 렌더링과 목록 렌더링은 데이터에 따라 보여 줄 컴포넌트를 어떻게 결정하나요?
        - 조건부 렌더링 : 조건에 따라 다른 UI 반환
        - 목록 렌더링 : 배열을 순회해 항목별 UI 생성
        - 목록의 key : 각 항목의 정체성을 구분하는 값 → 고유 id 사용 권장

  **핵심 정리**

  React는 화면을 컴포넌트 트리로 구성, 각 컴포넌트가 props와 state를 바탕으로 UI를 반환하는 방식

    - 컴포넌트 합성(Composition)
        - 큰 화면을 Header, List, Item처럼 역할 단위로 조립
        - 중복되는 UI는 공통 컴포넌트로 분리, 화면마다 다른 부분은 props로 전달
    - JSX 작성 규칙
        - 하나의 부모 요소가 필요하면 Fragment 사용
        - 이벤트는 onClick처럼 camelCase 사용, 문자열이 아닌 값은 중괄호 안에 작성
        - 컴포넌트는 대문자, HTML 태그는 소문자로 시작
    - 조건부 렌더링
        - 조건에 따라 다른 컴포넌트를 반환하거나, 조건이 false일 때 아무것도 렌더링하지 않을 수 있음
        - 로딩 / 에러 / 빈 목록 / 정상 목록처럼 화면 상태를 구분할 때 사용
    - 목록 렌더링
        - 배열의 각 요소를 컴포넌트로 변환
        - 항목 추가·삭제·정렬 시에도 같은 데이터를 같은 항목으로 인식하도록 key 필요
        - 배열 인덱스는 목록 순서가 고정일 때만 사용, 일반적으로 DB id 같은 고유값 사용
    - 추가로 알아두면 좋은 내용
        - 렌더링 함수는 같은 props, state에 대해 같은 UI를 반환하는 순수한 함수처럼 작성
        - API 요청, 타이머처럼 화면 계산과 무관한 작업은 렌더링 중 실행 X
        - 컴포넌트 이름은 대문자로 시작 → HTML 태그와 구분
    - 출처 / 참고 자료

- props와 단방향 데이터 흐름
    - 부모와 자식 컴포넌트 사이에서 props는 어떤 역할을 하나요?
        - props(Properties) : 부모가 자식에게 전달하는 읽기 전용 데이터
        - 자식은 props를 직접 수정 X, 변경이 필요하면 부모가 내려준 콜백 함수 호출
    - 데이터가 부모에서 자식으로만 흐르면 화면의 변화를 추적하는 데 어떤 도움이 되나요?
        - 부모 → 자식 방향으로만 데이터 전달
        - 값의 출처를 위쪽 state부터 추적 가능 → 변경 경로가 예측 가능
    - props에 TypeScript 타입을 붙이면 컴포넌트를 잘못 사용하는 실수를 어떻게 찾을 수 있나요?
        - 컴포넌트가 받는 데이터 형태를 타입으로 명시
        - 필수 props 누락, 잘못된 자료형 전달, 존재하지 않는 콜백 호출을 실행 전에 확인 가능

  **핵심 정리**

  props는 컴포넌트의 입력값, state는 컴포넌트 내부에서 관리하는 값

    - props의 특징
        - 부모가 값을 내려주고 자식은 받아서 화면에 사용
        - 같은 props를 받으면 같은 UI를 반환하도록 작성하면 재사용하기 쉬움
        - 자식이 부모의 값을 바꿔야 하면 onChange, onDelete 같은 콜백 props로 요청
    - 단방향 데이터 흐름
        - state는 위쪽에 두고 아래로 전달
        - 이벤트는 아래에서 발생해도 콜백을 통해 위쪽 state를 변경
        - 데이터가 어디서 바뀌는지 추적 가능 → 디버깅, 유지보수에 유리
    - TypeScript와 props
        - props 인터페이스에 필수/선택 여부와 콜백의 인자·반환 타입 작성
        - 컴포넌트를 사용하는 위치에서 잘못된 조합을 컴파일 시점에 확인
    - children props
        - 컴포넌트 태그 사이에 넣는 내용을 받아 레이아웃 컴포넌트를 만들 때 사용
        - Card, Modal처럼 공통 틀은 같고 내부 내용만 달라지는 경우에 유용
    - 추가로 알아두면 좋은 내용
        - props 값을 복사해 state로 관리하면 원본 props와 동기화 문제 발생 가능
        - 독립적인 편집 상태가 필요한 경우에만 state로 분리
        - 이벤트 props는 onClick, onChange처럼 on으로 시작하는 이름 사용

- 상태와 리렌더링
    - 일반 변수와 state(상태)는 값이 바뀐 뒤 화면을 다시 보여 주는 방식이 어떻게 다른가요?
        - 일반 변수 변경 : React가 변화를 알지 못함 → 화면 다시 그리기 X
        - state : 컴포넌트가 기억해야 하는 값, setter 호출 시 새 state 기준으로 UI 다시 계산
    - React에서 원본 상태를 직접 수정하지 않고 새로운 값으로 업데이트해야 하는 이유는 무엇일까요?
        - state 원본을 직접 수정하면 이전 값과 다음 값 비교가 어려움
        - 배열은 map, filter, 전개 문법 등으로 새 배열 생성
        - 객체는 변경 경로마다 새 객체 생성 → 예측 가능한 업데이트
    - 이전 상태로 다음 상태를 계산할 때 업데이터 함수를 사용하는 이유는 무엇일까요?
        - 다음 state가 이전 state에 의존할 때 사용
        - 여러 업데이트가 묶여 처리되어도 최신 이전 값 기준으로 계산 가능

  **핵심 정리**

  state는 “현재 화면에서 사용하는 값의 스냅샷”으로 이해하는 것이 좋음

    - 리렌더링 흐름
        - 이벤트 발생 → setter 호출 → React가 다음 렌더링 예약 → 새 state로 UI 계산
        - setter는 값을 즉시 바꾸는 대입 연산이 아님
    - 배열 / 객체 state 업데이트
        - 배열 추가 : 전개 문법으로 새 배열 생성
        - 배열 수정 : map으로 대상 항목만 새 객체로 교체
        - 배열 삭제 : filter로 대상 항목을 제외한 새 배열 생성
        - 객체 수정 : 전개 문법으로 필요한 속성만 덮어쓰기
    - 업데이터 함수 사용 시점
        - 이전 count에 1을 더하는 것처럼 이전 값이 다음 값 계산에 필요한 경우
        - 여러 setter 호출이 하나로 묶이는 상황에서도 안전
    - state 설계
        - 화면에 필요한 최소 값만 state로 저장
        - 다른 state로 계산 가능한 값은 렌더링 중 계산 → 중복 state, 동기화 문제 감소
    - 추가로 알아두면 좋은 내용
        - setter 호출 직후 현재 렌더링의 state 값은 바로 바뀌지 않음 → 다음 렌더링에 반영
        - 다른 state에서 계산 가능한 값은 별도 state로 중복 저장 X
        - state가 여러 곳에서 어긋나기 시작하면 공통 부모로 끌어올릴지 확인

        - React 공식 문서 - Updating Objects in State
- 상태 공유와 Context
    - 여러 컴포넌트가 같은 상태를 사용해야 할 때 상태를 어느 컴포넌트에 두는 것이 좋을까요?
        - 같은 state를 사용하는 컴포넌트들의 가장 가까운 공통 부모에 둠
        - 상태 끌어올리기(Lifting State Up) : 하나의 값을 여러 곳에서 따로 관리하는 문제 방지
    - props 전달, 상태 끌어올리기와 Context는 각각 어떤 상황에 알맞을까요?
        - props : 가까운 부모·자식 관계, 데이터 흐름이 명확함
        - 상태 끌어올리기 : 형제 컴포넌트가 같은 값 사용
        - Context : 테마, 로그인 사용자, 언어처럼 넓은 트리에서 사용하는 값
    - 모든 값을 Context로 전달하면 어떤 문제가 생길 수 있을까요?
        - Provider의 value 변경 시 해당 Context를 구독하는 컴포넌트 리렌더링
        - 역할이 다른 값을 한 Context에 넣으면 관리·성능 측면에서 불리
        - 자주 바뀌는 값, 역할이 다른 값은 Context 분리

  **핵심 정리**

  상태 공유는 “이 값을 실제로 누가 함께 사용하는가”를 기준으로 설계

    - 상태 끌어올리기
        - 형제 컴포넌트가 같은 값을 보여주거나 함께 바꿔야 하면 공통 부모에 state를 둠
        - 단일 진실 공급원(Single Source of Truth)을 만들어 값 불일치 방지
    - props drilling
        - 중간 컴포넌트가 사용하지 않는 props를 여러 단계 전달하는 상황
        - 전달 단계가 조금 있다는 이유만으로 Context를 쓰기보다, 구조와 재사용성 먼저 확인
    - Context 구성
        - createContext로 Context 생성 → Provider로 value 제공 → 하위 컴포넌트에서 useContext로 사용
        - theme, locale, 로그인 사용자처럼 트리 전반에서 필요한 값에 적합
    - 주의점
        - Provider의 value가 바뀌면 Context를 구독하는 컴포넌트가 다시 렌더링
        - 인증, 테마, 알림처럼 역할별로 Context 분리
        - 자주 바뀌는 큰 객체를 하나의 Context에 넣는 것은 피하는 편이 좋음
    - 추가로 알아두면 좋은 내용
        - Context는 state 자체가 아니라 값을 멀리 전달하는 통로
        - props drilling이 있다고 무조건 Context 사용 X
        - 구조가 단순하거나 중간 컴포넌트도 값을 사용하면 props가 더 명확할 수 있음
    - 출처 / 참고 자료
        - React 공식 문서 - Passing Data Deeply with Context
        - React 공식 문서 - Scaling Up with Reducer and Context
