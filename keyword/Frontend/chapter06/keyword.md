- query key와 요청 상태
    - 목록, 검색과 상세에 같은 query key를 쓰면 어떤 문제가 생길까요? 페이지 번호, 검색어와 영화 ID를 포함하는 이유도 함께 생각해 보세요.

      #### 1. query key의 역할

        - TanStack Query는 query key를 기준으로 캐시를 관리한다.
        - query key는 쿼리 함수에서 사용하는 값 중 바뀌는 변수를 모두 포함해야 한다. key가 곧 그 데이터를 설명하는 이름이기 때문이다.
        - query key는 쿼리 함수의 의존성 역할을 한다. `useEffect`의 의존성 배열과 비슷하게 생각하면 된다.

      #### 2. 같은 key를 쓰면 생기는 문제

      같은 key는 캐시에서 같은 칸을 가리킨다. 서로 다른 요청이 한 칸을 같이 쓰면 다음 문제가 생긴다.

      | 문제 | 설명 |
              | --- | --- |
      | 데이터 덮어쓰기 | 목록(`results` 배열)과 상세(영화 객체 하나)가 같은 칸에 저장되어 서로 덮어쓴다. |
      | 이전 결과가 계속 보임 | 페이지, 검색어, 영화 ID가 바뀌어도 key가 같아서 이전 캐시를 그대로 재사용한다. (워크북 트러블슈팅 예시: 검색어를 바꿔도 이전 검색 결과가 보임) |
      | 자동 재조회 안 됨 | 변수가 바뀌어도 key가 안 바뀌면 새 데이터를 요청할 계기가 없다. |
      | 타입 충돌 | 같은 key에 서로 다른 형태의 데이터가 들어가 `data`의 타입이 맞지 않게 된다. |

      #### 3. 페이지 번호, 검색어, 영화 ID를 key에 포함하는 이유

      key에 의존하는 변수를 넣으면 쿼리가 독립적으로 캐시되고, 변수가 바뀔 때마다 자동으로 다시 조회된다. (staleTime 설정에 따라 다름)

      | 화면 | query key | 포함하는 값 | 이유 |
              | --- | --- | --- | --- |
      | 목록 | `["movies", "list", { page }]` | 페이지 번호 | 페이지별 결과가 다르므로 페이지마다 캐시를 따로 저장한다. 1 → 2 → 1 이동 시 1페이지 캐시를 재사용할 수 있다. |
      | 검색 | `["movies", "search", { query }]` | 검색어 | 검색어마다 결과가 다르므로 검색어별로 캐시를 구분한다. |
      | 상세 | `["movies", "detail", movieId]` | 영화 ID | 영화마다 상세 정보가 다르므로 ID별로 캐시를 구분한다. |
    - `enabled: false`인데도 `isPending`이 참일 수 있는 이유는 무엇이며, 이때 `isLoading`은 어떤 값일까요?

      #### 1. status와 fetchStatus는 서로 다른 값이다

      | 구분 | 의미 | 값 |
              | --- | --- | --- |
      | `status` | 데이터가 있는지 | `pending`, `error`, `success` |
      | `fetchStatus` | queryFn이 지금 실행 중인지 | `fetching`, `paused`, `idle` |
        - `isPending`은 `status === 'pending'`과 같고, 쿼리에 아직 데이터가 없다는 뜻이다. 요청을 보냈는지는 보지 않는다.
        - `fetchStatus`는 queryFn이 실행 중인지 알려 주는 별도 값이다.
        - 두 값이 따로 있는 이유는 백그라운드 재조회 때문이다. success 상태에서도 백그라운드 재조회 중이면 fetching일 수 있고, 데이터 없이 마운트됐는데 네트워크가 없으면 pending이면서 paused일 수 있다.

      #### 2. enabled: false일 때 isPending이 참인 이유

        - 캐시된 데이터가 없는 쿼리는 `status === 'pending'`, `fetchStatus === 'idle'` 상태로 시작한다.
        - 비활성화된 쿼리는 마운트될 때 자동으로 fetch하지 않고, 백그라운드 재조회도 하지 않는다.
        - 요청을 안 보냈으니 데이터가 영원히 없고, 그래서 `isPending`은 계속 `true`다.
        - 로딩 중이어서 `true`인 것이 아니라 **데이터가 없어서** `true`인 것이다.

      #### 3. 이때 isLoading은 false

        - `isLoading`은 `isPending && isFetching`으로 계산되는 값이라, 쿼리가 처음으로 실제 fetch 중일 때만 true다.
        - `enabled: false`이면 fetch를 하지 않으므로 `isFetching`이 `false`이고, 따라서 `isLoading`도 `false`다.
        - 비활성화(lazy) 쿼리에서는 이 `isLoading`을 쓰면 된다.

      #### 4. 상태별 비교

      | 상황 | status | fetchStatus | isPending | isLoading |
              | --- | --- | --- | --- | --- |
      | `enabled: false`, 캐시 없음 | `pending` | `idle` | true | **false** |
      | `enabled: true`, 첫 요청 중 | `pending` | `fetching` | true | **true** |
      | 오프라인으로 요청 대기 | `pending` | `paused` | true | false |
      | 조회 성공 | `success` | `idle` | false | false |
- 캐시 수명과 재조회
    - `staleTime`과 `gcTime`은 각각 언제부터 계산하며, 시간이 지난 뒤 캐시에 어떤 차이가 생길까요?

      #### 1. 각각 언제부터 계산하는가

      | 구분 | 계산 시작 시점 | 기본값 |
              | --- | --- | --- |
      | `staleTime` | 요청이 완료되어 데이터가 캐시에 저장된 시점부터 계산하고, 설정한 시간이 지나면 stale로 표시된다. | `0` (바로 stale) |
      | `gcTime` | 해당 query를 사용하는 인스턴스가 하나도 남지 않은 시점부터 계산한다. (컴포넌트가 unmount되어 inactive가 된 때) | 5분  |
        - `staleTime`은 데이터가 얼마나 최신인지를 따진다. `staleTime`이 설정된 query는 그 시간이 지나기 전까지 fresh로 취급한다.
        - `gcTime`은 안 쓰는 캐시를 언제 메모리에서 지울지를 따진다. 쓰는 중에는 작동하지 않고, 안 쓰게 되는 순간부터 작동한다.
        - 두 시간은 서로 독립적이다. `staleTime`이 지나도 캐시는 삭제되지 않는다.

      #### 2. 시간 흐름

        1. 요청이 끝나 데이터가 캐시에 저장되면 **fresh**가 되고 `staleTime` 계산이 시작된다.
        2. `staleTime`이 지나면 **stale**이 된다. 캐시는 그대로 남아 있다.
        3. 화면을 벗어나 컴포넌트가 unmount되면 **inactive**가 되고 `gcTime` 계산이 시작된다.
        4. `gcTime` 안에 다시 쓰이지 않으면 캐시 데이터가 삭제되고 garbage collect된다.

      #### 3. 시간이 지난 뒤 캐시의 차이

      | 시점 | 캐시 데이터 | 다시 화면에 들어왔을 때 |
              | --- | --- | --- |
      | `staleTime` 안 (fresh) | 있음 | 캐시를 그대로 사용하고 요청하지 않는다. |
      | `staleTime` 지남, `gcTime` 안 (stale) | 있음 | 캐시된 데이터를 즉시 보여주면서 백그라운드로 다시 요청하고, 성공하면 새 데이터로 채운다. |
      | `gcTime` 지남 | 삭제됨 | 캐시가 없어 처음 조회할 때처럼 로딩 상태가 되고 요청한다. tanstack |
        - stale이 됐다고 바로 요청하지는 않는다. stale query는 새 인스턴스가 mount될 때, 창에 다시 포커스될 때, 네트워크가 다시 연결될 때 백그라운드에서 자동으로 재조회된다.
        - `staleTime`의 기본값이 `0`이라 기본 설정에서는 이미 본 페이지로 돌아가도 다시 요청한다. 캐시는 있지만 바로 stale로 취급하기 때문이다.

      #### 4. 워크북 예시로 보기

      `staleTime: 1분`, `gcTime: 5분(기본값)`일 때 목록에서 1 → 2 → 1페이지로 이동하는 경우:

      | 상황 | 결과 |
              | --- | --- |
      | 1페이지로 돌아옴 (조회 후 1분 안) | fresh이므로 캐시를 사용하고 요청하지 않는다. Network 탭에서 확인할 수 있다. |
      | 1페이지로 돌아옴 (1분 지남, 5분 안) | stale이므로 캐시를 먼저 보여주고 백그라운드로 다시 요청한다. |
      | 1페이지로 돌아옴 (벗어난 지 5분 지남) | 캐시가 삭제되어 처음처럼 로딩 후 요청한다. |
    - 전역 기본값과 개별 `useQuery`의 `staleTime`은 어떤 기준으로 정하면 좋을까요?

      #### 1. 두 가지 설정 방법

      | 구분 | 위치 | 적용 범위 |
              | --- | --- | --- |
      | 전역 기본값 | `new QueryClient({ defaultOptions: { queries: { staleTime } } })` | 별도 설정이 없는 모든 query |
      | 개별 설정 | `useQuery({ ..., staleTime })` | 해당 query만 (전역 기본값 대신 적용) |
        - `staleTime`은 전역과 query별로 모두 설정할 수 있고, 값이 길수록 데이터를 덜 자주 다시 조회한다. tanstack
        - 설정하지 않으면 기본값이 `0`이라 가져온 데이터를 바로 stale로 취급한다.

      #### 2. 데이터 성격에 따른 기준

      | 데이터 성격 | staleTime | 설명 |
              | --- | --- | --- |
      | 앱이 실행되는 동안 바뀌지 않는 데이터 (기능 플래그, 로그인 시 불러오는 권한, 고정된 참조 테이블) | `'static'` | 공식 문서가 이런 데이터에 `'static'`을 쓰라고 안내한다. 수동 invalidate로도 재조회되지 않는다. |
      | 거의 안 바뀌지만 필요하면 직접 갱신하고 싶은 데이터 | `Infinity` | `Infinity`는 수동 invalidate 전까지 재조회하지 않고, 수동 갱신은 여전히 가능하다. |
      | 자주 바뀌지 않거나 요청 비용이 큰 데이터 (영화 목록, 상세 등) | 수십 초 ~ 수 분 | 예를 들어 2분으로 설정하면 그동안 재조회 없이 캐시에서 읽는다. |
      | 자주 바뀌고 최신 값이 중요한 데이터 | 짧게 또는 기본값 `0` | 보여줄 때마다 최신 여부를 확인한다. 주기적으로 갱신하려면 `refetchInterval`을 함께 쓴다. Guides & Concepts +2 |

      #### 3. 정하는 순서

        1. 앱 대부분의 화면에 무난한 값을 **전역 기본값**으로 정한다. (워크북은 1분)
        2. 데이터 성격이 다른 query만 **개별 `staleTime`*으로 덮어쓴다. (워크북은 인물 상세만 30초)
        3. 전역에서 정한 값이 맞지 않는 query가 많아지면 전역 값을 다시 조정한다.

      | 구분 | 워크북 예시 |
              | --- | --- |
      | 전역 | `staleTime: 60 * 1000` (1분) |
      | 개별 | 인물 상세 `staleTime: 30 * 1000` (30초) |

      #### 4. 정할 때 확인할 점

        - **최신성과 요청 수의 균형**: `staleTime`이 길수록 요청은 줄지만 서버의 최신 값과 달라질 수 있다.
        - **재조회 시점은 다른 옵션으로도 조절 가능**: `staleTime`을 설정하는 것이 불필요한 재조회를 막는 권장 방법이고, `refetchOnMount`, `refetchOnWindowFocus`, `refetchOnReconnect`로도 재조회 시점을 조절할 수 있다. tanstack
        - **`refetchInterval`은 `staleTime`과 독립적**: 주기적 재조회는 `staleTime`과 별개로 동작한다.
        - **`gcTime`과는 별개**: `staleTime`이 길어도 캐시 삭제 시점은 `gcTime`이 결정한다.
