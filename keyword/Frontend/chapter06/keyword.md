- query key와 요청 상태
  - 목록, 검색과 상세에 같은 query key를 쓰면 어떤 문제가 생길까요? 페이지 번호, 검색어와 영화 ID를 포함하는 이유도 함께 생각해 보세요.
    - **query key**
      - TanStack Query에서 서버 데이터를 캐시에 저장하고 구분하기 위해 사용하는 고유한 식별자
      - 동일한 query key를 사용하면 같은 캐시 데이터를 공유함
    - **같은 query key를 사용할 때 발생하는 문제**
      - 영화 목록과 상세 정보에 같은 key를 사용하면 서로 다른 데이터가 같은 캐시에 저장되어 잘못된 정보가 표시될 수 있음
      - 페이지 번호가 달라도 같은 key를 사용하면 이전 페이지의 데이터를 재사용할 수 있음
      - 검색어가 달라도 같은 key를 사용하면 이전 검색 결과가 표시될 수 있음
    - **query key에 값을 포함하는 이유**
      - 페이지 번호: 페이지별 영화 목록을 구분하기 위해
      - 검색어: 검색 조건에 따른 결과를 각각 저장하기 위해
      - 영화 ID: 영화마다 서로 다른 상세 정보를 저장하기 위해
    - **query key 구성 예시**
      - 영화 목록: movies → list → 페이지 번호
      - 영화 검색: movies → search → 검색어 → 페이지 번호
      - 영화 상세: movies → detail → 영화 ID

    → 요청에 영향을 주는 값을 query key에 포함하면 서로 다른 데이터를 구분하여 캐시를 관리하고, 불필요한 API 요청을 줄일 수 있음

  - `enabled: false`인데도 `isPending`이 참일 수 있는 이유는 무엇이며, 이때 `isLoading`은 어떤 값일까요?
    - **enabled: false**
      - 해당 쿼리가 자동으로 실행되지 않도록 설정하는 옵션
      - 필요한 조건이 충족된 이후에 API 요청을 실행하고 싶을 때 사용함
    - **isPending**
      - 아직 성공적으로 받아온 데이터가 없고 쿼리가 완료된 상태도 아닌 경우 true
      - 실제 API 요청이 진행 중인지와는 별개로 판단함
      - 따라서 enabled: false로 요청을 실행하지 않았더라도 캐시 데이터가 없다면 true가 될 수 있음
    - **isLoading**
      - 데이터를 처음 불러오기 위한 API 요청이 실제로 진행 중일 때 true
      - isPending과 isFetching이 모두 true일 때만 true가 됨
      - enabled: false이고 요청이 진행되지 않는 상태라면 false
    - **상태 비교**


            | 상황 | isPending | isLoading |
            | --- | --- | --- |
            | 요청 비활성화, 캐시 없음 | true | false |
            | 최초 요청 진행 중 | true | true |
            | 요청 성공, 데이터 존재 | false | false |
            | 기존 데이터를 재조회 중 | false | false |
        
        → isPending은 아직 데이터가 준비되지 않은 상태를, isLoading은 최초 데이터를 실제로 불러오는 중인 상태를 나타냄
        
        따라서 enabled: false를 사용하는 경우 로딩 화면을 표시할 때 isPending보다 isLoading을 사용하는 것이 적절

- 캐시 수명과 재조회
  - `staleTime`과 `gcTime`은 각각 언제부터 계산하며, 시간이 지난 뒤 캐시에 어떤 차이가 생길까요?
    - **staleTime**
      - 캐시 데이터를 최신 상태로 간주하는 시간
      - 데이터를 성공적으로 받아와 캐시에 저장하거나 갱신한 시점부터 계산함
      - 설정한 시간이 지나면 데이터가 오래된 상태인 stale로 변경됨
      - stale 상태가 되어도 캐시 데이터는 삭제되지 않음
      - 이후 컴포넌트가 새로 마운트되거나 브라우저 창에 다시 접근하는 등의 조건에서 재요청이 발생할 수 있음
    - **gcTime**
      - 사용하지 않는 캐시 데이터를 메모리에 보관하는 시간
      - 해당 쿼리를 사용하는 활성 컴포넌트가 없어져 캐시가 비활성 상태가 된 시점부터 계산함
      - 설정한 시간이 지나도록 다시 사용되지 않으면 캐시 데이터를 삭제함
      - 삭제된 데이터가 다시 필요해지면 새로운 API 요청으로 데이터를 받아와야 함
    - **예시**
      - staleTime을 1분, gcTime을 5분으로 설정한 경우
      - 데이터를 받아온 후 1분이 지나면 오래된 데이터로 판단하지만 캐시는 유지됨
      - 사용 중인 컴포넌트가 사라진 후 5분 동안 다시 사용하지 않으면 캐시가 삭제됨
      - 단, staleTime이 지나도 즉시 API 요청이 발생하는 것은 아님

    → staleTime은 데이터를 언제 다시 확인할지 결정하는 기준이고, gcTime은 사용하지 않는 데이터를 얼마나 오래 보관할지 결정하는 기준

  - 전역 기본값과 개별 `useQuery`의 `staleTime`은 어떤 기준으로 정하면 좋을까요?
    - **전역 기본값**
      - 애플리케이션 전체의 쿼리에 공통으로 적용할 staleTime
      - 대부분의 API에서 사용할 수 있는 적절한 시간을 기본값으로 설정함
      - 지나치게 짧으면 불필요한 API 요청이 증가하고, 너무 길면 오래된 정보가 표시될 수 있음
    - **개별 useQuery의 staleTime**
      - 데이터마다 변경되는 빈도와 최신 정보의 중요도가 다르므로 필요에 따라 개별 설정함
      - 개별 쿼리에 설정한 staleTime은 전역 기본값보다 우선 적용됨

    → 전역에서는 대부분의 API에 적합한 기본값을 설정하고, 개별 쿼리에서는 데이터 변경 빈도와 최신 정보의 중요성에 따라 staleTime을 조절하는 것이 좋음
