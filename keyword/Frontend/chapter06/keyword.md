- query key와 요청 상태
  - 목록, 검색과 상세에 같은 query key를 쓰면 어떤 문제가 생길까요? 페이지 번호, 검색어와 영화 ID를 포함하는 이유도 함께 생각해 보세요.
    목록, 검색, 상세 조회에 같은 query key를 사용하면 서로 다른 데이터가 같은 캐시에 저장될 수 있다. 이로 인해 목록 데이터가 상세 데이터로 덮어씌워지거나 잘못된 데이터가 화면에 표시될 수 있다. 따라서 각각의 요청 목적에 맞게 query key를 구분해야 한다.
    페이지 번호는 현재 몇 번째 목록을 요청했는지 구분하기 위해 필요하다.
    검색어는 검색 조건에 따라 결과가 달라지므로 query key에 포함해야 한다.
    영화 ID 역시 영화마다 상세 정보가 다르기 때문에 반드시 포함해야 한다.
    이처럼 query key를 구체적으로 설정하면 캐시를 효율적으로 관리하고 불필요한 데이터 충돌을 방지할 수 있다.
  - `enabled: false`인데도 `isPending`이 참일 수 있는 이유는 무엇이며, 이때 `isLoading`은 어떤 값일까요?
    **`enabled: false`**는 쿼리가 자동으로 실행되지 않도록 설정하는 옵션이다. 쿼리가 실행되지 않았기 때문에 아직 데이터를 가져오지 못한 상태로 남아 있을 수 있다. 이때 데이터가 없는 초기 상태이므로 **`isPending`**은 **`true`**가 될 수 있다. 하지만 실제 요청이 시작된 것은 아니기 때문에 **`isLoading`**은 **`false`**
- 캐시 수명과 재조회
  - `staleTime`과 `gcTime`은 각각 언제부터 계산하며, 시간이 지난 뒤 캐시에 어떤 차이가 생길까요?
    **`staleTime`**은 데이터를 가져온 시점부터 계산되며, 설정한 시간이 지나면 데이터는 오래된 상태인 **`stale`**로 변경된다. 이때 캐시에서 데이터가 바로 삭제되는 것은 아니며, 재조회 조건이 충족되면 새로운 데이터를 가져올 수 있다.
    **`gcTime`**은 해당 쿼리를 사용하는 컴포넌트가 모두 사라져 쿼리가 비활성화된 시점부터 계산된다. 설정한 시간이 지나면 더 이상 사용하지 않는 캐시 데이터가 메모리에서 제거된다.
  - 전역 기본값과 개별 `useQuery`의 `staleTime`은 어떤 기준으로 정하면 좋을까요?
    전역 기본값은 대부분의 쿼리에 공통으로 적용할 수 있는 적절한 시간을 설정하는 것이 좋다. 예를 들어 자주 변경되지 않는 일반적인 데이터라면 비교적 긴 **`staleTime`**을 설정할 수 있다. 반대로 실시간으로 변경되는 데이터는 짧은 시간을 설정하는 것이 적절하다.
    개별 **`useQuery`**에서는 데이터의 특성과 최신 정보가 필요한 정도에 따라 별도로 설정하면 된다.영화 상세 정보처럼 자주 변경되지 않는 데이터는 긴 시간을 설정할 수 있다. 반면 실시간 인기 순위나 자주 바뀌는 검색 결과는 짧은 시간을 설정하는 것이 좋다.
