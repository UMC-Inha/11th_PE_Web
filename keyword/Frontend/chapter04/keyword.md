- Web Storage
    - localStorage와 sessionStorage는 저장값의 수명과 공유 범위가 어떻게 다른가요?
        - **localStorage**
            - 브라우저를 닫아도 데이터가 유지됨
            - 사용자가 직접 삭제하거나 코드로 삭제하기 전까지 남아 있음
            - 같은 origin(프로토콜 + 도메인 + 포트)에서 공유됨
        - **sessionStorage**
            - 현재 탭을 닫으면 데이터가 삭제됨
            - 같은 사이트라도 다른 탭과는 기본적으로 저장 공간이 분리됨
            - 현재 탭에서만 임시로 사용할 데이터에 적합함
    - 객체나 배열을 저장할 때 JSON 문자열로 바꿔야 하는 이유는 무엇일까요?
        - localStorage와 sessionStorage는 문자열 형태의 값만 저장할 수 있음
        - 객체나 배열을 그대로 저장하면 브라우저가 강제로 문자열로 변환하기 때문에 기존 데이터의 구조가 유지되지 않음
            - 예를 들어 `{ name: "수빈", age: 21 }`이라는 객체를 그대로 저장하면
              `"[object Object]"`라는 문자열로 변환됨
            - 이 경우 객체의 속성인 name, age와 해당 값들이 사라져 원래 데이터를 복원할 수 없음
        - 따라서 `JSON.stringify()`를 사용해 객체나 배열의 구조와 값을 유지하면서 JSON 문자열로 변환해야 함
            - 예: { name: "수빈", age: 21 } → '{"name":"수빈","age":21}'
        - 저장된 데이터를 다시 사용할 때는 `JSON.parse()`를 통해 JSON 문자열을 원래 객체나 배열 형태로 변환함
    - Web Storage에는 어떤 데이터를 저장하는 것이 적절할까요?
        - Web Storage에는 **브라우저에서 잠깐 또는 간단하게 유지할 필요가 있는 사용자 상태 데이터**를 저장하는 것이 적절
            - 예를 들면
            - 북마크한 영화 ID 목록
            - 최근 검색어
            - 사용자가 선택한 필터나 정렬 조건
        - 반대로 **비밀번호, 주민등록번호, 결제 정보, 중요한 인증 정보처럼 민감한 데이터는 저장하면 안 됨**
            - Web Storage의 데이터는 브라우저의 JavaScript에서 접근할 수 있기 때문에 XSS 공격이 발생하면 탈취될 위험이 있음
- 클라이언트 상태와 전역 상태 관리
    - 컴포넌트 상태와 전역 상태는 사용하는 범위가 어떻게 다른가요?
        - **컴포넌트 상태**
            - 특정 컴포넌트 내부에서만 사용하는 상태
            - 보통 useState로 관리함
            - 그 컴포넌트 안에서만 필요하거나, 가까운 자식 컴포넌트 정도까지만 전달하면 될 때 사용함
            - 예: 모달 열림 여부, 입력창 값, 현재 페이지 번호
        - **전역 상태**
            - 여러 컴포넌트나 여러 페이지에서 함께 사용하는 상태
            - 한 컴포넌트에만 두기보다 앱 전체에서 접근할 수 있게 관리함
            - Zustand, Redux 같은 도구를 사용할 수 있음
            - 예: 로그인한 사용자 정보, 장바구니, 테마 설정, 여러 페이지에서 공유하는 북마크 정보
        - 차이
            - 컴포넌트 상태 → **사용 범위가 좁음**
            - 전역 상태 → **앱 여러 곳에서 공유함**
            - 여러 컴포넌트가 같은 상태를 필요로 하는데 계속 props로 전달해야 한다면 전역 상태를 고려할 수 있음
    - 여러 화면에서 사용하는 북마크 상태를 전역으로 관리하면 어떤 장점과 비용이 생길까요?
        - **장점**
            - 여러 화면에서 같은 북마크 상태를 쉽게 공유할 수 있음
                - 예: 영화 목록에서 북마크를 추가하면 상세 페이지나 북마크 페이지에서도 바로 같은 상태를 사용할 수 있음
            - 컴포넌트마다 북마크 상태를 따로 만들 필요가 없어 **상태 불일치 문제를 줄일 수 있음**
            - 여러 단계의 컴포넌트를 거쳐 props로 상태와 함수를 계속 전달하는 **Props Drilling을 줄일 수 있음**
            - 북마크 관련 로직을 한 곳에서 관리할 수 있어 수정이나 확장이 쉬워짐
        - **비용**
            - Zustand, Redux 등 전역 상태를 관리하기 위한 추가 구조가 필요함
            - 단순한 기능인데 전역 상태를 사용하면 오히려 코드가 복잡해질 수 있음
            - 전역 상태가 변경될 때 이를 사용하는 여러 컴포넌트에 영향을 줄 수 있어 상태의 흐름을 파악하기 어려워질 수 있음
            - 잘못 사용하면 상태 변경 시 필요하지 않은 컴포넌트까지 다시 렌더링될 수 있음
    - Zustand와 Web Storage는 북마크 상태를 관리할 때 각각 어떤 역할을 할까요?
        - **Zustand**
            - 앱이 실행되는 동안 북마크 상태를 **전역에서 관리하고 공유하는 역할**
            - 영화 목록, 상세 페이지, 북마크 페이지 등 여러 화면에서 같은 북마크 상태를 사용할 수 있게 해줌
            - 북마크 추가/삭제 같은 상태 변경 로직도 한 곳에서 관리할 수 있음
        - **Web Storage**
            - 북마크 상태를 브라우저에 **저장해서 새로고침이나 재접속 후에도 유지하는 역할**
            - 예를 들어 localStorage에 북마크된 영화 ID를 저장해 두면 페이지를 새로고침해도 다시 불러올 수 있음
        - **함께 사용하면**
            - Zustand → 현재 앱에서 사용할 북마크 상태 관리
            - Web Storage → 그 상태를 브라우저에 저장해서 유지
        - 예를 들어
            - 사용자가 영화 3번을 북마크함
            - Zustand의 북마크 상태가 [3]으로 변경됨
            - 그 값을 localStorage에도 저장함
            - 새로고침하면 localStorage에서 [3]을 읽어 Zustand 상태를 다시 복원함
