- Web Storage

  - localStorage와 sessionStorage는 저장값의 수명과 공유 범위가 어떻게 다른가요?

    - localStorage : 브라우저를 닫아도 데이터가 영구적으로 유지된다. 유저가 데이터를 직접 삭제하거나 코드를 통해 삭제하지 않는 한 계속 남아있다. 또한 같은 출처의 모든 탭과 창이 하나의 저장소를 공유한다.
    - sessionStorage : 현재 열려 있는 탭이나 창이 닫히면 즉시 데이터가 삭제된다. 탭마다 각자 다른 저장소를 사용(공유가 아닌 복사)한다.

  - 객체나 배열을 저장할 때 JSON 문자열로 바꿔야 하는 이유는 무엇일까요?

    - 데이터를 저장하는 곳은 보통 문자열(String) 형태의 데이터만 직접 저장할 수 있다. 따라서 문자열이 아닌 값을 저장하면 브라우저가 String()으로 강제 변환하는데 이 과정에서 구조가 망가질 수 있다.

    ```jsx
    const user = {
      name: "철수",
      age: 20,
      hobbies: ["축구", "게임"]
    };
    //이걸 localStorage에 직접 저장하면
    localStorage.setItem("user", user);
    // -> 객체가 문자열로 변환되면서 사실상 [object Object]
    ```

    - 그래서 JSON으로 변환한다.

      ```jsx
      localStorage.setItem("user", JSON.stringify(user));
      ```

      JSON.stringify()는 객체나 배열이 저장하기 좋은 문자열 형태로 직렬화 하는 것이고

      JSON.parse()는 그 문자열을 원래 자료구조로 복원하는 것이다.

  - Web Storage에는 어떤 데이터를 저장하는 것이 적절할까요?

    - Web Storage(localStorage, sessionStorage)에는 브라우저에서 잠깐, 또는 지속적으로 저장해야하는 작은 크기의 데이터를 저장하는것이 적합하다.
    - 판단 기준은 다음과 같다. 1. 노출되어도 괜찮은가? 2. 크기가 작은가 3. 이 브라우저에만 있어도 되는가?
      1. Web Storage에 저장된 데이터는 JavaScript에서 쉽게 접근할 수 있다. 보호 장치가 없기 때문에 민감한 데이터는 넣지 않는 것이 적절하다.
      2. Web Storage는 대용량 데이터를 저장하도록 설계되지 않았기 때문에 일반적으로 몇 MB 정도의 작은 공간을 사용한다. 문자열로 저장되기 때문에 큰 데이터를 JSON 문자열로 변환하면 처리 비용이 크게 증가한다. 또한 Web Storage API는 동기적으로 동작하므로 큰 데이터를 저장하거나 읽으면 그 작업을 처리하는 동안 기다려야해서 속도가 느려질 수 있다.
      3. Web Storage에 있는 값은 값이 있는 해당 브라우저에만 존재하므로 다른 서버에서도 똑같이 보여야 하는 데이터는 서버가 원본을 가져야 한다.

- 클라이언트 상태와 전역 상태 관리

  - 컴포넌트 상태와 전역 상태는 사용하는 범위가 어떻게 다른가요?

    - 컴포넌트 상태 : 특정 컴포넌트 내부에서만 필요한 state이다. 특정 컴포넌트에 묶여 있어 컴포넌트가 화면에 나타날 때 생기고 사라질 때 함께 사라지며 다른 컴포넌트에게 전달하려면 props를 통해 자식에게 내려주는 수밖에 없다.

      ex) input값, 탭 선택, hover 상태

    - 전역 상태: 여러 컴포넌트에서 공유해야 하는 state이다. 컴포넌트 트리 바깥에 있는 저장소에 값을 두고 필요한 컴포넌트가 어디에 있든 직접 구독해 읽고 바꿀 수 있게 한다. 개별 컴포넌트가 사라져도 값은 남아있어 페이지를 이동했다가 돌아와도 값이 유지된다. 그러나 새로고침하면 메모리가 비워지므로 함께 사라진다. (전역 상태를 localStorage에 저장하면 새로고침 후에도 유지)

  - 여러 화면에서 사용하는 북마크 상태를 전역으로 관리하면 어떤 장점과 비용이 생길까요?

    - 장점
      - 상태를 여러 화면에서 쉽게 공유할 수 있음 : 모두가 하나의 원본을 공유하기 때문에 props 전달 단계가 사라지고 여러 층을 거쳐 내려보낼 필요 없이 필요하면 컴포넌트가 바로 저장소에서 꺼내 사용한다.
      - 상태의 기준이 하나가 됨 : 화면마다 북마크를 따로 관리해서 생기는 문제를 줄일 수 있다.
      - 로직의 집중 : 토글 규칙을 저장소 한 곳에 저장해 두면 화면마다 같은 코드를 반복하지 않아도 된다.
    - 비용
      - 의존성 증가 → 상태 관리 코드 늘어남 : 컴포넌트가 특정 저장소에 의존하게 되어 독립적인 테스트가 어려워진다. 따라서 전역 상태를 만들고, 수정하는 방법과 구조를 정해야 한다.
      - 변경 범위 증가 : 북마크 상태가 변경되었을 때 이를 사용하는 여러 컴포넌트가 다시 렌더링 된다.

  - Zustand와 Web Storage는 북마크 상태를 관리할 때 각각 어떤 역할을 할까요?

    - Zustand : 확장 가능한 상태관리 라이브러리

      - Web Storage는 기본적으로 값을 저장하고 가져오는 API이지, React 컴포넌트들에게 상태가 변경됐으니 다시 렌더링하라고 알려주는 상태 관리 시스템이 아님. Zustand 에서는 해당 상태를 구독하고 있는 컴포넌트들에게 변경을 알린다.
      - 여러 컴포넌트가 북마크 상태를 공유하고 변경할 수 있게 관리하는 역할을 한다.
      - store 상태 만듦(JS 메모리에 저장) → 컴포넌트가 구독 → 상태변경되면 구독중인 컴포넌트에게 변경 사실을 알려 다시 재렌더링
      - store에는 크게 두 가지가 들어가는데 state와 action이 들어간다. → 즉 데이터와 데이터를 변경하는 함수 하나의 store에서 관리 가능.

    - Web Storage

      - 브라우저를 새로고침하거나 다시 방문해도 데이터를 유지하기 위한 저장소
      - 새로고침해도 \*\*`localStorage`\*\*에 저장된 데이터는 남아 있기 때문에 다시 가져올 수 있음.

    - 두 장점을 합치는 방법이 persist 미들웨어이다. 앱이 시작될 때 localStorage에서 값을 읽어 저장소를 채우고(rehydration), 이후 상태가 바뀔 때마다 JSON으로 직렬화해 localStorage에 다시 쓴다. Zustand는 현재 상태를 관리하고, persist는 그 상태를 Web Storage에 자동으로 저장·복원해주는 역할

      ```plaintext
                   Zustand Store
                ┌─────────────────┐
                │ bookmarks       │
                │ addBookmark()   │
                │ removeBookmark()│
                └────────┬────────┘
                         │
                   persist middleware
                         │
                         ↓
                ┌─────────────────┐
                │  localStorage   │
                │  "bookmarks"    │
                └─────────────────┘
      ```

      Zustand는 북마크의 현재 상태를 여러 컴포넌트에서 공유하고, `persist`는 그 Zustand 상태를 Web Storage에 저장했다가 새로고침 후 다시 Zustand로 복원해주는 역할을
