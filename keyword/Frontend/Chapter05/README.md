# Frontend Chapter05

## 키워드 정리

### HTTP와 API

#### API, endpoint, HTTP method와 status code는 요청과 응답에서 각각 어떤 역할을 할까요?

- **API (Application Programming Interface):** 클라이언트와 서버가 서로 통신할 수 있도록 연결해 주는 접점 및 규격 전체입니다.
- **Endpoint (엔드포인트):** 서버 내에서 특정 리소스(데이터)에 접근하기 위해 지정된 세부 URL 주소입니다. (예: `/movie/popular`, `/search/movie`)
- **HTTP Method (요청 방식):** 해당 엔드포인트에서 수행할 작업의 목적을 서버에 알립니다.
    - `GET`: 데이터 조회 / `POST`: 데이터 생성 / `PUT`·`PATCH`: 데이터 수정 / `DELETE`: 데이터 삭제
- **Status Code (응답 상태 코드):** 서버가 요청을 처리한 결과 상태를 3자리 숫자로 알립니다.
    - `200 OK`: 요청 성공
    - `400 Bad Request`: 잘못된 요청
    - `401 Unauthorized`: 인증 실패 (토큰 미비/오류)
    - `404 Not Found`: 리소스가 없음
    - `500 Internal Server Error`: 서버 내부 오류

#### 브라우저와 API 서버의 origin이 다를 때 CORS는 어떤 역할을 할까요?

- **CORS (Cross-Origin Resource Sharing):** 브라우저의 기본 보안 정책인 SOP(Same-Origin Policy)로 인해 출처(Origin = Protocol + Host + Port)가 다른 서버 간 데이터 요청이 차단되는 것을 해결하기 위한 "교차 출처 자원 공유 허용 메커니즘"입니다.
- **역할:** 브라우저가 다른 Origin으로 요청을 보낼 때, 서버가 Response Header에 `Access-Control-Allow-Origin`을 실어 보내 "이 Origin의 접근을 허용한다"고 알려주면, 브라우저가 안심하고 응답 데이터를 자바스크립트에 전달하도록 허용합니다.

### Promise와 비동기 처리

#### Promise의 pending, fulfilled와 rejected 상태는 각각 무엇을 의미할까요?

- **Pending (대기):** 비동기 처리가 아직 완료되지 않고 진행 중인 초기 상태
- **Fulfilled (이행/성공):** 비동기 처리가 성공적으로 완료되어 결과 값을 가지고 있는 상태 (`resolve()` 호출)
- **Rejected (거부/실패):** 비동기 처리 중 오류가 발생하여 실패한 상태 (`reject()` 호출)

#### `.then().catch()`와 `async/await`는 같은 비동기 흐름을 어떻게 다르게 표현하나요?

- **`.then().catch()` (Promise Chaining):** 성공 시 실행할 콜백 함수를 `.then()`에, 실패 시 콜백 함수를 `.catch()`에 등록하는 체이닝 방식입니다. 간단한 연결에는 직관적이지만, 단계가 많아지면 콜백 체인이 길어져 가독성이 떨어집니다.
- **`async/await`:** `async` 함수 내에서 `await`를 사용해 비동기 코드를 마치 동기식 코드(위에서 아래로 읽히는 코드)처럼 연달아 작성하는 방식입니다. 자바스크립트의 표준 `try-catch` 문을 그대로 사용해 에러 처리를 깔끔하게 묶을 수 있습니다.

#### `await`를 사용해도 브라우저 전체가 멈추지 않는 이유는 무엇일까요?

- 자바스크립트는 싱글 스레드지만, `await`는 스레드를 멈추는 게 아니라 **해당 `async` 함수의 실행만 잠시 미뤄두고(일시 중단)** 호출 스택을 비워 다른 코드(이벤트 처리, 렌더링 등)가 계속 실행되게 합니다.
- Promise가 resolve/reject 되면 그 결과가 **마이크로태스크 큐(Microtask Queue)**에 들어가고, 이벤트 루프가 현재 실행 중인 동기 코드를 다 처리한 뒤 꺼내서 이어서 실행합니다.
- 즉 `await` 이후 코드는 "나중에" 실행될 뿐이고, 그 사이에도 브라우저는 다른 작업(스크롤, 클릭 등)을 계속 처리할 수 있습니다.

### fetch와 HTTP 요청 라이브러리

#### `fetch`에서 네트워크 오류와 HTTP 오류를 따로 처리해야 하는 이유는 무엇일까요?

- **네트워크 오류 (Network Error):** 인터넷 끊김, CORS 오류, DNS 조회 실패 등으로 요청 자체가 서버에 도달하지 못한 경우이며, `fetch`는 이때만 Promise를 Reject합니다. (`.catch()`에서 포착)
- **HTTP 오류 (4xx, 5xx):** `404 Not Found`나 `500 Internal Server Error`처럼 서버에 요청은 잘 전달되었으나 서버가 에러 응답을 반환한 경우입니다.
- **따로 처리해야 하는 이유:** `fetch`는 404/500 에러 응답도 "네트워크 통신 자체는 성공"으로 간주해 Promise를 Resolve하기 때문에, 개발자가 반드시 `if (!response.ok)`로 HTTP 에러 상태를 별도로 직접 확인해야 합니다.

#### 순수 `fetch`로 여러 API 함수를 작성하면 어떤 설정과 처리가 반복될까요?

- **공통 URL & Header 중복:** API Base URL 및 `Authorization` 인증 토큰 헤더를 매 요청마다 반복 작성
- **반복적인 `response.ok` 검사:** 에러 처리를 위해 모든 요청마다 `if (!response.ok) throw new Error(...)` 작성
- **JSON 변환 연산:** 매 요청마다 `await response.json()`을 명시적으로 호출
- **쿼리 스트링 파싱:** `new URLSearchParams(...)`를 매번 수동으로 생성해 URL 뒤에 붙이는 작업

#### ky와 Axios는 JSON 응답을 읽고 공통 요청 처리를 추가하는 방식이 어떻게 다를까요?

- **ky (Fetch 기반의 경량 라이브러리)**
    - 브라우저 표준 `fetch` API를 내부적으로 확장해서 만들어졌으며 매우 가볍습니다.
    - **JSON 읽기:** `ky.get(...).json<T>()` 메서드를 호출해 JSON 파싱과 타입 추론을 한 번에 수행합니다.
    - **공통 처리:** `ky.create({ baseUrl, headers, hooks })` 인스턴스 옵션으로 공통 처리 및 인터셉터(hooks)를 설정합니다.
- **Axios (XHR 기반의 전통적 라이브러리)**
    - 과거의 `XMLHttpRequest`를 바탕으로 만들어진 별도의 HTTP 클라이언트입니다.
    - **JSON 읽기:** 응답 객체의 `response.data` 속성에 이미 자동으로 파싱된 JSON 객체가 담겨 옵니다.
    - **공통 처리:** `axios.create({ baseURL, headers })` 인스턴스 생성과 `axios.interceptors` 객체로 요청/응답 단계를 가로채 처리합니다.

### 비동기 데이터의 UI 상태

#### 서버 데이터를 보여주는 화면에서 로딩, 오류, 빈 결과와 성공 상태를 구분해야 하는 이유는 무엇일까요?

- **유저 경험(UX) 향상:** 비동기 작업은 언제 데이터가 도착할지 알 수 없으므로, 현재 진행 상황을 사용자에게 명확히 전달해야 불안감을 줄일 수 있습니다.
- **안정적 렌더링:** 데이터가 아직 없는데(`null` 또는 `undefined`) 화면을 그리려고 할 때 발생하는 런타임 에러를 방지합니다.

#### 각 상태를 사용자가 이해할 수 있게 표현하려면 어떤 정보와 동작이 필요할까요?

- **Loading:** "데이터를 가져오는 중이니 잠시만 기다려주세요."
- **Error:** 에러 메시지 + Retry 버튼 — 사용자가 원인을 파악하고 재시도할 수 있는 액션을 제공합니다.
- **Empty:** "검색 결과가 없습니다." 같은 안내 문구 — 시스템 오류가 아니라 요청 결과 데이터가 0건임을 명확히 구분해 줍니다.
- **Success:** 정상적인 데이터 목록/상세 카드를 렌더링합니다.

#### API 응답 타입과 화면에서 사용하는 타입을 분리하면 어떤 상황에서 도움이 될까요?

- **데이터 가공 및 변환 용이:** 백엔드/외부 API의 키 이름(`poster_path`)을 프론트엔드 컨벤션(`posterUrl`)으로 변환해 화면단에 깔끔하게 전달할 수 있고, 서버에서 받아온 이미지 상대경로(`/abc.jpg`)를 화면에서 바로 쓸 수 있는 완전한 CDN URL로 전처리할 수 있습니다.
- **API 변경에 대한 유지보수성:** 외부 API의 응답 스펙이 변경되더라도 어댑터 함수 내부의 변환 로직만 고치면 되고, UI 컴포넌트 전체를 수정하지 않아도 됩니다.
- **파생된 상태(Derived Data) 결합:** API 응답 데이터에 클라이언트 전역 상태를 결합해 UI 전용 데이터 객체로 만들어 쓰기 유용해집니다.
