- HTTP와 API
    - API, endpoint, HTTP method와 status code는 요청과 응답에서 각각 어떤 역할을 할까요?
    
    API는 프로그램끼리 데이터를 주고받는 약속이고, endpoint는 특정 기능에 접근하는 주소다. HTTP method는 수행할 작업을, status code는 서버가 처리한 결과를 나타낸다.
    
    실제 요청을 이해하려면 **주소에서 대상을 지정하는 부분과 조건을 지정하는 부분**을 구분하는 것이 좋다.
    
    | 요청 구성 | UMCine에서의 사용 | 의미 |
    | --- | --- | --- |
    | Path | /movie/969681 | 어떤 영화의 정보를 가져올지 지정 |
    | Query | language=ko-KR | 응답 언어와 같은 조회 조건 전달 |
    | Header | Authorization | 요청에 필요한 인증 정보 전달 |
    | Method | GET | 해당 정보를 조회 |
    | Status code | 200 | 요청이 성공적으로 처리됐음을 표시 |
    
    HTTP method에는 **멱등성**이라는 개념도 있다. 같은 요청을 여러 번 보내도 서버에 의도한 최종 효과가 한 번 보냈을 때와 같은 성질이다. 영화 목록을 GET으로 여러 번 조회해도 영화가 새로 생성되지는 않는다. 반면 리뷰를 생성하는 POST 요청을 중복 전송하면 리뷰가 두 개 등록될 수 있으므로 중복 제출에 주의해야 한다. 멱등성은 매번 응답 내용이 똑같다는 뜻은 아니다.
    
    - 브라우저와 API 서버의 origin이 다를 때 CORS는 어떤 역할을 할까요?
    
    Origin은 프로토콜, 호스트, 포트의 조합이다. **같은 컴퓨터에서 실행해도 포트가 다르면 서로 다른 origin**이다. 따라서 localhost의 5173 포트에서 실행한 프론트엔드와 8080 포트에서 실행한 백엔드 사이에도 CORS가 적용될 수 있다. 경로만 다른 경우에는 origin이 달라지지 않는다. 
    
    CORS는 서버가 허용한 범위를 브라우저가 확인하여 다른 origin의 응답을 프론트엔드 코드에 제공하는 방식이다. Authorization처럼 특정 헤더가 포함되면 브라우저가 **OPTIONS 요청으로 실제 요청의 허용 여부를 먼저 확인**할 수 있다. Network에 OPTIONS와 GET이 함께 보여도 영화 조회가 두 번 실행된 것은 아닐 수 있다. 
    
    CORS와 사용자 인증은 별개다. CORS가 허용되어도 토큰이 잘못되면 인증에 실패한다. 또한 Postman이나 서버 간 요청에는 브라우저의 동일 출처 제한이 그대로 적용되지 않으므로, **Postman에서는 성공하지만 브라우저에서는 실패하는 상황**이 발생할 수 있다. 이때는 API 주소와 토큰뿐 아니라 CORS 응답 헤더도 확인해야 한다.
    
- Promise와 비동기 처리
    - Promise의 pending, fulfilled와 rejected 상태는 각각 무엇을 의미할까요?
    
    Promise는 비동기 작업의 결과를 나타내는 객체다. 결과를 기다리는 동안은 pending, 결과값이 정해지면 fulfilled, 실패 이유가 정해지면 rejected가 된다. fulfilled와 rejected를 묶어서 **settled, 즉 결과가 확정된 상태**라고 부른다.
    
    한 번 결과가 정해진 Promise를 다시 pending으로 되돌릴 수는 없다. 같은 요청을 다시 실행하려면 요청 함수를 다시 호출해서 새로운 Promise를 만들어야 한다. 이미 만들어진 Promise에 then을 두 번 연결하는 것은 요청을 두 번 보내는 것과 다르다.
    
    또한 **fulfilled는 해당 Promise가 성공했다는 뜻이지, 화면에 필요한 모든 처리가 끝났다는 뜻은 아니다.** fetch의 Promise가 Response 객체를 반환한 뒤에도 응답 본문을 JSON으로 읽는 작업이 남아 있다. 따라서 응답을 받는 단계는 성공했지만 JSON 형식이 잘못되어 본문을 읽는 단계에서 실패할 수도 있다.
    
    - `.then().catch()`와 `async/await`는 같은 비동기 흐름을 어떻게 다르게 표현하나요?
    
    .then().catch()는 성공 후 실행할 작업과 오류 처리 작업을 연결해서 표현한다. async/await는 결과를 기다리는 지점을 await로 표시하여 코드를 위에서 아래로 읽을 수 있게 한다. 어느 방식을 사용하든 **결과를 다음 작업에 제대로 전달하고 오류를 어디에서 처리할지 정하는 것**이 중요하다.
    
    then 안에서 또 다른 비동기 요청을 실행한다면 그 Promise를 반환해야 다음 단계가 완료를 기다릴 수 있다. async/await에서는 기다려야 할 작업에 await를 붙인다. 영화 상세 정보를 받은 뒤 그 영화의 ID로 추가 정보를 요청해야 한다면, 첫 번째 결과를 받은 후 두 번째 요청을 실행하도록 연결해야 한다.
    
    catch에서 오류를 출력하고 일반 값을 반환하면 이후 흐름은 정상적으로 이어질 수 있다. 영화 요청에 실패했을 때 무조건 빈 배열을 반환하면, 화면에서는 **“요청 실패”를 “검색 결과 없음”으로 오해할 수 있다.** 화면에서 오류를 표시해야 한다면 오류를 전달하거나 별도의 오류 상태를 저장해야 한다.
    
    - `await`를 사용해도 브라우저 전체가 멈추지 않는 이유는 무엇일까요?
    
    await는 현재 async 함수의 다음 실행을 미루면서 실행권을 돌려준다. 네트워크 응답을 기다리는 동안 메인 스레드를 계속 점유하지 않으므로, 브라우저는 사용자 입력이나 화면 갱신 같은 다른 작업을 처리할 수 있다. 다만 async 함수 안에서도 긴 반복문이나 무거운 계산을 실행하면 메인 스레드가 바빠져 화면이 멈출 수 있다.
    
    **비동기로 작성했다고 해서 여러 요청이 자동으로 동시에 시작되는 것은 아니다.** 첫 번째 요청을 호출하고 await로 기다린 뒤 두 번째 요청을 호출하면 두 요청은 순서대로 진행된다.
    
    서로 독립적인 요청이라면 먼저 함께 시작하고 Promise.all로 결과를 기다릴 수 있다. 영화 상세 정보에 1초, 출연진 정보에 1초가 걸린다고 가정하면 순서대로 요청할 때는 약 2초가 필요하지만, 함께 시작하면 약 1초에 두 결과를 받을 수 있다. 다만 Promise.all은 하나라도 실패하면 전체 결과가 실패하며, 이미 실행 중인 나머지 작업을 자동으로 취소하지는 않는다.
    
- fetch와 HTTP 요청 라이브러리
    - `fetch`에서 네트워크 오류와 HTTP 오류를 따로 처리해야 하는 이유는 무엇일까요?
    
    fetch는 서버가 오류 상태를 응답하더라도 **응답을 받았다는 사실 자체는 성공으로 처리**한다. 따라서 401이나 404 응답을 받았다고 자동으로 catch로 이동하지 않는다. response.ok 또는 status를 확인하고 필요한 경우 직접 오류를 발생시켜야 한다. 
    
    오류를 구분하면 확인해야 할 원인도 달라진다.
    
    | 발생 상황 | 실패한 단계 | 확인할 내용 |
    | --- | --- | --- |
    | 인터넷 연결이나 DNS 문제 | 요청·연결 단계 | 네트워크 연결, 서버 주소 |
    | 401 응답 | 인증 처리 | 토큰 누락·오타·유효성 |
    | 404 응답 | 요청 대상 조회 | endpoint와 영화 ID |
    | 500 응답 | 서버 내부 처리 | 서버 오류 내용 |
    | 200 응답이지만 JSON 해석 실패 | 응답 본문 처리 | 실제 응답 형식과 내용 |
    
    이 구분은 재시도 여부를 판단할 때도 유용하다. 잠깐 끊긴 네트워크는 다시 요청하면 성공할 수 있지만, 잘못된 토큰이나 존재하지 않는 영화 ID는 같은 요청을 반복해도 해결되지 않는다.
    
    - 순수 `fetch`로 여러 API 함수를 작성하면 어떤 설정과 처리가 반복될까요?
    
    공통 API 주소, 인증 헤더, query 구성, HTTP 오류 검사, JSON 변환 등이 반복된다. 문제는 코드가 길어지는 것뿐 아니라 **같은 규칙을 여러 곳에서 각각 관리하게 된다는 점**이다. 토큰 설정을 한 파일에서만 수정하고 다른 파일에서는 빠뜨리면 목록은 정상인데 상세 화면만 실패할 수 있다.
    
    이를 줄이려면 공통 요청 설정과 개별 기능을 나눌 수 있다. 공통 클라이언트는 주소와 인증을 담당하고, getMovies나 searchMovies는 endpoint와 검색 조건을 담당하며, 화면 컴포넌트는 로딩과 오류 문구를 담당하는 식이다.
    
    **ky나 Axios를 설치해야만 공통화할 수 있는 것은 아니다.** fetch를 감싼 공통 함수를 직접 만들 수도 있다. 라이브러리는 이러한 반복 처리를 미리 제공해 주는 도구다.
    
    UMCine에서는 tmdbClient에 주소와 토큰을 설정했지만, 영화 목록과 상세 화면의 오류 문구는 각각 다르게 관리한다. 공통 요청 규칙은 공유하면서도 사용자가 보게 되는 설명은 화면의 목적에 맞추는 것이다.
    
    - ky와 Axios는 JSON 응답을 읽고 공통 요청 처리를 추가하는 방식이 어떻게 다를까요?
    
    둘 다 HTTP 요청의 반복 작업을 줄여 주지만, 결과를 꺼내는 위치와 설정 이름이 다르다.
    
    | 항목 | ky 2.x | Axios |
    | --- | --- | --- |
    | JSON 본문 읽기 | .json()의 결과 | 응답 객체의 data |
    | 공통 인스턴스 생성 | ky.create() | axios.create() |
    | 기본 주소 설정 | baseUrl | baseURL |
    | Query 설정 | searchParams | params |
    | 요청 전후 공통 처리 | hooks | interceptors |
    
    TMDB 응답 본문에 results가 있다면 ky의 .json()으로 받은 값에서는 results를 읽고, Axios 응답에서는 data.results를 읽는다. **Axios의 data는 TMDB가 추가한 필드가 아니라 Axios 응답 객체의 구조**다.
    
    공통 인스턴스에는 고정된 주소와 헤더를 설정하고, 요청 전후에 실행할 동작은 hooks나 interceptors에 둘 수 있다. 로그인 상태가 바뀔 때마다 최신 토큰을 넣거나 여러 요청의 오류를 공통으로 처리하는 데 활용할 수 있다. 
    
    두 라이브러리 모두 요청 처리를 도와주지만, **영화 목록의 로딩 표시나 검색 결과 유지 같은 React 화면 상태까지 자동으로 관리하지는 않는다.**
    
- 비동기 데이터의 UI 상태
    - 서버 데이터를 보여 주는 화면에서 로딩, 오류, 빈 결과와 성공 상태를 구분해야 하는 이유는 무엇일까요?
    
    데이터만 저장하면 현재 상황을 정확히 표현하기 어렵다. 영화 배열이 비어 있어도 아직 요청하지 않았을 수도 있고, 요청 중이거나 실패했을 수도 있으며, 실제 검색 결과가 없을 수도 있다. 따라서 **데이터의 값과 요청의 진행 상태를 함께 관리**해야 한다.
    
    여러 상태를 따로 관리할 때는 서로 모순되지 않게 바꾸는 것도 중요하다. 이전 요청의 오류 문구를 지우지 않고 새 요청을 시작하면 로딩 중인데 과거 오류가 함께 보일 수 있다. 새 요청을 시작할 때 오류를 초기화하고, 성공·실패가 확정되면 로딩을 종료하는 흐름이 필요하다.
    
    화면이 복잡해지면 처음 불러오는 상태와 기존 데이터를 갱신하는 상태를 나눌 수도 있다. 처음에는 영화 정보가 없으므로 로딩 화면이 필요하지만, **이미 목록이 있는 상태에서 새로 불러올 때는 기존 목록을 유지하면서 갱신 중임을 표시**할 수 있다. 같은 네트워크 요청 중이라도 사용자가 볼 수 있는 데이터가 있는지에 따라 적절한 화면이 달라진다.
    
    - 각 상태를 사용자가 이해할 수 있게 표현하려면 어떤 정보와 동작이 필요할까요?
    
    사용자가 화면을 보고 **현재 무슨 일이 일어나고 있으며 다음에 무엇을 할 수 있는지** 알 수 있어야 한다. 개발자에게 필요한 오류 정보와 사용자에게 보여 줄 안내는 다를 수 있다. “401 Unauthorized”를 그대로 보여주는 것보다 상황에 맞는 안내를 제공하고, 상세 원인은 개발자 도구에서 확인하도록 구분할 수 있다.
    
    | 상황 | 화면 표현 | 사용자가 할 수 있는 일 |
    | --- | --- | --- |
    | 검색어를 입력하지 않음 | “어떤 영화를 찾고 있나요?” | 검색어 입력 |
    | 검색 요청 진행 중 | “검색 결과를 불러오는 중이에요.” | 기다리거나 검색어 수정 |
    | 요청 성공, 결과 없음 | “‘입력한 검색어’에 해당하는 영화가 없어요.” | 다른 검색어로 검색 |
    | 상세 영화가 존재하지 않음 | “영화를 찾을 수 없어요.” | 영화 목록으로 이동 |
    | 이미지 정보만 없음 | 포스터 영역에 “이미지 없음” 표시 | 제목·줄거리 등 나머지 정보 확인 |
    
    검색 화면에서는 **응답이 도착하는 순서와 사용자가 요청한 순서가 다를 수 있다는 점**도 고려해야 한다. “스파이더맨”을 검색한 뒤 “인셉션”을 검색했는데 첫 요청이 늦게 도착하면 화면이 다시 스파이더맨 결과로 바뀔 수 있다. 이런 문제를 race condition이라고 한다. 이전 요청의 결과를 무시하는 정리 로직을 두면 현재 검색 결과가 덮어써지는 것을 막을 수 있다.
    
    - API 응답 타입과 화면에서 사용하는 타입을 분리하면 어떤 상황에서 도움이 될까요?
    
    서버 응답은 데이터를 전달하기 위한 구조이고, 화면은 사용자가 읽기 좋은 구조가 필요하다. API 응답 타입과 화면용 타입을 분리하면 **서버 형식이 여러 화면에 직접 퍼지는 것을 줄일 수 있다.**
    
    | 서버에서 받은 값 | 화면에서 필요한 값 |
    | --- | --- |
    | poster_path에 이미지 경로 | 전체 이미지 주소 |
    | runtime에 숫자 125 | “2시간 5분” |
    | genres에 장르 객체 배열 | “액션, 모험” |
    | release_date에 날짜 문자열 | 화면 디자인에 맞춘 날짜 표현 |
    | 이미지 경로에 null | 이미지 없음 영역 |
    
    여러 화면이 같은 형식의 영화 카드를 사용한다면, 변환 과정을 한곳에 모아 둘 수 있다. 이후 서버의 필드 이름이 바뀌더라도 변환 부분을 수정하여 화면에 미치는 영향을 줄일 수 있다. 다만 화면이 단순하고 가공할 값이 적다면 처음부터 모든 타입을 분리할 필요는 없다.
    
    **타입 선언과 실제 데이터 검증도 구분해야 한다.** TypeScript에 숫자 타입을 적거나 타입 단언을 사용한다고 서버가 보낸 문자열이 숫자로 바뀌지는 않는다. 잘못된 응답을 실행 중에 확인하려면 별도의 검사 과정이 필요하다. 
    
    또한 서버에서 받은 영화 정보와 사용자가 선택한 북마크 상태는 변경되는 이유가 다르다. UMCine처럼 영화 ID로 두 정보를 연결하면 API 데이터를 새로 받아도 사용자의 북마크를 별도로 유지할 수 있다.
