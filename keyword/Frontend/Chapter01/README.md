# Frontend Chapter01

## 키워드 정리

- TypeScript와 정적 타입 검사
    - JavaScript와 비교했을 때 TypeScript는 오류를 언제, 어떤 방식으로 확인하나요?
        - JavaScript는 코드가 실제로 실행되는 시점에 오류를 발견하는 반면, TypeScript는 코드가 실행되기 전 정적 분석 단계에서 문법 오류와 타입 오류를 검사한다
        - 문법 오류는 파싱 단계에서 발견될 수 있으며, 타입 오류는 타입 검사 단계에서 추가로 확인된다
    - 컴파일 타임 오류와 런타임 오류는 어떤 차이가 있나요?
        - 컴파일 타임 오류는 코드가 실행되기 전 컴파일러 또는 타입 검사 단계에서 찾는 문제이고, 런타임 오류는 실제 JavaScript가 실행되는 동안 발생한다
        - 컴파일 타임 오류는 항상 타입 오류만을 뜻하지 않으며, JavaScript로 변환되는 과정에서 문법이나 설정 문제도 발견될 수 있다
        - 런타임 오류는 실제 값을 계산하거나 함수 호출을 수행할 때 발생하며, console에 결과를 출력하는 과정에서도 나타날 수 있다
    - TypeScript의 타입 정보가 실행되는 JavaScript에 남지 않는 이유는 무엇일까요?
        - TypeScript의 타입 어노테이션, `interface`, `type` alias는 보통 JavaScript로 emit될 때 제거되므로 런타임에는 타입 정보가 남지 않는다
        - 다만 `enum`, 데코레이터, 일부 메타데이터 기능처럼 런타임 자바스크립트 코드로 변환되는 TypeScript 구문도 존재한다

- 타입 추론과 타입 모델링
    - TypeScript가 타입을 추론하도록 두는 경우와 타입을 직접 작성하는 경우는 각각 언제 알맞을까요?
        - TypeScript는 초기화된 값, 함수의 반환값 등을 매우 정확하게 추론함. 불필요한 타입 명시를 줄이면 코드가 간결해지고 유지보수가 쉬워짐
        - 코드의 안정성을 확보하거나 TypeScript가 내 의도를 알지 못할 때 직접 작성해주어야함
    - 객체와 함수의 형태를 타입으로 표현하면 어떤 실수를 미리 찾을 수 있을까요?
        - 객체 타입을 잘못 정의하거나 필수 속성을 누락했을 때
        - 함수 선언 시 인자 오류나 반환값 오류
    - `type`과 `interface`는 표현 범위와 확장 방식에서 어떤 차이가 있을까요?
        - 둘 다 객체의 형태를 설명할 수 있지만, `interface`는 선언 병합과 `extends`를 지원하며 객체 구조를 확장하는 데 적합하다
        - `type`은 원시 타입, 유니온, 인터섹션, 튜플 등 더 넓은 타입 표현에 적합하며, 선언 병합은 지원하지 않는다
        - 선택 기준으로는 객체 형태를 확장하고 합치고 싶다면 `interface`, 복합 타입을 조합해야 한다면 `type`을 고려하는 것이 좋다

- 유니언 타입과 타입 좁히기
    - 여러 타입 중 하나가 될 수 있는 값을 유니언 타입으로 표현하면 어떤 장점이 있나요?
        - 허용되지 않은 타입을 차단하고
        - 타입 좁히기를 통해 예외 처리하지 않고 추론할 수 있다
    - 조건문, `typeof`와 판별 프로퍼티는 타입을 어떻게 좁히나요?
        - 조건문은 값의 존재 여부와 참/거짓 여부를 기준으로 타입을 더 구체적으로 좁힐 수 있다
        - `typeof`는 변수의 런타임 타입을 문자열로 반환하며, 예를 들어 `"string"`, `"number"`, `"boolean"` 등을 판별한다
        - 여러 객체 타입이 묶인 유니온 타입일 때, 공통 프로퍼티를 이용하거나 각 객체가 갖는 고유한 리터럴 값을 비교해 타입을 구분한다
        - 단, `if (value)`는 `null`/`undefined`만 검증하는 것이 아니라 `0`, `""`, `false`, `NaN`도 거짓으로 처리하므로 널 체크와 동일하지 않다
        - `strictNullChecks`를 켜두면 null/undefined 처리 여부를 타입 시스템이 강제하며, 사용자 정의 타입 가드 `value is T`로 더 명확하게 타입을 좁힐 수 있다
    - `null`과 `undefined`가 포함된 값을 안전하게 다룰 때 옵셔널 체이닝과 널 병합 연산자는 어떤 역할을 하나요?
        - 옵셔널 체이닝: 좌측 값이 null 혹은 undefined이면 에러를 내지 않고 undefined를 반환
        - 널 병합 연산자: 좌측 값이 null 또는 undefined이면 우측의 기본값을 반환하고, 아니면 좌측의 원래 값을 반환

- 타입 안전성과 제네릭
    - `any`와 `unknown`은 타입 검사를 허용하는 방식이 어떻게 다른가요?
        - any는 타입 검사를 완전히 비활성화하고, unknown은 모든 타입을 허용하지만 사용하기 전 타입 검사를 강제한다
    - 여러 타입을 받을 때 `unknown`과 제네릭은 각각 어떤 상황에 알맞을까요?
        - unknown은 어떤 값이 들어올지 전혀 알 수 없을 때 사용하고,
        - 제네릭은 어떤 값이 들어올지는 모르지만 그 타입을 유지하고 추적해야할 때 사용한다
    - 제네릭은 입력 타입과 출력 타입의 관계를 어떻게 유지하나요?
        - 제네릭이 항상 입력과 출력의 관계를 보장하는 것은 아니며, `T`가 반환 타입이나 다른 연관된 타입 위치에 사용될 때만 관계가 유지된다
        - 예를 들어 `function f<T>(value: T): T`는 입력 타입을 반환 타입에 연결하지만, `function f<T>(value: T): number`는 입력 타입을 출력 타입으로 전달하지 않는다
        - 컴파일러는 함수를 호출할 때 인자의 타입을 추론하여 `T`를 고정하므로, 관계를 연결한 제네릭 함수는 안전하게 동작한다
