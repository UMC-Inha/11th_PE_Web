- 프레임워크의 역할
    - Next.js는 TanStack Router에 더해 어떤 기능을 제공하나요?
    
    TanStack Router는 URL과 화면을 연결하고, 경로에 필요한 데이터를 불러오며, 페이지 이동을 관리하는 라우팅 라이브러리다. Next.js는 이러한 라우팅 기능과 함께 서버 실행, 렌더링, 캐시, 최적화 등을 하나의 구조로 제공하는 React 기반 프레임워크다.
    
    **프레임워크의 역할은 기능을 제공하는 것과 함께, 여러 기능을 어떤 구조와 규칙으로 연결할지 정하는 데 있다.** 개발자가 기능마다 도구를 선택하고 연결해야 하는 부담을 줄이는 대신, 프레임워크가 정한 실행 방식과 제약을 이해해야 한다.
    
    | 구분 | TanStack Router | Next.js |
    | --- | --- | --- |
    | 기본 역할 | 경로, 페이지 이동, URL 상태를 관리하는 라우팅 라이브러리다. | 라우팅부터 서버 실행과 렌더링까지 통합하는 프레임워크다. |
    | 데이터 로딩 | 경로별 loader, 미리 불러오기, 외부 데이터 관리 도구와의 연동 등을 지원한다. | Server Component의 데이터 조회와 캐시, 스트리밍 등을 함께 구성할 수 있다. |
    | 서버 렌더링 | SSR을 지원하며 필요한 서버 실행 구성을 연결할 수 있다. | 서버 렌더링과 정적 생성, 페이지 갱신 기능을 프레임워크 안에서 제공한다. |
    | 서버 기능 | 라우터 자체의 범위를 넘어서는 서버 기능은 별도로 구성한다. | Route Handler와 Server Function 등을 통해 요청 처리와 데이터 변경을 구현할 수 있다. |
    | 화면 최적화 | 필요한 도구를 선택해 조합한다. | 이미지·폰트 최적화와 메타데이터 설정 등을 통합해 제공한다. |
    
    TanStack Router에도 SSR 지원이 있으므로 서버 렌더링을 Next.js만의 기능으로 이해해서는 안 된다. 차이는 서버 렌더링의 지원 여부뿐 아니라, 서버와 브라우저의 코드를 구성하고 빌드·배포하는 과정까지 얼마나 함께 제공하는지에 있다.
    
    TanStack Router를 기반으로 서버 렌더링, 서버 함수, 빌드 구성 등을 통합한 별도의 풀스택 프레임워크로 TanStack Start도 있다. 따라서 TanStack Router와 TanStack Start는 구분해서 이해해야 한다.
    
    Next.js를 사용한다고 해서 기존 백엔드를 반드시 대체해야 하는 것도 아니다. 예를 들어 Spring 서버가 회원 관리와 핵심 업무 로직을 담당하고, Next.js가 화면을 구성하거나 화면에 필요한 데이터를 조회하도록 역할을 나눌 수 있다. 여러 백엔드의 응답을 화면에 맞게 조합하는 BFF 역할로 활용할 수도 있다.
    
    또한 Next.js의 서버 데이터 처리와 TanStack Query의 클라이언트 데이터 관리는 함께 사용할 수 있다. 서버에서 첫 화면에 필요한 데이터를 준비하고, 브라우저에서는 목록 갱신이나 무한 스크롤, 낙관적 업데이트 등을 관리하는 식으로 역할을 나눌 수 있다.
    
    - 고객 대상 서비스와 사내 서비스 등 상황이 달라져도 Next.js가 항상 가장 좋은 선택일까요?
    
    Next.js가 항상 가장 좋은 선택인 것은 아니다. 서비스의 목적과 데이터 특성, 팀의 경험, 배포 환경을 함께 고려해야 한다.
    
    | 상황 | 선택할 때 중요하게 볼 기준 |
    | --- | --- |
    | 검색으로 유입되는 영화 상세·상품·콘텐츠 페이지 | 검색 노출, 링크 공유 정보, 첫 화면의 콘텐츠 제공, 캐시 활용이 중요하다. |
    | 로그인 후 사용하는 사내 관리 화면 | 검색 노출보다 복잡한 입력, 표 편집, 필터, 기존 API 연동이 중요할 수 있다. |
    | 사용자별 정보를 많이 보여주는 서비스 | 인증 정보를 어디에서 처리할지, 사용자별 데이터를 어떻게 조회하고 갱신할지 고려해야 한다. |
    | 이미 안정적으로 운영 중인 서비스 | 도입 효과뿐 아니라 마이그레이션 비용, 기존 코드와의 호환성, 팀의 운영 경험을 고려해야 한다. |
    
    영화 상세 페이지처럼 공개된 콘텐츠를 검색 엔진과 사용자에게 빠르게 제공해야 한다면 Next.js의 렌더링과 메타데이터 기능을 활용하기 좋다. 반면 기존 백엔드 API를 사용하면서 브라우저 상호작용이 중심인 관리 화면이라면 Vite, React, TanStack Router를 조합한 구조도 충분한 선택지가 될 수 있다.
    
    다만 사내 서비스라는 이유만으로 Next.js가 불필요하다고 단정할 수는 없다. 서버에서 인증 정보를 처리하거나 여러 API의 응답을 조합해야 하는 경우, 또는 팀이 Next.js에 익숙한 경우에는 사내 서비스에서도 활용할 이유가 있다.
    
    **도구를 선택할 때는 기능의 수보다 현재 서비스에서 실제로 필요한 기능과 운영 부담을 비교해야 한다.** 서버 기능을 사용한다면 서버 실행 환경과 캐시 갱신 방식까지 이해해야 한다. 통합 기능이 개발을 편리하게 만드는 만큼, 문제가 발생했을 때 어느 환경과 처리 단계에서 발생했는지도 구분할 수 있어야 한다.
    
- Server Component와 Client Component
    - 어떤 기준으로 Server Component와 Client Component를 나누면 좋을까요?
    
    컴포넌트는 필요한 실행 환경과 기능을 기준으로 나누는 것이 좋다.
    
    | 필요한 작업 | 적합한 위치 |
    | --- | --- |
    | 서버에서 API나 DB에 접근해 데이터를 조회한다. | Server Component |
    | 서버에 보관된 비공개 환경 변수를 사용한다. | Server Component |
    | 데이터를 가공해 화면에 표시할 내용을 준비한다. | Server Component |
    | 클릭, 입력, 드래그와 같은 사용자 이벤트를 처리한다. | Client Component |
    | useState로 상태를 변경하거나 useEffect를 사용한다. | Client Component |
    | localStorage, window 등 브라우저 API를 사용한다. | Client Component |
    
    **화면에 데이터가 표시된다는 이유만으로 Client Component가 필요한 것은 아니다.** 서버에서 데이터를 조회한 뒤 그 결과를 화면에 표시하는 작업은 Server Component로 처리할 수 있다. 사용자의 행동에 따라 브라우저 안에서 상태를 바꾸거나 이벤트를 처리해야 하는 부분을 Client Component로 분리하면 된다.
    
    예를 들어 영화 상세 화면에서 제목, 줄거리, 출연진을 표시하는 부분은 서버에서 준비할 수 있다. 즐겨찾기 버튼, 별점 입력, 리뷰 작성 폼처럼 사용자와 상호작용하는 부분은 클라이언트에서 처리할 수 있다.
    
    Server Component는 정적인 내용만 담당하는 컴포넌트가 아니다. 요청을 받은 뒤 로그인한 사용자의 정보를 읽거나 최신 데이터를 조회해 화면을 만드는 경우에도 사용할 수 있다. Server와 Client의 구분은 화면의 내용이 바뀌는지보다 어떤 환경에서 어떤 기능을 실행하는지에 관한 구분이다.
    
    서버에서 클라이언트로 데이터를 전달할 때는 props가 React가 지원하는 방식으로 직렬화될 수 있어야 한다. 문자열, 숫자, 배열, 일반 객체와 같은 데이터를 전달할 수 있지만, 서버에서 만든 일반적인 이벤트 핸들러를 그대로 넘기는 방식은 사용할 수 없다. 클릭 이벤트는 Client Component 안에서 정의하는 것이 기본이며, Server Function 호출은 별도로 지원되는 방식이다.
    
    또한 서버에서 조회한 데이터라도 Client Component의 props로 전달하면 브라우저로 넘어간다. 따라서 서버에서만 사용해야 하는 값까지 객체 전체에 포함해 전달하지 않도록 하고, 화면에서 필요한 필드를 골라 전달하는 것이 좋다.
    
    - `"use client";` 지시어를 `page.tsx` 최상단에 선언해도 될까요?
    
    page.tsx 최상단에 `"use client"`를 선언해도 된다. 페이지의 주된 역할이 사용자 입력과 상호작용이라면 Client Component로 구성할 수 있다.
    
    다만 다음과 같은 영향을 고려해야 한다.
    
    - 해당 파일에서 불러오는 컴포넌트와 연결된 실행 코드가 클라이언트 코드에 포함될 수 있다.
    - 서버 전용 기능을 해당 컴포넌트에서 직접 사용할 수 없다.
    - 같은 파일에서 metadata나 generateMetadata를 export할 수 없다.
    - Client Component 함수 자체를 async 함수로 선언할 수 없다.
    
    마지막 항목은 클라이언트에서 비동기 작업을 할 수 없다는 뜻은 아니다. 버튼의 이벤트 핸들러에서 API를 호출하거나 클라이언트 데이터 요청 도구를 사용하는 것은 가능하다. 컴포넌트 함수 자체에 async를 붙이는 것과 내부에서 비동기 작업을 수행하는 것은 구분해야 한다.
    
    페이지에 서버에서 처리할 내용이 많다면 page.tsx는 Server Component로 유지하고, 상태와 이벤트가 필요한 부분을 별도 파일로 분리하는 구성이 적합하다. 이렇게 하면 브라우저에서 실행할 필요가 없는 코드까지 클라이언트로 전달하는 일을 줄일 수 있다.
    
    여기서 중요한 점은 **클라이언트 경계가 화면상의 부모·자식 관계만으로 결정되는 것은 아니라는 점이다.**`"use client"`는 해당 파일과 그 파일에서 import하는 의존 관계에 영향을 준다. 반면 Server Component에서 만든 내용을 Client Component의 children으로 전달하는 구성은 가능하다.
    
    app/components/detail-panel.tsx
    
    ```tsx
    "use client";
    
    import { useState, type ReactNode } from "react";
    
    export default function DetailPanel({
      children,
    }: {
      children: ReactNode;
    }) {
      const [open, setOpen] = useState(false);
    
      return (
        <section>
          <button onClick={() => setOpen((value) => !value)}>
            {open ? "상세 정보 닫기" : "상세 정보 보기"}
          </button>
          {open && children}
        </section>
      );
    }
    ```
    
    app/page.tsx
    
    ```tsx
    import DetailPanel from "./components/detail-panel";
    
    function MovieDetails() {
      return <p>영화의 줄거리와 출연진 정보를 표시한다.</p>;
    }
    
    export default function Page() {
      return (
        <DetailPanel>
          <MovieDetails />
        </DetailPanel>
      );
    }
    ```
    
    DetailPanel은 열림 상태와 클릭 이벤트를 관리하므로 Client Component다. MovieDetails는 Server Component인 Page에서 만들고 children으로 전달하므로 서버에서 처리할 수 있다.
    
    이 구조에서는 DetailPanel이 MovieDetails를 직접 import하지 않는다. 화면상으로 Client Component 안에 들어가 있어도 내부 콘텐츠까지 자동으로 클라이언트 코드가 되는 것은 아니다.
    
    또한 버튼을 누르는 순간 MovieDetails를 서버에서 처음 실행하는 구조도 아니다. 서버에서 준비해 전달한 콘텐츠의 표시 여부를 클라이언트 상태로 바꾸는 구조다.
    
- 렌더링 방식
    - `"use client";` 지시어가 붙은 Client Component는 브라우저에서만 렌더링될까요?
    
    Client Component도 첫 화면을 보여주기 위한 HTML을 서버에서 만드는 과정에 참여할 수 있다. 따라서 `"use client"`가 붙었다는 이유만으로 해당 컴포넌트의 모든 코드가 브라우저에서만 실행된다고 생각하면 안 된다.
    
    처음 페이지에 접근하는 과정은 다음과 같이 이해할 수 있다.
    
    1. 서버가 처음 보여줄 HTML을 준비한다. 이 과정에는 Client Component의 초기 화면도 포함될 수 있다.
    2. 브라우저가 전달받은 HTML을 표시하고 필요한 JavaScript를 불러온다.
    3. React가 기존 HTML에 이벤트와 상태 동작을 연결해 상호작용할 수 있도록 만든다.
    
    세 번째 과정을 하이드레이션이라고 한다. 사용자가 버튼을 볼 수 있는 시점과, JavaScript가 연결되어 해당 버튼이 동작하는 시점은 다를 수 있다.
    
    브라우저에는 window와 localStorage가 있지만 서버에는 없다. 따라서 Client Component의 함수 본문에서 localStorage를 바로 읽으면 서버에서 초기 화면을 만드는 과정에 오류가 발생할 수 있다. 브라우저에서만 알 수 있는 값은 이벤트 핸들러나 useEffect처럼 브라우저에서 실행되는 시점에 읽어야 한다.
    
    ```tsx
    "use client";
    
    import { useEffect, useState } from "react";
    
    export default function RecentSearch() {
      const [keyword, setKeyword] = useState("");
    
      useEffect(() => {
        setKeyword(localStorage.getItem("recentSearch") ?? "");
      }, []);
    
      return (
        <p>
          {keyword ? `최근 검색어: ${keyword}` : "최근 검색어 없음"}
        </p>
      );
    }
    ```
    
    이 코드는 서버와 브라우저의 첫 렌더링에서 모두 빈 문자열을 초기 상태로 사용한다. 이후 브라우저에서 useEffect가 실행되면 저장된 검색어를 읽어 화면을 갱신한다.
    
    **하이드레이션에서는 서버가 만든 HTML과 브라우저의 첫 렌더링 결과가 일치해야 한다.** 단순히 `typeof window !== "undefined"`로 분기해 서버 오류를 피하더라도, 서버에서는 없는 내용을 브라우저의 첫 렌더링에서 바로 표시하면 불일치가 발생할 수 있다.
    
    또한 Client Component가 초기 HTML 생성에 참여한다고 해서 그 안에서 나중에 조회하는 데이터까지 모두 초기 HTML에 들어가는 것은 아니다. useEffect에서 API를 호출한다면 해당 데이터는 브라우저가 실행된 뒤에 도착한다. 처음부터 데이터가 포함된 화면이 필요하다면 서버에서 데이터를 준비해 전달하는 방식 등을 고려해야 한다.
    
    - SSR과 SSG를 더 정리해 보고, ISR과 ISSG가 각각 어떤 의미로 쓰이는지 조사해 보세요. 페이지 생성 시점과 렌더링 방식을 기준으로 서로 어떤 관계가 있는지도 살펴보세요.
    
    SSR, SSG, ISR은 페이지를 언제 만들고, 만들어진 결과를 어떻게 재사용하거나 갱신하는지에 초점을 맞춘 개념이다. Server Component와 Client Component는 코드의 실행 경계에 관한 구분이므로 서로 다른 기준이다.
    
    | 방식 | 페이지 생성 시점 | 결과의 재사용과 갱신 | 활용 예시 |
    | --- | --- | --- | --- |
    | SSR | 요청을 받은 뒤 서버에서 화면을 생성한다. | 요청에 맞는 화면을 생성하며, 데이터 캐시는 별도로 활용할 수 있다. | 사용자별 정보가 필요한 페이지 |
    | SSG | 일반적으로 빌드할 때 페이지를 미리 생성한다. | 생성한 결과를 여러 요청에서 재사용한다. | 소개 페이지, 변경이 적은 안내 문서 |
    | ISR | 미리 생성하거나 요청 시 생성한 정적 결과를 활용한다. | 전체 사이트를 다시 빌드하지 않고 필요한 결과를 갱신한다. | 주기적으로 내용이 바뀌는 상품·콘텐츠 페이지 |
    | ISSG | 빌드 이후에도 필요한 페이지를 점진적으로 생성한다는 의미로 쓰인다. | 처음 요청된 경로의 결과를 생성해 이후 요청에서 재사용하는 동작을 강조한다. | 페이지 수가 매우 많은 영화 상세 서비스 |
    
    **SSR은 요청 시점의 화면 생성에 초점을 둔다.**
    
    SSR은 Server-Side Rendering의 약자다. 요청이 들어온 뒤 서버에서 해당 요청에 필요한 화면을 생성한다. 로그인 정보나 요청 조건에 따라 다른 내용을 보여주는 경우에 활용할 수 있다.
    
    다만 SSR을 사용한다고 해서 조회하는 모든 데이터가 항상 최신이라는 뜻은 아니다. 화면을 요청 시점에 생성하더라도 데이터 조회 과정에서 캐시를 사용하면 캐시된 데이터를 바탕으로 화면을 만들 수 있다. 화면의 생성 시점과 데이터의 갱신 시점은 따로 생각해야 한다.
    
    **SSG는 요청 전에 결과를 준비해 재사용하는 데 초점을 둔다.**
    
    SSG는 Static Site Generation의 약자다. 일반적으로 빌드 과정에서 페이지를 미리 생성하므로, 요청이 들어왔을 때 이미 준비된 결과를 전달할 수 있다.
    
    여기서 정적이라는 표현은 버튼이 동작하지 않거나 화면을 변경할 수 없다는 뜻이 아니다. 미리 생성한 페이지에서도 Client Component를 통해 입력, 상태 변경, API 요청과 같은 상호작용을 구현할 수 있다. 정적인 것은 주로 초기 화면을 준비하는 방식이다.
    
    또한 동적 경로와 동적 렌더링은 서로 다른 개념이다. `[id]`는 URL에 따라 값이 달라지는 경로라는 의미이며, 해당 페이지를 반드시 요청마다 새로 생성한다는 뜻은 아니다.
    
    예를 들어 app/movies/[id]/page.tsx에서 다음과 같이 미리 처리할 ID를 지정할 수 있다.
    
    ```tsx
    export function generateStaticParams() {
      return [{ id: "550" }, { id: "551" }];
    }
    ```
    
    이 함수는 영화 ID 550과 551에 해당하는 경로를 빌드 시점에 준비할 수 있도록 한다. 다만 해당 페이지가 요청 시점의 정보나 캐시하지 않은 데이터를 추가로 읽는다면, 그 영역은 별도의 동적 처리가 필요할 수 있다.
    
    따라서 폴더 이름에 대괄호가 있거나 컴포넌트가 async 함수라는 사실만으로 SSR이라고 판단해서는 안 된다.
    
    **ISR은 정적 결과를 유지하면서 필요한 부분을 다시 갱신하는 방식이다.**
    
    ISR은 Incremental Static Regeneration의 약자다. 정적으로 생성된 결과의 빠른 응답을 활용하면서, 내용이 바뀌었을 때 사이트 전체를 다시 빌드하지 않고 필요한 페이지나 캐시를 갱신한다.
    
    예를 들어 영화의 소개나 포스터처럼 모든 사용자에게 공통으로 보이는 정보는 캐시해 재사용하고, 일정 시간이 지난 뒤 새 정보로 갱신하도록 구성할 수 있다.
    
    시간 기반 갱신에서 재검증 간격을 60초로 설정했다고 해서 서버가 정확히 60초마다 자동 작업을 실행하는 것은 아니다. 기존 결과를 제공하면서 백그라운드에서 갱신하는 방식에서는, 시간이 지난 뒤 요청이 들어왔을 때 재검증을 시작하고 새 결과가 준비된 이후의 요청부터 갱신된 내용을 제공할 수 있다.
    
    따라서 갱신 간격이 지났다는 사실과 모든 사용자가 즉시 최신 결과를 받는다는 것은 다르다. 데이터 변경 직후 반영이 필요한 경우에는 변경 작업과 연결해 캐시를 무효화하거나 갱신하는 방식도 고려해야 한다.
    
    **ISSG는 필요한 정적 페이지를 점진적으로 생성한다는 의미를 강조하는 표현이다.**
    
    ISSG는 Incremental Static Site Generation이라는 뜻으로 쓰이며, 자료에 따라 Incremental Static Generation을 가리키기도 한다.
    
    예를 들어 영화가 수십만 개 있다면 모든 상세 페이지를 빌드할 때 생성하는 데 시간이 오래 걸릴 수 있다. 자주 방문하는 영화만 먼저 생성하고, 나머지는 실제 요청이 들어왔을 때 생성해 재사용하는 식으로 필요한 페이지를 점진적으로 늘릴 수 있다.
    
    다만 ISSG는 Next.js에서 ISR과 분리된 독립 모드명으로 일관되게 사용하는 용어는 아니다. 현재 ISR 기능 설명에는 기존 페이지의 갱신뿐 아니라, 구성에 따라 미리 만들지 않은 경로를 요청 시점에 생성하는 동작도 포함된다.
    
    따라서 ISSG는 추가 생성만 담당하고 ISR은 기존 페이지 수정만 담당한다고 엄격하게 나누기보다, 다음 두 가지를 구분하는 것이 좋다.
    
    - 처음 생성할 때는 모든 페이지를 미리 만들지, 필요한 페이지를 요청 시점에 만들지 결정한다.
    - 생성한 뒤에는 결과를 계속 재사용할지, 언제 어떤 조건으로 갱신할지 결정한다.
    
    **하나의 페이지에서도 생성 시점은 섞일 수 있다.**
    
    예를 들어 공통 헤더와 영화 소개는 미리 준비하고, 로그인한 사용자의 즐겨찾기 여부는 요청을 받은 뒤 준비할 수 있다. Partial Prerendering은 이러한 정적인 부분을 먼저 제공하고, 동적인 부분을 준비되는 대로 전달하는 방식이다.
    
    이때 Suspense는 준비 중인 영역의 대체 화면과 전달 경계를 구성하는 데 사용한다. Suspense로 감쌌다는 사실만으로 해당 부분이 동적 렌더링으로 바뀌는 것은 아니며, 요청 시점의 데이터가 필요한지와 캐시 설정 등을 함께 확인해야 한다.
    
    Cache Components를 활성화한 환경에서는 캐시할 범위를 `"use cache"`로 지정하고, 캐시 유지와 갱신 정책을 cacheLife 등으로 설정한다. 기존 방식의 `export const revalidate` 같은 설정과 사용 방식이 다르므로, 렌더링 예제를 적용할 때는 프로젝트의 캐시 설정도 함께 확인해야 한다.
