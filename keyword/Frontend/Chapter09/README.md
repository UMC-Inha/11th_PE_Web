# Frontend Chapter09

## 키워드 정리

### 프레임워크의 역할

#### Next.js는 TanStack Router에 더해 어떤 기능을 제공하나요?

**TanStack Router**

- React 애플리케이션의 라우팅을 중심으로 하는 라이브러리. 타입 안전한 경로·검색 파라미터와 라우트별 데이터 로딩 지원.

**Next.js**

- 라우팅뿐 아니라 서버 렌더링, 정적 생성, 캐시 재검증, 서버 엔드포인트, 이미지·폰트 최적화, 메타데이터 관리까지 제공하는 React 프레임워크.

**관계**

- Next.js가 TanStack Router 위에 기능을 추가하는 구조는 아님.
- TanStack Router 자체도 SSR을 지원하며, 풀스택 프레임워크끼리 비교할 때는 Next.js와 TanStack Start가 더 적절한 비교 대상.

#### 고객 대상 서비스와 사내 서비스 등 상황이 달라져도 Next.js가 항상 가장 좋은 선택일까요?

서비스 유형만으로 결정하기 어렵다. 필요한 렌더링 방식과 배포·운영 비용을 함께 고려해야한다.

| 고려 기준 | Next.js가 적합할 수 있는 경우 | SPA 구성이 더 단순할 수 있는 경우 |
| --- | --- | --- |
| 검색 노출과 초기 HTML | 공개 페이지의 검색 노출이나 초기 HTML이 중요 | 로그인 이후 화면이 중심이고 검색 노출이 불필요 |
| 서버 기능 | 프런트엔드에서도 서버 렌더링, 캐시 재검증 등이 필요 | 기존 API를 호출하고 브라우저에서 화면을 구성하는 것으로 충분 |
| 배포와 운영 | 서버 기능에서 얻는 이점이 운영 비용보다 큼 | 정적 파일 배포만으로 요구사항 충족 가능 |

**판단 기준**

- 고객용인지 사내용인지보다 초기 HTML이 필요한지,
- 기존 백엔드와 역할을 어떻게 나눌지,
- 서버를 운영할 이유가 있는지가 중요.

### Server Component와 Client Component

#### 어떤 기준으로 Server Component와 Client Component를 나누면 좋을까요?

| 구분 | 선택 기준 |
| --- | --- |
| Server Component | 서버에서 데이터에 접근하거나 비밀 키 같은 서버 전용 정보를 사용해야 하는 경우. 별도의 브라우저 상태나 이벤트 처리 없이 결과를 표시하는 경우에도 적합 |
| Client Component | `useState`, `useEffect`, 클릭 이벤트, 브라우저 API처럼 브라우저에서 실행할 동작이 필요한 경우 |

기본 구분: App Router의 `page.tsx`와 `layout.tsx`는 기본적으로 Server Component.

**분리 기준**

- 페이지 전체가 아니라 상호작용이 필요한 범위를 기준으로 Client Component 경계 설정.
- 서버에서 처리할 부분을 유지하면서 브라우저로 보내는 JavaScript 범위를 줄일 수 있음.

#### `"use client";` 지시어를 `page.tsx` 최상단에 선언해도 될까요?

선언 가능하다. 다만 해당 파일이 클라이언트 모듈의 경계가 되므로, 그 파일이 가져오는 모듈도 클라이언트 모듈 그래프에 포함.

**제약**

- 해당 `page.tsx`에서 서버 전용 모듈을 직접 사용할 수 없고, `metadata`나 `generateMetadata`도 내보낼 수 없음.

**선택 기준**

- 페이지 대부분이 상호작용 중심이라면 페이지 단위로 선언 가능.
- 서버 데이터 조회와 상호작용이 섞여 있다면 페이지는 Server Component로 두고 필요한 부분만 분리하는 편이 적절.

**주의**

- 이 선언이 상위 `layout.tsx`까지 Client Component로 바꾸는 것은 아님.

### 렌더링 방식

#### `"use client";` 지시어가 붙은 Client Component는 브라우저에서만 렌더링될까요?

아니다. 일반적인 첫 페이지 로드에서는 Client Component도 서버에서 초기 HTML을 미리 만드는 과정에 참여. 이후 브라우저에서 해당 컴포넌트의 JavaScript를 실행하고, 하이드레이션을 통해 이벤트 처리 등 상호작용을 연결.

- `"use client";`의 의미: 브라우저에서 실행할 수 있는 컴포넌트의 경계 선언.
- 의미하지 않는 것: SSR 비활성화 또는 브라우저에서만 렌더링.
- 주의: 최초 렌더링에 서버가 관여할 수 있으므로 `window`, `localStorage` 등은 `useEffect`나 이벤트 핸들러처럼 브라우저에서 실행되는 시점에 접근.

#### SSR과 SSG를 더 정리해 보고, ISR과 ISSG가 각각 어떤 의미로 쓰이는지 조사해 보세요. 페이지 생성 시점과 렌더링 방식을 기준으로 서로 어떤 관계가 있는지도 살펴보세요.

| 용어 | 페이지 생성 시점 | 생성 결과의 활용 |
| --- | --- | --- |
| SSR — Server-Side Rendering | 이 비교에서는 요청 시점에 서버에서 HTML 생성 | 요청 시점의 데이터나 사용자별 조건 반영 |
| SSG — Static Site Generation | 일반적으로 빌드 시점에 HTML 생성 | 미리 생성한 정적 결과를 여러 요청에 재사용 |
| ISR — Incremental Static Regeneration | 정적 결과를 최초 생성한 뒤 배포 후에도 필요에 따라 재생성 | 페이지별 결과를 캐시하고, 일정 시간 경과 또는 요청에 따른 재검증으로 갱신 |
| ISSG — Incremental Static Site Generation | 문맥에 따라 빌드 때 만들지 않은 경로를 첫 요청에 생성하는 의미로 사용 | 필요한 경로를 점진적으로 생성해 정적 결과로 재사용. 현재 Next.js에서 ISR과 별개로 정의하는 공식 렌더링 모드는 아님 |

- SSR과 ISR의 차이: 둘 다 요청을 계기로 HTML을 만들 수 있지만, SSR은 해당 요청에 맞는 결과 생성, ISR은 생성 결과의 재사용과 갱신에 초점.
- SSG와 ISR의 관계: 둘 다 정적 결과를 재사용. ISR은 정적 생성에 전체 재빌드 없이 배포 후에도 갱신하는 방식을 더한 것.
- ISSG와 ISR의 관계: ISSG는 문맥에 따라 아직 없는 정적 페이지의 최초 생성을 강조하는 표현. ISR의 지원 범위에는 설정에 따라 빌드에서 만들지 않은 경로를 요청 시 생성하는 동작도 포함될 수 있음.
- 별도의 판단 기준: Server/Client Component는 컴포넌트의 실행 환경과 상호작용, SSR/SSG/ISR은 페이지 결과의 생성 시점과 재사용 방식에 관한 구분. 정적으로 생성한 페이지에도 Client Component 포함 가능.
