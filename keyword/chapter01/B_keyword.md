- PK, FK란?
    
    ## PK (Primary Key, 기본키)
    
    한 테이블에서 **각 데이터를 유일하게 식별하기 위한 키**이다.
    
    예를 들어 USER 테이블에서 `id`를 PK로 사용하면 각 사용자를 고유하게 구분할 수 있다.
    
    ### USER
    
    | id (PK) | nickname | email |
    | --- | --- | --- |
    | 1 | 철수 | a@test.com |
    | 2 | 영희 | b@test.com |
    
    ### 특징
    
    - 하나의 행을 **고유하게 식별**할 수 있다.
    - 같은 PK 값은 중복될 수 없다.
    - 일반적으로 `id` 같은 값을 PK로 많이 사용한다.
    - 다른 테이블에서 FK를 통해 참조할 수 있다.
    
    ---
    
    ## FK (Foreign Key, 외래키)
    
    **다른 테이블의 PK를 참조하여 테이블 간 관계를 연결하는 키**이다.
    
    예를 들어 REVIEW 테이블의 `user_id`가 USER 테이블의 `id`를 참조하면, 해당 리뷰를 어떤 사용자가 작성했는지 알 수 있다.
    
    ### USER
    
    | id (PK) | nickname |
    | --- | --- |
    | 1 | 철수 |
    | 2 | 영희 |
    
    ### REVIEW
    
    | id (PK) | user_id (FK) | content |
    | --- | --- | --- |
    | 10 | 1 | 재밌어요 |
    | 11 | 2 | 별로예요 |
    
    `REVIEW.user_id → USER.id`
    
    즉 `user_id = 1`이면 USER 테이블의 `id = 1`인 철수가 작성한 리뷰라는 뜻이다.
    
    ### 특징
    
    - 다른 테이블의 PK를 참조한다.
    - 테이블과 테이블 사이의 관계를 표현할 때 사용한다.
    - FK 값은 중복될 수 있다.
    - 하나의 테이블에 여러 개의 FK가 존재할 수도 있다.
    
    ---
    
    ## PK와 FK 차이
    
    | 구분 | PK | FK |
    | --- | --- | --- |
    | 의미 | Primary Key | Foreign Key |
    | 역할 | 자기 테이블의 데이터 식별 | 다른 테이블과 연결 |
    | 중복 | 불가능 | 가능 |
    | 예시 | `USER.id` | `REVIEW.user_id` |
    
    ### 한 줄 정리
    
    **PK = 내 테이블에서 나를 구분하는 값**
    
    **FK = 다른 테이블의 데이터를 가리키는 값**
    
- ERD란?
    
    ## ERD (Entity Relationship Diagram)
    
    데이터베이스를 만들기 전에 **어떤 테이블이 있고, 각 테이블에 어떤 컬럼이 있으며, 테이블끼리 어떤 관계를 가지는지 그림으로 나타낸 설계도**이다.
    
    쉽게 말하면,
    
    > **DB 구조를 미리 그려놓은 그림**
    > 
    
    이라고 생각하면 된다.
    
    ### 예시
    
    회원이 게시글을 작성하는 서비스라면 다음과 같이 설계할 수 있다.
    
    ### USER
    
    | id (PK) | name | email |
    | --- | --- | --- |
    | 1 | 철수 | a@test.com |
    
    ### POST
    
    | id (PK) | user_id (FK) | title |
    | --- | --- | --- |
    | 10 | 1 | 첫 게시글 |
    
    관계는 다음과 같다.
    
    `USER 1 : N POST`
    
    즉, **한 명의 사용자는 여러 개의 게시글을 작성할 수 있다.**
    
    ### ERD에서 주로 표현하는 것
    
    - 테이블(Entity)
    - 컬럼(Attribute)
    - PK, FK
    - 테이블 간 관계
    - `1:1`, `1:N`, `N:M` 관계
    
    ### 한 줄 정리
    
    **ERD = 데이터베이스의 테이블 구조와 관계를 그림으로 표현한 설계도**
    
- 연관관계란? 그리고 연관관계를 설정하는 방법은?
    
    ## 연관관계란?
    
    연관관계란 **서로 다른 테이블의 데이터가 어떤 관계를 가지고 연결되는지 나타내는 것**이다.
    
    예를 들어 한 명의 사용자가 여러 개의 게시글을 작성할 수 있다면,
    
    `USER 1 : N POST`
    
    라는 연관관계를 가진다.
    
    ### 예시
    
    ### USER
    
    | id (PK) | name |
    | --- | --- |
    | 1 | 철수 |
    
    ### POST
    
    | id (PK) | user_id (FK) | title |
    | --- | --- | --- |
    | 10 | 1 | 첫 게시글 |
    | 11 | 1 | 두 번째 글 |
    
    `POST.user_id → USER.id`
    
    즉, POST 테이블의 `user_id`가 USER 테이블의 `id`를 참조하면서 두 테이블이 연결된다.
    
    ---
    
    ## 연관관계를 설정하는 방법
    
    연관관계는 보통 **FK(외래키)를 이용해서 설정한다.**
    
    ### 1. 1 : 1 관계
    
    한 데이터가 다른 테이블의 데이터 하나와만 연결되는 관계
    
    예: 사용자 ↔ 프로필
    
    `USER 1 : 1 PROFILE`
    
    ---
    
    ### 2. 1 : N 관계
    
    한 데이터가 여러 개의 데이터와 연결되는 관계
    
    예: 사용자 ↔ 게시글
    
    `USER 1 : N POST`
    
    한 명의 사용자가 여러 게시글을 작성할 수 있다.
    
    보통 **N쪽 테이블에 FK를 둔다.**
    
    예:
    
    `POST.user_id(FK) → USER.id(PK)`
    
    ---
    
    ### 3. N : M 관계
    
    여러 데이터가 서로 여러 데이터와 연결되는 관계
    
    예: 학생 ↔ 수업
    
    한 학생은 여러 수업을 들을 수 있고, 한 수업에도 여러 학생이 참여할 수 있다.
    
    `STUDENT N : M CLASS`
    
    이 경우에는 두 테이블을 바로 연결하지 않고 **중간 테이블**을 만든다.
    
    ### ENROLLMENT
    
    | id (PK) | student_id (FK) | class_id (FK) |
    | --- | --- | --- |
    
    이를 통해
    
    `STUDENT 1 : N ENROLLMENT`
    
    `CLASS 1 : N ENROLLMENT`
    
    형태로 바꿔서 관리한다.
    
    ---
    
    ## 한 줄 정리
    
    **연관관계 = 테이블끼리 어떤 방식으로 연결되어 있는지 나타내는 것**
    
    **연관관계는 주로 FK를 이용해 설정한다.**
    
- 정규화란?
    
    ## 정규화란?
    
    정규화란 **데이터의 중복을 줄이고, 데이터가 꼬이거나 이상하게 저장되는 문제를 줄이기 위해 테이블을 나누는 과정**이다.
    
    쉽게 말하면,
    
    > **중복되는 데이터를 정리해서 DB 구조를 깔끔하게 만드는 것**
    > 
    
    이라고 생각하면 된다.
    
    ### 정규화 전
    
    | 학생 | 수업 | 교수 |
    | --- | --- | --- |
    | 철수 | DB | 김교수 |
    | 영희 | DB | 김교수 |
    | 민수 | DB | 김교수 |
    
    `DB`, `김교수` 정보가 계속 반복된다.
    
    ### 정규화 후
    
    ### STUDENT
    
    | id (PK) | name |
    | --- | --- |
    | 1 | 철수 |
    | 2 | 영희 |
    | 3 | 민수 |
    
    ### CLASS
    
    | id (PK) | class_name | professor |
    | --- | --- | --- |
    | 10 | DB | 김교수 |
    
    ### ENROLLMENT
    
    | student_id (FK) | class_id (FK) |
    | --- | --- |
    | 1 | 10 |
    | 2 | 10 |
    | 3 | 10 |
    
    이렇게 나누면 같은 정보를 반복해서 저장하지 않아도 된다.
    
    ### 정규화를 하는 이유
    
    - 데이터 중복 감소
    - 수정할 때 데이터가 서로 달라지는 문제 방지
    - 데이터 관리가 쉬워짐
    - 테이블 구조가 더 명확해짐
    
    ### 한 줄 정리
    
    **정규화 = 중복 데이터를 줄이고 데이터 구조를 깔끔하게 만들기 위해 테이블을 분리하는 과정**
    
- 반 정규화란?
    
    ## 반정규화란?
    
    반정규화란 **조회 성능을 높이기 위해 일부러 데이터를 중복해서 저장하거나, 나눠진 테이블을 다시 합치는 과정**이다.
    
    쉽게 말하면,
    
    > **정규화로 너무 잘게 나눈 테이블을 성능 때문에 일부 다시 합치는 것**
    > 
    
    이라고 생각하면 된다.
    
    ### 예시
    
    정규화된 구조:
    
    ### USER
    
    | id (PK) | name |
    | --- | --- |
    | 1 | 철수 |
    
    ### ORDER
    
    | id (PK) | user_id (FK) | price |
    | --- | --- | --- |
    | 10 | 1 | 10000 |
    
    사용자 이름을 확인하려면 USER와 ORDER를 JOIN해야 한다.
    
    반정규화를 하면 ORDER 테이블에 사용자 이름을 같이 저장할 수도 있다.
    
    ### ORDER
    
    | id (PK) | user_id (FK) | user_name | price |
    | --- | --- | --- | --- |
    | 10 | 1 | 철수 | 10000 |
    
    이렇게 하면 JOIN 없이 바로 조회할 수 있다.
    
    ### 반정규화를 하는 이유
    
    - 조회 속도 향상
    - JOIN 횟수 감소
    - 자주 사용하는 데이터를 빠르게 조회 가능
    
    ### 단점
    
    - 데이터 중복이 생길 수 있다.
    - 수정할 때 여러 곳을 같이 변경해야 할 수 있다.
    - 데이터 불일치 문제가 생길 수 있다.
    
    ### 한 줄 정리
    
    **반정규화 = 성능 향상을 위해 일부러 데이터 중복을 허용하는 설계 방법**
    
- DB에서의 상속 관계 표현은 어떻게 하는가?
    
    ## DB에서 상속 관계 표현
    
    DB에서는 객체지향처럼 상속을 직접 지원하지 않기 때문에, **부모-자식 관계를 테이블 구조로 표현**한다.
    
    예를 들어 `USER`를 부모로 두고 `STUDENT`, `TEACHER`가 자식이라고 해보자.
    
    ---
    
    ### 1. 하나의 테이블에 모두 저장
    
    ### USER
    
    | id (PK) | name | type | student_no | subject |
    | --- | --- | --- | --- | --- |
    | 1 | 철수 | STUDENT | 2026001 | NULL |
    | 2 | 김교수 | TEACHER | NULL | DB |
    
    `type` 컬럼으로 어떤 종류인지 구분한다.
    
    **장점**
    
    - 구조가 단순하다.
    - 조회가 쉽다.
    
    **단점**
    
    - 필요 없는 컬럼에 `NULL`이 많이 생길 수 있다.
    
    ---
    
    ### 2. 부모와 자식 테이블을 분리
    
    ### USER
    
    | id (PK) | name |
    | --- | --- |
    | 1 | 철수 |
    | 2 | 김교수 |
    
    ### STUDENT
    
    | user_id (PK, FK) | student_no |
    | --- | --- |
    | 1 | 2026001 |
    
    ### TEACHER
    
    | user_id (PK, FK) | subject |
    | --- | --- |
    | 2 | DB |
    
    `STUDENT.user_id → USER.id`
    
    `TEACHER.user_id → USER.id`
    
    공통 정보는 부모 테이블에 두고, 자식만 가지는 정보는 각각의 테이블에 저장한다.
    
    **장점**
    
    - 중복이 적고 구조가 명확하다.
    
    **단점**
    
    - 조회할 때 JOIN이 필요할 수 있다.
    
    ---
    
    ### 한 줄 정리
    
    **DB의 상속 관계는 부모의 공통 정보와 자식의 개별 정보를 테이블로 나누거나, 하나의 테이블에서 타입 컬럼으로 구분해서 표현한다.**
    
- 인덱스란?
    
    ## 인덱스란?
    
    인덱스는 **DB에서 원하는 데이터를 더 빠르게 찾기 위해 사용하는 자료구조**이다.
    
    쉽게 말하면,
    
    > **책의 목차나 색인처럼, 원하는 데이터를 빠르게 찾게 해주는 것**
    > 
    
    이라고 생각하면 된다.
    
    ### 예시
    
    USER 테이블에 데이터가 아주 많다고 해보자.
    
    ### USER
    
    | id | name | email |
    | --- | --- | --- |
    | 1 | 철수 | a@test.com |
    | 2 | 영희 | b@test.com |
    | 3 | 민수 | c@test.com |
    
    `email`에 인덱스가 없다면 원하는 이메일을 찾기 위해 많은 데이터를 확인해야 할 수 있다.
    
    하지만 `email`에 인덱스를 만들면 해당 값을 더 빠르게 찾을 수 있다.
    
    ```sql
    CREATE INDEX idx_user_email
    ON USER(email);
    ```
    
    ### 인덱스를 사용하는 이유
    
    - 데이터 조회 속도 향상
    - 검색 성능 향상
    - `WHERE`, `JOIN`, `ORDER BY` 등에 자주 사용되는 컬럼의 조회를 빠르게 할 수 있음
    
    ### 단점
    
    - 인덱스도 별도의 저장 공간을 사용한다.
    - INSERT, UPDATE, DELETE 시 인덱스도 함께 수정해야 해서 성능이 조금 느려질 수 있다.
    - 모든 컬럼에 인덱스를 만드는 것은 좋지 않다.
    
    ### 한 줄 정리
    
    **인덱스 = 데이터를 빠르게 찾기 위해 만들어두는 검색용 구조**
