# 1주차 핵심 키워드

<details>
<summary><b>PK, FK란?</b></summary>

### 1. 기본 키 (PK, Primary Key)

테이블에서 **각 행(Row)을 유일하게 식별**하는 컬럼, 또는 컬럼의 조합이다.

**특징**

- **유일성**: 같은 PK 값을 가진 행은 존재할 수 없다.
- **최소성**: 행을 식별하는 데 꼭 필요한 최소한의 컬럼으로만 구성한다.
- **NOT NULL**: 반드시 값이 있어야 한다. 즉 PK는 `NOT NULL` + `UNIQUE` 제약을 모두 가진다.
- **테이블당 하나**: PK는 하나만 지정할 수 있다. 단, 여러 컬럼을 묶은 **복합키**로 하나의 PK를 만들 수는 있다.

### 2. 외래 키 (FK, Foreign Key)

**다른 테이블의 행을 참조**하기 위해, 그 테이블의 PK(또는 UNIQUE 컬럼) 값을 저장하는 컬럼이다. 두 테이블을 연결하는 다리 역할을 한다.

- **부모 테이블**: 참조되는 테이블 (예: `member`)
- **자식 테이블**: FK를 가진 테이블 (예: `member_mission`)

**특징**

- **참조 무결성**: FK 값은 부모 테이블에 실제로 존재하는 값이어야 한다.
  - 예: 존재하지 않는 999번 회원의 미션 수행 기록은 저장할 수 없다.
- **중복 허용**: 한 회원이 여러 미션을 수행하면 `member_mission`에 같은 `member_id`가 여러 번 들어간다.
- **NULL 허용 가능**: 관계가 필수가 아니라면 NULL을 허용할 수 있다. 필수라면 `NOT NULL`로 막는다.
- **참조 대상 조건**: 참조되는 컬럼은 PK 또는 UNIQUE여야 하고, FK와 데이터 타입이 같아야 한다.

**부모 데이터를 삭제할 때의 동작 (ON DELETE)**

- `RESTRICT` / `NO ACTION`: 자식 데이터가 있으면 부모 삭제를 거부한다. (MySQL 기본값)
- `CASCADE`: 부모를 삭제하면 자식도 함께 삭제한다.
- `SET NULL`: 부모를 삭제하면 자식의 FK를 NULL로 바꾼다.

<summary><b>ERD란?</b></summary>

### ERD

**ERD(Entity Relationship Diagram)** 는 데이터베이스에 저장할 데이터(엔티티)와 그 데이터들 사이의 관계를 **그림으로 표현한 다이어그램**이다. ERD를 사용하면 복잡한 구조를 한눈에 볼 수 있다.

<summary><b>연관관계란? 그리고 연관관계를 설정하는 방법은?</b></summary>

### 1. 연관관계란?

**연관관계**는 두 데이터(테이블 또는 객체)가 논리적으로 연결되어, **한쪽에서 다른 쪽을 참조할 수 있는 관계**를 말한다.

- 예: 가게는 하나의 지역에 속한다. 회원은 여러 미션을 수행한다.

같은 연관관계라도 **테이블과 객체는 표현 방식이 다르다.**

| 구분 | 테이블 (DB) | 객체 (Java, JPA) |
| --- | --- | --- |
| 연결 방법 | FK | 참조 필드 (`private Region region`) |
| 방향 | 없음. JOIN으로 양쪽 모두 조회 가능 | 있음. 참조 필드를 가진 쪽에서만 접근 가능 |
| N:M 표현 | 매핑 테이블이 반드시 필요 | 컬렉션으로 표현 가능하지만 실무에서는 매핑 엔티티 사용 |

### 2. DB에서 연관관계를 설정하는 방법

DB에서는 **FK**로 관계를 설정한다.

- **1:N**: N쪽 테이블에 FK를 둔다. (예: `store.region_id`)
- **1:1**: 한쪽 테이블에 FK를 두고 `UNIQUE` 제약을 건다.
- **N:M**: 매핑 테이블을 만들고, 양쪽 FK를 모두 둔다. (예: `member_mission`)

### 3. 연관관계를 설정할 때 고려할 3가지

#### 3-1. 다중성

| 어노테이션 | 관계 | 예시 |
| --- | --- | --- |
| `@ManyToOne` | 다대일 (N:1) | 가게 → 지역 |
| `@OneToMany` | 일대다 (1:N) | 지역 → 가게 목록 |
| `@OneToOne` | 일대일 (1:1) | 회원 → 회원 상세정보 |
| `@ManyToMany` | 다대다 (N:M) | 회원 ↔ 미션 (실무에서는 비권장) |

#### 3-2. 방향성

- **단방향**: 한쪽 엔티티만 상대를 참조하는 필드를 가진다.
- **양방향**: 양쪽 엔티티가 서로를 참조하는 필드를 가진다. 사실은 단방향 관계 2개를 합친 것이다.

#### 3-3. 연관관계의 주인

양방향이면 FK를 관리하는 곳이 두 곳이 되므로, **FK를 관리할 쪽 하나를 주인으로 정해야 한다.**

- **주인**: FK가 있는 테이블과 매핑된 엔티티. 1:N에서는 항상 N쪽(`@ManyToOne`)이다. `@JoinColumn`을 사용한다.
- **주인이 아닌 쪽**: `mappedBy`를 사용한다. 이쪽에서 바꾼 값은 **DB의 FK에 반영되지 않는다.**
- 그래서 객체 상태와 DB가 어긋나지 않도록 **연관관계 편의 메서드**로 양쪽 값을 한 번에 설정한다.

</details>

<summary><b>정규화란?</b></summary>

### 1. 정규화 (Normalization)

**정규화**는 이상 현상이 있는 테이블을 분해하여 이상 현상을 없애는 과정이다. 테이블을 분해하는 정규형 단계가 높아질수록 이상 현상이 줄어든다.

### 2. 이상 현상 (Anomaly)

데이터가 한 테이블에 중복 저장되어 있을 때 생기는 문제다.

### 3. 정규화의 목적과 장단점

**목적**

- 데이터 중복을 줄여 저장 공간을 최소화하고, 데이터 무결성을 유지한다.
- 데이터 변경 시 이상 현상을 줄인다.
- 테이블을 논리적이고 직관적으로 구성한다.

**장점**

- 데이터 변경 시 이상 현상을 제거할 수 있다.
- 새로운 데이터를 확장할 때 테이블 구조를 변경하지 않거나 일부만 변경해도 된다.

**단점**

- 테이블이 분해되면서 JOIN 연산이 많아진다.
- 지나친 JOIN으로 성능 저하가 생기면 반정규화로 개선한다.

### 4. 정규형 단계

| 단계 | 조건 | 쉽게 말하면 |
| --- | --- | --- |
| 1NF | 모든 속성이 원자값을 가짐 | 한 칸에 값 여러 개를 넣지 않는다 |
| 2NF | 1NF + 부분 함수 종속 제거 | 복합키의 일부에만 딸린 컬럼을 분리한다 |
| 3NF | 2NF + 이행 함수 종속 제거 | PK가 아닌 컬럼에 딸린 컬럼을 분리한다 |
| BCNF | 3NF + 모든 결정자가 후보키 | 값을 결정하는 컬럼은 전부 키여야 한다 |

실무에서는 보통 **3NF 또는 BCNF까지** 진행한다.

</details>

<summary><b>반 정규화란?</b></summary>

### 1. 반정규화 (Denormalization)

**반정규화**는 성능 향상을 위해 의도적으로 데이터 중복을 허용하고 조인을 줄이는 방법이다. 조회 속도는 빨라지지만 데이터 모델의 유연성은 낮아진다. 조인으로 인한 성능 저하가 예상될 때 사용한다.

### 2. 반정규화 절차

1. **대상 조사 및 검토**: 데이터 처리 범위, 조회 빈도, 통계성 등을 확인한다.
2. **다른 방법 검토**: 인덱스 추가, 쿼리 튜닝, 캐시(Redis), 뷰 등으로 해결되는지 먼저 확인한다.
3. **반정규화 적용**: 테이블, 속성, 관계 단위로 적용한다.

### 3. 반정규화 기법

**테이블 반정규화**

- **테이블 병합**: 자주 조인하는 두 테이블을 하나로 합친다.
- **테이블 수직 분할**: 컬럼을 기준으로 테이블을 나눈다. 자주 쓰지 않거나 용량이 큰 컬럼(예: `TEXT` 본문)을 분리한다.
- **테이블 수평 분할**: 행의 값을 기준으로 테이블을 나눈다. 예를 들어 연도별로 주문 테이블을 분리한다.

**컬럼 반정규화**

- **계산된 컬럼 추가**: 총 주문 금액, 좋아요 수처럼 매번 집계해야 하는 값을 미리 계산해 컬럼으로 저장한다.
- **중복 컬럼 추가**: 조인을 없애기 위해 다른 테이블의 컬럼을 복사해 둔다.

**관계 반정규화**

- 자주 함께 조회하는 테이블 사이에 중복 관계(FK)를 추가해 조인 단계를 줄인다.

</details>

<summary><b>DB에서의 상속 관계 표현은 어떻게 하는가?</b></summary>

### 1. 상속 관계 매핑이란?

**상속 관계 매핑**은 엔티티 간의 상속 관계를 데이터베이스에 표현할 필요가 있을 때 사용하는 모델링 기법이다.

RDBMS는 상속 개념을 직접 지원하지 않으므로, **슈퍼타입-서브타입 관계(Super-Type Sub-Type Relationship)** 라는 기법으로 이를 대체한다.

**필요한 경우**

- **is-a 관계**: 특정 엔티티가 다른 엔티티의 특성을 물려받을 때
- **부모 타입으로 일관된 관리**: 여러 엔티티를 공통 부모 타입으로 묶어 관리하거나, 부모 타입으로 다형적 쿼리(부모 타입으로 전부 조회)를 지원해야 할 때

**모델링 방법**

부모(슈퍼타입)와 자식(서브타입)의 관계를 명확히 하여, 객체 상속 구조와 DB의 슈퍼타입-서브타입 관계를 매핑한다.

- **슈퍼타입**: 서브타입들이 공통으로 가지는 속성을 모아둔 것
- **서브타입**: 각 타입에만 해당하는 고유 속성을 가진 것
- 서브타입을 구분하기 위한 **타입 구분자 컬럼**(예: `DTYPE`)을 둔다.

### 2. 상속 관계 매핑 전략

슈퍼타입-서브타입 논리 모델을 실제 물리 모델로 구현하는 방법이다.

#### 2-1. 조인 전략 (JOINED)

각 엔티티를 별도의 테이블로 만든 후, **조인**으로 전체 데이터를 구성한다.

**특징**

- 부모와 자식이 각각 개별 테이블로 분리된다.
- 자식 테이블의 PK는 부모 테이블의 PK를 FK로 함께 사용한다.
- 부모 클래스는 추상 클래스로 구현하는 것이 권장된다.
- 정규화된 구조라 DBA들이 선호한다.

**장점**

- 테이블이 정규화되어 있고, FK 참조 무결성 제약조건을 활용할 수 있다.
- 설계가 깔끔하고 저장 공간 효율이 높다.
- 자식 고유 컬럼에 NOT NULL 제약을 걸 수 있다.

**단점**

- 조회 시 조인이 많아 성능이 저하될 수 있고, 쿼리가 복잡해진다.
- 데이터를 저장할 때 INSERT SQL이 두 번 실행된다.

#### 2-2. 단일 테이블 전략 (SINGLE_TABLE)

모든 엔티티를 **하나의 통합 테이블**에 저장한다. JPA의 기본 전략이다.

**특징**

- 서브타입을 구분하기 위해 구분자 컬럼(`DTYPE`)이 반드시 필요하다.
- 부모 클래스는 추상 클래스로 구현하는 것이 바람직하다.

**장점**

- 조인이 없어 조회 성능이 빠르고 쿼리가 단순하다.

**단점**

- 자식 엔티티에 매핑된 컬럼은 모두 `NULL`을 허용해야 한다. 자신의 컬럼이 아닌 데이터가 NULL로 채워지기 때문이다.
- 모든 데이터가 한 테이블에 쌓여 테이블이 커지고, 상황에 따라 조회 성능이 오히려 나빠질 수 있다.

#### 2-3. 구현 클래스마다 테이블 전략 (TABLE_PER_CLASS)

각 **서브타입마다 별도의 테이블**을 만들고, 부모 테이블은 만들지 않는다. 부모의 공통 속성은 각 자식 테이블에 중복해서 들어간다.

**장점**

- 서브타입을 명확하게 구분해 처리할 수 있고, NOT NULL 제약조건을 적용할 수 있다.

**단점**

- 여러 자식 테이블을 함께 조회할 때 `UNION` SQL이 필요해 성능이 떨어진다.
- 자식 테이블을 통합해 쿼리하기 어려워 사용이 권장되지 않는다.

</details>

<details>
<summary><b>인덱스란?</b></summary>

### 1. 정의

**인덱스(Index)** 는 추가적인 쓰기 작업과 저장 공간을 활용하여, 데이터베이스 테이블의 **검색 속도를 향상시키기 위한 자료구조**다.

책의 맨 뒤에 있는 찾아보기(색인)와 같은 개념이다. 책 전체를 한 장씩 넘기는 대신 색인에서 단어를 찾아 페이지 번호로 바로 이동하는 것처럼, DB도 테이블의 모든 데이터를 처음부터 훑는 대신 **데이터와 그 데이터의 위치를 담은 자료구조**를 미리 만들어 두고 빠르게 조회한다.

- **인덱스 없음**: 테이블 전체를 스캔한다. (Full Table Scan, O(N))
- **인덱스 있음**: 인덱스를 타고 바로 찾아간다. (Index Scan, O(log N))

### 2. 인덱스의 자료구조

- **B-Tree (B+Tree)**: 가장 널리 쓰이는 구조로, MySQL의 기본 인덱스다. 데이터가 정렬된 상태로 유지되어 **동등 비교(`=`)뿐 아니라 범위 검색(`>`, `<`, `BETWEEN`)과 정렬(`ORDER BY`)에도 효과적**이다.
- **Hash**: 해시 함수로 값을 찾아 동등 비교는 매우 빠르지만, 정렬된 상태가 아니라 **범위 검색과 정렬에는 사용할 수 없다.**

### 3. 인덱스의 관리

DBMS는 인덱스를 **항상 최신의 정렬된 상태로 유지**해야 원하는 값을 빠르게 탐색할 수 있다. 그래서 인덱스가 걸린 컬럼에 변경 작업이 일어나면 추가 연산이 필요하고, 그만큼 오버헤드가 발생한다.

- **INSERT**: 새로운 데이터에 대한 인덱스를 추가한다.
- **DELETE**: 삭제하는 데이터의 인덱스를 사용하지 않는다고 표시한다.
- **UPDATE**: 기존 인덱스를 사용하지 않음 처리하고, 갱신된 데이터에 대한 인덱스를 새로 추가한다.

이처럼 DELETE와 UPDATE 시 인덱스가 바로 삭제되지 않고 남아 있기 때문에, 변경이 잦은 테이블은 인덱스가 실제 데이터보다 비대해질 수 있다.

### 4. 장점과 단점

**장점**

- 테이블 조회 속도와 그에 따른 성능을 향상시킬 수 있다.
- 전반적인 시스템 부하를 줄일 수 있다.

**단점**

- 인덱스를 관리하기 위해 DB의 약 10%에 해당하는 저장 공간이 추가로 필요하다.
- 인덱스를 관리하기 위한 추가 작업이 필요해 INSERT, UPDATE, DELETE 성능이 떨어진다.
- 잘못 사용하면 오히려 성능이 저하되는 역효과가 발생한다.

### 5. 인덱스를 걸면 좋은 컬럼과 그렇지 않은 컬럼

**좋은 경우**

- `WHERE`, `JOIN`, `ORDER BY`에 자주 쓰이는 컬럼
- 카디널리티가 높은 컬럼 (값의 종류가 많아 중복이 적은 컬럼)
- 데이터 변경이 적고 조회가 많은 테이블

**좋지 않은 경우**

- 카디널리티가 낮은 컬럼 (성별처럼 값의 종류가 몇 개 없는 경우, 인덱스를 타도 걸러지는 양이 적어 효과가 없다)
- INSERT, UPDATE가 매우 잦은 컬럼
- 테이블의 데이터 양 자체가 적은 경우
